Stop Pushing to Registry: How to Use Local Docker Images with Minikube

Source: Stack Overflow ↗ · 689 votes

I still remember the first time I set up a local Kubernetes cluster, feeling pretty smug about my Dockerfile until I realized Minikube had absolutely no idea my image existed. I spent a good three hours pushing 500MB images to Docker Hub just to test a one-line code change, feeling like a total amateur as my bandwidth bill climbed and my patience hit zero.

The reason this happens is simple: Minikube runs inside its own isolated environment—usually a virtual machine or a separate container—that has its own Docker daemon. When you run docker build on your laptop, that image is stored in your host’s local Docker daemon. Since the Minikube cluster is physically separated from your host machine, it can’t "see" your local images. When Kubernetes tries to pull your image, it looks at the registries it knows about, fails to find your local tag, and gives you that dreaded ImagePullBackOff error.

To fix this, you don't need to touch a remote registry at all. The easiest way I’ve found to handle this is by pointing your local terminal's Docker environment directly to the one inside Minikube. Just run this command in your terminal before you build your image:


eval $(minikube docker-env)

Once you run that, your local shell is effectively "talking" to the Docker daemon running inside Minikube. Now, when you run docker build -t my-app:latest ., the image is built directly inside the Minikube node. You can verify it worked by running docker images, and you'll see your custom image sitting right there in the cluster's internal registry. Just make sure your Kubernetes deployment manifest has imagePullPolicy: IfNotPresent set, otherwise K8s will still try to reach out to the internet to find the latest version of your image.

To keep your workflow clean, my biggest tip is to always use a specific tag instead of relying on latest. If you stick with latest, you’ll constantly run into caching issues where Minikube thinks it already has the "latest" image even after you’ve updated your code. If you tag your builds with the current timestamp or a git commit hash, you'll never have to guess whether your cluster is actually running your newest changes.

Happy coding, and may your deployments be crash-free today!

Minikube 開發地獄：別再為了測試一個小改動，苦苦等待 Docker Hub 上傳了！

來源：Stack Overflow ↗ · 689 票

記得剛開始玩 Kubernetes 的時候，我真的差點崩潰。當時為了測試一個微小的程式碼變更，我每次都要跑一遍 docker build，然後手動 docker push 到 Docker Hub，再切換回 Minikube 的終端機去 kubectl rollout restart。最慘的一次，公司網路那天慢得像烏龜，光是上傳一個 500MB 的映像檔就讓我足足盯著螢幕發呆了二十分鐘，那種「明明程式碼改好了，卻因為網路傳輸卡死而什麼都做不了」的挫折感，簡直是工程師的惡夢。

會遇到這種情況，其實是因為 Minikube 預設運行在一個隔離的虛擬機或容器環境裡。雖然你的電腦上有 Docker，但 Minikube 的環境完全不知道你本地的 Docker daemon 裡有什麼。它就像是一個被關在圍牆裡的獨立小王國，當你要求它拉取映像檔時，它只認得公開的 Registry，根本抓不到你電腦裡剛蓋好的那份 Image，所以才會一直報 ImagePullBackOff 的錯，看了真的會讓人火大。

後來我發現，其實根本不需要繞遠路。最快的方法就是直接告訴 Minikube：「嘿，這東西就在你家門口，直接拿去用吧！」只要在 build 映像檔之前，先執行這行指令，把你的 Terminal 指向 Minikube 內部的 Docker 環境：


eval $(minikube docker-env)

執行完這行後，接著你在同一個視窗執行 docker build -t my-app:v1 .，這個映像檔就會直接被塞進 Minikube 的肚子裡。這時候你的 Deployment 設定檔記得要把 imagePullPolicy 改成 IfNotPresent，這樣 Kubernetes 發現本地已經有了，就不會傻傻地跑去網路上抓，瞬間就能跑起來，那個部署速度簡直是飛一般的體驗。

為了避免下次又因為忘了切換環境而鬼打牆，我現在養成了一個習慣，就是把這行指令直接寫在 .bashrc 或 .zshrc 的 Alias 裡，或者乾脆在開工前檢查 minikube status。如果你的專案很大，建議還是要學會用 minikube image load 指令，雖然稍微慢一點，但比起要把整個 Docker daemon 切換來切換去，有時候這種方式反而更穩定，不會搞混你本地跟虛擬機裡的環境。

希望這招能救你脫離無止盡的等待，快去試試看吧，別再浪費時間在傳輸檔案上了！
