How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 201 votes

I still remember the first time I moved a PyTorch model to a GPU. I had spent all afternoon getting my data pipeline just right, feeling like a genius, only to have the training loop crash on the very first iteration with that dreaded RuntimeError. I spent two hours staring at my screen, convinced my GPU drivers were broken or my CUDA installation was cursed, before I realized I was just being lazy with my data handling.

The root cause of this error is actually pretty straightforward once you stop panicking: PyTorch is strict about where your tensors live. When you call model.to(device), you’re successfully moving all your model's weights and biases to the GPU’s VRAM. However, your input data—the tensors coming out of your dataloader—are still sitting comfortably in your system's RAM (the CPU). PyTorch refuses to perform math operations between a CPU tensor and a GPU tensor because they exist in completely different memory spaces. It’s like trying to bake a cake with ingredients sitting in two different kitchens on opposite sides of the city.

To fix this, you have to manually move your input data onto the same device as your model inside your training loop. I usually handle this right after I pull the data from the iterator. You’ll want to make sure your inputs and labels are sent to the device variable you defined earlier. Here is how I structure it to keep things clean:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # This is the line that fixes the crash:
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... proceed with loss calculation

Once you add those .to(device) calls, the error vanishes instantly. It feels a bit redundant to write it every single time, but it’s a necessary step to ensure your tensors and your model are playing on the same field.

To prevent this in the future, I’ve made it a habit to define a small helper function or a wrapper class that automatically pushes data to the target device as it comes out of the dataloader. If you’re feeling fancy, you can even write a custom collate_fn for your DataLoader to handle the device transfer automatically, though I usually just keep it in the loop for clarity.

Hope this saves you the headache it caused me back in the day—happy coding!

PyTorch 報錯：Input type 和 weight type 不一致？別慌，這只是設備沒對齊而已

來源：Stack Overflow ↗ · 201 票

記得剛開始接觸 PyTorch 的時候，為了趕一個重要的實驗數據，我熬夜把模型架構弄好，信心滿滿地按下執行鍵，結果螢幕上瞬間噴出一行紅色的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。那一刻我真的差點崩潰，心想：「我不是明明把模型丟到 GPU 了嗎？為什麼還跟我說型態不對？」當時盯著螢幕看了半小時，懷疑人生到差點把電腦給砸了。

其實這個問題的核心概念很簡單，就是 PyTorch 非常嚴格，它不允許你把 CPU 上的資料直接餵給 GPU 上的模型。你看，你的模型雖然透過 .to(device) 移到了 GPU，但從 dataloader 讀出來的資料 inputs 預設還是待在 CPU 的記憶體裡。這就像是你準備好了一台法拉利引擎（GPU），卻硬要塞進一輛腳踏車（CPU）的零件，PyTorch 當然會直接罷工，告訴你這兩者不是同一種「物質」，無法混用。

解決的方法其實很直觀，我們必須在把資料餵給模型之前，手動把這些資料也「搬」到同一個裝置上。我當時解決的寫法是這樣的，在訓練迴圈裡多加一行 .to(device)：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵在這裡！要把 inputs 和 labels 也同步移動到跟 model 同樣的設備
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 後續計算 loss 時，labels 也要記得在 GPU 上
    loss = criterion(outputs, labels)

這樣寫完後，再執行一次，看到那一條條平穩下降的 Loss 曲線，心裡那種如釋重負的感覺真的無法言喻。

為了避免以後再被這個低級錯誤卡住，我現在有個習慣，就是在寫 dataloader 迴圈時，養成「資料進來就立刻對齊設備」的模組化習慣。你可以寫一個小小的 Helper Function，或者直接在訓練腳本的最上方定義好設備變數，每次寫訓練迴圈時就用 inputs.to(device) 作為肌肉記憶的一部分。只要確保所有參與運算的張量（Tensor）都在同一個地方，這個惱人的錯誤就永遠不會再找上你了。

搞定這個小麻煩，現在可以放心去喝杯咖啡，繼續跑我的實驗囉！
