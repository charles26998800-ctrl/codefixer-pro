How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27245 votes

I still remember the first time I accidentally committed a massive node_modules folder and a handful of local environment variables to a repo. I was halfway through a midnight coding session, feeling like a genius, until I realized I’d just pushed my private API keys into version control. I spent two hours sweating bullets and frantically Googling commands, convinced I’d ruined the entire project history before I finally stumbled upon the power of git reset.

The reason this happens is pretty simple: Git is designed to be a ledger of your work, and by default, it assumes that every commit you make is an intentional, permanent step forward. When you run git commit, you’re essentially telling Git to take a snapshot of your current state and lock it into the project history. If you realize you’ve staged the wrong files or typed a messy commit message, Git doesn’t automatically give you an "undo" button because it prioritizes data integrity. You’re essentially fighting against the tool's attempt to keep your history clean, which is why it feels so intimidating to backtrack.

When I need to walk back a mistake, I rely on git reset. The specific command you need depends on what you want to do with the files you just committed. If you just want to kill the commit but keep the changes in your working directory so you can fix them, I always use a soft reset. This moves the HEAD pointer back one commit without touching your actual files, which is a lifesaver when I’ve messed up a commit message or forgot to add one last file.


git reset --soft HEAD~1

If you’ve truly made a mess of the code and want to completely nuke the last commit and everything in it, reverting your files back to the exact state they were in before you committed, you’ll want to use the hard flag. Be careful with this one, because it’s destructive.


git reset --hard HEAD~1

Once you’ve run these, your local history is rewritten as if that commit never existed. Just remember that if you’ve already pushed these commits to a shared remote branch, you’re entering dangerous territory—always stick to these commands only for local work that hasn't been shared yet.

To keep this from happening again, I’ve started using the -p flag with git add whenever I’m committing. Instead of running a lazy git add ., which grabs everything in sight, git add -p lets me review each "hunk" of code interactively. It forces me to slow down and verify exactly what I’m sending to the repository, and it’s saved me from countless "oops" moments over the last few years.

Hopefully, this saves you from the same panic I felt during my first big Git mishap. Happy coding, and may your commits always be clean!

手滑提交了不該送出的程式碼？別慌，Git 救得回來！

來源：Stack Overflow ↗ · 27245 票

還記得那次我正準備趕在下班前把功能推上遠端，結果因為太想喝咖啡，腦袋一抽直接 git commit -am "fix bugs"，按下 Enter 的那瞬間我才驚覺——慘了，剛剛測試用的 API 金鑰跟一堆除錯用的 console.log 全部被我鎖進 Commit 裡了！那一刻我真的差點崩潰，心跳漏了兩拍，腦中浮現出一堆重寫程式碼的恐怖畫面，深怕一個手殘把整個分支搞爛，那種「我要被祭天了」的絕望感，相信有過類似經驗的工程師一定懂。

其實會發生這種慘劇，通常是因為我們對 Git 的 Commit 機制還不夠「冷血」。簡單來說，Git 就像一個嚴格的紀錄員，當你執行 git commit 時，它就把這些變更永久地寫入歷史清單。但只要你還沒執行 git push，這些錯誤就還在你的本地端，就像是你寫在筆記本上的鉛筆字，只要還沒影印發給大家，我們都有機會用橡皮擦把它擦掉。

我後來學會最優雅的解決方案就是使用 git reset。如果你只是想撤銷最後一次 Commit，但想保留剛剛辛苦寫的程式碼（只是不想讓它留在 Commit 紀錄裡），直接用 git reset --soft HEAD~1 就好。執行完後，你會發現檔案還是原本修改過的樣子，只是 Commit 紀錄消失了，這時候你就可以大方地把那些多餘的 API 金鑰刪掉，再重新 Commit 一次，完全沒人會發現你剛剛犯過蠢。

但如果你是真的想要「徹底毀滅」剛剛那次提交，連帶把檔案變更也一起丟掉，那就用 git reset --hard HEAD~1。這招非常暴力，執行下去後你的檔案會直接回到上一個 Commit 的乾淨狀態，千萬要小心用，因為這代表你剛剛寫的那些代碼會直接消失在宇宙中，再也找不回來，我第一次用這招時還特地先備份了整個資料夾，深怕誤刪什麼心血。

至於要怎麼預防這種悲劇再次發生？我現在強烈建議大家養成「小步快跑」的習慣，並且在 Commit 前一定要習慣性地跑一下 git status 或是 git diff --cached。看一眼到底有哪些檔案被「暫存」起來了，這短短幾秒鐘的檢查，能幫你省下後面好幾小時的除錯與崩潰時間。

以後如果不小心又手滑 Commit 了什麼奇怪的東西，記得保持冷靜，反正只要沒 Push 出去，一切都還有轉圜的餘地。
