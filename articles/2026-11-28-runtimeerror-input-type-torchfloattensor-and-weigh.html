How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I saw this error back when I was just getting comfortable with GPU training. I had spent three hours fine-tuning a model, finally hit run, grabbed a coffee to celebrate my "perfect" code, and came back to find the terminal screaming at me in bright red text. I stared at it for a good ten minutes, convinced that my GPU drivers had spontaneously combusted, only to realize I’d simply forgotten to move my training data to the device.

The reason this happens is actually quite straightforward once you stop pulling your hair out. PyTorch is extremely strict about data placement; your model parameters live on one device (usually the GPU, if you’ve sent it there), but your input tensors are still sitting in your system's RAM by default. When you try to run a forward pass, PyTorch tries to perform mathematical operations between tensors on different devices. Since the hardware can't talk across that bridge during a calculation, it throws this specific runtime error to tell you that the "types" don't match—even though they are both floats, their memory locations are fundamentally incompatible.

To fix this, you need to manually push your input data to the same device where your model is residing during every iteration of your training loop. I usually handle this by referencing the same device object I used to initialize the model. Here is how I typically structure that in my training loop:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    inputs, labels = data
    # Move the inputs and labels to the GPU before feeding them into the model
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... proceed with loss calculation and backprop

If you really want to avoid this headache in the future, my best advice is to stop hardcoding device movements inside your loops if your codebase grows. I like to write a simple utility function or a custom dataset wrapper that handles the device transfer automatically. Even better, if you're using something like PyTorch Lightning, it handles this device placement for you under the hood, which saves me from writing these same three lines of code a hundred times over.

Hope this saves you a bit of time so you can get back to the actual model architecture. Good luck with the training!

又是那個惱人的 RuntimeError：PyTorch 設備不對稱的除錯指南

來源：Stack Overflow ↗ · 202 票

剛開始學 PyTorch 那陣子，我真的是被這個錯誤搞到快崩潰。記得那天我為了趕論文的進度，熬夜把模型訓練程式碼寫好，興沖沖地按下執行鍵，結果螢幕上那行血紅色的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same 直接讓我原地石化。我盯著螢幕看了半小時，心想：「大哥，我明明都寫了 .to(device) 了啊，你到底是在跟我鬧什麼？」

其實這問題的核心原因單純到讓人想笑，說穿了就是「溝通不良」。當你把模型丟到 GPU 上（也就是 torch.cuda.FloatTensor），但你的輸入資料（也就是 inputs）還乖乖地留在 CPU 的記憶體（torch.FloatTensor）裡時，PyTorch 就會像個固執的強迫症患者，拒絕讓這兩者進行運算。你想像一下，模型在 GPU 的高速跑道上準備賽車，結果你卻把油料留在 CPU 的停車場，這車當然發不動啊！我當時最痛苦的時刻，就是明明檢查了模型有放到 GPU，卻忘記檢查每一批從 DataLoader 撈出來的數據，導致跑了半個小時才噴出這個錯，那種「我的人生被浪費了」的無力感，真的是誰經歷誰知道。

要解決這件事，其實只要在迴圈裡多加一個小動作就好。你必須確保每一次從 DataLoader 拿出來的 inputs 和 labels，都要主動搬運到跟模型一樣的設備上。我現在寫程式時，習慣會直接寫成這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就在這裡！一定要把資料也搬過去
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就是正常的 loss 計算與反向傳播

為了避免以後再被這個錯誤氣死，我現在養成了一個習慣，就是定義一個統一的 device 變數之後，絕對不在程式裡硬編碼（hard-code）設備名稱。而且，我會在 DataLoader 的下一行直接養成肌肉記憶，反射性地加上 .to(device)，就像寫完 if 之後一定要加冒號一樣自然。如果你覺得這樣寫很麻煩，也可以考慮寫一個小工具函式來處理資料搬運，這樣看起來會乾淨很多。

希望這篇筆記能幫你省下寶貴的除錯時間，別再為了這種設備不對稱的小事浪費生命了。如果還有哪裡卡住，隨時回來找我聊聊，祝你的模型 Loss 降得飛快！
