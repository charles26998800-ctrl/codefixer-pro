How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours straight scratching my head, wondering why my shiny new deployment kept spitting out ImagePullBackOff errors despite the image clearly existing in my local Docker engine. It was maddening—I’d build the image, tag it, and watch as Kubernetes stubbornly refused to see it, eventually realizing that Minikube lives in its own little world, completely oblivious to my host machine’s Docker daemon.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside a virtual machine or a separate containerized environment. When you run docker build on your laptop, those images are stored in your host’s Docker daemon. Minikube, however, has its own isolated Docker engine running inside its node. When you tell Kubernetes to pull an image, it asks the Minikube node to find it, and since that node doesn’t have access to your host's local registry, it tries to reach out to Docker Hub, fails, and leaves you staring at a crash loop.

The most efficient way I’ve found to bridge this gap is by pointing your local terminal directly at the Docker daemon inside Minikube. Instead of pushing to a registry, you run a simple command that reconfigures your shell environment. Just execute this in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build commands you execute will happen directly inside the Minikube environment. It’s like magic—your images are immediately available to your cluster. If you’re building a massive project, you can even use minikube image load to manually push an existing local image into the cluster if you don't want to rebuild it from scratch. Just make sure your deployment's imagePullPolicy is set to IfNotPresent so Kubernetes doesn't try to go searching the internet for an image that’s already sitting right there in front of it.

To keep your workflow clean and prevent future headaches, I highly recommend adopting a tagging strategy for your local development. I always tag my local images with :dev or :latest. If you stick with :latest, make sure you explicitly set imagePullPolicy: Always during testing, or you'll find yourself wondering why your code changes aren't reflecting even after you've rebuilt the image.

Hopefully, this saves you the afternoon of frustration I had to endure. Happy coding!

別再把 Docker Image 推到 Registry 了！在 Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 688 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的改動，我每次都要把 Docker Image 給 docker push 到 Docker Hub，然後再讓 Minikube 去 docker pull 下來。那時候網路慢得要命，我光是盯著那個進度條跑完，脾氣都快磨沒了，甚至有好幾次因為網路抖動，推上去的 Image 還壞掉，導致 Pod 一直卡在 ImagePullBackOff 的輪迴地獄裡，真的差點把鍵盤給砸了。

會發生這種鳥事，是因為 Minikube 本質上是一個跑在虛擬機（或是容器）裡的獨立節點，它的 Docker Daemon 跟我們宿主機（Host）的 Docker Daemon 是完全隔離的。簡單來說，Minikube 就像是個關在小房間裡的工程師，你放在自己電腦桌上的檔案，他根本看不到，除非你把它丟到公共網路（Registry）上，不然他怎麼可能拿得到你的 Image？

其實最快、最不廢話的解決方案，就是讓你的終端機直接去操作 Minikube 內部的 Docker 環境。只要執行下面這行指令，你的 docker 指令就會暫時「轉移」到 Minikube 的空間裡：


eval $(minikube docker-env)

執行這行之後，你在同一個視窗輸入 docker build -t my-app:v1 .，這個 Image 就會直接蓋在 Minikube 的肚子裡了。這時候你再去更新 Kubernetes 的 YAML 設定，把 imagePullPolicy 改成 IfNotPresent，Pod 就會乖乖抓取本地的 Image，再也不用去跟 Registry 搶頻寬，速度快到讓你懷疑人生。

不過要提醒一下，這個設定只對當前的終端機視窗有效。如果你關掉視窗重開，或是切換到別的分頁，記得要再執行一次。如果你覺得每次都要 eval 很煩，建議可以把這個指令寫進你的 .zshrc 或 .bashrc 裡，或者在開發初期乾脆直接用 minikube image load 這個指令，它能幫你把本機的 Image 直接「複製」進去，雖然稍微慢一點，但比起推到雲端還是快多了。

以後開發測試時，千萬別再傻傻地把程式碼推到雲端了，直接在本地把它塞進 Minikube，節省下來的時間拿去喝杯咖啡不香嗎？
