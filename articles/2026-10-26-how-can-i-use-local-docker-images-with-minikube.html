How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I remember the first time I set up a local Kubernetes cluster, I spent a solid three hours banging my head against the wall because my pods were stuck in ImagePullBackOff. I was convinced my YAML was perfect, yet Minikube refused to see the image I had just built locally, and I kept trying to push it to a private registry just to "see if it would work." It’s an incredibly common rite of passage, but it’s honestly one of the most frustrating things to deal with when you’re just trying to iterate on a new microservice.

The reason you’re running into this is that Minikube runs inside its own isolated virtual machine or container. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Minikube, however, has its own separate Docker daemon inside its cluster environment. When your Kubernetes pods try to pull an image, they look at the Minikube internal registry, not your laptop’s local storage. Since your image isn't there, Kubernetes tries to reach out to Docker Hub, fails because the image is private or non-existent, and gives up.

The easiest way I’ve found to fix this is to point your host terminal to the Minikube Docker daemon. Instead of building locally and hoping for the best, you run a simple command to redirect your local Docker CLI to talk directly to Minikube’s internal engine. On Mac or Linux, you just run this in your terminal:


eval $(minikube docker-env)

Once you’ve run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it worked by running docker images—you’ll see your local image listed right there alongside the standard Kubernetes infrastructure images. Now, when you apply your YAML, set your imagePullPolicy to IfNotPresent (or Never), and Kubernetes will find the image waiting for it without ever trying to hit an external registry. Just remember that if you open a new terminal tab, you’ll need to run that eval command again because it only affects your current shell session.

To prevent this headache in the future, I always make it a habit to check my imagePullPolicy in my deployment manifests. If you’re doing rapid development, setting it to IfNotPresent is a lifesaver because it tells the cluster to use the local version if it’s already available, saving you from waiting on network latency or registry authentication issues.

Hope this saves you from the same three hours of frustration I dealt with. Happy coding, and may your deployments always stay in the 'Running' state!

Minikube 讀不到本地 Docker Image？別再傻傻推上 Docker Hub 了！

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，為了測試一個小小的 API 改動，我竟然天真地把 Image 推到 Docker Hub 再讓 Minikube 拉下來。結果那天網路慢得要死，來回等了二十分鐘，最後發現程式有個低級拼字錯誤，那一刻我真的是差點在電腦前崩潰，恨不得直接把鍵盤砸了。明明 Docker Image 就在我的電腦裡，為什麼 Minikube 就是抓不到？那個 ImagePullBackOff 的錯誤訊息，簡直是我當時的惡夢。

其實這背後的道理很簡單，Minikube 預設運作在一個獨立的虛擬機或容器環境裡，它根本看不見你宿主機（Host）上的 Docker Daemon。這就像是你把東西放在自己的房間，卻要求住在隔壁棟大樓的 Minikube 去拿，它當然找不到，只能無助地嘗試去遠端的 Registry 抓取。

解決這個問題，最快的方法就是讓你的終端機直接「共用」Minikube 內部的 Docker 環境。只要執行下面這行指令，把你的環境變數切換過去：


eval $(minikube docker-env)

切換之後，你再執行 docker build -t my-app:v1 .，這個 Image 就會直接建立在 Minikube 的內部環境裡。這時候你只要把 Deployment 裡的 imagePullPolicy 改成 IfNotPresent，K8s 就會乖乖用你本地的 Image，再也不會去外面亂抓了。如果你懶得每次都打這行，也可以用 minikube image load ，這招直接把本地的 Image 塞進去，省心又省力。

為了避免以後又遇到這種「明明有圖卻拉不到」的窘境，我現在習慣在寫 deployment.yaml 時，養成習慣把 imagePullPolicy 設為 IfNotPresent。這樣就算網路斷了或是 Registry 掛了，只要我有這個 Image，我的 Pod 就能順利跑起來。

開發這條路本來就充滿了各種奇怪的設定坑，希望這招能幫你省下不少等候上傳下載的時間，早點把工作做完去休息吧！
