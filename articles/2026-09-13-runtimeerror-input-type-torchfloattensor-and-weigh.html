How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a training loop on a shiny new GPU instance, feeling like a total genius until my terminal exploded with this exact error. I spent three hours obsessively checking my model layers and data shapes, convinced I’d broken the actual hardware, only to realize I’d simply forgotten to move my tensors to the device I’d spent all morning configuring. It's one of those classic "welcome to deep learning" rites of passage that makes you want to throw your monitor out the window, but once you understand the underlying mechanism, it never catches you off guard again.

The root cause here is actually quite straightforward: PyTorch is strictly typed when it comes to memory location. Your model weights are sitting happily on your GPU (thanks to the .to(device) call), but your input data is still chilling in your standard system RAM (the CPU). When you pass that CPU-bound data into a GPU-bound model, PyTorch throws an error because it can't perform math operations across different memory spaces. It’s essentially the software equivalent of trying to plug a European power adapter into an American wall outlet—it just doesn't fit, no matter how hard you push.

The fix is incredibly simple once you know where to look. You need to explicitly push your input tensors to the same device your model is using during every iteration of your training loop. I usually handle this right after I unpack my data from the dataloader. Here is the snippet I use to keep things clean and error-free:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    inputs, labels = data
    # Move the data to the device before passing it to the model
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

To prevent this from ever ruining your day again, I highly recommend creating a small utility function or a wrapper class that handles device assignment automatically. You can also get into the habit of checking inputs.device with a quick print statement if you're debugging a new pipeline; if you see cpu when you're expecting cuda, you know exactly where the bottleneck is.

Hope this saves you a few hours of head-scratching! Happy training and may your gradients always converge.

又是這個經典錯誤：RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor)

來源：Stack Overflow ↗ · 202 票

記得那是個趕專案進度的深夜，我把模型架好、資料集切好，滿心期待按下執行鍵準備跑訓練，結果螢幕上那一串紅通通的錯誤訊息瞬間讓我心涼了一半。看著那個 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same，我當下真的差點把鍵盤砸了，心想：「明明我已經設定了 model.to(device) 啊，為什麼還是不聽話？」

其實這問題的根本原因說穿了就是「溝通障礙」。PyTorch 的原則很死，模型的參數（weights）跟丟進去的資料（input）必須住在同一個「房間」裡。當你把模型搬到 GPU（cuda）上，但資料還留在 CPU（FloatTensor）時，它們就像是兩個不同次元的生物，根本沒辦法進行矩陣運算。最讓人痛苦的時刻，莫過於你以為自己已經設定好設備了，結果因為迴圈裡的一個小細節沒處理，導致模型在 GPU 裡乾瞪眼，卻在那邊抱怨你餵給它的資料「冷冰冰的」。

解決這個問題的方法其實很直覺，就是要強迫資料也跟著搬家。在你的 for 迴圈裡，當你拿到 inputs 和 labels 的當下，就得立刻把這些數據送到跟模型一樣的裝置上。我當時的修改方式是這樣的，直接在讀取資料的那一行動手腳：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵，把資料也 move 到同一個 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... 後續的訓練步驟

改完這兩行，程式就順利跑起來了。不過為了避免以後又因為這種低級失誤浪費時間，我現在習慣寫一個簡單的輔助函式，或者乾脆在定義完 device 之後，養成一個「資料進來就順手送過去」的肌肉記憶。如果你的專案比較大，建議在資料讀取器（DataLoader）之後，或是自定義的 Dataset 類別裡統一處理，這樣之後寫程式會輕鬆很多。

以後看到這行錯誤先別急著崩潰，通常就是哪裡的資料忘記跟上 GPU 的腳步了。祝大家之後訓練模型都能順順利利，一次就跑通！
