How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 201 votes

I still remember the first time I set up a distributed training job and thought I was being clever by moving my model to the GPU. I proudly hit run, grabbed a coffee, and came back to find my terminal screaming at me in a wall of red text that I’d been hit by the classic mismatch error. I spent way too long staring at the code, convinced my GPU was broken, only to realize I’d completely forgotten that PyTorch doesn't automatically move your incoming data to the device, no matter how nicely you ask the model to move.

The root cause here is actually pretty straightforward once you stop the panic. PyTorch is extremely strict about data locality; it requires the model weights and the input tensors to live on the exact same hardware. When you call model.to(device), you’re successfully migrating your model’s parameters to your GPU, but your dataloader is still yielding tensors that are sitting comfortably in your system’s CPU RAM. When you try to pass those CPU-bound inputs into a GPU-bound model, PyTorch throws this runtime error because it can’t perform mathematical operations between different memory spaces.

To fix this, you have to manually move your data to the same device as the model during your training loop. It’s a simple addition, but it’s the step everyone misses at least once. Inside your loop, before you pass the inputs to the model, just call .to(device) on your tensors. Here is how I handle it in my projects:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Explicitly move both inputs and labels to the target device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you want to prevent this from ever ruining your workflow again, stop hardcoding your device management inside the loop. Instead, I always recommend writing a small utility function or using a helper class that handles the device transfer automatically based on the model's current device. If you make it a habit to check next(model.parameters()).device if you're ever unsure where your model is, you’ll save yourself a massive headache during debugging.

Hope this clears things up so you can get back to training your models without the constant crashing. Happy coding, and may your GPU memory stay forever empty!

PyTorch 報錯：Input type 和 weight type 不一致？別慌，這只是設備沒對齊而已

來源：Stack Overflow ↗ · 201 票

記得剛開始接觸 PyTorch 的時候，為了趕一個論文的 Demo，我熬夜把模型寫完，想說趕快跑個 epoch 驗證一下效果。結果按下執行鍵的那一刻，螢幕直接跳出那行紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。當下我真的差點崩潰，心想：「我不是明明已經把 model 搬到 cuda 了嗎？到底還有哪裡漏掉？」在那種死線逼近的深夜，這種簡單的錯誤真的會讓人想把鍵盤砸了。

其實這個錯誤的原因很單純，就是「雞同鴨講」。PyTorch 很嚴格，它要求參與運算的張量（Tensor）必須在同一個設備上，就像是你不能要求一個住台北的人，直接去拿住在高雄家裡的鑰匙一樣。雖然你已經用 model.to(device) 把模型搬到了 GPU 上，但你的資料 inputs 卻還乖乖地待在 CPU 的記憶體裡。當這兩者在計算層相遇時，PyTorch 就會因為兩邊「物種不同」而直接罷工。

要解決這個問題，其實只要在迴圈裡多加一行搬運指令就搞定了。我通常會在讀取資料後的當下，直接把它們丟到指定的裝置上。你可以試試看這樣寫：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！把資料也搬到同一個 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就可以快樂地算 Loss 了

這招下去通常就能解決 90% 的情況。至於要怎麼預防下次再被這種小錯誤卡住？我現在習慣寫一個簡單的 config 或者工具函數來統一管理設備。每次寫新的專案，我都會直接把 device 宣告為全域變數，或是寫一個自動轉移資料的 Wrapper 類別。甚至如果你懶得每次都寫 .to(device)，也可以在資料讀取器（DataLoader）的層面去處理，但最簡單的做法，就是養成在處理 inputs 時隨手檢查 device 的習慣。

希望下次你在跑模型時，能順利避開這個坑，別再被這種錯誤搞到懷疑人生了。如果你還遇到什麼奇怪的報錯，再跟我聊聊，我這幾年踩過的坑絕對比你吃過的飯還多！
