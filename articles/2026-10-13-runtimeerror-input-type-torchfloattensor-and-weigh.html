How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I saw this error pop up in my terminal. I had spent nearly three hours debugging a custom training loop, convinced that my model architecture was the problem, only to realize I’d completely forgotten to move my input tensors onto the GPU. I felt like such an amateur staring at that cryptic type mismatch, especially since I thought I’d already handled the device assignment for the model itself.

The reason this happens is actually quite straightforward once you step back from the frustration. PyTorch is extremely strict about where your data lives; it insists that the model's weights and the input data reside on the exact same device. When you define your model and run model.to(device), you’re successfully shipping your layers over to the GPU, but that doesn't magically move the data coming out of your DataLoader. Because your input tensors are still hanging out in your system RAM (the CPU), PyTorch throws a fit because it can't perform the math operations between a GPU-bound weight and a CPU-bound input.

To fix this, you need to manually push your input data to the same device your model is using during every iteration of your training loop. I usually handle this by grabbing the device from the model itself, which is a cleaner way to ensure everything stays in sync. Here is how I structure my loop to avoid the mismatch entirely:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move inputs and labels to the same device as the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you really want to make sure you never trip over this again, I’ve found that creating a small helper function or a custom wrapper to handle the device transfer is the way to go. Instead of manually typing .to(device) everywhere, I often just define a move_to(obj, device) utility function that recursively handles tensors, lists, and dictionaries. It saves me from those late-night debugging sessions where I’m hunting for that one missing line of code that keeps my GPU from actually doing its job.

Hope this saves you a few hours of head-scratching today. Happy coding, and may your GPU utilization stay high!

PyTorch 報錯 RuntimeError：當你的模型在 GPU，資料卻還在 CPU 的崩潰日常

來源：Stack Overflow ↗ · 202 票

還記得剛開始學 PyTorch 那陣子，我滿心期待地把顯卡驅動灌好、CUDA 環境搞定，想說終於可以擺脫 CPU 跑模型的龜速了。結果當我興高采烈地按下 Run，螢幕直接噴出一大串紅字：RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。那一刻我真的差點把鍵盤砸了，心想明明都已經寫了 .to(device) 了，這傢伙到底是在跟我裝什麼傻？

其實說穿了，這問題就是「牛頭不對馬嘴」。PyTorch 的規則很嚴格，模型的參數（weights）和傳進去的資料（inputs）必須待在同一個地方。我的模型確實已經被 .to(device) 移到了 GPU 上，但我的資料在 dataloader 讀出來之後，預設還是躺在 CPU 的記憶體裡。當這兩位「異地戀」的傢伙要在計算層強行相遇時，PyTorch 就會因為兩邊的數據類型不匹配直接罷工。這就像是你把一個住在台北的資料，硬要丟給一個住在東京的運算核心處理，它們根本溝通不了啊。

解決這件事其實不難，重點就是要在迴圈讀取資料的時候，手動幫它們「搬個家」。我通常會在 for 迴圈裡面，直接把 inputs 和 labels 同步推送到我定義好的 device 上，程式碼大概長這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # 就是這裡，記得把資料也丟過去！
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就可以安心地做 loss 計算了

那一陣子我最痛苦的時刻，就是好不容易訓練了一整晚，結果半夜醒來發現程式在第一輪就掛掉，看著 GPU 使用率 0% 的畫面，真的是欲哭無淚。

為了避免以後再被這個低級錯誤搞到心態崩掉，我現在養成了一個習慣：在寫訓練迴圈時，第一行永遠是 inputs = inputs.to(device)。或者，如果你不想每次都寫這麼麻煩，也可以寫一個簡單的 helper function 或者自訂一個 Dataset 的處理邏輯，確保資料在進入模型前就已經自動對齊裝置。只要記住，模型去哪，資料就得跟著去哪，這樣就不會再被這類錯誤糾纏了。

希望大家都能順利避開這個坑，GPU 跑起來的速度絕對會讓你覺得一切都值得啦！
