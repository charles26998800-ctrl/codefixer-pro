Why Your React 18 App is Crashing: Solving the Hydration Mismatch Error

Source: Stack Overflow ↗ · 341 votes

I remember the first time I upgraded a legacy project to React 18, thinking it would be a breezy Sunday afternoon of dependency bumps and minor refactors. Instead, I spent four hours staring at my console while the "Hydration failed" error mocked me, turning my perfectly good homepage into a flickering mess of broken layouts. It’s one of those bugs that makes you question your sanity because the code looks identical on both the server and the client, yet React is convinced you’ve committed a cardinal sin.

The root cause is actually quite logical once you peel back the layers: React expects the HTML sent from the server to be a perfect twin of the HTML generated during the initial client-side render. When you use server-side rendering (SSR), the server spits out a static snapshot of your app. When that snapshot hits the browser, React kicks in to "hydrate" it—attaching event listeners and making it interactive. If your client-side code decides to render something different than what the server provided—even something as tiny as a timestamp, a random ID, or a conditional check based on window—React panics. It sees the mismatch, assumes the server lied to it, and gives up, resulting in that dreaded hydration error.

Fixing this usually comes down to ensuring your rendering logic is deterministic. In my case, I was using new Date().toLocaleTimeString() inside a component, which meant the server rendered one time and the client rendered another a few milliseconds later. The simplest way to handle this is to defer the rendering of client-only data until after the component has mounted. By using a simple useEffect hook, you can force the component to wait until it's safely in the browser environment before injecting the dynamic content.


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? new Date().toLocaleTimeString() : 'Loading...'}
    </div>
  );
};

If you’re dealing with browser-specific APIs like localStorage or window, wrap those calls in a check as well. Sometimes, developers try to wrap the entire app in a typeof window !== 'undefined' check, but that’s often overkill. Keeping your server and client logic in sync is the goal, so if you don't absolutely need the data for SEO, keeping it behind an isClient flag is the cleanest way to stop React from throwing a tantrum.

To prevent this headache in the future, get into the habit of checking for "client-only" dependencies early. If you find yourself reaching for window or document inside a component body, stop and ask yourself if that code will exist on the server. If it doesn't, your component isn't pure, and you’re just inviting a hydration mismatch to ruin your day.

Hope this saves you from the same debugging rabbit hole I fell down. Good luck with the build!

React 18 Hydration 報錯？別慌，這其實是 SSR 的常見「時差」問題

來源：Stack Overflow ↗ · 341 票

還記得剛升級到 React 18 那個週末嗎？我本來想說趁著放假把專案重構一下，結果一跑起來，瀏覽器 Console 直接噴出一整排紅色的「Hydration failed」錯誤訊息，當下真的差點從椅子上摔下來。我看著螢幕上那行寫著「initial UI does not match」的字樣，心想明明邏輯都沒動，為什麼伺服器渲染出來的 HTML 跟瀏覽器剛接手時長得不一樣？那天我為了這個 bug 從下午坐在電腦前到凌晨兩點，真的是會被這種「看不見的差異」搞到懷疑人生。

其實這問題的根本原因說穿了就是「時差」。伺服器在生成 HTML 時，它讀不到瀏覽器特有的東西，比如 window、localStorage，或者是像 new Date() 這種會隨著時間變動的數值。當伺服器吐出一個 HTML 給瀏覽器，React 準備在瀏覽器端接手渲染（Hydration）時，它發現瀏覽器跑出來的結果跟伺服器剛才給的不一樣，React 就會因為「這對不起來啊！」而直接報錯，甚至乾脆放棄渲染，導致畫面閃爍或是功能失效。最痛苦的就是那種隨機出現的 bug，有時候重新整理又好了，搞得你像在玩猜謎遊戲。

要解決這個問題，最核心的原則就是：確保伺服器渲染跟第一次瀏覽器渲染時，拿到的資料是一模一樣的。通常我處理這種狀況，會讓元件在「掛載完成後」才去處理那些不確定的資料。最簡單的做法就是利用 useEffect，因為這段程式碼只會在瀏覽器環境執行，伺服器完全碰不到，這能完美避開差異。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <span>現在時間是：{new Date().toLocaleTimeString()}</span>
      ) : (
        <span>載入中...</span>
      )}
    </div>
  );
}

透過這種方式，伺服器只會吐出「載入中」這幾個字，而瀏覽器在接手後會觸發 useEffect，把狀態更新成真正的時間，這樣兩邊就不會因為時間戳記不同而吵架了。

至於怎麼預防這種狀況再次發生？我強烈建議大家在寫 SSR 元件時，心裡要隨時有個「防火牆」概念。只要是會用到 window 物件、瀏覽器 LocalStorage，或者任何會隨機生成的數值，一律通通丟進 useEffect 或是 useLayoutEffect 裡面去處理。只要在開發時多問自己一句：「這東西伺服器拿得到嗎？」，基本上就能避開 90% 的 Hydration 錯誤。

希望這篇筆記能救回你幾個小時的寶貴睡眠，下次遇到這紅字別氣餒，當作是跟 React 溝通的小磨合就好啦！
