Debugging React 18 Hydration Mismatches in Next.js

Source: Stack Overflow ↗ · 341 votes

I remember the first time I saw the "Hydration failed" error in a Next.js project; I was staring at my terminal at 2:00 AM, convinced my code was perfect because it worked flawlessly in development. I spent a solid three hours refactoring my entire component tree, only to realize I had a simple new Date() call triggering a different timestamp on the server versus the client. It’s one of those errors that makes you question your sanity, especially since the UI usually looks fine until you open the browser console and see the sea of red text.

At its core, this issue happens because React 18 is incredibly strict about the "handshake" between your server and the browser. When Next.js renders your page, it sends a static HTML string to the client. Once that HTML hits the browser, React kicks in to "hydrate" it—attaching event listeners and making it interactive. If the DOM structure generated by the browser during that first pass doesn't perfectly match the HTML string the server sent, React throws its hands up and declares a hydration mismatch. This is common when you use browser-only APIs like window, localStorage, or dynamic values like timestamps that change the moment the page loads.

To fix this, the most reliable method is to delay the rendering of the problematic component until the component has actually mounted on the client. By using a simple useEffect hook, you can create a flag that tells React to wait until the client-side environment is ready. I’ve found that creating a custom NoSSR wrapper is the cleanest way to handle this across a codebase. Here is how I usually implement it:


import { useState, useEffect } from 'react';

const ClientOnly = ({ children }) => {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null;
  }

  return <>{children}</>;
};

export default ClientOnly;

Once you have this component, you just wrap the specific part of your UI that relies on browser-only state—like a dark mode toggle or a library that reads from window.innerWidth—inside the component. Because hasMounted stays false during the initial server render, the server sends nothing (or a loading placeholder), and the browser waits until it's safe to inject the dynamic content.

If you want to stop this from haunting your future projects, my best advice is to audit your global state and logic early on. Whenever you find yourself reaching for window or document inside a component body, stop and ask if that logic truly needs to run on the server. If it doesn't, treat it as a "client-only" dependency immediately rather than waiting for the hydration error to pop up once you deploy to production.

Hope this saves you from the same late-night debugging session I went through. Happy coding!

React 18 Hydration Error：別再讓伺服器跟瀏覽器吵架了！

來源：Stack Overflow ↗ · 341 票

還記得那次趕專案上線，我滿心期待地把剛寫好的 SSR 功能推上測試環境，結果打開瀏覽器控制台一看，那紅通通的一整排錯誤訊息直接讓我原地心跳漏半拍。當時螢幕上寫著「Hydration failed because the initial UI does not match what was rendered on the server」，我心裡想說：「大哥，我明明寫的是同一個組件，怎麼伺服器渲染出來的 HTML 跟瀏覽器剛接手時看到的不一樣？」那種辛苦寫好的功能卻因為一個莫名其妙的警告而掛掉，真的會讓人想把鍵盤給拆了。

其實這問題的根源說穿了就是「溝通不良」。在 React 18 的機制下，伺服器會先產生一份 HTML 靜態結構，當這份資料傳到瀏覽器時，React 會進行「Hydration（水合）」過程來把綁定事件掛上去。問題就在於，如果你的頁面內容包含了一些會隨著環境變動的參數——比如 new Date()、隨機數 Math.random()，或是依賴 localStorage 的判斷，伺服器算出一個時間，瀏覽器執行時又算出另一個時間，React 一比對發現兩邊長得不一樣，為了安全起見，它就會直接報錯並放棄原本的 SSR 結果，選擇重渲染整個頁面。這不僅浪費效能，還會讓使用者看到頁面閃爍，體驗超級差。

當初我發現是因為在組件裡直接用了當前時間來判斷樣式，我找到的解法其實很單純，就是利用 useEffect 確保這段程式碼只在瀏覽器端執行。既然伺服器端沒辦法保證兩邊一致，那我就乾脆讓伺服器先不要渲染那塊會變動的內容，或者給它一個預設值，等到瀏覽器啟動後再換成正確的資料。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <div>現在時間是：{new Date().toLocaleTimeString()}</div> : <div>正在載入中...</div>}
    </div>
  );
}

其實要預防這種鳥事再發生，最簡單的原則就是「保持純粹」。只要是會變動、跟環境有關的邏輯，盡量都把它丟進 useEffect 裡，或者乾脆確保伺服器產出的 HTML 跟初始狀態的 React 元件是一模一樣的。我後來養成習慣，只要寫到涉及 window、localStorage 或時間戳的邏輯，我一定會先問自己：「這東西在伺服器端跑出來會跟瀏覽器端有差異嗎？」只要有風險，我就一定會做這種防禦性處理。

希望這篇心得能幫你少走點彎路，別再被這種 Hydration 錯誤搞到懷疑人生了，大家寫 Code 平安順利！
