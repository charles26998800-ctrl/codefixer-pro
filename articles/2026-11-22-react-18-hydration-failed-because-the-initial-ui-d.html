Fixing the "Hydration failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in React 18. I had just migrated a legacy project, feeling pretty proud of myself, only to refresh the browser and see my entire console turn into a giant, angry wall of red text. I spent three hours staring at the screen, convinced that React was hallucinating, before I realized that my server-side logic and client-side state were having a complete communication breakdown.

The root of this problem is actually quite simple, though it’s incredibly annoying. When you use Server-Side Rendering (SSR), React generates the HTML on the server and sends it to the browser. Once the browser receives that HTML, it tries to "hydrate" it by attaching event listeners and turning it into a fully interactive React app. If the HTML the browser receives doesn't perfectly match the HTML React generates during its first client-side render, React throws its hands up and declares a hydration mismatch. This usually happens because you’re using data that changes between the server and the client, like Math.random(), dynamic timestamps, or local storage values that aren't available on the server.

To fix this, I’ve learned that the secret is to delay the rendering of the problematic components until the component has actually mounted on the client. By waiting for the useEffect hook to fire, I can ensure that the server renders a neutral placeholder, and the client renders the dynamic content only after it's safe to do so. Here is how I typically structure that fix:


import { useState, useEffect } from 'react';

function HydrationSafeComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This only renders on the client: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By using that isClient flag, I stop React from trying to compare two different versions of the component during the initial load. The server renders the "Loading..." state, and the client immediately updates to the dynamic content once it mounts. This keeps the initial tree matching perfectly and silences that pesky hydration error for good.

The best way to prevent this in the future is to be extremely disciplined about your component dependencies. If you find yourself reaching for window or localStorage inside a component, wrap that logic in a custom hook or a client-only gate immediately. It’s better to show a quick loading state for a millisecond than to deal with the performance hit and console noise of a hydration mismatch.

Hope this saves you a few hours of debugging. Happy coding!

React 18 Hydration Error：那個讓我熬夜找兇手的「伺服器與客戶端不對盤」惡夢

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 的那個週末，我原本想說趁著沒人打擾，把專案好好重構一番，結果螢幕上那行紅通通的「Hydration failed」直接把我從椅子上嚇醒。我明明寫的是標準的 SSR 邏輯，為什麼瀏覽器控制台卻像是在跟我吵架，堅持說伺服器產出的 HTML 跟客戶端執行後的結果對不上？那種感覺真的很無力，就像是你準備好了一份完美的講稿，結果上台時麥克風卻突然壞掉，完全沒人聽得懂你在說什麼。

其實這個問題的根本原因，說穿了就是「時差」的問題。伺服器在生成頁面時，它讀到的環境參數可能跟瀏覽器執行時完全不同。最常見的兇手就是動態資料，比如日期、時間，或是依賴瀏覽器環境的 window 物件。當伺服器跑出一個時間戳，瀏覽器啟動後又跑出另一個，React 一比對發現：「誒？不對啊，這兩個畫面長得不一樣！」它就會為了保險起見，乾脆直接報錯，拒絕進行 Hydration，導致你整個頁面直接閃退。

我當時是在一個顯示「當前時間」的小元件上踩到坑，後來發現解決方案其實很直覺，就是強制讓這部分邏輯「延後執行」。只要確保該元件只在瀏覽器端渲染，就能避開這個不一致的問題。我習慣用一個簡單的 Hook 來判斷，或是直接把會變動的部分包在 useEffect 裡，像這樣：


import { useState, useEffect } from 'react';

function ClientOnlyComponent() {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null; // 或者放一個靜態的 loading 佔位符
  }

  return <div>這裡放那些會導致不一致的動態內容</div>;
}

解決這個問題後，我學到最重要的一招就是「防患未然」。以後只要遇到會用到 localStorage、window 屬性，或是任何依賴當下瀏覽器環境的邏輯，我一律會先檢查元件是否已經掛載完成（Mounted）。與其讓 React 試圖去猜測伺服器端該渲染什麼，不如大方地告訴它：「嘿，這部分等瀏覽器準備好再處理就好」，這樣心智負擔真的會少很多。

希望下次你們遇到這行紅字的時候，別像我當初那樣焦慮，喝杯咖啡，把這幾行檢查補上去就沒事了。祝大家除錯順利，少點 bug！
