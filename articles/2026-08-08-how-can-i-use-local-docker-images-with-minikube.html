How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours banging my head against the wall because my pods kept stuck in ImagePullBackOff, despite seeing my image sitting right there in my local Docker daemon when I ran docker images. I felt like I was losing my mind, convinced I had mistyped a tag or messed up a registry path, only to realize that Minikube lives in its own little world and doesn't naturally peek at your host machine's images.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside a virtual machine or a containerized environment of its own. Because of this isolation, the Docker daemon running on your host machine is completely separate from the Docker daemon running inside your Minikube cluster. When Kubernetes tries to pull an image, it looks inside that internal Minikube environment, sees nothing, and attempts to reach out to Docker Hub. Since your image isn't public, the request fails. It's a classic case of "it works on my machine" taken quite literally.

The fix is surprisingly straightforward, and once I learned it, my development loop became infinitely faster. Instead of pushing to a registry just to test a one-line code change, I point my local shell to the Minikube Docker environment. You can do this by running a single command in your terminal before building your image:


eval $(minikube docker-env)

Once you run that, your local docker commands are now talking directly to the Docker daemon inside Minikube. Now, when you run docker build -t my-app:latest ., the image is built directly inside the cluster's environment. You can verify it worked by running minikube ssh -- docker images, and you'll see your image sitting there ready to be used. Just make sure your Kubernetes manifest has imagePullPolicy: IfNotPresent set, otherwise it will still try to reach out to the internet to find a newer version of the tag.

To prevent this headache in the future, I always stick to a simple rule: keep your image tags strictly versioned or use a specific dev tag like :latest. If you find yourself switching back and forth between your host Docker and Minikube, remember that the eval command only affects your current terminal session. If you open a new tab, you'll need to run it again, or you'll be building images for your host machine and wondering why Minikube still can't find them.

Hope this saves you from the same three-hour frustration I dealt with. Happy coding, and may your pods always reach the Running state on the first try!

別再浪費時間推送到 Docker Hub 了！如何在 Minikube 直接用本地鏡像

來源：Stack Overflow ↗ · 688 票

剛開始玩 Kubernetes 的時候，我真的差點崩潰。當時我寫好了一個微服務，想在 Minikube 上跑跑看，結果為了測試一個小小的功能修改，我居然要把 Image 推送到 Docker Hub，然後再讓 Minikube 下載回來。光是等待上傳下載的時間，我就能喝完兩杯咖啡了，最慘的是，好不容易等到部署成功，才發現少改了一行程式碼，整段流程又要重跑一次，那種「人生浪費在等待進度條」的感覺，真的會讓人想把螢幕砸了。

會遇到這種情況，其實是因為 Minikube 本質上是一個跑在虛擬機（或容器）裡的獨立環境。你電腦上的 Docker daemon 跟 Minikube 內部的 Docker daemon 根本就是兩碼子事。當你在終端機執行 docker build 時，鏡像只是存在你的宿主機裡，Minikube 當然「看不見」你的私藏貨，它只會乖乖地嘗試去遠端 Registry 抓取，抓不到就給你一個經典的 ImagePullBackOff 錯誤，看著那個紅色字體，心情真的會跌到谷底。

後來我發現，其實根本不需要那麼麻煩。最簡單暴力的方法，就是把 Minikube 的環境變數直接指向你當下的 Docker daemon。只要在終端機輸入這行指令，讓你的 shell 直接跟 Minikube 內部的 Docker 對接：


eval $(minikube docker-env)

執行完這一行後，你再下 docker build -t my-app:v1 .，這個鏡像就會直接被塞進 Minikube 的肚子裡。這時候你只要把 Kubernetes 的 deployment 設定檔裡的 imagePullPolicy 改成 IfNotPresent，Minikube 就會發現：「喔！原來這東西已經在本地了，不用去外面找。」那一刻看著 Pod 秒啟動，真的會感動到想哭。

為了避免以後又踩到這種坑，我現在養成了一個習慣，就是專門寫一個簡單的 Makefile。每次要部署測試時，我只要打 make deploy，裡面就自動包含了切換環境變數跟 build 的指令，這樣就不用怕自己忘記切換環境而白忙一場。其實 Kubernetes 沒那麼難搞，只是這些環境隔離的細節真的很容易讓人掉坑。

希望這招能幫你省下不少喝咖啡的時間，趕快回去寫 Code 吧！
