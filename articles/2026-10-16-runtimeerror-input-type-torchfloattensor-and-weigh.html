How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I built a custom training loop in PyTorch, feeling like a total genius until I hit that dreaded RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same. I spent three hours staring at my screen, convinced my GPU was broken or my drivers were toast, only to realize I’d simply forgotten to move my data to the device I had so carefully assigned to my model. It’s one of those classic "welcome to deep learning" hurdles that makes you want to throw your keyboard out the window.

The reason this happens is actually quite logical once you stop pulling your hair out. In PyTorch, your model's weights and your input data must reside on the same hardware—either both on the CPU or both on the GPU—to perform the necessary matrix multiplications. If your model is sitting on the GPU (because you called .to(device)), but your input tensors are still hanging out in your system's RAM, the CUDA kernels simply won't know how to handle the data. The runtime error is PyTorch's way of telling you that you’ve created a memory mismatch that makes computation impossible.

To fix this, you have to be intentional about moving your input tensors to the same device as your model during every iteration of your training loop. I learned the hard way that you can't just move the model once and expect the data to follow suit. You need to explicitly call .to(device) on your inputs (and your labels, if you're calculating loss) inside the loop. Here is the standard way to handle it:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Explicitly move data to the same device as the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # Now your loss calculation won't crash either
    loss = criterion(outputs, labels)

If you want to save yourself the headache in the future, the best habit I’ve adopted is to write a small helper function or simply keep the .to(device) call right next to the data unpacking step. I usually make it a point to define a device variable at the very top of my script and then treat it like a constant throughout the entire project. If you get into the rhythm of typing .to(device) every time you pull a batch from your dataloader, this error will basically vanish from your life.

Hope this saves you a few hours of debugging time today. Happy coding and good luck with those training runs!

救命！PyTorch 報錯：Input type 和 weight type 不匹配的崩潰現場

來源：Stack Overflow ↗ · 202 票

還記得我剛開始接觸 PyTorch 的時候，那天晚上熬夜趕專案，好不容易把模型架構寫好，準備跑個測試集看看效果。按下 Enter 那一刻，我信心滿滿地去泡了杯咖啡，結果回來一看螢幕，那行紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same 直接讓我心跳停了一拍。當時我盯著螢幕看了半小時，心裡想說：「老兄，我明明都把 model 搬到 GPU 了，你到底在跟我鬧什麼脾氣？」那種明明邏輯寫對了，卻被硬體設備不一致卡住的無力感，真的是工程師最想摔鍵盤的時刻之一。

其實後來冷靜下來想想，這問題真的挺單純的，就是典型的「雞同鴨講」。PyTorch 是一個很嚴謹的框架，它要求參與運算的「模型權重（weight）」和「輸入數據（input）」必須待在同一個物理空間裡。如果你把模型丟到 GPU 上，但你的資料還在 CPU 的記憶體裡待著，PyTorch 執行運算時就會發現：「欸？你的權重在顯示卡，但我輸入的資料卻還在系統記憶體，這要我怎麼算？」這就是為什麼它會跳出這個錯誤訊息，強迫你要手動把兩者同步起來。

解決方案其實非常直觀，就是要在進入迴圈讀取資料的時候，順手把資料也「搬」到跟模型一樣的設備上。我通常會直接在 dataloader 的迴圈裡，把 inputs 和 labels 透過 .to(device) 方法轉移過去。你可以參考我下面這段寫法，只要確保你的 device 變數在前面已經定義好，這樣寫就萬無一失了：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵，要把資料搬到跟模型同一個 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也要確保在同個裝置上

為了避免下次再被這種低級錯誤搞到崩潰，我後來養成了一個習慣，就是把裝置定義寫成一個全域的常數，或者直接在訓練函數裡把所有輸入參數都加上 .to(device)。你甚至可以寫一個簡單的輔助函數，專門用來處理資料搬移，這樣不僅程式碼看起來乾淨很多，以後再也不用擔心漏掉哪一個 Tensor 沒轉移，導致模型又在那邊鬧脾氣了。

寫 code 嘛，這種卡關難免啦，下次遇到類似的報錯，記得先檢查一下是不是有誰還在 CPU 沒跟上大部隊就好囉！
