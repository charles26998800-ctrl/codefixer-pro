Troubleshooting RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same

Source: Stack Overflow ↗ · 202 votes

I vividly remember the first time I set up a distributed training job for a computer vision project, feeling pretty proud of myself for getting the GPU drivers installed on the first try. Then, I hit this error immediately after starting the training loop. I spent nearly three hours digging through my data loading pipeline, convinced my dataset was corrupted, only to realize I had simply forgotten to move the batch tensors to the device I’d so carefully selected. It’s one of those "face-palm" moments that every PyTorch developer has to go through at least once.

The root cause here is actually quite logical: PyTorch is incredibly strict about hardware affinity. When you call model.to(device), you’re successfully shipping your model weights to the GPU's memory. However, the data coming out of your dataloader is still sitting comfortably in your system's RAM (as a FloatTensor). When you try to pass that CPU-resident tensor into the model, PyTorch throws an error because it can’t perform matrix multiplication between tensors living on different devices. It’s like trying to bake a cake in your kitchen while your ingredients are still sitting at the grocery store—the model is the oven, but it can't reach the data.

To fix this, you need to explicitly move your input tensors onto the same device as your model during every iteration of your training loop. I usually handle this right after I unpack my data batch. Here is the standard way I patch this up:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the line you're missing
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # Proceed with your loss calculation...

If you’re working with complex objects or custom datasets, you can even write a small helper function to move everything to the device in one go, which keeps your training loop looking clean.

To prevent this from ever ruining your day again, I recommend adopting the habit of defining your device once at the top of your script and creating a small utility function to move your data. If you make it a standard part of your boilerplate code, you’ll never have to debug this specific mismatch again.

Hope this saves you a few hours of frustration today—happy coding!

PyTorch 報錯 `RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same`，這坑我幫你踩過了！

來源：Stack Overflow ↗ · 202 票

還記得當年剛開始用 PyTorch 跑模型的時候，為了省時間直接把資料丟進去訓練，結果程式跑不到一分鐘就直接跳出這個討厭的 Runtime Error。當時看著螢幕上那一串紅通通的錯誤訊息，心裡真的只有「崩潰」兩個字，明明都寫了 model.to(device) 了，為什麼還是在吵資料型態不對？那時候為了抓這個 Bug，浪費了整個下午在檢查路徑和環境設定，結果最後發現原因蠢到讓我差點把鍵盤吃掉。

其實這個問題的核心邏輯很簡單，就是你的「模型」已經被搬到 GPU 上了，但你的「資料」還在 CPU 裡面睡覺。PyTorch 非常嚴格，它要求參與運算的張量（Tensor）必須在同一個設備（Device）上，不然它們就像是講不同語言的人，根本沒辦法溝通。當你的模型權重已經在 cuda，但傳進去的 inputs 卻還在 cpu 時，系統就會因為找不到匹配的記憶體位置而直接報錯。

解決的方法其實一點都不難，只要在迴圈裡面，順手把資料也搬過去就行了。我通常會直接在取得資料後，加上一行 .to(device)。你可以參考一下我現在常用的寫法：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就在這，要把資料也搬到同一個 device 上
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接著進行後續的 loss 計算...

只要這樣改，那個惱人的型態不匹配錯誤就會立刻消失。至於要怎麼預防下次再被雷到，我現在寫程式時，習慣會把 device 設定成一個全域變數，或是直接寫一個簡單的工具函式來處理資料搬移，這樣就不用每次寫 for 迴圈都要提心吊膽。還有一招就是養成習慣，只要看到任何涉及 Tensor 的操作，就先檢查它們的 .device 屬性，這樣能省下很多 debug 的冤枉時間。

希望這篇心得能幫你少走點彎路，順利把模型跑起來！
