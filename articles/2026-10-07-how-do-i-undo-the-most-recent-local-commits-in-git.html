How to Undo Your Most Recent Local Git Commits Without Losing Your Work

Source: Stack Overflow ↗ · 27242 votes

I still remember the first time I accidentally committed a massive debug log file full of API keys to a production-bound repository. I stared at my terminal in pure horror, sweating bullets because I knew a git push was only one accidental keystroke away. I spent about two hours frantically Googling commands, convinced I was about to delete my entire project history, only to realize that Git is actually much more forgiving than it looks.

The root of the problem is usually just a classic case of "fat-fingering" a commit or grabbing files you didn't mean to include in your staging area. When you run git commit, you’re essentially creating a permanent snapshot of your files in the local repository database. Since you haven't pushed to the remote server yet, that history exists only on your machine, which is great news. The confusion usually stems from the different ways you might want to "undo" things—sometimes you want to keep your file changes, and other times you want to nuke the entire commit as if it never happened.

If you’re in this situation, the command you’re looking for is git reset. To undo your most recent commit while keeping all your work in your staging area so you can fix it, I always use the soft reset. Just run this in your terminal:


git reset --soft HEAD~1

This effectively rolls back the commit, but keeps all the files you changed as "staged" and ready to go. If you decide you actually messed up the code entirely and want to wipe out the commit and all the changes you made in those files, you’ll want to perform a hard reset. Be careful with this one, because it’s destructive:


git reset --hard HEAD~1

Once you run the hard reset, those changes are gone for good, so make sure you really want to discard that work. If you just want to unstage the files but keep the work in your working directory without the commit, use git reset HEAD~1 without any flags. It’s the middle ground that I find myself using the most when I realize I forgot to include one last file before committing.

To stop this from happening in the future, I’ve made it a habit to use git status religiously before I ever type git commit. It sounds basic, but stopping for five seconds to scan the list of staged files has saved me from more "oops" moments than I can count.

Hope this clears up the panic and gets your repo back in order. Happy coding!

手滑提交了不該送出的程式碼？別慌，Git 救得回來！

來源：Stack Overflow ↗ · 27242 票

還記得有次趕專案進度，凌晨三點腦袋已經快當機，我明明只想提交一個功能模組，結果手殘直接 git commit -a，連帶把一堆測試用的髒檔案和私人筆記全部塞進了版控。當下看到終端機顯示「commit success」的那一刻，我整個人心跳漏了一拍，想著這要是推送到遠端伺服器，主管隔天看到這堆垃圾檔案，肯定會覺得我這工程師是來鬧的。那種「完蛋了，我把庫搞砸了」的絕望感，真的會讓人瞬間清醒，冷汗直流。

其實這問題發生很簡單，Git 的設計邏輯就是讓你把每一次的變更都當成一個「存檔點」。當你執行 commit 時，你只是在自己的本地端建立了一個快照，但因為這個步驟實在太順手了，我們常常會因為一時疏忽，把不該進去的檔案也順手打包進去。這並不代表你的程式碼毀了，只是你剛才的那個「存檔點」裡面裝了太多雜物，我們只需要把這個存檔點拆掉，讓檔案退回到還沒提交前的狀態就好。

這時候最好的救星就是 git reset 指令。如果我只是想取消上一次的提交，但想保留我辛苦寫好的程式碼變更，我會用 --soft 這個參數。你只需要輸入：

git reset --soft HEAD~1

執行下去後，你剛剛那次的 commit 紀錄會直接消失，但你改動的檔案都會好端端地留在暫存區（Staging Area），讓你重新選取要提交的檔案。但如果你的情況更糟，連寫的程式碼都是錯的，想把所有修改都徹底拋棄、恢復到完全沒改過之前的樣子，那就直接用 --hard：

git reset --hard HEAD~1

這一招下去，所有改動都會直接原地消失，記得使用前先確認一下，不然辛苦熬夜寫的程式碼也可能會跟著一起不見，那個痛苦指數絕對是破表的。

為了避免以後又發生這種「手滑」的慘劇，我現在養成了一個習慣，就是每次 commit 前一定會先打 git status 看一下到底有哪些檔案被選中。現在我甚至會用 git add -p 來進行互動式新增，這樣我可以一塊一塊地檢查程式碼片段，確保我送出去的東西都是乾淨、正確的。多這幾秒鐘的檢查，真的能省下後面處理亂七八糟 commit 紀錄的麻煩。

希望這招能救到正處於崩潰邊緣的你，趕快去把你的 Git 紀錄整理乾淨吧！
