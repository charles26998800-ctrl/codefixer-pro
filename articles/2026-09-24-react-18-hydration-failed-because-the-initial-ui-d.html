Debugging the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a Next.js project. I spent three hours staring at my terminal, convinced that my code was perfect, only to realize I had a simple Date.now() call inside a component that was rendering differently on the server than it was in the browser. It’s one of those bugs that makes you want to throw your monitor out the window because the UI looks exactly how you want it to, yet React is screaming at you because the DOM tree doesn't align.

The root cause of this frustration is actually quite logical once you look past the panic. When you use Next.js, the server generates the initial HTML of your page and sends it to the browser. Once the browser receives that HTML, React "hydrates" it, essentially attaching event listeners and turning it into an interactive app. If the HTML the server generated doesn’t match the HTML the client generates during that first render—even by a single attribute or a misplaced tag—React throws its hands up and warns you that the hydration failed. This often happens because of browser-specific APIs (like window or localStorage) or dynamic data like timestamps that change the moment the client-side code executes.

To fix this, I’ve learned that the golden rule is to defer client-specific logic until the component has actually mounted. I usually handle this by using a simple useEffect hook to toggle a state flag. By checking if the component is mounted before rendering anything that relies on the browser environment, I can ensure the server renders a neutral placeholder (or nothing at all) and the client fills in the dynamic content immediately after. Here’s how I usually structure that fix:


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Your browser-only code goes here */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

If you want to prevent this from ruining your day in the future, my best advice is to treat your server-side rendering as a "static snapshot" process. Always ask yourself: "Will this component render exactly the same way on a Linux server and a Chrome browser?" If the answer is no, wrap that logic in a mounted check or use dynamic imports with ssr: false in Next.js to keep the server out of the equation entirely for those specific modules.

Hopefully, this saves you from the same headache I went through. Let me know if you run into any other weird edge cases!

React 18 Hydration 錯誤：那個讓你懷疑人生的「UI 不匹配」惡夢

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我正興高采烈地要把一個舊專案遷移到 Next.js。結果部署上去之後，打開開發者工具一看，滿屏紅通通的 Hydration failed 錯誤直接把我嚇傻。我當時盯著螢幕看了半小時，心想：「明明程式碼寫得好好的，為什麼伺服器端渲染出的 HTML 跟瀏覽器拿到的不一樣？」那種明明寫對了卻被系統打臉的無力感，真的是工程師職涯中最想原地爆炸的時刻之一。

其實這問題的根本原因很單純，說穿了就是「時差」。React 18 在進行 Hydration（注水）時，要求伺服器產生的 HTML 結構必須跟瀏覽器第一次渲染出的內容完全一致。但我們在開發時，常常會不小心用到一些「只有瀏覽器才知道」的資訊，像是 window 物件、本地時間 new Date()，或者是隨機亂數 Math.random()。當伺服器渲染時，它用的是伺服器的時間；等到瀏覽器一接手，它拿到的是使用者裝置的時間，兩者一對，「恭喜你，內容不匹配！」系統就直接拋出錯誤，甚至可能導致頁面閃爍或部分功能直接失效。

要解決這個問題，最直覺的做法就是「強制讓元件等到瀏覽器端才渲染」。我後來發現，只要確保那個會產生變動的內容只在 useEffect 之後出現，就能完美避開這個坑。最常見的做法是設定一個 isMounted 的狀態，等到頁面掛載完成後才顯示該內容。

你可以試著這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者放一個簡單的 Loading 佔位符
  }

  return (
    <div>
      {/* 這裡放那些會讓 Hydration 崩潰的邏輯，例如 new Date().toLocaleString() */}
      {new Date().toLocaleString()}
    </div>
  );
}

這招雖然看起來有點「暴力」，但確實能保證伺服器端回傳的是乾淨的靜態內容，避免了前後端數據衝突。

至於怎麼預防這種惡夢再次發生？我現在養成一個習慣，只要寫到會依賴環境變數或瀏覽器 API 的邏輯，我都會先問自己：「這東西在 Node.js 環境跑得出來嗎？」如果不行，就直接把它丟進 useEffect 或是 dynamic import 並設定 { ssr: false }。畢竟開發的時候多想這一步，上線後就能少熬好幾個深夜的夜班。

希望這篇心得能幫你省下幾小時的除錯時間，趕快去把那些紅字消滅掉吧！
