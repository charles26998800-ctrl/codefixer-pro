How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a distributed training job for a computer vision project, thinking I had everything perfectly configured for my GPU. I pushed the run button, walked away to grab a coffee, and returned only to find my terminal screaming this exact error at me after just two seconds of execution. I honestly spent three hours staring at the screen, convinced my CUDA drivers were corrupted or that I’d somehow installed the wrong version of PyTorch, only to realize I’d completely forgotten to move my input tensors to the device.

The reason this happens is actually quite straightforward once you step back: PyTorch is strict about where your data lives. Your model is residing on the GPU because you called model.to(device), but your data is still sitting comfortably in your computer's RAM (the CPU). When the model tries to perform matrix multiplication, it expects the weights and the inputs to be in the same memory space. If the model is on the GPU and the data is on the CPU, PyTorch throws this mismatch error to stop you from trying to perform operations across different memory architectures.

To fix this, you simply need to move your input data onto the same device as your model during the training loop. I usually do this right after I pull the data out of my dataloader. You don't need to overcomplicate it; just call the .to(device) method on your tensors before passing them into the model. Here is how I handle it in my own scripts:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move the inputs and labels to the same device as the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you want to prevent this from ruining your day in the future, my best advice is to write a small helper function or a custom wrapper for your training step that handles device placement automatically. Don't rely on manually moving tensors every single time you write a new loop. Once you abstract the device movement into a utility function, you’ll never have to worry about these annoying mismatch errors again.

Hope this saves you some of the headache I went through. Happy coding and good luck with your training runs!

PyTorch 報錯：Input type 和 weight type 不一致？別讓 GPU 變成裝飾品！

來源：Stack Overflow ↗ · 202 票

記得剛開始碰 PyTorch 的時候，我熬夜跑一個訓練腳本，好不容易把模型架構寫好，看著螢幕上顯示 model.to(device) 順利執行，心裡還想著「穩了」。結果按下 Run 的那一刻，終端機直接噴出一大串紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same，當下真的是一口老血差點吐出來，心想明明都已經搬到 GPU 了，怎麼還會跟我說兩邊型態不同？

這其實是一個超級經典的「裝置不對稱」問題。簡單來說，就是你的模型雖然已經乖乖移到 GPU 上等著工作了，但當你從 DataLoader 抓資料出來時，那些 inputs 卻還待在 CPU 的記憶體裡。PyTorch 很龜毛，它不允許模型在 GPU 運算時，吃進來的資料還留在 CPU，就像是你請了一個頂級廚師（GPU），結果你卻把食材（Data）丟在隔壁鄰居家，這廚師當然會罷工給你看。

解決方法其實很直覺，就是要確保資料在餵給模型之前，也跟著搬到跟模型一樣的裝置上。我當時發現這個問題後，寫了一小段程式碼來處理，只要在迴圈裡加上 .to(device) 就行了：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！記得把 inputs 和 labels 都推過去
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也要確保在同一個裝置上

自從踩過這個坑之後，我後來學乖了，為了避免這種「一忙就忘」的蠢事再次發生，我現在寫專案時會習慣寫一個簡單的 helper 函數，或者直接在定義 Dataset 的時候就確認好資料型態。另外，如果你是用一些比較複雜的架構，建議在訓練迴圈剛開始時，加個小小的檢查點 assert inputs.device == next(model.parameters()).device，這樣只要一發生這種裝置不一致的情況，程式會立刻停止並告訴你哪裡出錯，省下不少除錯的時間。

說真的，這種 bug 在模型跑了半小時才噴出來的時候最讓人崩潰，大家寫 code 時還是多留心一下資料的「所在地」吧！希望這篇筆記能幫你省下寶貴的開發時間，趕快去把模型跑起來吧。
