How to Fix the "Input type and weight type should be the same" Error in PyTorch

Source: Stack Overflow ↗ · 201 votes

I remember the first time I ran into this error back when I was building my first custom ResNet implementation. I had spent three hours fine-tuning my hyperparameters and waiting for the environment to spin up on a cloud GPU instance, only to have the script crash literally two seconds after starting the training loop. I stared at the screen for a solid minute, feeling like a complete amateur, wondering why my GPU-accelerated model was throwing a tantrum at my perfectly normal-looking CPU-bound data.

The reason this happens is actually pretty straightforward once you stop yelling at your monitor: PyTorch is strictly typed when it comes to hardware devices. When you move your model to the GPU using model.to(device), you’re essentially telling the model, "Hey, all your weights and biases live on the graphics card now." However, your data loader is still grabbing batches of images or tensors from your system RAM, which defaults to the CPU. When you feed that CPU-based tensor into a GPU-based model, PyTorch throws this RuntimeError because it can't perform mathematical operations between two different hardware devices. It’s like trying to plug a European power adapter into an American wall outlet—the pieces just don’t fit.

Fixing this is a quick one-liner that I always keep in my back pocket now. You simply need to move your input tensors to the same device as your model inside your training loop. I usually make sure my device is set at the start of the script and then call .to(device) on my data as it comes out of the loader. Here is how I handle it in my projects:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move inputs and labels to the same device as the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

To keep this from biting you again, I’ve found that the best practice is to always define your device variable at the top of your training script and reference it consistently. If you're working on a larger project, I’d suggest writing a small helper function that automatically pushes your data batches to the device; that way, you don't have to remember to manually move every single tensor every time you add a new input type to your training pipeline.

Hope this saves you the headache it caused me back in the day. Happy coding!

PyTorch 的經典惡夢：Input 和 Weight 型別不合的除錯指南

來源：Stack Overflow ↗ · 201 票

那天我正準備跑一個訓練了半天的模型，看著進度條慢慢爬升，心裡想著「這次應該穩了吧」，結果才剛過第一個 iteration，終端機就直接噴出一行紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。我當時真的是差點把咖啡噴到螢幕上，那種「明明把模型丟到 GPU 了，為什麼還跟我吵型別不合」的無力感，相信每個寫 PyTorch 的工程師都懂，心臟真的會漏跳一拍。

其實這個問題的根本原因說穿了很單純，就是「模型在 GPU 上，但你的資料還留在 CPU 的記憶體裡」。PyTorch 很講究門當戶對，模型權重（weight）如果已經搬到了 GPU，那傳進去的輸入（input）也必須要是 CUDA tensor 才行。雖然我們在程式開頭寫了 model.to(device)，但這只把模型搬過去了，並沒有自動把後續撈出來的資料也跟著一起搬過去。這就是最常見的陷阱，我們常常以為程式會自動幫忙處理跨裝置的搬運，但很遺憾，PyTorch 對這點可是嚴格得很。

要解決這個問題其實不難，只要在迴圈撈出資料的那一刻，順手把它們也推到同一個 device 就行了。我在發現這個坑之後，習慣會在迴圈裡多加一行 .to(device)。你只需要把程式碼改成這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 把 inputs 和 labels 都搬到跟模型一樣的地方
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也記得要用搬過去的 labels

如果你想避免之後又因為這種低級錯誤被卡住，我強烈建議養成一個好習慣：在定義 dataset 或 dataloader 的時候，盡量確保邏輯單純，並且在進入 model 之前，強制檢查一下資料的 device。如果不放心的話，甚至可以寫一個小的輔助函式專門處理搬運，或者是直接把這行 .to(device) 寫成一個慣例，寫久了就會像肌肉記憶一樣，看到 dataloader 就會自動加上去，再也不用擔心這種尷尬的錯誤毀了你的訓練過程。

希望這招能救你脫離苦海，下次寫 code 順利點，別再被這種小細節折磨啦！
