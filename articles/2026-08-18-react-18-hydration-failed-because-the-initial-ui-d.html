Why Your Next.js App is Crashing: Solving the Hydration Mismatch Error

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in React 18. I had just finished migrating a legacy dashboard, feeling pretty proud of my performance optimizations, when I opened the console and saw a wall of red text screaming that my server-rendered HTML didn't match what the client expected. I spent three hours staring at a simple timestamp component, convinced I’d broken the entire framework, only to realize I was just rendering the current date differently on the server than I was on the client. It’s one of those bugs that makes you want to throw your laptop out the window, but once you understand the mechanism, it’s actually pretty straightforward to fix.

The root cause of this headache is a fundamental mismatch between the static HTML the server sends to the browser and the dynamic content React tries to inject once it kicks in on the client side. When you use Next.js, the server generates a snapshot of your page. If your component logic relies on something like Math.random(), new Date(), or even a user’s local storage preference that the server can't possibly know, the initial render on the server will be different from the first render on the client. React notices this discrepancy, panics, and throws the hydration error because it doesn't know which version of the truth to trust.

To fix this, I’ve learned to embrace the useEffect hook as my best friend. Since useEffect only runs on the client after the component mounts, it’s the perfect place to initialize state that depends on browser-only APIs. I usually create a "mounted" state variable to prevent the component from rendering the dynamic part until the client is ready. Here is how I typically structure that fix:


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a static skeleton/loader
  }

  return (
    <div>
      {/* Now it's safe to use browser-specific data */}
      Current Time: {new Date().toLocaleTimeString()}
    </div>
  );
}

By returning null or a static placeholder until isMounted is true, I guarantee that the server-rendered HTML is identical to the first client-side pass. React is happy, the hydration warning disappears, and my app stays performant.

If you want to prevent this from happening in the future, my biggest tip is to be extremely careful with global browser objects like window or localStorage inside your render body. Whenever you feel the urge to access them directly in your component, ask yourself if the server needs that data to build the initial page. If it doesn't, force yourself to wrap that logic in a useEffect or a custom hook that checks for the component's mounted state. It’ll save you from those late-night debugging sessions that I know all too well.

Hope this clears up the confusion and helps you get your build back on track. Catch you in the next one!

React 18 Hydration 錯誤：為什麼我的頁面又崩潰了？

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地想體驗 SSR 的效能提升，結果專案一跑起來，瀏覽器 Console 直接噴出一大串紅通通的「Hydration failed」錯誤。當時我真的差點崩潰，明明程式碼邏輯看起來沒問題，伺服器渲染出來的 HTML 跟瀏覽器初次渲染的畫面硬是對不上，導致整個頁面直接閃退重載，那種「明明只差一步卻怎麼也跨不過去」的挫折感，真的是開發者生涯中最想掐死自己的時刻之一。

其實會發生這種問題，簡單來說就是 React 在「搞分裂」。當你使用 Next.js 進行伺服器渲染時，伺服器會先產生一份 HTML 發送給瀏覽器，但當瀏覽器收到這份 HTML 後，React 想要進行 Hydration（水合作用）把這些靜態元素變成可互動的組件時，卻發現瀏覽器環境裡的內容竟然跟伺服器給的不一樣。最常見的原因通常是我們在組件裡用了 window 物件、隨機數 Math.random()，或是根據當前時間產生的內容。因為伺服器沒有這些資訊，導致兩邊產出的 DOM 結構出現微妙的差異，React 一旦發現「對不上」，為了避免顯示錯誤的資料，就會直接選擇報錯重來。

我當時花了好幾個小時把程式碼翻遍，最後發現最有效的解法就是「先讓它安靜地等一下」。如果你必須在組件中使用依賴於瀏覽器的變數，最簡單的做法是確保這個邏輯只在組件掛載（Mounted）後才執行。我通常會寫一個簡單的 useEffect 來處理，像這樣：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>現在是瀏覽器環境：{window.location.href}</p>
      ) : (
        <p>載入中...</p>
      )}
    </div>
  );
}

這樣一來，伺服器渲染時永遠只會看到「載入中」，直到瀏覽器接手後才真正渲染出依賴 window 的內容，Hydration 就再也不會報錯了。

為了預防這種地獄輪迴，我現在養成了習慣，只要涉及到可能會變動的狀態，我都會先問自己：「這東西在伺服器端真的拿得到嗎？」如果答案是否定的，我絕對不會把它直接塞在組件的初始渲染邏輯裡。保持組件的「純粹」，讓伺服器和瀏覽器在第一次碰面時能夠達成共識，才是避開這個坑最穩的方式。

希望這篇心得能幫你省下幾個小時的除錯時間，這坑踩過一次就夠了，共勉之！
