How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 688 votes

I remember the first time I set up a local Kubernetes cluster, I spent a solid three hours banging my head against the wall because my pods kept stuck in ImagePullBackOff. I was convinced my YAML was broken, only to realize I had built my image locally and Minikube, running in its own isolated VM, had absolutely no clue that image existed on my laptop. It’s one of those classic "aha!" moments that every K8s developer hits, and it honestly makes you feel a bit foolish until you realize just how the architecture is actually separated.

The reason this happens is that Minikube runs inside its own isolated environment—usually a virtual machine or a separate container—which has its own Docker daemon. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Kubernetes, however, asks the Minikube daemon for the image, and since they aren't sharing a brain, the pull fails. You don't need to push your code to a registry just to test a one-line change, but you do need to tell Minikube to look in the right place.

The quickest way I’ve found to bridge this gap is by pointing your local terminal to the Minikube Docker daemon. By running a single command, you can make your host's docker CLI talk directly to the daemon inside Minikube. Just execute this in your terminal:


eval $(minikube docker-env)

Once you’ve run that, any docker build command you execute will build the image directly inside the Minikube environment. You can then verify it’s there by running docker images, and your pods will be able to see it immediately. Just keep in mind that this only affects your current terminal session. If you open a new tab, you’ll need to run that command again. Also, don't forget to set your imagePullPolicy to IfNotPresent in your Kubernetes deployment YAML; otherwise, K8s might still try to reach out to a remote registry even if the image is sitting right there.

To keep things smooth in the future, I highly recommend using a local image registry or just sticking to the minikube image load command if you prefer a more explicit workflow. If you don't want to mess with your environment variables, you can just build your image normally and then run minikube image load . It’s a bit slower since it copies the image over, but it keeps your host Docker environment clean and prevents those weird conflicts where your local and cluster images get out of sync.

Hopefully, this saves you the headache it caused me back in the day. Happy coding, and may your pods always reach the Running state on the first try!

別再把 Image 推到 Docker Hub 了！Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 688 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的修改，我每次都得 docker build 然後 docker push 到遠端的 Registry，再讓 Minikube 去 pull 下來。最讓我崩潰的一次，是網路剛好慢得像蝸牛，光是等那個幾百 MB 的 Image 上傳再下載，我就在那邊盯著螢幕發呆了快半小時，咖啡喝完了、進度條還在跑，真的會氣到想把鍵盤砸了。那種「我明明就在同一台電腦上，為什麼還要繞過半個地球」的無力感，相信很多人都懂。

其實這背後的原因很單純，因為 Minikube 為了模擬真實的叢集環境，它是跑在一個獨立的虛擬機（或是容器）裡面的。簡單來說，Minikube 裡面的 Docker Daemon 跟我們宿主機（Host）上的 Docker 完全是兩回事，它們根本不在同一個空間，所以當你在宿主機 build 好 image，Minikube 的節點當然看不到，它只會傻傻地去網路上找，找不到就給你一個 ImagePullBackOff 的錯誤訊息，讓你崩潰。

後來我終於發現，最快的方法其實就是讓 Minikube 直接使用當前的 Docker 環境。如果你是用 docker driver 的話，只要在 build 之前執行下面這行指令，把環境變數切換過去就行了：


eval $(minikube docker-env)

執行這行之後，你的終端機就會直接連上 Minikube 內部的 Docker Daemon。這時候你再跑 docker build -t my-app:v1 .，這個 image 就會直接被建立在 Minikube 的肚子裡。接著，記得把你的 Deployment YAML 檔裡的 imagePullPolicy 改成 IfNotPresent，這樣 Kubernetes 看到本地已經有這個 image，就不會再跑去網路上抓，部署速度快到讓你懷疑人生。

當然，如果你不想每次開新視窗都要設定環境變數，我強烈建議養成一個習慣，就是把 Image 的 Tag 加上版本號，而不是一直用 latest。因為 IfNotPresent 的邏輯在遇到 latest 時有時候會很固執，加上明確的版本號，不僅能避免這種「明明更新了卻沒生效」的撞牆期，回滾版本的時候也會輕鬆很多。

以後別再浪費時間等上傳了，直接把 Minikube 當成你本地的開發環境就好，祝大家開發順利，少點加班！
