Debugging the "Hydration failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw that dreaded "Hydration failed" warning flashing in my browser console. I’d just migrated a legacy project to Next.js, feeling pretty proud of my architecture, only for the entire page to jitter and throw a massive error the moment it loaded. I spent three hours refactoring my components, convinced I’d messed up my server-side data fetching, only to realize it was something as silly as a timestamp rendering differently between the server and the client.

The reason this happens is actually quite straightforward once you stop pulling your hair out. React 18's hydration process expects the HTML generated by the server to be a perfect clone of what the client-side JavaScript produces during the initial render. If you have code that behaves differently based on whether it's running on the server or the browser—like checking window object properties, using local storage, or generating random numbers—the two versions will conflict. When React notices the server-rendered HTML doesn't match the virtual DOM it built on the client, it throws its hands up and triggers the hydration error because it doesn't know which version of the truth to trust.

The fix usually involves delaying the rendering of the "dynamic" part of your component until the client has officially mounted. I’ve found that the cleanest way to handle this is by using a simple useEffect hook to track the mounting state. By forcing the component to wait until it's on the client before rendering the problematic UI, you ensure the server-side render remains predictable and static. Here is how I usually implement this pattern:


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a static loading placeholder
  }

  return (
    <div>
      {/* Your dynamic content that depends on window or browser state */}
      {window.innerWidth}
    </div>
  );
}

By returning null or a generic loading skeleton while isMounted is false, you stop the server from trying to render browser-specific logic that it can't possibly know about. Once the component hits the client, useEffect fires, updates the state, and triggers a re-render with the data you actually need.

To prevent this from becoming a recurring nightmare, my biggest tip is to always treat your server-side rendering as a "first pass" that should be as deterministic as possible. If you find yourself reaching for window or document inside your main component body, stop and wrap that logic in a custom hook or a client-only component. Keeping your server-side logic pure is the best insurance policy you can have against hydration mismatches.

Good luck with your debugging, and I hope you get back to building features instead of fighting console errors soon!

當 React 18 的 Hydration Error 讓你懷疑人生：別慌，這其實是「時差」惹的禍

來源：Stack Overflow ↗ · 341 票

前陣子為了把專案升級到 Next.js 新版本，我心想這應該是個輕鬆的週末午後，結果才剛跑起來，控制台（Console）就噴出一大串刺眼的紅色錯誤訊息，直接告訴我「Hydration failed」。我看著那行錯誤，心裡真的只有一個字：慘。我明明在 Server 端寫得好好的，結果瀏覽器一打開，Server 渲染出來的 HTML 跟客戶端第一次執行 React 時產生的畫面根本對不上，那一刻我真的是差點把咖啡噴在螢幕上，完全搞不懂明明都是同一份程式碼，怎麼會鬧這種時差。

其實這背後的道理說穿了就是「溝通不良」。React 18 在進行 Hydration 時，會去比對伺服器吐出來的靜態 HTML 和瀏覽器接手後生成的 UI 樹。如果你的程式碼裡用了 Date()、隨機數 Math.random()，或者是依賴了只有瀏覽器才有的 window 或 localStorage 物件，伺服器在執行時拿不到這些值或是拿到的值跟客戶端不一樣，React 就會因為「這兩邊長得不一樣」而直接報錯，甚至乾脆放棄治療，整塊畫面重新渲染，導致效能大打折扣。

我後來發現，最常見的兇手就是那些會在 Server 和 Client 產生不同結果的邏輯，或者是這類在 SSR 環境下根本不該存在的判斷。解決這個問題最快的方法，就是確保元件在「掛載完成（Mounted）」之前，不要去渲染那些會導致差異的內容。我通常會寫一個簡單的 isMounted 狀態來控制，像這樣：


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者你可以放一個簡單的 Loading skeleton
  }

  return (
    <div>
      現在時間是: {new Date().toLocaleString()}
    </div>
  );
};

透過這種方式，我強制讓元件在瀏覽器端確認「準備好了」之後才開始跑那些會產生差異的邏輯，這樣 Server 渲染時只會收到一個空的佔位符，就不會跟瀏覽器打架了。

說真的，為了預防這種問題再次發生，我現在養成了一個習慣：只要是用到 window、localStorage 或者當前時間的邏輯，我一律預設它們是「危險分子」。我會盡量把這些操作移到 useEffect 裡面，或者乾脆使用 dynamic import 並設定 ssr: false，直接告訴 Next.js 說：「兄弟，這段程式碼你不用管，讓瀏覽器自己處理就好。」

Debug 的過程雖然痛苦，但看到 Console 變回乾乾淨淨的樣子，那種成就感真的無可取代。希望下次你再遇到這個錯誤時，能少走點冤枉路，早點收工去休息！
