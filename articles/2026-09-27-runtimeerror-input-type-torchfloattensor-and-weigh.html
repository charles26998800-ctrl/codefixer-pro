How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a training loop on a new GPU server back in my junior days. I was so excited to see that "cuda is available" flag flip to true that I rushed through the boilerplate, only to be slapped in the face by this cryptic RuntimeError five minutes into training. I spent three hours staring at the console, convinced my drivers were broken or my PyTorch installation was cursed, before I realized I was essentially trying to force a CPU-bound tensor to talk to a GPU-bound model.

The root cause of this headache is actually quite simple, even if the error message makes it sound like a disaster. PyTorch is extremely strict about where your data lives. When you move your model to the GPU using model.to(device), you’re essentially packing your model's weights and biases into the GPU's memory. However, when you iterate through your dataloader, those tensors are still sitting comfortably in your system's RAM (the CPU). When you pass those CPU tensors into your GPU model, PyTorch throws an error because the mathematical operations can't span across different memory architectures. It’s like trying to play a video game on your console while the disc is still sitting in the box on your shelf.

Fixing this is straightforward once you know where to look. You don’t need to change your architecture; you just need to ensure that your input data takes the same trip to the device that your model did. Inside your training loop, you should explicitly move your inputs and labels to the device before passing them into the model. Here is the snippet that finally saved my sanity:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the line you're missing
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your loss calculation

If you want to avoid this headache in the future, get into the habit of writing a small helper function or a custom collate function that handles device placement automatically. Personally, I like to keep a to_device() utility function handy that recursively moves tensors to the specified device. It saves me from having to manually call .to(device) on every single input, target, or hidden state, and it’s a total lifesaver when you’re dealing with complex nested dictionaries or lists of data.

Hope this clears up the confusion and gets your training loop running smoothly. Happy coding, and may your loss curves always trend downwards!

PyTorch 報錯：Input type 和 weight type 不一致，別再被 GPU 搞瘋了！

來源：Stack Overflow ↗ · 202 票

記得剛開始碰 PyTorch 的時候，有一次為了趕在 Deadline 前訓練完模型，我熬夜寫了好久的 code。好不容易把環境都架好、資料跑起來，結果按下執行鍵不到三秒，螢幕直接噴出一大串紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。那一刻我真的差點崩潰，心想：「我不是明明都寫了 model.to(device) 了嗎？這是在跟我開什麼玩笑？」

其實這問題的根本原因說穿了就是「溝通不良」。PyTorch 是個很嚴謹的傢伙，它要求參與運算的資料必須在同一個「領地」上。當你把模型搬到 GPU（也就是 cuda）之後，它就像是一個住進了豪宅的貴族，但你的資料（input）卻還留在 CPU（FloatTensor）的貧民窟裡。當你把資料丟進模型時，它們就像是語言不通的兩群人，GPU 看到 CPU 寄來的資料，直接就報錯拒絕執行了。

解決方法其實很簡單，就是要在把資料丟進模型前，順手把資料也搬到 GPU 上。我當時發現，很多人（包括那時候的我）只記得把模型 to(device)，卻忘了在迴圈裡對 inputs 和 labels 做同樣的操作。你只需要在 dataloader 的迴圈裡，加個 .to(device) 就搞定了：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！要把輸入資料也搬到跟模型同一個裝置上
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就可以進行後續的 loss 計算啦

為了避免以後再被這種低級錯誤氣到，我現在養成了一個習慣：只要寫到需要處理輸入資料的地方，我會在寫 model.to(device) 的下一行，直接寫一個 helper function 或者統一的變數轉換邏輯。甚至如果你想偷懶，也可以直接定義一個 move_to(data, device) 的小函式，把所有資料類型（不管是 Tensor、list 還是 dict）都自動轉過去。只要記得這個「資料跟模型要住在一起」的鐵則，之後開發效率真的會順很多。

希望大家都能避開這個坑，別讓這種小 bug 成為你深夜修 code 的絆腳石啦！
