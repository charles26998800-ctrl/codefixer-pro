Stop Pushing to Registry: How to Use Local Docker Images with Minikube

Source: Stack Overflow ↗ · 689 votes

I still remember the first time I set up a local Kubernetes cluster, back when I thought I had to push every single experimental change to Docker Hub just to see if a config tweak worked. I spent three hours one Saturday afternoon waiting for my slow home upload speeds to finish, only to realize I’d made a typo in my deployment manifest. I felt like a total clown staring at my screen, knowing there had to be a way to point Minikube directly at my local engine.

The reason this happens is simple: Minikube runs inside its own isolated virtual machine or container. When you run docker build on your laptop, that image lives in your host’s Docker daemon, not inside the Minikube environment. Because Kubernetes nodes are effectively "blind" to your host machine's storage, they look for the image in the configured registry, fail to find it, and trigger that dreaded ImagePullBackOff error.

To fix this, the trick is to point your local terminal's Docker environment to the one inside Minikube. By running a single command, you can make your shell talk directly to the Minikube Docker daemon, meaning every docker build command you run happens inside the cluster's context.

First, you need to set your environment variables by running:


eval $(minikube docker-env)

Once you’ve run that, any image you build with docker build -t my-app:v1 . will be instantly available to your Minikube cluster. You just need to make sure your Kubernetes deployment manifest has imagePullPolicy: IfNotPresent (or Never) set, so it doesn't try to head out to the internet to find an image that already exists right under its nose. If you’re ever done and want to switch back to your host's Docker daemon, just run eval $(minikube docker-env -u).

To keep this from driving you crazy in the future, get into the habit of checking your context before you start building. If you’re ever confused about which daemon you’re talking to, just run docker ps and look for the specific container names Minikube uses; if you see those, you know you’re in the right place.

Hope this saves you from the registry-pushing madness I went through. Happy coding!

在 Minikube 裡直接用本地 Docker Image：別再傻傻地推送到 Docker Hub 了！

來源：Stack Overflow ↗ · 689 票

還記得剛開始玩 Kubernetes 的時候，我整個人被「ImagePullBackOff」這個錯誤訊息搞到快崩潰。當時我寫好了一個微服務，本地 Docker build 完，心想馬上就能在 Minikube 跑起來，結果每次部署 Pod 就一直卡在下載鏡像。為了測試一個小改動，我竟然真的跑了 docker push 再 docker pull，光是等待上傳下載就花掉我半小時，更別提中間網路不穩斷線時那種想把鍵盤砸了的衝動，簡直是工程師的惡夢。

會發生這種事，其實是因為 Minikube 本質上是一個跑在虛擬機或容器裡的獨立環境。當你在終端機打 docker build 時，鏡像其實是存放在你本機的 Docker Daemon 裡，但 Minikube 的那台虛擬機根本看不到你本機的 Docker 環境，它只能去 Docker Hub 或私有 Registry 找鏡像。因為它「看不到」，所以當然就報錯說鏡像不存在啦。

解決這個問題其實有個超級簡單的偷吃步，根本不需要什麼複雜的設定。只要在 build 鏡像之前，先執行這條指令，把你的終端機環境「切換」到 Minikube 內部的 Docker Daemon：


eval $(minikube docker-env)

執行完這行後，接下來你下的 docker build -t my-app:v1 . 指令，就會直接在 Minikube 的虛擬機內部進行打包。這樣一來，你的鏡像會直接存在 Minikube 裡面，Kubernetes 部署時就能秒讀本地鏡像，完全不用再去連外部網路。不過要提醒一下，這個設定只對當前的終端機視窗有效，如果你開了新的分頁，記得要重新執行一次。

如果你覺得每次都要 eval 很麻煩，或者怕哪天又不小心忘記，我建議乾脆把 minikube docker-env 寫進你的 .zshrc 或 .bashrc 裡做個 alias，或者養成習慣在開發專案時，先把這個指令當作儀式感的一部分。只要確保你在部署 YAML 檔案裡的 imagePullPolicy 設定為 IfNotPresent，Minikube 就會優先檢查本地有沒有鏡像，這樣你以後再也不用忍受漫長的推送等待時間了。

學會這招之後，我的開發效率簡直是起飛，希望也能幫你省下不少崩潰的時光！
