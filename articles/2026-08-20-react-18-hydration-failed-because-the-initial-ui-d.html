Fixing the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the dreaded "Hydration failed" warning in React 18. I had just migrated a fairly complex dashboard to Next.js, and for a solid three hours, I was convinced my server-side rendering logic was completely broken because the site would flicker and then vomit a wall of red text in the console. It turned out I was just being lazy with how I handled browser-specific timestamps, and that tiny mismatch between the server's static HTML and the client's dynamic rendering sent React into a full-blown panic.

The root cause of this headache is actually quite logical once you stop pulling your hair out. When you use Next.js, the server renders your component into static HTML and sends it to the browser. Once that HTML lands, React "hydrates" it, meaning it attaches event listeners and turns it into an interactive app. If the HTML the server generated doesn't perfectly match what the client generates on its first pass—perhaps because of a Date() call, a random number generator, or checking window object properties—React throws its hands up. It assumes the server is wrong, wipes the DOM, and re-renders everything, which kills your performance and causes that jarring UI flicker.

Fixing this usually comes down to delaying the rendering of dynamic content until the component has officially mounted on the client. I stopped trying to force the server to guess browser-only values and started using a simple useEffect hook to toggle the state. By initializing my state as false and only updating it once the component mounts, I ensure the server and the initial client render stay perfectly in sync. Here is how I usually structure that fix:


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This only shows up after hydration: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
};

This approach forces the server to render a static "Loading..." state, which is perfectly fine, and then lets the client take over once it's safe to use browser APIs.

To prevent this from happening in the future, I’ve made it a rule to never access window, localStorage, or dynamic time-based functions directly in my component body. If I need those values, I wrap them in a custom hook or a useEffect to ensure the server-side render remains deterministic. It’s saved me so much debugging time that I honestly don’t even think about it anymore.

Hope this clears up the confusion and saves you from the same three-hour headache I had. Happy coding, and may your logs stay clean!

React 18 的 Hydration Error：別讓伺服器跟瀏覽器吵架了！

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 的那天，我心想「終於能享受 Concurrent Features 了」，結果一打開開發環境，滿螢幕紅通通的 Hydration failed 直接把我從天堂踹回地獄。明明程式碼看起來沒毛病，但瀏覽器就是在那邊瘋狂報錯，說伺服器產出的 HTML 跟客戶端拿到的不一樣。最讓我崩潰的是，有時候這錯誤還會因為隨機的內容（比如時間戳記）閃爍消失，這種「薛丁格的 Bug」真的會讓人想把鍵盤給砸了。

會發生這種狀況，其實就是因為 React 在「伺服器端渲染 (SSR)」與「瀏覽器端 Hydration」中間產生了認知落差。簡單說，伺服器算出來的 HTML 長這樣，但當瀏覽器接手時，因為某些原因（比如用了 new Date()、隨機數，或是瀏覽器獨有的 API），它執行出來的結果跟伺服器給的不一樣。React 發現兩邊對不上，為了避免畫面顯示錯誤，它乾脆直接放棄伺服器渲染的那塊，強行重新渲染一次。這不只造成效能損耗，還會讓使用者看到畫面閃爍，體驗極差。

我當時踩坑的常見原因之一，就是把會變動的數值直接塞進了渲染路徑。如果你也遇到這個問題，最直觀的解法就是確保「第一次渲染」時，兩邊的內容是一致的。我後來學會了用 useEffect 來處理那些只有瀏覽器才有的邏輯，或是強制讓元件在掛載後才顯示。舉個例子，如果你的元件需要顯示當前時間，千萬別直接在渲染函式裡寫 new Date()，試著這樣改：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    // 確保這段邏輯只在瀏覽器端執行
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    // 在伺服器端或還沒掛載時，先回傳一個穩定的佔位符
    return null; 
  }

  return <div>現在時間是：{new Date().toLocaleString()}</div>;
}

透過這種方式，我們直接跳過了伺服器端對不準的那個瞬間，等到瀏覽器確認掛載完成後才補上內容，Hydration Error 瞬間就消失了。

至於怎麼預防這種惱人的狀況再次發生？我現在養成了一個好習慣，就是嚴格審視所有會根據環境變數、時間或隨機亂數產生的 UI。如果你的元件內容在不同環境下有「不確定性」，請務必把它隔離在 useEffect 或是 typeof window !== 'undefined' 的檢查之後。只要確保伺服器渲染出來的 HTML 是「靜態且一致的」，你跟 React 之間的這場紛爭就會少很多。

希望大家都能順利避開這個坑，別再被這該死的 Hydration 錯誤搞到懷疑人生啦！
