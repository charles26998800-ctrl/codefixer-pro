How to Undo Your Last Local Git Commit Without Losing Your Mind

Source: Stack Overflow ↗ · 27241 votes

I still remember the first time I accidentally committed a folder full of sensitive API keys and massive binary logs to a repository. I was five minutes away from a deadline, my heart was racing, and I hit git commit before realizing I hadn't even staged the right files. I spent a solid hour frantically googling commands while sweating bullets, terrified that I’d accidentally nuke my entire project history or end up in a "detached HEAD" state that would take me all afternoon to fix.

The root cause is usually just a classic case of "git-happy" fingers. When you run git commit, you’re essentially taking a snapshot of your staging area and cementing it into your local history. Because Git is designed to be a distributed version control system, it treats your local machine as a full-fledged repository. It doesn't know—and honestly doesn't care—that you didn't mean to include that node_modules folder or that half-baked feature branch. It just does what you told it to do, leaving you with a commit object that exists in your local timeline but hasn't been pushed to the remote server yet.

To fix this mess, I always turn to the git reset command. If you want to undo the commit but keep your changes in the staging area so you can fix the file list, you’ll want to use a soft reset. This is my go-to move:


git reset --soft HEAD~1

By running this, the commit is wiped away, but your files stay exactly where they were in the staging area. You can then unstage the files you didn't want, add the correct ones, and commit again properly. If you’re truly fed up and want to nuke the changes entirely—meaning you want your working directory to look exactly like it did before that commit—you should use the hard reset flag. Just be careful, because this is destructive:


git reset --hard HEAD~1

This will throw away those changes for good, so only use it if you’re certain you don't need that code.

The best way to prevent this recurring nightmare is to get into the habit of running git status before every single commit. I started forcing myself to look at that list of green and red files every time I type git commit -m. It takes an extra three seconds, but it’s saved me from countless headaches and late-night reverts.

Hope this saves you from the same panic I felt back then. Happy coding, and keep your history clean!

救命！我不小心把垃圾 commit 推上去了，Git 還原指南

來源：Stack Overflow ↗ · 27241 票

記得有一次凌晨兩點，我正趕著要下班，腦袋已經呈現登出狀態，手一滑就把一堆還在測試階段、甚至帶有敏感設定檔的程式碼給 git commit 了。當下看到終端機顯示「commit successful」時，我整個人差點從椅子上彈起來，心跳快到以為要心臟病發，那種「慘了，這下要是推上去肯定被同事笑死」的恐懼感，真的是身為工程師最不想面對的惡夢。

其實會發生這種狀況，通常是因為我們在開發時太習慣 git commit -a 這種無腦指令，或是開發分支切換得太頻繁，一時之間沒意識到其實還沒準備好要打包這些變更。Git 本質上就是一個時光機器，它記錄了你每一個版本的變動，但很多人一看到 commit 歷史就慌了，以為一旦提交就覆水難收。其實只要你還沒執行 git push 把這些髒東西推送到遠端伺服器，一切都還有救，Git 的 reset 指令就是我們最好的解藥。

我當時的做法很簡單，就是直接用 git reset 來抹掉那個錯誤的紀錄。如果你的檔案不想留著，只想徹徹底底地把那個 commit 當作沒發生過，我建議你用 git reset --hard HEAD~1，這會直接把你上一次的提交連同檔案修改全部砍掉，回到 commit 之前的狀態。但如果你只是想把 commit 拆掉，但想保留剛剛辛苦寫的程式碼繼續修改，那就用 git reset --soft HEAD~1，這樣 commit 會被取消，但你的變更會全部留在「暫存區（Staging Area）」，這時候你就可以把那些不該 commit 的檔案移出，重新整理後再提交一次。

為了不要再經歷這種心臟漏跳一拍的時刻，我現在養成了一個好習慣：在執行 commit 之前，一定會先下 git status 掃一眼。如果真的很怕手殘，可以考慮在 IDE 裡面安裝一些視覺化的 Git 工具，或者乾脆設定一個 alias，強制自己在 commit 前跳出一個確認視窗。像我現在就養成了「小步快跑」的習慣，盡量讓每一個 commit 都保持乾淨且單純，這樣就算真的錯了，要修補起來也沒那麼痛苦。

說真的，Git 指令用久了自然就熟了，大家都是這樣一路踩坑過來的，下次如果不小心又手滑，記得深呼吸，別急著亂砍分支就好啦！
