How to Undo Your Most Recent Local Git Commits Without Losing Your Work

Source: Stack Overflow ↗ · 27240 votes

I still remember the first time I accidentally committed a massive directory of local build artifacts and a few sensitive environment files right before a demo. I panicked, thinking I’d permanently messed up my local history, and I spent a solid hour manually moving files to a backup folder just to reset my branch. It’s a classic rite of passage for every developer, and honestly, we’ve all been there—staring at the screen, sweating, hoping we didn't just break everything.

The reason this happens is that Git is designed to be a ledger of your history; once you commit, you’ve essentially "recorded" that state of your project. If you haven't pushed those changes to a remote repository yet, you’re in a great spot because your local history is still entirely under your control. Git doesn't automatically delete the work you've done; it just moves the "HEAD" pointer—the marker that tells Git where your current branch is—to a previous point in time, leaving your actual file changes sitting there waiting for you to fix them.

When I need to undo a commit, I reach for git reset. The command you’ll want to use 99% of the time is git reset --soft HEAD~1. This command moves the branch pointer back by one commit, but it keeps all the changes you made in that commit in your "staging area." It’s the perfect "oops" button because it essentially lets you un-commit without losing your code.


# Undo the last commit, but keep the changes staged
git reset --soft HEAD~1

If you realize that you actually messed up the files themselves and want to completely wipe the changes from that commit, you can use the --hard flag instead. Just be careful—this will permanently destroy any work that was in that commit.


# Undo the last commit and completely discard all changes
git reset --hard HEAD~1

If you’re working on a feature and find yourself committing too often, I’ve found that the best way to prevent this headache is to get into the habit of running git status every single time before I hit that commit button. It takes two seconds, but it’s saved me from committing junk files or forgotten debugging logs more times than I can count.

Hope this saves you some stress the next time your fingers move faster than your brain. Happy coding!

手殘黨救星：如何優雅地撤銷 Git 的最後一次 Commit？

來源：Stack Overflow ↗ · 27240 票

記得剛入行沒多久，有次我在趕一個急件，想說先把改好的程式碼 commit 一下，結果手一抖，竟然把還在除錯的半成品跟一堆臨時檔案全塞進去，按下 Enter 的瞬間我心臟差點沒停掉。當下看著螢幕上顯示的 commit 成功訊息，真的有一種想把電腦直接關機裝死、或是乾脆請假回家避難的衝動，畢竟還沒 push 上去還好，要是推上遠端伺服器，那真的就是大型社死現場了。

其實這問題的根本原因很單純，就是 Git 的「暫存區」機制。當你執行 git commit 時，Git 已經把你當下暫存區（Staging Area）的內容包成一個記錄點了。但重點是，這只是在你本地的資料庫裡動手腳，只要你還沒執行 git push，這些錯誤記錄就還沒流向團隊的共用倉庫。所以，你完全不需要慌張，我們有的是時間把這些錯誤的 commit 像沒發生過一樣抹掉。

要解決這個問題，我通常會用 git reset 這個指令。如果你只是想撤銷 commit，但想保留你辛苦寫的檔案修改，只要下這行指令就好：

git reset --soft HEAD~1

這行指令的意思是「保留我的檔案修改，但把 commit 記錄往前退一步」，所以你剛剛 commit 的內容會回到「已暫存（Staged）」的狀態，你就可以趕快修正那些漏掉的檔案，再重新 commit 一次。但如果你的情況更慘，連檔案改得一塌糊塗，想直接把這一次的 commit 當作從沒發生過，連檔案修改都不要了，那就果斷一點用：

git reset --hard HEAD~1

這招真的好用，但用之前一定要確定你真的不要那些修改了，不然檔案消失的那一刻，你真的會感覺到什麼叫人間絕望。

為了避免這種「手滑」悲劇重演，我現在養成了一個習慣，就是每次 commit 前一定會先下 git status 檢查一遍，看看有哪些檔案被標記為紅色或綠色。如果真的還是怕，甚至可以考慮用 git add -p，它會讓你逐行確認到底要加入哪些修改，雖然麻煩點，但至少能保證你不會把什麼不該出現的 debug log 或奇怪的設定檔一併送進版本庫裡。

Git 這東西雖然強大，但真的很容易讓人心跳漏半拍。希望這幾個指令能救回你的工作進度，以後 commit 前多看一眼，心臟會健康很多。
