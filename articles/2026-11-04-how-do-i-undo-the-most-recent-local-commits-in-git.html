How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27251 votes

I’ll never forget the time I spent three hours debugging a production issue only to realize I’d accidentally committed my entire node_modules folder and a local .env file containing my actual API keys. I was staring at my terminal, heart pounding, convinced I’d just permanently ruined my repository history right before a Friday afternoon deploy. It’s a rite of passage for every developer, but that sinking feeling when you realize you’ve botched a commit is something I still don't miss.

The root of the problem is that Git is designed to be a persistent record of your work. When you run git commit, you’re essentially "sealing" a state of your project into the history. If you haven't pushed those changes to a remote repository yet, you’re in a safe zone—the commit exists only on your machine. However, because Git is so good at tracking changes, it doesn't just let you "delete" a commit without understanding what you want to happen to the files you were working on. You have to tell Git whether you want to keep your changes in the staging area, keep them as modified files, or blow them away entirely.

When I need to fix this, I always reach for git reset. The command you use depends entirely on whether you want to keep the work you did or pretend it never happened. If I realize I just committed too early but I want to keep all my changes in my current working directory so I can keep editing, I run:


git reset --soft HEAD~1

This command moves the HEAD pointer back by one commit. The "soft" flag is my best friend here because it keeps all those files I just "uncommitted" in my staging area, ready to be tweaked or added to a better commit. If I want to keep the changes but I don't want them staged yet, I use --mixed instead, which is actually the default behavior if you just run git reset HEAD~1.

Now, if I’ve completely messed up and I want to nuke the commit and every single change I made within it because the code is garbage, I use the "hard" reset:


git reset --hard HEAD~1

Be extremely careful with this one. It will destroy any uncommitted changes you have in your working directory, so make sure you truly don't need that code anymore before you hit enter.

To keep this from happening again, I’ve started using a pre-commit hook to run a quick script that checks for sensitive files or massive folder sizes before allowing a commit to go through. It’s saved me from committing junk files more times than I can count.

Hope this saves you a few gray hairs next time you make a git mistake. Happy coding!

救命！我不小心 commit 了不該 commit 的東西，Git 怎麼反悔？

來源：Stack Overflow ↗ · 27251 票

那天下午我正趕著要在下班前把功能發上去，心急如焚地一陣亂敲，結果一個手滑，把沒寫完的測試代碼跟一堆 debug 用的 log 全部 commit 進去了。當下我看到終端機顯示「commit successful」時，心臟差點沒停掉，尤其想到這些垃圾代碼要是被推到遠端，我明天絕對會被同事當成笑話看。那種「完了，我要毀掉整個團隊進度」的恐懼感，真的是每個工程師的惡夢。

會發生這種事，其實就是 Git 的「暫存區」機制太好用了，導致我們常常在還沒檢查好的情況下就習慣性 git commit。Git 其實很聰明，它把每一次操作都當作是歷史的一部分，所以當你 commit 下去的那一刻，它就認定這是一個正式的節點。但問題在於，我們通常只是想先在本地存個檔，或者不小心選錯了檔案，卻沒意識到這個動作已經寫入了版本控制的歷史記錄裡。

好險，只要你還沒把這些 commit push 到遠端伺服器，一切都還有救。我當時立刻冷靜下來，用了 git reset 這個最強大的工具。如果你只是想撤銷最後一次 commit，但想保留剛剛修改的檔案內容（繼續修改），你可以直接執行：


git reset --soft HEAD~1

這樣一來，你的 commit 紀錄會不見，但你剛剛寫好的代碼會全部留在「暫存區」裡，你可以直接把不需要的檔案從暫存區移出來，或是修改後再重新 commit。但如果你是想把這次 commit 的東西徹底刪掉，連檔案都不留，那就用這個狠一點的：


git reset --hard HEAD~1

這招下去，剛剛那些寫錯的檔案會直接「原地消失」，所以用之前一定要確認你真的不想要這些東西了，不然真的會哭出來。

為了避免這種心跳加速的時刻再度發生，我現在養成了習慣，在 commit 之前一定會先打 git status 看一下到底有哪些檔案被選中。還有，如果你跟我一樣懶，很常把所有變更一次打包，強烈建議你把 git add . 這個指令戒掉，改用 git add -p。這個指令會讓你一段一段地確認到底加了什麼進去，雖然多花幾秒鐘，但能幫你省下後面好幾個小時的除錯時間，真心不騙。

好了，現在趕快去檢查你的 git status，希望你這次能安全下莊！
