How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27243 votes

I still remember the first time I accidentally committed a massive, half-baked feature branch containing secrets I definitely didn't want in the repo. I spent three hours sweating, convinced I’d permanently nuked my project history, only to realize that Git is actually a lot more forgiving than it feels in the moment of panic. It’s a classic rite of passage for every developer, and if you're reading this, you’ve probably just realized you’ve made a mistake you need to walk back immediately.

The reason we get into this mess is that Git is designed to be a ledger of every single thing you do. When you run git commit, you’re essentially carving your current workspace into the project's permanent record. If you haven't pushed those changes to a remote server, that record only exists on your machine, but it still feels like you've locked yourself into a corner. You aren't actually "deleting" the work; you’re just telling Git to move the pointer of your current branch back to a previous state, which is why it feels so intimidating to beginners.

When I need to undo a commit, I reach for git reset. If you just want to get rid of the commit but keep your hard work in your staging area so you can fix your mistake and commit again, you’ll want to use a soft reset. This is my go-to when I forgot a file or botched a commit message.


git reset --soft HEAD~1

If you want to go a step further and get rid of the commit *and* all the changes you made in that commit, you’ll use a hard reset. Be careful with this one—it’s the "nuclear option"—because it will discard every change you made since that last commit. I only use this when I know for a fact that the code I wrote was completely wrong and I want to start from a clean slate.


git reset --hard HEAD~1

Once you've run these, your local branch will be pointing back to the state it was in before you made that mistake. If you’ve already pushed your code to a shared repository, stop right there. Resetting a commit that is already public will cause a headache for your entire team, so make sure you only use these commands on work that strictly lives on your local machine.

The best way to prevent this from happening in the future is to get into the habit of running git status before you finalize anything. I know it sounds basic, but taking those two seconds to scan the list of staged files has saved me from committing build artifacts or personal config files more times than I can count. It’s a tiny friction point that pays for itself ten times over by keeping your git log clean and your stress levels low.

Good luck cleaning up your repo, and don't worry—we’ve all been there! Happy coding.

手殘黨救星：還沒推上遠端前，如何優雅地撤銷 Git Commit？

來源：Stack Overflow ↗ · 27243 票

記得有一次，我正趕著要在半夜前把 feature 修好，結果腦袋當機，順手就把一堆還在測試階段、甚至帶有除錯用 console.log 的亂七八糟程式碼給 commit 下去。按下 Enter 的那一瞬間，我看著終端機顯示的「commit hash」，心跳直接漏了一拍，那種「完了，我把垃圾推上歷史紀錄」的絕望感，真的會讓人想當場把筆電闔上直接睡覺。

其實會發生這種慘劇，通常是因為我們太習慣用 git commit -a 這種無腦指令，結果連不該動到的檔案也一起打包進去。當 commit 還留在本地端、還沒執行過 git push 時，你其實是在跟自己的 Git 歷史紀錄對話，Git 本身是非常寬容的，只要還沒公開，一切都還有救。

當我發現自己 commit 錯東西時，我通常會用 git reset 來處理。如果你只是單純想撤銷最後一次 commit，但想保留修改過的檔案內容（為了繼續改），我會下這個指令：


git reset --soft HEAD~1

這行指令的神奇之處在於，它會把你的 commit 紀錄刪除，但你剛剛改過的那些檔案，會乖乖地回到「暫存區（Staging Area）」。這樣你就可以針對那些檔案進行微調，該刪的刪、該改的改，之後再重新 commit 一次。

如果你是連檔案內容都覺得「錯得離譜，全都不想要了」，想徹底把一切恢復到 commit 之前的狀態，那就要狠一點，用這個：


git reset --hard HEAD~1

這招下去，你該次 commit 的所有修改會直接蒸發，所以用之前一定要確認好，別把辛苦寫了兩天的程式碼給砍了，我以前就因為手滑打成 --hard 結果痛哭流涕過，那種心血全無的感覺真的會讓人懷疑人生。

為了避免這種心驚膽跳的時刻，我現在強迫自己養成一個習慣：在 commit 之前，絕對會先輸入 git status 看一眼清單。如果檔案太多，我會改用 git add -p 這種互動模式，一個一個 hunk 確認要加入什麼，雖然麻煩一點，但至少不會再發生把測試用的 secret key 或一堆亂七八糟的偵錯 log 塞進版本庫的蠢事。

以後如果不小心又手殘，記得冷靜下來先確認有沒有 push，只要還在本地，一切都好談。
