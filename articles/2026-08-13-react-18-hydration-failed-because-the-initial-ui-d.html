Debugging React 18 Hydration Mismatch Errors in Next.js

Source: Stack Overflow ↗ · 341 votes

I remember the first time I saw the dreaded "Hydration failed" error in a React 18 project. I was three hours deep into a late-night coding session, convinced my logic was flawless, only to be slapped in the face by a console full of red text telling me the server and client weren't talking to each other. I stared at my screen for an embarrassing amount of time, questioning my entire understanding of how SSR works before realizing I had simply introduced a bit of randomness that the server couldn't possibly predict.

The reason this happens is actually quite logical once you stop pulling your hair out. When you use Next.js, the server renders your component into HTML and sends it to the browser. Then, React "hydrates" that static HTML by attaching event listeners and turning it into a dynamic application. If the HTML the browser generates on the first pass doesn't match the HTML the server sent, React panics. It assumes something went wrong during the transition and throws the mismatch error. Usually, this is caused by using browser-only APIs like window or localStorage, or even something as simple as new Date().toLocaleTimeString(), which results in a different time on the server than it does on the user's machine milliseconds later.

When I finally tracked down the root cause in my own app, I realized I needed a way to defer the rendering of those specific components until the client had fully loaded. The cleanest way to handle this is to use a useEffect hook to toggle a state variable, which ensures that the component only renders its dynamic content once it's safely on the client side.


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a skeleton loader
  }

  return <div>{window.location.href}</div>;
};

By waiting for the component to mount, I effectively tell React, "Hey, don't worry about the server-rendered version of this specific block, just wait until the client is ready." This keeps the HTML structure consistent during the initial load and clears up that annoying console error instantly.

To prevent this from becoming a recurring headache, I’ve made it a rule to always isolate non-deterministic code. Whenever I find myself reaching for window, document, or any external data that might change between the server and client, I wrap it in a custom useIsMounted hook or a Dynamic import with ssr: false. Keeping your component logic predictable is the best way to keep the hydration process smooth and error-free.

Hope this saves you from losing as much sleep as I did! Happy coding, and may your console remain blissfully empty of red errors.

React 18 搞死人的 Hydration Mismatch：別讓 SSR 成為你的惡夢

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 的那個週末嗎？我原本以為只是簡單的套件升級，結果打開瀏覽器控制台一看，整片紅通通的 "Hydration failed" 錯誤訊息直接往我臉上砸。當時我正在趕一個客戶的專案上線，看著頁面上的 UI 一下子閃爍、一下子跑版，那種「我明明寫得好好的，為什麼伺服器跟瀏覽器硬是看不對眼」的無力感，真的差點讓我直接把鍵盤砸了，心裡只想著：這到底是在演哪齣？

其實說穿了，這個錯誤的本質就是「資訊不對稱」。簡單來說，Next.js 在伺服器端（SSR）渲染出了一份 HTML 給瀏覽器，但當瀏覽器載入 JavaScript 並開始執行 React 的 Hydration 過程時，React 發現它拿到的 DOM 結構跟當初伺服器吐出來的不一樣。最常見的情況就是你的程式碼裡用了 typeof window !== 'undefined' 這種判斷，或者是用了像 Date.now()、隨機數產生器，甚至是瀏覽器特定的 API。因為伺服器跑一次、瀏覽器又跑一次，兩邊算出來的結果兜不攏，React 就會覺得這世界亂套了，直接報錯給你看。

我後來發現，最常見的兇手其實是我們在渲染時不小心用了跟環境有關的資料。比如我那次是因為用了 localStorage 來判斷使用者的登入狀態，伺服器根本沒這東西，所以兩邊的初始 UI 就這麼硬生生地錯開了。解決這個問題最有效的招數，就是讓 React 先「緩一緩」，等到元件確定已經掛載（Mounted）到瀏覽器之後，再進行這些會產生差異的操作。我通常會封裝一個簡單的 useMounted Hook 來處理這種狀況：


import { useState, useEffect } from 'react';

export function useMounted() {
  const [mounted, setMounted] = useState(false);
  useEffect(() => {
    setMounted(true);
  }, []);
  return mounted;
}

// 在你的元件中使用它：
function MyComponent() {
  const isMounted = useMounted();

  if (!isMounted) return null; // 或者放一個骨架屏 (Skeleton)

  return <div>這裡放會依賴 window 的內容</div>;
}

為了避免以後再踩到這種坑，我現在養成了一個習慣：只要是用到了瀏覽器專屬物件（比如 window、localStorage、navigator），我一律都會把它們丟到 useEffect 裡去處理，或者乾脆改用動態導入（Dynamic Imports）並設定 ssr: false。這樣一來，Next.js 就不會試圖在伺服器端強行渲染這些不穩定的元件，自然也就避開了 Hydration 失敗的窘境。

除錯這條路就是這樣，永遠都有修不完的 Bug，但搞懂原理之後，下次再看到滿版紅字，至少心跳不會再漏半拍了。希望這篇筆記能幫你省下幾個熬夜修 Bug 的夜晚，我們下次見！
