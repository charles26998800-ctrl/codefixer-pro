How to Undo Your Most Recent Local Git Commits Without Losing Your Work

Source: Stack Overflow ↗ · 27228 votes

I still remember the first time I accidentally committed a massive debug log and a half-finished feature to the main branch right before a demo. I spent three hours sweating, convinced I’d somehow permanently corrupted my local history, only to realize that Git is actually much more forgiving than I gave it credit for. We’ve all had that heart-stopping moment when you hit enter on a git commit and immediately realize you weren't ready.

The reason this happens is usually just a classic case of "Git-panic." When you commit, you’re creating a snapshot in your local repository’s history. Because Git is designed to be a distributed version control system, it treats your local commits as a distinct layer on top of your current branch. If you haven't pushed those commits to a remote server yet, they exist purely in your local .git directory. The root cause of the confusion is often thinking that a commit is "final" the moment it’s recorded, but in reality, your local history is just a sequence of pointers that you have full authority to move around.

When I need to fix this, I reach for git reset. It’s the Swiss Army knife for undoing local work. If I just want to undo the commit but keep my changes staged and ready to be fixed, I run:


git reset --soft HEAD~1

This command moves your branch pointer back one step, but it leaves your files exactly as they were, sitting in the staging area. If I want to go a step further and unstage those files too—effectively putting them back into my working directory so I can edit them or decide not to include them at all—I use the mixed reset:


git reset HEAD~1

Now, if I made a complete mess of things and I want to nuke the commit and all the changes associated with it because I realized the entire approach was wrong, I use the hard reset. Be careful with this one, because it’s destructive:


git reset --hard HEAD~1

This command discards the commit and wipes out any changes to the files you were working on, reverting your project to the exact state of the previous commit.

To prevent this from happening again, I’ve started using the --dry-run flag with my commands, but more importantly, I’ve adopted the habit of using git status religiously before every single commit. Taking those two seconds to review exactly what is being staged saves me from those "oh no" moments and keeps my commit history clean and intentional.

Hopefully, this helps you clean up your history without the stress. Happy coding!

手滑把不該送出的檔案 Commit 了？別怕，Git 還沒推上去都有救！

來源：Stack Overflow ↗ · 27228 票

記得剛進這行沒多久，有次為了趕下班，我一股腦地把所有修改過的檔案通通 git add . 然後 git commit -m "update"，結果送出後才發現，我不小心把剛才測試用的資料庫設定檔還有滿滿的 Debug log 也一起打包進去了。當下看著螢幕上那個 Commit ID，心臟真的差點停掉，那種「完了，這要是推上去肯定被同事罵死」的恐懼感，真的是每個工程師的共同夢魘。

其實會發生這種慘劇，通常就是因為我們對 Git 的「暫存區」太有信心，或是手速太快忘了檢查 git status。簡單來說，當你執行 git commit 時，Git 只是把這些改變記錄在你的本地倉庫歷史裡。只要你還沒執行 git push 到遠端伺服器，這些歷史紀錄其實就像是寫在沙灘上的字，要抹掉它再容易不過了。

我後來學會的救命絕招就是 git reset。如果你只是想撤銷最後一次 Commit，但又想保留那些檔案的修改（方便你調整後重新送出），我會用這個指令：


git reset --soft HEAD~1

這行指令的意思是把 HEAD 指標退回到上一個版本，但會把你剛剛 Commit 的那些檔案留在暫存區（Staging Area），這樣我就能直接把不需要的檔案拿掉，重新調整好再 Commit 一次，簡直是救命神器。如果你是連那些修改都不想要了，想徹底「回到過去」，那就用 --hard：


git reset --hard HEAD~1

不過用 --hard 要特別小心，因為它會直接把你工作目錄裡的所有修改全部抹除，如果不小心裡面有寫到一半的正經程式碼，真的會欲哭無淚。

為了不再重演這種手忙腳亂的戲碼，現在我強迫自己養成一個習慣：在打出 git commit 之前，一定會先執行 git status 看一眼到底有哪些檔案在清單上。如果真的很怕手滑，也可以考慮設定 Git 的 pre-commit hook，或者乾脆改用 GUI 工具（像 GitKraken 或 Sourcetree）來做 Commit 前的最後檢查，視覺化介面真的能幫你擋掉很多這種低級錯誤。

以後遇到這種情況真的不用慌，只要還沒推上去，一切都還有救，趕快去把你的紀錄「洗白」吧！
