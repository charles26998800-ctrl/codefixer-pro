Solving the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours deep into a late-night debugging session, convinced I’d written some genius server-side logic, only to have my console scream at me that my UI didn't match the server output. I spent way too long checking my API calls and state management, feeling like I was losing my mind, until I realized my browser extensions and local timestamps were playing a cruel joke on my server-rendered HTML.

The root cause of this frustration is actually quite simple, even if it feels like a nightmare at the time. When you use Next.js, the server renders your initial HTML and sends it down to the browser. Then, React "hydrates" that HTML by attaching event listeners and making it interactive. If the HTML the server generated is even slightly different from what the browser generates on its first pass—perhaps because you’re using Date.now(), a random number generator, or a browser-specific check like typeof window—React panics. It sees that the DOM nodes don't align and throws in the towel, because it doesn't know which version of the truth to trust.

I finally fixed this by ensuring that the initial render is deterministic. If you have content that must be different on the client, you need to delay that rendering until after the component has mounted. I usually use a simple useState hook combined with useEffect to manage this transition. By waiting for the mount to finish, you ensure the server renders a neutral state, and the client only injects the dynamic, browser-only data once it's safe to do so.


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This is the browser-only content: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

To prevent this from happening in the future, my golden rule is to avoid any browser-dependent logic inside your render path. If you absolutely need to use localStorage, window, or a dynamic timestamp, always wrap that logic in a useEffect or use a "client-only" flag to force the component to wait. Keeping your initial render phase pure and identical across both server and client is the secret to avoiding those pesky hydration warnings for good.

Hope this saves you from the same headache I had! Happy coding, and may your builds stay green.

React 18 的 Hydration 惡夢：為什麼伺服器跟瀏覽器總是在吵架？

來源：Stack Overflow ↗ · 341 票

記得那天是專案上線前夕，我正準備把最後一個 SSR 功能跑起來，結果打開瀏覽器控制台一看，整排紅通通的「Hydration failed」直接讓我心跳漏了半拍。明明在開發環境看起來都好好的，結果一上線就炸開，那種「明明程式碼沒動，為什麼你會報錯」的無力感，真的讓人很想把鍵盤直接丟出窗外，當時我盯著螢幕上的錯誤訊息發呆了快半小時，心裡只有一個念頭：這到底是誰的問題？

其實這個問題說穿了，就是伺服器（Server）跟瀏覽器（Client）這兩個人在「雞同鴨講」。當我們用 Next.js 做 SSR 時，伺服器會先幫你產生一份 HTML，然後送到瀏覽器端，接著 React 會開始進行 Hydration（注水），也就是把事件綁定上去。問題來了，如果伺服器算出來的 HTML 結構，跟瀏覽器第一次渲染出來的結構有哪怕一丁點的不一樣，React 就會直接崩潰。最常見的兇手通常是使用了 Date.now()、隨機數 Math.random()，或是根據瀏覽器視窗大小來變動的 UI 邏輯。伺服器渲染時這些值是 A，到了瀏覽器執行時變成了 B，React 一比對發現對不上，直接判定這場渲染失敗。

我當時踩到的坑其實很愚蠢，是因為我在 UI 裡直接用了一個會隨機變動的 ID 作為 Key，解決這個問題其實只要確保這兩個環境拿到同樣的資訊就好。最簡單的解法是利用 useEffect，因為這個 Hook 只會在瀏覽器端執行，伺服器根本碰不到它，所以我們可以把那些會導致不一致的邏輯往後移。你可以試著定義一個 State，然後在 useEffect 裡才去更新它，像這樣：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>現在是在瀏覽器渲染的內容</span> : <span>伺服器預設內容</span>}
    </div>
  );
}

透過這種方式，你就強制讓伺服器和瀏覽器的初始渲染內容保持一致，等到瀏覽器跑起來後，再透過 useEffect 把正確的動態內容「補」上去。

為了避免以後再被這個錯誤搞到懷疑人生，我現在養成一個習慣：只要涉及到 window 物件、本地儲存（localStorage）或是任何依賴當下時間、隨機數的邏輯，一律都會用 useEffect 包起來，或者直接用 typeof window !== 'undefined' 做個簡單判斷。只要心裡隨時掛著「伺服器看不到瀏覽器的狀態」這個原則，大部分的 Hydration 錯誤其實都能避開。

希望大家都能順利避開這個坑，別讓這小小的報錯毀了你的週末。
