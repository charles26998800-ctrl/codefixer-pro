How to Fix the "digital envelope routines::unsupported" Error in React

Source: Stack Overflow ↗ · 2573 votes

I remember the exact moment this error ruined my morning. I had just pulled a legacy project from a repository, sat down with a fresh coffee, and typed npm start expecting the dev server to boot up, only to be greeted by a wall of red text screaming about digital envelope routines. I spent three hours refactoring my environment variables and questioning my life choices before realizing it wasn't my code, but a fundamental mismatch between my Node version and the project's outdated build tools.

The root cause of this headache is the transition from OpenSSL 1.1.1 to OpenSSL 3.0, which happened when Node.js moved to version 17 and beyond. Older versions of Webpack, which many React projects rely on for bundling, use legacy algorithms that OpenSSL 3.0 considers insecure and has effectively blocked by default. Because the build process tries to use these deprecated hashing methods, Node.js throws the "unsupported" error to protect you, even though it feels more like it’s just throwing a wrench into your workflow.

The quickest way I’ve found to fix this is to tell Node to revert to the legacy OpenSSL provider, which essentially lets you keep using your older dependencies without having to rewrite your entire build pipeline. If you’re on macOS or Linux, you can run this command in your terminal before starting your development server:


export NODE_OPTIONS=--openssl-legacy-provider
npm start

If you’re working on Windows, the syntax is a bit different, so you’ll want to set it in your command prompt like this:


set NODE_OPTIONS=--openssl-legacy-provider
npm start

If you want a more permanent fix so you don't have to type that every single time, you can edit your package.json file. Just look for the scripts section and inject the variable directly into your start command:


"scripts": {
  "start": "react-scripts --openssl-legacy-provider start",
  "build": "react-scripts --openssl-legacy-provider build"
}

To prevent this from haunting you in the future, my best advice is to keep a close eye on your engines field in package.json. By explicitly defining the Node.js version your project requires, you can use tools like nvm (Node Version Manager) to ensure you aren't accidentally running a project on a newer Node version than its dependencies can handle. It’s a simple defensive move that saves you from dealing with these breaking changes until you’re actually ready to upgrade your dependencies.

Hope this saves you the three hours of frustration I had to endure. Happy coding!

遇到 Node.js 的「digital envelope routines」報錯？別慌，這其實是版本升級的代價

來源：Stack Overflow ↗ · 2573 票

前陣子我剛換了一台新筆電，想說把手邊的一個老專案拿出來跑跑看，結果才剛下完 npm start，終端機就噴出一大串紅通通的錯誤訊息，那個 error:0308010C:digital envelope routines::unsupported 簡直讓我當場傻眼。我當時心想：「不是吧？我連一行程式碼都還沒改，怎麼就直接罷工了？」那種明明趕著要 demo，結果環境怎麼弄都跑不動的無力感，真的是會讓人想直接把電腦蓋起來去喝杯咖啡冷靜一下。

其實這個問題的原因說穿了就是「世代隔閡」。簡單來說，這是因為你現在安裝的 Node.js 版本太新（通常是 v17 以上），而你專案裡用的 Webpack 版本太舊。新版的 Node.js 為了安全性，引入了 OpenSSL 3.0，但舊版的 Webpack 在加密演算法的處理上跟這個新標準不合拍，所以它們就吵架了。這就是為什麼你的專案明明之前跑得好好的，一旦升級 Node.js 就會崩潰。

解決這個問題其實比想像中簡單，我們不需要大費周章去重寫整個 Webpack 設定。最快的方法就是告訴 Node.js：「嘿，請暫時用舊版的加密演算法模式來跑這個專案」。如果你是用 Mac 或 Linux，只要在啟動指令前面加上一段環境變數設定就行了。像這樣：


# Mac 或 Linux
export NODE_OPTIONS=--openssl-legacy-provider
npm start

如果你是在 Windows 的 PowerShell 環境下，設定方式稍微有點不同：


# Windows PowerShell
$env:NODE_OPTIONS = "--openssl-legacy-provider"
npm start

如果你不想每次都要手動打這串指令，最懶人也最推薦的做法，就是直接去 package.json 的 scripts 區塊，把 start 的指令改成這樣：


"scripts": {
  "start": "react-scripts --openssl-legacy-provider start",
  "build": "react-scripts --openssl-legacy-provider build"
}

這樣改完之後，以後不管你是誰來執行專案，它都會自動帶上這個參數，再也不會半路噴錯了。

至於要怎麼預防這種狀況再次發生，我建議大家養成一個習慣，就是盡量在專案裡放一個 .nvmrc 檔案，裡面寫好這個專案指定的 Node.js 版本號。這樣當你或是你的隊友切換環境時，只要用 nvm use 就能確保大家都在同一個基準線上，省下很多這種因為版本差異而產生的奇葩 bug。

好了，現在趕快去試試看吧，希望你的終端機也能順利跑出綠色的成功訊息！
