Debugging the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" warning pop up in my console while migrating a legacy project to React 18. I spent three hours refactoring components, convinced I’d somehow broken my entire state management logic, only to realize I was just rendering a random number generator inside a component that the server and client were seeing differently. It’s one of those silent, infuriating bugs that makes you want to throw your keyboard out the window because the app looks perfectly fine right up until the moment it crashes.

The root cause of this mess is actually quite logical once you peek under the hood of how Next.js works. When you're using Server-Side Rendering (SSR), the server generates the initial HTML and ships it to the browser. React then takes over on the client side to "hydrate" that static HTML, turning it into a fully interactive application. The problem kicks in when the HTML the server sent doesn't match the HTML the client generates during that first render. If you’re using something like Date.now(), a random number, or even checking typeof window !== 'undefined' inside your render logic, the server and client will inevitably disagree on what the initial UI should look like. React sees this mismatch, panics, and throws the hydration error rather than trying to guess which version to trust.

The fix usually involves ensuring that your component doesn't attempt to render dynamic content until it's officially mounted on the client. I’ve found that the cleanest way to handle this is by using a useEffect hook to trigger a state update only after the component has reached the browser. Here is how I typically structure this to stop the errors in their tracks:


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This is rendered only on the client: {Math.random()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
};

By wrapping the sensitive logic in that isClient check, you ensure that the server renders a safe, static placeholder, and the client updates it to the "real" content only after hydration is complete. It’s a simple shift in mindset: treat the server render as a static preview and defer the dynamic heavy lifting to the client.

To prevent this from coming back to haunt you, get into the habit of auditing your components for any external dependencies that change between the server and the browser. If you’re using browser-only APIs like localStorage or window, always wrap them in a useEffect or use a library that handles the hydration delay for you. Keeping your render functions pure and predictable is the best way to stay sane in the world of Next.js.

I hope this helps you save those hours I lost staring at my monitor. Happy coding, and may your builds stay green!

React 18 Hydration 錯誤：為什麼我的頁面總是「兩面不是人」？

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地想體驗 SSR 的效能提升，結果專案一跑起來，瀏覽器 Console 直接噴出一整排刺眼的紅色錯誤訊息。看著那個「Hydration failed」的提示，我真的差點崩潰，明明程式碼在本地跑得好好的，怎麼一進到生產環境就變成了這副德性？最痛苦的是，我明明檢查了老半天，HTML 結構看起來完全一致，但那個錯誤就像是在笑我一樣揮之不去，讓我那天原本排好的下班行程直接泡湯。

其實這背後的道理說穿了並不複雜，簡單來說就是「伺服器端」跟「瀏覽器端」對於第一眼看到的內容有了分歧。SSR 的機制是伺服器先生成好靜態 HTML 傳給瀏覽器，然後瀏覽器再接手讓它「活過來」（Hydration）。如果伺服器渲染出來的內容，跟瀏覽器第一次執行 JavaScript 產生的內容有一丁點誤差，React 就會覺得：「哎呀，這不是我當初預期的樣子！」然後乾脆選擇放棄，直接重刷整個頁面。最常見的兇手通常是會隨機變動的內容，例如 Date.now()、隨機亂數，或是根據瀏覽器環境（如 window 物件）判斷後才渲染的 UI。

針對這個問題，我後來發現最乾淨的解法，就是確保元件在「伺服器端」和「瀏覽器端」的第一次渲染完全一致。如果你的元件真的需要依賴瀏覽器環境（比如讀取 localStorage），千萬不要直接在渲染流程裡寫判斷式，而是要利用 useEffect。因為 useEffect 只會在瀏覽器端執行，這能確保伺服器先送出一個「乾淨」的預設值，等瀏覽器接手後再進行更新。你可以參考這個模式：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>這是瀏覽器才有的內容</span> : <span>載入中...</span>}
    </div>
  );
}

為了避免未來再被這個問題搞到想摔鍵盤，我現在養成了一個習慣，就是在處理任何依賴環境變數的邏輯時，預設先關掉 SSR 渲染，或者乾脆寫一個簡單的 useMounted hook。只要確保在伺服器端渲染時，永遠給它一個固定的初始狀態，就不會再出現這種前後不一致的尷尬場面了。

希望這些經驗能幫你少走點彎路，別讓 Hydration 錯誤毀了你的一天，趕快修好去喝杯咖啡吧！
