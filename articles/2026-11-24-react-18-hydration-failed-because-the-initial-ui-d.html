Solving the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours deep into a late-night debugging session, convinced my API routes were broken or my database connection was timing out, only to realize I was just rendering a simple Date() object in my component. It’s one of those classic React moments where you stare at the screen, questioning your sanity, because the code looks perfectly fine in your IDE but the browser console is screaming at you like you’ve committed a cardinal sin.

The root cause of this frustration is actually quite logical once you peek under the hood. When you use Server-Side Rendering (SSR) with Next.js, the server generates the initial HTML based on the state of your application at that exact moment. When the browser receives that HTML, React attempts to "hydrate" it—basically attaching event listeners and turning it into a fully interactive app. If the browser tries to render the component and the output differs even slightly from what the server sent over, React throws its hands up in the air. This happens most often when you use dynamic data like current timestamps, random numbers, or browser-only APIs like localStorage that simply don't exist on the server.

To fix this, I’ve learned that the secret is to delay the rendering of the mismatched content until the component has officially mounted in the browser. I usually reach for a simple useEffect hook to manage this state transition. By initializing a state variable to false and flipping it to true inside useEffect, I can ensure that the "client-only" content only renders once the browser is in control.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or return a loading skeleton
  }

  return (
    <div>
      {/* This will only render on the client, avoiding hydration mismatches */}
      <p>Current time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

If you’re working with libraries that absolutely refuse to play nice with SSR, you can also use Next.js's dynamic imports with ssr: false to force a component to render only on the client side. It’s a cleaner way to keep your main render path free of potential hydration landmines.

To prevent this from becoming a recurring nightmare, I’ve made it a rule to always double-check any code that relies on global browser objects or unpredictable data. Before you push that code, ask yourself: "Would this look different if I ran it on a Linux server versus my Chrome browser?" If the answer is yes, wrap it in a mount check or a dynamic import immediately, and you'll save yourself a world of headache.

Hope this helps you get your app back on track without losing your mind. Happy coding!

救命！React 18 的 Hydration 錯誤快把我搞瘋了

來源：Stack Overflow ↗ · 341 票

那天我正準備把一個舊專案升級到 React 18，想說順便搞定 SSR 優化，結果一跑起來，瀏覽器的 Console 直接噴出一整排刺眼的紅色錯誤：「Hydration failed because the initial UI does not match what was rendered on the server」。我當時盯著螢幕看了半小時，心想：「這不是一樣的程式碼嗎？為什麼伺服器渲染出來的 HTML 跟瀏覽器拿到的不一樣？」那種明明寫對了卻被系統打臉的無力感，真的是工程師職涯中的痛苦時刻之一，恨不得直接把鍵盤砸了。

其實這問題的根本原因說穿了就是「時差」。你想想，SSR 是在伺服器端先跑一次代碼生成 HTML，然後送到瀏覽器，這時 React 開始「補水」（Hydration）接管頁面。如果你的程式碼裡用了 new Date()、隨機數 Math.random()，或是判斷了瀏覽器特有的 window 或 localStorage，伺服器跑出來的內容跟瀏覽器第一次渲染的內容就會出現「誤差」。React 這種處女座性格的框架，一旦發現伺服器說「這裡應該是 A」，但瀏覽器卻說「我現在看是 B」，它就會直接報錯並放棄優化，這就是為什麼你的畫面會閃爍或是功能失效。

我當初解決這個問題的方法，其實就是強迫 React 等到瀏覽器環境準備好再渲染。最簡單的手段就是用一個 useEffect 來控制渲染時機，因為 useEffect 只會在客戶端執行，這樣伺服器那邊就只會拿到一個預設的空狀態，不會因為環境差異而產生衝突。我的做法通常是這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <div>這是只有在客戶端才顯示的內容</div> : <div>Loading...</div>}
    </div>
  );
}

這樣一來，伺服器端永遠只會輸出那個 Loading 狀態，而瀏覽器在執行後會自動切換成正確的內容，完美繞過了伺服器與客戶端渲染不一致的坑。

為了預防下次又踩到這種雷，我現在養成了檢查程式碼的好習慣，特別是那些會用到 window 物件或時間戳記的邏輯，一律先問自己：「這段邏輯在伺服器上跑會不會有問題？」如果會，就乖乖用上面的狀態切換技巧。如果你真的懶得寫這些判斷，有些套件也支援 dynamic import 並設定 ssr: false，這也是個很實用的逃生門。

搞定這個之後，終於可以安心去喝杯咖啡了，祝大家的 Console 永遠乾乾淨淨！
