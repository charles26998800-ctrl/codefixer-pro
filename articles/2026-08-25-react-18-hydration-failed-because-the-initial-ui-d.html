Debugging the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a Next.js project. I spent three hours late on a Tuesday night convinced that my server configuration was corrupted, only to realize I was just rendering a random number generator inside a component that lived on both the server and the client. It’s one of those infuriating bugs where the code looks perfectly valid, yet the browser console screams at you because the server’s "truth" and the client’s "truth" are fighting like siblings over a toy.

The root cause of this mess is actually quite simple: React wants to be efficient. When you use Server-Side Rendering (SSR), the server generates the initial HTML and sends it to the browser. Once the browser receives that HTML, React "hydrates" it by attaching event listeners and turning it into a dynamic app. The problem happens when the server produces one version of the UI and the client immediately produces another version during that first render. If you’re checking for a window object, using new Date(), or rendering a random ID, the server generates one value, the client generates a different one, and React throws its hands up in the air because the DOM tree doesn't match what it expected.

To fix this, I’ve learned that you have to be explicit about when code should run. If you have a component that relies on browser-specific APIs or dynamic data that isn't available on the server, you need to wait until the component has mounted on the client side before rendering that specific part. I typically use a useState hook combined with a useEffect to track the mounting status. Here is the pattern I use to keep things stable:


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <span>The dynamic content: {window.location.href}</span>
      ) : (
        <span>Loading...</span>
      )}
    </div>
  );
}

By ensuring that the server renders a static placeholder or nothing at all, you give the client a clean slate to inject the dynamic content once it's actually in the browser environment. This completely eliminates that mismatch because the server isn't trying to guess what the client-side window object looks like.

The best way to prevent this in the future is to adopt a "server-first" mindset. Before you write a component, ask yourself if it absolutely needs client-side data to exist. If you can avoid using useEffect for the initial render or keep your browser-only logic wrapped in a client-side check, you’ll save yourself a massive amount of headache. Keep your server and client logic strictly separated, and you won’t have to deal with these hydration nightmares anymore.

Hope this helps you clear those console errors and get back to building cool stuff. Let me know if you run into any other weird React quirks!

Next.js 遇到 Hydration Failed？別慌，這其實是 React 在跟你玩「找不同」

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地把專案跑起來，結果打開瀏覽器控制台一看，整排紅通通的 Hydration failed 警告直接炸開。那時候我真的是差點崩潰，明明程式碼邏輯都沒錯，伺服器渲染（SSR）出來的 HTML 跟瀏覽器第一次渲染的結果就是對不上，看著那串長長的報錯訊息，我當時心裡的 OS 是：「我明明寫了一樣的東西，你是哪裡看不懂啦！」

其實這背後的道理說穿了很單純。React 的 Hydration 機制其實就是在玩「找不同」。伺服器會先產生一份靜態 HTML 給瀏覽器，等瀏覽器下載完 JS 後，React 會接手並把它變成互動式的 UI。問題就出在，如果伺服器算出來的結果，跟瀏覽器第一次跑出來的結果有哪怕一丁點誤差——比如一個隨機生成的 ID、時間戳記，甚至是瀏覽器插件偷偷塞進去的 HTML 標籤——React 就會因為「這跟我預期的長得不一樣」而直接報錯，甚至乾脆放棄渲染，讓你的網頁瞬間變得很難看。

最常見的痛苦時刻，就是當你用了 new Date().toLocaleDateString() 或者隨機數產生器時，伺服器跑出來的時間跟用戶瀏覽器本地時間對不上，導致兩邊內容不一致。要解決這個，最快的方法就是讓 React 先「裝死」一下，等到元件真正掛載到瀏覽器之後再進行渲染。我通常會封裝一個簡單的 useHasMounted Hook，確保元件只在客戶端渲染：


import { useState, useEffect } from 'react';

export function useHasMounted() {
  const [hasMounted, setHasMounted] = useState(false);
  useEffect(() => {
    setHasMounted(true);
  }, []);
  return hasMounted;
}

// 在元件中使用：
function MyComponent() {
  const hasMounted = useHasMounted();
  if (!hasMounted) return null; // 或者放個 Loading
  
  return <div>現在時間是：{new Date().toLocaleString()}</div>;
}

為了避免之後再次踩到這個坑，我現在養成了一個習慣，就是儘量把所有依賴瀏覽器環境的邏輯（像是 localStorage、window 物件或是隨機數）全部都丟進 useEffect 裡處理。如果在渲染邏輯中真的需要用到這些東西，我會預設給一個靜態的 fallback 值，保證伺服器產出的 HTML 內容跟瀏覽器第一次渲染時的預設值是一模一樣的，這樣 React 就不會整天在那邊喊著要「找不同」了。

寫程式就是這樣，很多時候我們以為是框架在刁難，其實只是我們太想讓它「一秒變身」，給它一點緩衝空間，世界就和平了。希望這招能救你脫離紅字地獄，趕快去喝杯咖啡休息一下吧！
