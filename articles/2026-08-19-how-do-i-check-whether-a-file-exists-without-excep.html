The Cleanest Way to Check if a File Exists in Python

Source: Stack Overflow ↗ · 7349 votes

Early in my career, I remember writing a script to process thousands of log files, and I wrapped every single open() call in a massive try-except block. I thought I was being clever, but my logs became a graveyard of FileNotFoundError exceptions, and my code looked like it had been through a shredder. I spent three hours debugging a race condition where I thought the file was there, but the OS had other plans, and I ended up realizing I was just overcomplicating a simple existence check.

The reason this feels like a hurdle is that Python’s philosophy—"easier to ask for forgiveness than permission"—usually pushes us toward try-except. While that approach is technically robust for handling race conditions, it’s often overkill when you just need to know if a file is sitting in a directory before you trigger a process. Developers often get stuck trying to decide between the older os.path module and the more modern pathlib library, which can lead to messy, inconsistent codebases if you’re mixing styles across your project.

To fix this, I always reach for the pathlib module now. It’s been the standard since Python 3.4, and it makes your code look significantly more readable. You simply create a Path object and call the .exists() method. It’s clean, it’s intuitive, and it handles the heavy lifting for you.


from pathlib import Path

file_path = Path("my_data.txt")

if file_path.exists():
    print("The file is right where it belongs.")
else:
    print("File not found, moving on.")

If you’re stuck working on a legacy codebase that hasn't migrated to pathlib yet, you can use the older os.path.exists() function. It does the exact same thing, though it feels a bit more like "old-school" procedural Python.


import os

if os.path.exists("my_data.txt"):
    print("Still there!")

The best way to prevent this from becoming a nightmare in your production code is to stop checking for existence entirely unless it's absolutely necessary. If you’re just going to open the file anyway, just write the try-except block to handle the FileNotFoundError directly. Checking if a file exists and then opening it creates a "Time-of-check to time-of-use" (TOCTOU) bug, where the file could be deleted by another process in the millisecond between your check and your action. If you don't need to perform a conditional branch based on the file's presence, just try to open it and catch the error if it fails.

Hope this clears up the confusion and saves you from those messy nested blocks. Happy coding!

別再亂用 try-except 了！檢查檔案是否存在，你其實有更優雅的寫法

來源：Stack Overflow ↗ · 7349 票

記得剛入行那陣子，我寫了一個自動化處理報表的腳本，為了檢查設定檔在不在，我瘋狂地在程式碼裡塞滿 try-except FileNotFoundError。結果某次專案趕工，我把一個巨大的迴圈邏輯包在 try 裡面，最後發現只要檔案不存在就會噴錯，但因為我寫得太籠統，連帶把檔案讀取時的權限錯誤、甚至是磁碟空間不足的 bug 全都「吃」掉了。那次我盯著螢幕 debug 到凌晨三點，心裡真的只有崩潰兩個字，完全找不到問題點在哪，這種被自己的錯誤捕捉機制「背叛」的感覺，真的是工程師生涯最痛苦的時刻之一。

其實，會產生這種糾結，大多是因為我們太習慣「先執行看看，出錯再說」的思維。在 Python 裡，雖然 try-except 是處理例外狀況的標準做法，但如果只是單純想知道檔案在不在，還要特地寫個 try 區塊，程式碼讀起來真的會很髒，而且效能開銷其實也比較大。我們需要的應該是一個能直接回傳布林值的檢查方式，而不是每次都得去處理例外拋出。

後來我學乖了，直接改用 Python 內建的 pathlib 模組，這東西簡直是現代 Python 開發者的救星。它用起來非常直覺，程式碼寫起來就像是在讀英文一樣順。如果你還在用舊版的 os.path，真心建議你換過來。你可以這樣寫：


from pathlib import Path

file_path = Path('config.json')

if file_path.exists():
    print("檔案存在，可以繼續接下來的動作！")
else:
    print("檔案消失了，先去喝杯咖啡再說。")

如果是舊專案非得用 os 模組，那至少也要用 os.path.exists()，它同樣能幫你回傳 True 或 False，不用再去接那些煩人的錯誤。

為了預防這種問題再次發生，我現在養成了一個習慣，就是「檢查歸檢查，處理歸處理」。當我在做檔案操作時，我會先用 pathlib 確認路徑正確，然後在真的要讀取檔案的那一步，才真正加上 try-except 來處理「檔案被鎖住」或是「權限不足」這些真正不可控的例外。這樣把邏輯分開，你的程式碼不僅乾淨很多，萬一真的噴錯了，你也不會像我當初那樣，連問題出在哪都找不到。

寫程式就是這樣，慢慢把這些坑填平，心情自然就舒坦啦。
