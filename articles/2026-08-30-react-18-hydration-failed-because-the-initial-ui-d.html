Fixing the "Hydration Failed" Error in Next.js: A Practical Guide

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I encountered this cryptic hydration error while migrating a legacy dashboard to Next.js. I spent three hours staring at my screen, convinced that my code was perfect, only to realize I had a simple Date() call that was generating different timestamps on the server and the client. It’s one of those bugs that makes you feel like you’re losing your mind because the UI looks exactly how you want it, yet the browser console is screaming at you about a mismatch.

At its core, this error happens because React is a bit of a perfectionist. When you’re using Server-Side Rendering (SSR), the server generates the initial HTML and sends it to the browser. Once that HTML arrives, React "hydrates" it by attaching event listeners and turning it into a fully interactive app. The problem kicks in when the server-rendered HTML doesn't match the very first thing React tries to render on the client. If your component relies on data that changes between the server's render cycle and the client's mount—like local storage, browser-specific APIs, or randomized data—React realizes the two trees don't align and throws its hands up in frustration.

To fix this, the most common strategy I use is to delay the component's rendering until the client side is ready. You can achieve this by using a simple useEffect hook to toggle a state variable once the component has mounted. By checking if the component has mounted before rendering the content that triggers the mismatch, you ensure that the server-side version remains static and predictable.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or return a loading spinner
  }

  return (
    <div>
      {/* Your content that caused the hydration error goes here */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

If you’re using a library that specifically needs to render on the client, you can also look into Next.js’s dynamic imports with ssr: false set. This is a life-saver when you have third-party packages that try to access the window object immediately upon import, which obviously doesn't exist on the server.

The best way to prevent this in the long run is to keep your server-side logic strictly deterministic. I always try to ensure that any data displayed on the initial load comes from props passed down from getServerSideProps or getStaticProps, rather than relying on browser globals like localStorage or window.innerWidth inside the main render path. If you stick to that rule, you’ll save yourself a world of pain.

Hope this clears up the confusion and saves you a few hours of debugging. Happy coding, and don't let the hydration errors get you down!

React 18 惡夢：Hydration Failed 到底在搞什麼鬼？

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿懷興奮地想把 SSR（伺服器端渲染）搞定，結果一打開瀏覽器控制台，整排紅通通的錯誤訊息直接把我打入地獄。當時我為了趕一個該死的 UI 上線，盯著那行 "Hydration failed because the initial UI does not match what was rendered on the server" 發呆了整整兩小時，甚至一度懷疑是不是 React 的核心套件壞掉了，那種「我明明寫對了，為什麼瀏覽器死都不聽話」的無力感，真的是工程師職涯中最想原地退休的時刻之一。

其實後來冷靜下來去讀文件才發現，這問題的根本原因說起來有點尷尬。簡單來說，就是 React 的「雙重人格」衝突了：伺服器渲染出來的 HTML 結構，跟瀏覽器第一次跑 React 時產生的結構長得不一樣。你想想看，伺服器可能覺得現在是 UTC 時間，結果瀏覽器跑起來變成了台灣時間；或者你用了像 typeof window !== 'undefined' 這種判斷，導致伺服器渲染了一份內容，但瀏覽器讀取後發現怎麼跟當初說好的不一樣，React 一急，乾脆直接拋出 Hydration 錯誤，說我不玩了。

要解決這個問題，最常見的兇手通常是亂用日期函數，或是把會變動的內容直接塞在 render 邏輯裡。我當時的解法是確保組件在第一次渲染時，伺服器與客戶端拿到的是完全一致的初始狀態。如果一定要顯示動態內容，我會選擇在 useEffect 裡才去更新狀態，這樣就能強制組件在瀏覽器端才執行第二次渲染，避開初期的不一致。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  // 在伺服器端，isClient 為 false，渲染預設內容
  // 在瀏覽器端，useEffect 會執行，isClient 變為 true，渲染真正內容
  return (
    <div>
      {isClient ? <span>現在是動態時間：{new Date().toLocaleTimeString()}</span> : <span>載入中...</span>}
    </div>
  );
}

為了預防這種悲劇再次發生，我現在寫組件時都有個習慣：只要看到會用到 window、localStorage 或隨機數的地方，心裡就會響起警報。我會強制自己把這些邏輯封裝在一個自定義 Hook 裡，或者乾脆確保初始渲染時給一個「安全的預設值」，絕對不在 return 的最外層直接呼叫會造成差異的函數。

雖然修這東西真的很磨耐心，但只要搞定一次，下次看到紅字就不會想砸鍵盤了，大家加油啦！
