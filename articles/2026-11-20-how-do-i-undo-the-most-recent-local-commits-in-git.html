How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27250 votes

I still remember the first time I accidentally committed a massive set of debug logs and a half-finished configuration file to our production repo. I was rushing to meet a deployment deadline, typed git commit -am "fix stuff", and immediately realized I’d included files I wasn't supposed to touch. I spent about two hours sweating bullets, terrified I’d break the build or ruin my local history, before I finally learned how to handle the git reset command properly.

The reason this happens so often is that Git is designed to be a ledger of your work, and by default, it assumes you’re always ready to move forward. When you run a commit, you’re essentially taking a snapshot of your current state and locking it into the local branch history. If you realize your mistake before you push to the remote server, you’re in a great spot because the "damage" is still entirely contained on your machine. You aren't actually deleting the work you’ve done; you’re just telling Git to move the branch pointer back in time so you can adjust the files before finalizing them again.

To fix this, I always use git reset. If you just want to undo the commit but keep your changes in your staging area (so you can fix the files and commit again), you’ll want to use a "soft" reset. Just run this in your terminal:


git reset --soft HEAD~1

This command moves your branch back by one commit, but it keeps all your changes sitting in the staging area, ready to be tweaked. If you want to go a step further and completely unstage those files so they show up as "modified" but not ready to commit, you can use the mixed reset, which is actually the default behavior:


git reset HEAD~1

Now, if you’re like me and you occasionally commit something so broken that you just want to nuke the last commit and throw away all those changes entirely, you can use the hard reset. Be careful with this one, because it will permanently delete any uncommitted work in those files:


git reset --hard HEAD~1

If you really want to stop this from happening, I highly recommend getting into the habit of running git status before you run git commit. It takes two extra seconds, but it acts as a final sanity check to make sure you aren't about to package up a bunch of garbage files that don't belong in your repository.

Hope this saves you the panic I felt back when I was a junior dev. Happy coding!

手滑 commit 了機密檔案？Git 後悔藥這樣吃才對

來源：Stack Overflow ↗ · 27250 票

說真的，我第一次碰到這個狀況時，真的差點把手邊的咖啡噴出來。當時我正趕著要下班，腦袋已經飛到晚餐吃什麼了，結果在 git commit -m "update" 之後，才猛然發現自己把一堆不該進版控的環境設定檔還有測試用的垃圾 log 全塞進去。看著終端機上那行「Create mode 100644」，我心跳瞬間漏了一拍，那種「完了，這下要變公司罪人」的崩潰感，真的只有經歷過的人才懂。

其實這背後的原因很簡單，Git 的設計邏輯就是讓你隨時記錄當下的狀態，但它預設認為你提交的每一個檔案都是你想保留的。當我們在還沒 git push 到遠端之前，其實這些 commit 都只是存在你的本機而已。Git 就像是一個很聽話的秘書，你叫它存檔它就存，根本不知道你其實是不小心手滑，所以我們要做的，就是把這個「記錄」給抹掉，讓時光倒流回還沒 commit 的那個瞬間。

當時我手忙腳亂查到 git reset 這個指令，後來發現它真的是救命神器。如果你只是想撤銷最後一次 commit，但想保留你辛苦改好的程式碼，請直接在終端機輸入：


git reset --soft HEAD~1

這行指令最貼心的地方在於，它會把那個 commit 拆掉，但你的檔案修改內容會通通留在暫存區（Staging Area），你可以接著調整檔案，把不該進去的檔案 git reset 掉，然後重新 commit。但如果你是那種連檔案內容都想直接毀屍滅跡，確保那個 commit 從來沒發生過，那就用暴力一點的：


git reset --hard HEAD~1

這個指令下去，你的修改會直接消失，世界重回清靜。不過要提醒一下，用 --hard 之前一定要確定你真的不要那些修改了，不然真的會欲哭無淚。

為了不要再經歷這種心臟病發的時刻，我現在養成了一個習慣，就是在 commit 之前，一定會先敲一下 git status。這兩秒鐘的確認時間，真的能救我無數次。另外，我也建議大家把 .gitignore 設定好，把那些絕對不該進版控的檔案通通丟進去，這樣就算你手滑打了 git add .，Git 也會自動幫你擋掉，真的是工程師的保命符。

以後如果不小心又手滑了，記得深呼吸，反正還沒 push 之前一切都好說，Git 其實沒那麼可怕啦！
