How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a training loop on a multi-GPU server, feeling like a total genius until my terminal exploded with a wall of red text. I spent nearly three hours debugging my data loader and model weights, convinced my CUDA drivers were corrupted, only to realize I’d simply forgotten to move my tensors to the same device as my model. It’s that classic "junior dev" mistake that manages to bite even the most seasoned engineers when we're coding late at night.

The core of this issue is surprisingly simple: PyTorch is extremely strict about data locality. When you move your model to the GPU using .to(device), you’re essentially telling the model, "Hey, please live in your high-speed VRAM." However, when you iterate through your dataloader, those tensors are born on your CPU by default. When you try to pass those CPU-bound inputs into a GPU-bound model, PyTorch throws an error because it can’t perform matrix multiplication between tensors living in two different physical locations. They have to speak the same language, and in this case, that means they both have to reside on the same device.

To fix this, you need to explicitly move your input data to the same device your model is currently occupying inside your training loop. I usually handle this by grabbing the device from the model itself, which keeps the code clean and portable. Here is the standard way I patch this up:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the line that solves the crash
    inputs = data[0].to(device)
    labels = data[1].to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you have a complex dataset or a custom collate function, you might find it cleaner to write a small helper function to move everything in a batch to the device at once.

To prevent this from becoming a recurring headache in your projects, I’ve started adopting a habit of always defining a device variable at the top of my training script and creating a utility function that pushes entire dictionaries or lists of tensors to that device. If you bake that move operation into your loop right after the data is pulled from the loader, you’ll never see this specific runtime error again. It’s a small bit of boilerplate that saves you a massive amount of debugging time down the line.

Good luck with your model training, and don't let the CUDA errors keep you up too late!

PyTorch 報錯：Input type 和 weight type 不一致，別再被 GPU 搞瘋了！

來源：Stack Overflow ↗ · 202 票

記得剛開始碰 PyTorch 的時候，為了趕一個重要的 Demo，我熬夜寫了好幾個小時的 training loop。好不容易看到模型開始跑了，結果才跑不到一秒鐘，終端機就直接噴出紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。當下真的差點崩潰，心想：「我不是明明已經把 model 丟到 GPU 了嗎？為什麼還要刁難我？」那種看著 GPU 空轉，程式卻因為這行錯誤卡住的無力感，真的是每個煉丹師的惡夢。

其實這個錯誤的邏輯很單純，就是 PyTorch 在檢查運算時發現「你的模型已經在 GPU 上吃香喝辣了，但你的輸入資料（input）卻還被留在 CPU 的記憶體裡」。這就像是你邀請了一個大廚（GPU 模型）來做菜，結果卻把食材（CPU 資料）忘在門口的冰箱裡，大廚當然會因為拿不到食材而翻桌抗議。簡單來說，PyTorch 要求參與運算的所有張量（Tensor），必須要在同一個裝置（Device）上，不能跨區溝通。

解決這個問題的方法其實很直接，就是要在訓練迴圈裡，手動把讀進來的資料也搬到 GPU 上。我當時也是改了這行程式碼才順利解開：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵在這裡：把 inputs 和 labels 都丟到跟 model 同樣的 device 上
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就是計算 loss 等等...

只要確保資料在餵給模型之前，乖乖地用 .to(device) 同步到 GPU，問題就迎刃而解了。

為了避免以後再被這個錯誤搞到心態爆炸，我現在養成了一個習慣，就是在寫 DataLoader 處理資料時，直接寫一個通用的轉換函數，或是乾脆在訓練迴圈的最開頭就檢查裝置。如果你的模型比較複雜，記得連那些額外的輔助張量（例如 mask 或初始化的隱藏狀態）也要記得同步。養成這種「資料進門前先檢查裝置」的肌肉記憶，真的能省下不少除錯的時間。

希望這篇心得能幫你少走點冤枉路，趕快去把模型跑起來吧！
