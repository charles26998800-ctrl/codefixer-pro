How to Undo Your Most Recent Local Git Commits (Without Losing Your Work)

Source: Stack Overflow ↗ · 27242 votes

I still vividly remember the time I accidentally committed a massive .env file containing my local database credentials to a repo I was about to push to a public organization. My heart dropped into my stomach when I realized what I’d done, and I spent a solid forty-five minutes sweating over whether I’d have to delete the entire project folder and start my morning over. It’s one of those classic "oh no" moments that every developer goes through at least once, but once you learn how to handle it, you’ll never fear the commit button again.

The root of the issue is simply that Git is designed to be a ledger of your work, and by default, it assumes that every time you run git commit, you’re ready to carve that state into history. We often treat commits as "save points" like in a video game, but if you haven't pushed those changes to a remote server yet, that history is essentially just a local draft. You aren't actually "deleting" your work; you're just telling Git to move the pointer of your current branch back to a previous state, which effectively pretends those recent commits never happened.

When I need to walk back my mistakes, the command I reach for is git reset. If you just want to undo the very last commit but keep all your hard work sitting in your staging area, you’ll want to use a "soft" reset. Just run this in your terminal:


git reset --soft HEAD~1

This command moves your branch back one step, but it keeps all the files you changed in your staging area, so you can fix whatever you messed up—like removing that secret key—and then commit it again properly. If you want to go a step further and completely unstage everything, essentially moving the files back to your working directory, use the "mixed" reset instead:


git reset HEAD~1

However, if you’re like me and you accidentally committed a bunch of garbage files that you want to vaporize entirely, you can perform a "hard" reset. Just be careful, because this will permanently discard any changes you made in those commits:


git reset --hard HEAD~1

To keep this from ruining my day in the future, I’ve started using the --dry-run flag or simply running git status religiously before I hit enter on a commit command. I also highly recommend configuring your Git setup to use a pre-commit hook that scans for sensitive strings or large files; it’s saved me from myself more times than I care to admit.

Hope this helps you clean up your history without the stress. Happy coding!

救命！我不小心 commit 了不該 commit 的東西，Git 該怎麼反悔？

來源：Stack Overflow ↗ · 27242 票

記得有一次凌晨三點，我為了趕一個緊急的小功能，腦袋已經呈現半當機狀態，直接一個 git commit -m "update" 就把整個測試用的設定檔、還有裡面藏著測試用 API Key 的垃圾檔案全都塞進去了。當下看著終端機顯示 commit 成功的瞬間，我整個人心跳漏了一拍，那一刻真的差點崩潰，滿腦子想的都是：「完蛋了，要是現在 push 上去，我不就成了公司資安漏洞的頭號戰犯嗎？」那種冷汗直流、心臟狂跳的痛苦時刻，相信很多工程師都懂。

其實會發生這種事，通常就是 Git 的「暫存區」機制太好用，導致我們在 git add . 的時候太豪邁，根本沒檢查到底把什麼髒東西混進去了。Git 的設計邏輯是把 commit 當成一個個的時間節點，當你下達 commit 指令時，它就幫你把這些變更封裝進歷史紀錄裡。如果你還沒 push 到遠端伺服器，這些變更其實都還在你的本地端，就像是還沒寄出去的包裹，只要我們還沒把它丟到郵筒，通通都有救。

我後來學會的第一招，也是最常用的一招，就是直接用 git reset --soft HEAD~1。這個指令的神奇之處在於，它會把你的 commit 拆掉，但會把原本你 commit 進去的檔案完整地留在你的「暫存區」裡。這樣你就不會因為拆掉 commit 而弄丟辛苦寫的代碼，反而可以冷靜地把那些不該存在的垃圾檔案從暫存區剔除，重新整理好再 commit 一次。


# 把剛剛那次 commit 拆掉，檔案留在暫存區，方便你調整
git reset --soft HEAD~1

# 如果你是想把檔案連同修改內容一起「徹底抹除」，回到改動前的樣子
git reset --hard HEAD~1

如果你只是想把檔案從暫存區拿出來，但不想動到 commit，那 git restore --staged <檔案名稱> 也是我的愛用指令。說真的，只要還沒 push，Git 的歷史紀錄其實就像橡皮擦一樣好改，真的不需要太緊張。

為了不要再經歷這種心臟病發的時刻，現在我養成了一個好習慣：每次要 commit 之前，我一定會先打個 git status 看一眼清單。如果檔案太多，我會強迫自己改用 git add -p，這樣它會一段一段地問我：「這段程式碼你確定要加入嗎？」雖然剛開始用會覺得有點繁瑣，但為了保護自己的心臟，這點時間絕對值得花。

反正 Git 就是這樣，用久了就知道它其實挺包容的，只要記得「還沒 push 一切好說」這個黃金法則就好。下次遇到這種情況，先深呼吸，別急著亂打指令，我們下次見！
