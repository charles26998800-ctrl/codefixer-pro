How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 690 votes

I remember back when I was first getting comfortable with Kubernetes, I spent a solid three hours banging my head against the wall because my pods kept stuck in ImagePullBackOff. I was convinced I’d made a typo in my image tag, but it turned out I was just trying to pull an image that existed only on my laptop, not in the cloud. It’s one of those classic "newbie" hurdles that makes you feel like you’re losing your mind until you realize the architecture is literally designed to look in the wrong place.

The reason this happens is pretty straightforward once you understand how Minikube operates. When you spin up Minikube, it’s not just a process running on your machine; it’s a virtual machine or a containerized environment that acts as its own isolated cluster. When your Kubernetes deployment tries to pull an image, it asks the Minikube node to find it. Since Minikube has its own internal Docker daemon that’s completely separate from the one running on your macOS or Windows host, it naturally looks for the image inside its own isolated environment. It doesn't see your local Docker daemon, so it tries to reach out to a public registry, fails, and leaves you staring at an error log.

To get around this without wasting time pushing to a registry, I use the Minikube environment variables to point my local Docker client directly at the Minikube daemon. This is the cleanest way to do it. You just need to run a single command in your terminal, and for the duration of that session, any docker build command you run will build the image directly inside the Minikube environment.


# Point your shell to the Minikube docker daemon
eval $(minikube docker-env)

# Now build your image as you normally would
docker build -t my-local-image:v1 .

Once you’ve done that, you just need to make sure your Kubernetes manifest has the imagePullPolicy set to IfNotPresent (or Never), otherwise, Kubernetes might still try to check a remote registry if it thinks the tag is latest. If you’re ever done with this and want to point your terminal back to your host’s Docker, just run eval $(minikube docker-env -u). It’s a total lifesaver when you’re iterating quickly on a microservice and don’t want to clutter your Docker Hub or ECR with fifty different "test-build-v12" images.

The best way to prevent this from turning into a recurring headache is to keep a small script or a Makefile in your project root that handles the environment switching for you. I personally keep a Makefile with a build-local target that runs the environment switch, builds the image, and then switches back. It saves me from forgetting which daemon I’m currently talking to, which is usually how I end up accidentally building images in the wrong place anyway.

Hopefully, this saves you those three hours of frustration I had to endure. Happy coding and good luck with your cluster!

為什麼 Minikube 總是抓不到我的 Local Docker Image？別再傻傻推送到 Docker Hub 了！

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了測試一個簡單的 API 改動，每次都要把 Image 推送到 Docker Hub，然後再讓 Minikube 從遠端拉下來。最慘的是，網路速度一慢，或者 Docker Hub 的伺服器剛好抽風，我就得在那邊乾瞪眼等個十分鐘，那種「明明程式碼改一行，卻要花半小時在等待」的無力感，真的是會讓人想直接把鍵盤砸了。

其實會發生這種狀況，是因為我們對 Minikube 的運作機制有些誤解。Minikube 本質上是在你的電腦裡跑一個獨立的虛擬機（VM）或容器環境，它裡面的 Docker Daemon 跟我們宿主機（Host）的 Docker 是完全分開的兩個世界。簡單來說，你電腦上的 Image 就像是存在你家客廳的櫃子裡，而 Minikube 住在隔壁的獨立套房，它根本進不去你家客廳，當然就看不到你辛辛苦苦 Build 出來的 Image 囉。

要解決這個問題，其實不用那麼麻煩地把 Image 上傳到遠端。最快的方法就是直接告訴你的終端機：「嘿，現在請把指令導向 Minikube 內部的 Docker 環境」。只要在終端機輸入這行指令：


eval $(minikube docker-env)

執行完這行之後，你的終端機就會暫時「借用」Minikube 內部的 Docker 環境。這時候你在這個視窗執行 docker build -t my-app:v1 .，這個 Image 就會直接蓋在 Minikube 裡頭。接著只要在你的 Deployment YAML 檔裡面，把 imagePullPolicy 改成 IfNotPresent，Kubernetes 就會乖乖直接拿本地的 Image 來用，完全不需要再去網路上下載。

不過說真的，每次都要切換環境其實挺煩的，搞不好哪天你 Build 錯地方又開始鬼打牆。為了預防這種悲劇，我現在都會養成一個好習慣，就是直接把 Image 的 Tag 寫死，並且在開發階段盡量使用 eval $(minikube docker-env) 來確保環境的一致性。另外，如果你是用 Docker Desktop 當作 Minikube 的 driver，其實它現在已經支援直接共用 Image，不用切來切去，這也是個不錯的解法。

搞定之後看到 Pod 秒速啟動的感覺真的太爽了，希望這招能幫你省下不少浪費在等待上的青春！
