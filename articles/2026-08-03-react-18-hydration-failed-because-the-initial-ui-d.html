Fixing the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the dreaded "Hydration failed" error in a Next.js project. I had just migrated a legacy dashboard to React 18, and I was feeling pretty proud of myself until I opened the browser console and saw a wall of angry red text screaming that my server-rendered HTML didn't match my client-side build. I spent three hours—yes, three full hours—tearing apart my component tree, convinced it was some complex state management issue, only to realize I was blindly rendering the current date and time on the server.

The root cause of this frustration is actually quite simple: React expects the HTML generated by your server to be an identical twin of the HTML generated by your browser during the initial render. When you use server-side rendering (SSR), the server sends a static snapshot of your app to the user. Once that hits the browser, React kicks in to "hydrate" it, attaching event listeners and making it interactive. If your component uses something that changes between those two moments—like Date.now(), Math.random(), or even a check for localStorage—the browser sees a mismatch. React basically panics, throws its hands up, and discards the server-rendered DOM to rebuild it from scratch, which is exactly the performance hit you were trying to avoid with SSR in the first place.

To fix this, I’ve learned that the most effective strategy is to delay the rendering of the dynamic content until the component has officially mounted on the client. By using a simple useEffect hook, we can keep the server-side version static while letting the client take over once the page is interactive. Here is how I usually handle this in my projects:


import { useState, useEffect } from 'react';

export default function DynamicComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      <h1>Welcome to my app</h1>
      {isClient ? (
        <p>Current time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By adding that isClient flag, you ensure that the server renders the "Loading..." placeholder, which matches perfectly with the initial client render. Only after the component mounts does the state update, triggering a re-render that displays the actual dynamic data. It’s a clean, predictable way to handle the mismatch without sacrificing your SEO or the performance benefits of SSR.

If you want to prevent this from ruining your day in the future, my best advice is to audit your dependencies for anything that relies on browser-only APIs. Whenever you find yourself reaching for window or localStorage inside a component, wrap that logic in a useEffect or use a "client-only" wrapper component. If you force yourself to be intentional about what runs on the server versus what runs on the client, these hydration errors will stop haunting your console logs entirely.

Hope this saves you a few hours of debugging and lets you get back to building cool stuff. Good luck with the refactor!

React 18 Hydration 錯誤：那個讓我半夜想把螢幕砸了的「伺服器與客戶端不對稱」惡夢

來源：Stack Overflow ↗ · 341 票

還記得那天凌晨兩點，我正趕著發布一個 Next.js 專案的 beta 版本，滿心以為一切都大功告成，結果一打開瀏覽器控制台，整排紅通通的 Hydration failed 直接噴在我臉上。我當時真的是心涼了一半，明明程式碼在本地跑得好好的，為什麼一上線就開始鬧脾氣？更崩潰的是，頁面明明看起來沒什麼大問題，但 React 就是死活不肯放過我，甚至把整個 UI 的渲染邏輯都給卡住了，那種眼睜睜看著自己寫的元件被強制卸載、重新掛載的無力感，真的是工程師生涯最不想回憶的片段之一。

其實，會出現這個錯誤，核心原因就在於 React 18 的「嚴格模式」比以前敏感太多了。簡單來說，Next.js 的運作機制是先在伺服器端（SSR）產生 HTML，再傳送到瀏覽器讓 React 接手（Hydration）。當伺服器吐出來的 HTML 結構，跟瀏覽器第一次執行 JavaScript 算出來的 UI 不一樣時，React 就會崩潰。這通常是因為你用到了一些「只有瀏覽器才知道」的資訊，例如 window 物件、隨機數生成器，甚至是 new Date()。伺服器在跑的時候，這些東西的結果跟瀏覽器跑出來的不一樣，React 一對比發現：「欸？這內容怎麼跟我剛剛收到的 HTML 不一樣？」然後就報錯了。

我後來發現，最常見的兇手就是我在元件裡用了 typeof window !== 'undefined' 來判斷環境，結果在渲染邏輯裡寫了條件判斷。要解決這個問題，最乾淨的方式就是確保在 Hydration 完成之前，伺服器和客戶端看到的內容是一模一樣的。我後來學乖了，如果遇到這種非得用到瀏覽器 API 的情況，我會利用 useEffect 來處理。因為 useEffect 只會在瀏覽器端執行，這樣就能避開伺服器渲染時的差異。

我通常會這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  // 在這之前，伺服器和客戶端都渲染同樣的佔位符或空內容
  if (!isClient) return null; 

  // 之後再渲染那些會用到 window 或 localStorage 的複雜邏輯
  return <div>{window.innerWidth}</div>;
}

至於要怎麼預防下次再被搞瘋？我現在養成一個習慣，就是儘量把「依賴瀏覽器環境」的邏輯全部抽離到 Custom Hook 裡，並且永遠在元件掛載完成後才去讀取這些狀態。如果你發現你的 UI 裡有任何會根據時間、隨機亂數或是視窗寬度而變動的內容，一定要記得先給它一個固定的初始值，別讓伺服器和瀏覽器因為「資訊不對稱」而吵架。

祝大家寫 Next.js 的時候都能一路順風，別再被這些 Hydration 的小細節折磨啦！
