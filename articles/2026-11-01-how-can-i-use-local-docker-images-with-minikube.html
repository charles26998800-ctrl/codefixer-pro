How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster, feeling like a genius until I tried to deploy my first custom image. I spent three hours banging my head against the wall because my pods were stuck in ImagePullBackOff, even though I could clearly see the image sitting right there in my local Docker daemon. It’s one of those classic "gotcha" moments that makes you realize just how isolated the container runtime inside a virtual machine really is.

The reason this happens is pretty straightforward once you peel back the layers: Minikube runs inside its own virtual machine or container environment, which has its own isolated Docker daemon. When you build an image on your laptop, it lives in your host’s Docker daemon. Kubernetes, inside the Minikube VM, has no idea that your local environment even exists. It tries to pull the image from a registry, fails because your image isn't pushed anywhere, and gives up. You aren't doing anything wrong; you're just dealing with a fundamental boundary between your host OS and the cluster.

The absolute cleanest way I’ve found to fix this is by pointing your local Docker client directly at the Minikube daemon. Instead of building locally and then trying to push or transfer, you just tell your terminal to talk to the Minikube engine. Run this command in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. After that, you just need to make sure your Kubernetes deployment configuration has imagePullPolicy: IfNotPresent set. If you don't set that to IfNotPresent, K8s will still try to reach out to a registry to check for a newer version, which defeats the whole purpose. With that policy in place, Kubernetes sees the image is already there and skips the pull entirely.

If you want to avoid this headache in the future, my go-to move is to set up a small local registry or just stick to this environment-switching workflow for all my rapid development cycles. It saves you from polluting public registries with "test-image-v1" garbage while keeping your feedback loop lightning fast.

Hope this saves you a few hours of debugging—happy coding!

為什麼 Minikube 總是抓不到我的 Local Docker Image？別再傻傻推上 Docker Hub 了！

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了測試一個簡單的 API 改動，每次都要把 Image 打包、推送到 Docker Hub，再從 Minikube 裡面 pull 下來。當時網路慢得要命，我坐在電腦前看著終端機畫面發呆，心裡想著：「難道這世界上的工程師，每天都在做這種浪費生命的重複作業嗎？」最慘的是，好不容易跑起來發現改錯了，又要重來一遍，那種崩潰感真的會讓人想直接把筆電闔上。

其實這背後的原因很單純，因為 Minikube 本質上是一個跑在虛擬機（或是容器）裡的獨立環境，它跟你的宿主機（Host）是「平行世界」。當你執行 docker build 時，Image 是存在你電腦的 Docker daemon 裡，但 Minikube 的 Kubernetes 節點根本看不見這些檔案，它只認得它自己內部儲存庫裡的鏡像。所以無論你怎麼嘗試 imagePullPolicy: IfNotPresent，K8s 永遠會去遠端倉庫找，找不到就報 ErrImagePull 給你看。

後來我發現，最直覺的解決方案其實就是「讓 Minikube 直接共用你的 Docker 環境」。只要在執行 build 指令前，先下這行指令：


eval $(minikube docker-env)

這行指令的神奇之處在於，它會把你的 shell 環境變數指向 Minikube 內部的 Docker daemon。這時候你再跑 docker build -t my-app:v1 .，這個 Image 就會直接寫進 Minikube 的肚子裡。接著只要把 Deployment 的 imagePullPolicy 設定為 Never，K8s 就會乖乖地使用本地鏡像，再也不用經過網路傳輸，測試速度直接起飛！

為了避免以後又忘記這件事，我現在養成了一個習慣，就是把這個環境設定寫在 Makefile 裡。每次要開發測試時，只要打 make build，它就會自動幫我切換環境並打包，這樣我就不用再擔心哪天手殘忘了切換，結果在那邊對著錯誤訊息抓頭半天。

學會這招真的省下不少開發時間，希望你們也能早日脫離「推上去再抓下來」的惡夢，去喝杯咖啡吧！
