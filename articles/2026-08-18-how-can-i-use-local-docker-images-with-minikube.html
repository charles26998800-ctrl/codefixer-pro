How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up a local Kubernetes cluster with Minikube, feeling pretty clever until I tried to deploy my first custom container. I spent three hours banging my head against the wall because my pods were stuck in ImagePullBackOff, even though I could clearly see the image in my machine's Docker daemon. I was convinced I’d messed up my YAML syntax, but it turned out I was just fighting the architecture of how Minikube isolates its own environment from my host machine.

The reason you’re running into this is that Minikube runs inside its own virtual machine or container—it’s essentially a separate island. When you run docker build on your laptop, that image lives in your host’s Docker daemon. When Minikube tries to pull an image, it looks inside its *own* internal Docker daemon, not yours. It doesn’t know your host machine even exists, so it naturally fails to find the image and tries to reach out to Docker Hub, where your private local build obviously doesn't exist.

To fix this, the most reliable way I’ve found is to point your local terminal directly at the Minikube Docker daemon. Instead of pushing to a registry, you just run a quick environment command that tells your local Docker CLI to talk to the engine running inside the Minikube VM. Just run this in your terminal:


eval $(minikube docker-env)

Once you’ve executed that, any docker build command you run will build the image directly inside the Minikube environment. You can verify it worked by running docker images, and you’ll see your local images listed right there. Now, when you apply your Kubernetes manifest, set your imagePullPolicy to IfNotPresent in your deployment YAML. This tells K8s to check if the image is already there before trying to reach out to the internet, and since it’s already in the Minikube daemon, your pod will spin up almost instantly.

To prevent this headache from coming back, make it a habit to check your environment before you start a new build session. If you’re ever unsure if you’re pointing at Minikube or your host, just run docker info and look for "minikube" in the server version or the labels. If you don't see it, just run that eval command again and you're good to go.

Hope this saves you from the same three-hour rabbit hole I fell down. Happy coding, and may your pods always hit Running on the first try!

別再把 Image 推到 Docker Hub 了！Minikube 本地開發的省力技巧

來源：Stack Overflow ↗ · 688 票

記得剛開始接觸 Kubernetes 的時候，為了測試一個小小的功能改動，我每次都要跑一遍 docker build，接著 docker push 到 Docker Hub，然後再讓 Minikube 的 Pod 執行 imagePullPolicy: Always。那天下午網路慢到讓我崩潰，看著終端機顯示「Downloading...」的那幾分鐘，我真的覺得人生浪費在這種無意義的等待上，甚至一度想把鍵盤砸了。

會遇到這個坑，是因為 Minikube 本質上是一個跑在虛擬機（或容器）裡的獨立環境。當我們在宿主機（也就是你自己的筆電）執行 docker build 時，這個映像檔是存在你宿主機的 Docker Daemon 裡，但 Minikube 根本「看不見」它。Kubernetes 預設會去遠端倉庫抓取，如果你沒指定，它去 Docker Hub 找不到你的本地標籤，當然就直接給你一個 ImagePullBackOff 的紅字錯誤，看著那個錯誤訊息，真的會讓人懷疑自己是不是寫錯了什麼設定。

其實解決方法比你想的簡單太多了。最推薦的做法就是直接用 minikube image load 指令。這招能讓你直接把宿主機的映像檔「丟進」Minikube 的環境裡，根本不用經過網路傳輸。你只需要在 Build 完映像檔之後，補上這行指令：


minikube image load <你的映像檔名稱>:<標籤>

只要執行完這行，再把 Deployment 的 imagePullPolicy 改成 IfNotPresent，Pod 就會乖乖抓取本地已經載入的映像檔，完全不需要網路，瞬間就能啟動成功。如果你是用 Docker Driver，甚至可以直接在 Minikube 裡面執行 eval $(minikube docker-env)，這樣你的 docker build 指令就會直接對著 Minikube 內部的 Docker 環境生效，連 load 的步驟都省了，這對於開發階段來說簡直是救命稻草。

為了避免以後又因為這種事浪費時間，我現在養成一個習慣，就是把這些常用的指令寫成一個簡單的 Makefile。每次要測試時，只需要打一個 make deploy，它就會自動幫我完成 Build、Load 和 Apply 的動作。這樣不只省下打字的時間，也不會因為忘記載入映像檔而又在那邊對著錯誤訊息發呆。

設定好之後，開發體驗真的會提升好幾個檔次，祝大家都能順利避開這個惱人的等待地獄！
