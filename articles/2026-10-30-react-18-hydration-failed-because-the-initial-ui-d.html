Solving the "Hydration Failed" Error in Next.js: A Practical Guide

Source: Stack Overflow ↗ · 341 votes

I still remember the first time React 18 threw the "Hydration failed" error in my face. I had just migrated a legacy dashboard to Next.js, and everything looked perfect locally, but the moment I deployed it, my console turned into a graveyard of red warnings. I spent three hours staring at the screen, convinced that React was hallucinating, only to realize I was just being lazy with my date formatting. It’s one of those bugs that makes you want to throw your keyboard out the window, but once you understand the mechanism, it becomes much easier to squash.

Essentially, this error happens because the HTML generated by your server doesn't match the HTML generated by your browser during the initial load. When you use Server-Side Rendering (SSR), Next.js sends a snapshot of your page to the client. React then tries to "hydrate" that static HTML by attaching event listeners and making it interactive. If the server thinks the time is "10:00 AM" but the browser thinks it's "10:01 AM"—or if you're using something like typeof window to conditionally render components—the DOM nodes won't align. React sees the mismatch, panics, and dumps the error in your console to prevent a UI glitch.

The most common fix I’ve found is to delay the rendering of the component that depends on client-only data until the component has actually mounted. I used to try all sorts of clever hacks, but the cleanest approach is to use a simple useEffect hook to track the mounting state. Here is how I handle it in my projects:


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a skeleton loader
  }

  return <div>{new Date().toLocaleTimeString()}</div>;
};

By initializing isMounted as false, the server renders nothing (or a fallback), and the client renders the actual content only after it has successfully mounted. This ensures that the server and client are perfectly synchronized during that critical first paint. If you're using libraries that rely on window-specific APIs like localStorage or window.innerWidth, this pattern effectively silences the hydration error by ensuring the logic never runs on the server side.

To keep this from haunting your future builds, make it a habit to audit your components for any logic that depends on the current time, random number generators, or browser-only APIs. If you find yourself reaching for typeof window !== 'undefined', stop and ask if the component can wait until the client-side mount. Keeping your UI deterministic across environments is the best way to ensure a smooth experience for your users.

Hope this saves you a few hours of debugging and keeps your console clean. Happy coding!

React 18 Hydration Error：那個讓我熬夜到凌晨兩點的「不一致」惡夢

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地想體驗 SSR 的效能提升，結果專案一跑起來，瀏覽器 Console 直接噴出一大串紅通通的 Hydration failed 錯誤。當時我真的是盯著螢幕差點崩潰，明明程式碼邏輯看起來完全沒問題，伺服器算出來的 HTML 跟瀏覽器渲染出來的結果居然對不上，那種「我明明寫對了，但電腦卻跟我說我錯了」的挫折感，真的會讓人想當場把鍵盤給拆了。

這問題的核心其實很單純，就是 React 在進行「水合（Hydration）」時，發現伺服器端吐出的 HTML 結構，跟客戶端第一次執行 React 時產生的結構長得不一樣。你想想，伺服器渲染時可能拿不到瀏覽器特有的資訊（比如 window 物件或使用者的本地時間），導致伺服器算出來的 UI 是一套，等程式下載到瀏覽器執行時，因為拿到了這些動態資訊，UI 就自動「變形」了。React 發現兩者不匹配，為了保證穩定性，它就會直接拋出錯誤並強制重繪，這不僅造成效能浪費，還會讓整個頁面閃爍一下。

我後來發現，最常見的兇手就是我在元件裡直接用了 new Date() 或者是讀取了 localStorage。為了修好它，最簡單也最有效的方法就是讓這個「動態的部分」延後到客戶端渲染完成後才執行。我通常會寫一個 useHasMounted 的 Hook，確保元件在瀏覽器端掛載完成後才渲染那些不確定的內容：


import { useState, useEffect } from 'react';

function useHasMounted() {
  const [hasMounted, setHasMounted] = useState(false);
  useEffect(() => {
    setHasMounted(true);
  }, []);
  return hasMounted;
}

// 在元件中使用：
const MyComponent = () => {
  const hasMounted = useHasMounted();
  
  if (!hasMounted) return null; // 或者放一個骨架屏 (Skeleton)

  return <div>現在時間：{new Date().toLocaleString()}</div>;
};

用這種方式處理之後，伺服器端只會渲染出空的或是佔位符，等到瀏覽器真的接手後再補上真實資料，這兩邊的結構就完全對齊了。

至於怎麼預防這種惱人的狀況再次發生，我現在有個習慣，就是嚴格限制在 useEffect 以外的地方使用任何瀏覽器專屬的 API。只要腦袋裡隨時掛著「這行程式碼伺服器跑得動嗎？」這個警鐘，通常就能避開 90% 的 Hydration 地雷。養成這種防禦性開發的習慣，真的能幫你省下不少半夜 debug 的寶貴睡眠時間。

希望這招能救你脫離苦海，下次寫 SSR 元件記得多留個心眼，別讓 Hydration 成為你開發路上的絆腳石！
