How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a GPU training loop in PyTorch, feeling like a total wizard until I hit this exact error. I spent a good three hours staring at my screen, convinced my GPU was broken or my drivers were toast, only to realize I’d simply forgotten to tell my input data to "get on the bus" with the rest of the model. It’s one of those classic "welcome to deep learning" moments that makes you want to throw your keyboard out the window, but once you understand the underlying mechanism, it’s a trivial fix.

Essentially, this error boils down to a mismatch in hardware location. PyTorch is very strict about where your data lives; if your model’s parameters have been moved to the GPU (via model.to('cuda')), they expect the input tensors to be sitting in that same GPU memory space. When you load data from a DataLoader, it defaults to the CPU (the FloatTensor). When you try to perform a forward pass, PyTorch tries to perform math between a CPU-based input and a GPU-based weight, and it throws this RuntimeError because it can’t perform operations across different devices.

To fix this, you need to manually move your input tensors to the same device as your model during your training loop. I usually keep a reference to the device I'm using and apply it to my data as soon as it comes out of the iterator. Here is how I handle it in my scripts:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # Move the data to the same device as the model
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you’re working with a multi-output model or complex data structures, just make sure that every individual tensor that interacts with your model parameters is explicitly moved using the .to(device) method.

To prevent this from becoming a recurring headache in your projects, I’ve adopted a habit of defining a helper function or a simple wrapper that moves the entire batch to the device in one line. You can even create a small utility function that iterates through a dictionary of tensors and moves them all at once. If you start every loop with a quick check to push your data to the device, you’ll never have to worry about this mismatch again.

Hope this saves you a few hours of debugging time today. Happy coding!

為什麼 PyTorch 總是吵著說我的資料跟模型不同步？

來源：Stack Overflow ↗ · 202 票

還記得剛開始玩 PyTorch 的那個下午，我信心滿滿地寫好模型訓練迴圈，想說這下總算能把這兩週的實驗跑完，結果按下執行鍵不到三秒，螢幕就噴出一大串紅通通的錯誤訊息。看到「RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same」那一刻，我真的差點把咖啡噴在鍵盤上，心想：「大哥，我明明都把 model 丟到 GPU 了，你還在跟我吵什麼？」

其實這個問題的核心非常單純，就是「跑錯棚」。當我們在定義 device = torch.device("cuda") 並把 model.to(device) 之後，模型確實乖乖住進了顯存（GPU）裡，但我們餵給它的 inputs 資料卻還待在記憶體（CPU）裡。對 PyTorch 來說，這就像是你把法拉利引擎（GPU 上的模型）跟腳踏車輪胎（CPU 上的資料）硬湊在一起，系統當然會報錯告訴你它們「門不當戶不對」。那種滿心期待訓練開始，結果被一行冷冰冰的錯誤訊息擋下的痛苦，我絕對懂，畢竟我當時也是在那邊反覆檢查 code，直到懷疑人生才發現只是少寫一行。

解決這個問題的方法其實很直覺，我們只需要在迴圈讀取資料的時候，順手把資料也「搬」到跟模型一樣的地方就好了。我通常會直接在 for 迴圈裡把 inputs 和 labels 同步搬過去，這樣就不會發生這種資料還在 CPU 閒晃的尷尬狀況：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵在這裡：把讀進來的資料也丟到你定義好的 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... 後續的訓練步驟

為了預防下次又忘記這件事，我後來養成了一個習慣，就是定義一個全域的 device 變數後，寫一個小小的 Helper Function 或者直接在讀取資料的 Pipeline 就處理好。現在我只要寫訓練迴圈，第一件事絕對是先確認資料搬遷，畢竟與其事後 Debug 浪費時間，不如在寫 Code 的當下就把它處理得漂漂亮亮的。

希望這篇心得能幫你省下寶貴的除錯時間，別讓這小小的裝置不匹配毀了你的實驗進度！
