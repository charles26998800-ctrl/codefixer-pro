How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 690 votes

I remember the first time I set up Minikube, I felt like a genius until I tried to deploy a local image. I spent three solid hours scratching my head, watching my pods stay stuck in ImagePullBackOff while I frantically checked my Docker tags, convinced I’d made a typo. It felt like I was trying to hand someone a physical book while insisting they read it through a telescope from across the street; the infrastructure simply didn't know my local machine existed.

The reason you’re running into this is that Minikube runs inside its own isolated environment, usually a virtual machine or a container. When you run docker build on your laptop, that image lives in your host’s Docker daemon. Kubernetes, however, is looking for that image inside the Minikube node. Since they don't share the same internal storage, the cluster tries to pull the image from a remote registry (like Docker Hub), fails to find it, and gives up.

The quickest way I fixed this was by pointing my local terminal directly to the Minikube Docker daemon. Instead of building locally and trying to move files around, I run a simple command to swap my environment variables. By running eval $(minikube docker-env), your shell starts talking to the Docker engine inside Minikube. Now, when you run your build command, the image is created directly where Kubernetes can see it.


# Point your shell to the Minikube docker-daemon
eval $(minikube docker-env)

# Build your image
docker build -t my-local-image:v1 .

# Now your pod spec can use the image directly
# Ensure imagePullPolicy is set to Never or IfNotPresent

Once you’ve built the image, just make sure your Kubernetes manifest has imagePullPolicy: IfNotPresent or imagePullPolicy: Never set. If you leave it as the default Always, Kubernetes will still try to reach out to the internet to verify the image, which will lead to another round of frustration.

To keep this from biting you again, I’ve started using a simple naming convention for my local-only images to distinguish them from production-ready ones. If you make it a habit to always check your imagePullPolicy before applying a deployment, you'll save yourself from those mysterious ImagePullBackOff errors every single time.

Hope this saves you a few hours of debugging. Happy coding, and may your pods always reach Running status on the first try!

別再把 Docker Image 推上雲端了！教你如何讓 Minikube 直接吃本地映像檔

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，為了測試一個簡單的 API 改動，我每次都要把 Docker Image build 好，再乖乖地 docker push 到 Docker Hub，然後再回到 Minikube 裡 kubectl rollout restart。那個等待上傳又下載的過程簡直是惡夢，有時候網路慢一點，光是等 Image pull 下來我就能去泡兩杯咖啡了，最崩潰的一次是等了半天發現改錯變數，又要重來一次，那種想把鍵盤砸了的衝動真的只有經歷過的人才懂。

會發生這種「明明 Image 就在電腦裡，Minikube 卻死活找不到」的情況，其實是因為 Minikube 本身是一個跑在虛擬機（或是 Docker 容器）裡的獨立環境。對 Minikube 來說，它的世界就是那台虛擬機，它根本看不到你電腦主機裡那個 Docker Daemon 的倉庫。這就像是你把便當放在自己家冰箱，卻指望住在隔壁的鄰居（Minikube）能直接拿去吃一樣，物理上根本連不通啊。

要解決這個問題，其實最快的方法就是直接把你的環境變數「導」給 Minikube。我後來學乖了，只要在下指令前先執行這行：


eval $(minikube docker-env)

執行這行之後，你當前終端機的 Docker 指令就會直接連上 Minikube 內部的 Docker Daemon。這時候你再執行 docker build -t my-app:v1 .，這個 Image 就會直接出現在 Minikube 的肚子裡。接著記得把你的 Deployment YAML 裡的 imagePullPolicy 改成 IfNotPresent，不然 Kubernetes 還是會手癢跑去網路上抓舊版，只要設定正確，你就會發現 Pod 瞬間就跑起來了，完全不用再浪費時間等上傳。

為了避免以後又因為忘記切換環境而鬼打牆，我現在都習慣在開發初期就直接用這個指令，或者乾脆寫個簡單的 Makefile 把 build 和 deploy 流程串在一起。養成「先切換環境再開發」的肌肉記憶，真的能省下不少無謂的除錯時間。

以後別再為了測試一個小改動就跑去洗杯子等待了，直接把這個環境變數搞定，開發效率真的會起飛。
