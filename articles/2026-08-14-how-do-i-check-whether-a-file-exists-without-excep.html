The Right Way to Check if a File Exists in Python

Source: Stack Overflow ↗ · 7349 votes

Back when I was a junior developer working on my first automation script, I was convinced that wrapping every single file operation in a try...except block was the height of defensive programming. I spent three hours debugging a script that was bloated with nested error handling, only to realize I was essentially using a sledgehammer to crack a nut just to see if a configuration file was sitting in the directory. It was one of those classic "I'm making this way harder than it needs to be" moments that taught me the value of clean, readable code.

The root cause of this confusion usually stems from the "easier to ask for forgiveness than permission" (EAFP) philosophy that Python champions. While EAFP is generally the standard for production-grade code because it handles race conditions—where a file might disappear between the time you check for it and the time you open it—it can feel like massive overkill for simple scripts or CLI tools. Sometimes you just need to know if a path exists so you can display a "File not found" message to the user, rather than letting the entire application crash with a stack trace.

When I need to check for a file without the ceremony of a try...except block, I always reach for the pathlib module. It’s been the standard since Python 3.4, and frankly, it’s much more elegant than the old os.path methods. Here is how I handle it in my projects:


from pathlib import Path

file_path = Path("config.json")

if file_path.is_file():
    print("The file exists and I can proceed.")
else:
    print("That file isn't here, let's create a default one.")

If you’re still working on an ancient legacy codebase that hasn't made the jump to pathlib yet, you can fall back to the os.path module. It’s not as object-oriented, but it gets the job done just as reliably:


import os

if os.path.exists("config.json"):
    print("Found it!")

To prevent this from becoming a headache in the future, my biggest piece of advice is to be mindful of the "Time-of-check to time-of-use" (TOCTOU) bug. If your script is running in a multi-threaded environment or a system where other processes might delete files on the fly, checking is_file() isn't a guarantee that the file will still be there when you call open(). If you're building something mission-critical, just bite the bullet and use the try...except block anyway; it’s safer for your data integrity, even if it feels a bit clunky at first.

Hope this saves you from the same three-hour rabbit hole I fell down! Happy coding, and don't let those file paths get the best of you.

別再濫用 try-except 了！優雅檢查檔案是否存在的三種方式

來源：Stack Overflow ↗ · 7349 票

還記得剛轉職進軟體業那陣子，我寫了一個自動化清理 Log 的腳本，為了怕檔案讀不到崩潰，我幾乎每一行都在寫 try-except。當時我自以為防護做得滴水不漏，結果後來要維護時看到滿坑滿谷的 try-except，連我自己都看不下去，那種感覺就像走進一間堆滿雜物的倉庫，連路都找不到，差點崩潰到想直接把電腦砸了。

會遇到這種困擾，其實是因為 Python 的設計哲學鼓勵「請求原諒勝過尋求許可」（EAFP），所以很多新手（包括當年的我）會習慣直接用 try 包住所有可能出錯的檔案操作。雖然這在 Python 裡沒錯，但在檢查檔案是否存在這種情境下，一直觸發錯誤其實很耗效能，而且你的程式邏輯會被過多的異常處理搞得支離破碎，閱讀體驗真的極差。

其實，現在最推薦的做法是使用標準庫裡的 pathlib 模組。這玩意兒真的是我的救星，它把路徑當成物件處理，語法簡潔到不行。你只需要一行程式碼就能搞定：


from pathlib import Path

file_path = Path("my_config.json")

if file_path.exists():
    print("檔案還在，可以放心讀取！")
else:
    print("檔案早就消失了，別再找了。")

如果你是在維護一些比較舊的專案，不想大規模改寫成 pathlib，那用 os.path 也是完全沒問題的。雖然它比較老派，但功能依舊穩健，檢查起來一樣不囉唆：


import os

if os.path.exists("my_config.json"):
    # 做你想做的事
    pass

說真的，要預防這種「過度防禦」的惡夢再次發生，最好的建議就是養成「先檢查、後操作」的習慣，並且只針對真的「無法預期」的錯誤（比如權限不足、硬碟壞軌）才使用 try-except。把該有的路徑檢查寫在前面，你的程式碼邏輯會清晰很多，以後回頭看才不會懷疑人生。

好啦，希望這幾個小撇步能拯救你的程式碼，別再讓 try-except 淹沒你的邏輯囉！
