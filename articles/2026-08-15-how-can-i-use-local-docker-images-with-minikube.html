How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 688 votes

I remember the first time I set up a local Kubernetes cluster, I spent a solid three hours scratching my head because my pods kept stuck in ImagePullBackOff. I was convinced my YAML was broken, but it turned out I was just pushing images to a remote registry and pulling them right back down over my home Wi-Fi like a total amateur. It’s one of those rites of passage every Kubernetes dev goes through, and honestly, the sheer frustration of waiting for a 1GB image to upload just to test a single line of code is enough to make you want to go back to bare-metal deployments.

The reason this happens is simple: Minikube runs inside its own virtual machine or container environment, which is completely isolated from the Docker daemon running on your host machine. When you run docker build on your laptop, that image lives in your local Docker engine. When your Kubernetes pod tries to pull an image, it asks the Minikube node for it. Since the Minikube node doesn't have access to your host’s Docker socket, it looks for the image in the public Docker Hub, fails to find it, and throws an error. It’s not that you’re doing anything wrong; it’s just that the two environments aren't talking to each other by default.

The cleanest way I’ve found to fix this is by pointing your local terminal directly at the Docker daemon inside your Minikube instance. Instead of building locally and pushing to a registry, you run a simple environment command that tells your terminal, "Hey, for the next few minutes, run all these Docker commands inside the Minikube node." If you’re on macOS or Linux, run this command in your terminal:


eval $(minikube docker-env)

Once you’ve run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it’s working by running docker images, and you’ll see the Minikube-specific images listed there. Now, when you apply your Kubernetes manifest, make sure your imagePullPolicy in the deployment YAML is set to IfNotPresent or Never, otherwise, K8s might still try to reach out to the internet to verify the image.


spec:
  containers:
  - name: my-app
    image: my-local-image:latest
    imagePullPolicy: IfNotPresent

To prevent this from becoming a recurring nightmare, I highly recommend adopting a tagging strategy for your local development. Whenever I’m working on a feature, I always tag my local images with :latest or a specific dev tag and keep that imagePullPolicy: IfNotPresent constant in my development manifests. It saves me from ever having to worry about registry authentication or network latency again.

Hope this saves you a few hours of debugging and gets your pods running on the first try. Happy coding!

別再把 Docker Image 推到 Docker Hub 了！Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 688 票

記得剛開始碰 Kubernetes 的時候，我為了測試一個微服務，硬是把 Docker Image 推到了 Docker Hub，改個程式碼又要重新 docker build、docker push，然後在 Minikube 裡 kubectl delete pod 等它重新拉取。那時候網路慢得要死，我看著終端機顯示 ImagePullBackOff 的紅色字樣，真的差點直接把筆電闔上崩潰，心想：「我只是改了一行 log，為什麼要花我十分鐘在等上傳下載？」

其實這問題的根本原因很單純，Minikube 是一個跑在虛擬機（或是容器）裡的獨立環境，它根本看不見你本機電腦 Docker Daemon 裡那堆辛苦 build 出來的 images。對 Minikube 來說，它就像一個被隔離的孤島，你沒告訴它去哪找，它就只能乖乖去遠端的 Registry 抓。

要解決這個痛點，最快的方式就是直接把 Docker 的環境變數「指向」Minikube 內部的 Daemon。只要在終端機輸入這一行指令，你的 docker 指令就會直接跟 Minikube 溝通，而不是你的本機：


eval $(minikube docker-env)

執行完之後，你再試著 docker build -t my-app:v1 .，你會發現這個 image 直接就出現在 Minikube 的肚子裡了。這時候你只要把 Deployment 裡的 imagePullPolicy 設定成 IfNotPresent，Kubernetes 就會發現：「咦，這東西我這有啊，不用抓了」，部署速度瞬間快到飛起。不過要提醒一下，這個設定只對當前的終端機視窗有效，如果你開了新的視窗，記得要再跑一次。

如果你不想每次都要手動切換環境，我個人強烈建議在開發階段直接使用 minikube image load 指令。比如說你已經在本機 build 好了，直接下這個：


minikube image load my-app:v1

這招的好處是它比較乾淨，不會因為你切換了環境變數而導致本機的 docker 指令變得混亂，適合需要同時管理多個專案的時候使用。至於預防措施嘛，最好的辦法就是把這個流程寫進你的 Makefile 或者 taskfile 裡，讓 make build 自動幫你執行 load 的動作，這樣就算以後忘記怎麼設定，交給腳本處理就萬無一失了。

現在我的開發流程順暢多了，再也不用為了等 Image 拉取而浪費生命，希望能幫你們省下不少喝咖啡的時間！
