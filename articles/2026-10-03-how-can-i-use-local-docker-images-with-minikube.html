How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours banging my head against the wall, wondering why my brand-new pod kept sitting in an ErrImagePull state despite the image staring right back at me in my local docker images list. I felt like an absolute amateur, convinced I'd messed up my YAML manifest or some obscure networking setting, when in reality, I was just fighting the fundamental architecture of how container runtimes communicate with the host.

The reason this happens is simple: Minikube runs inside its own isolated environment, usually a virtual machine or a separate container. When you run docker build on your laptop, those images live in your host's Docker daemon. Your Minikube cluster has absolutely no visibility into that local registry. It’s like trying to access a file on your neighbor’s computer; unless you explicitly bridge the gap, the cluster looks at its own internal registry, sees nothing, and tries to reach out to Docker Hub, which is why your deployment fails.

The fastest way I’ve found to fix this is to point your local shell directly at the Docker daemon running inside Minikube. By doing this, any docker build command you run will build the image directly inside the Minikube environment, making it instantly available to your pods. Just run this command in your terminal:


eval $(minikube docker-env)

Once you’ve run that, go ahead and build your image as you normally would: docker build -t my-app:latest .. Now, when you deploy your Kubernetes manifest, make sure your imagePullPolicy is set to IfNotPresent or Never. If you leave it as Always, Kubernetes will try to reach out to a remote registry and fail again. Here is what that looks like in your deployment file:


spec:
  containers:
  - name: my-app
    image: my-app:latest
    imagePullPolicy: IfNotPresent

If you ever need to switch back to your host's Docker daemon, just run eval $(minikube docker-env -u).

To prevent this headache in the future, I highly recommend adopting a tagging strategy early on. Whenever I’m iterating on a project, I always give my local images a specific version tag rather than relying on latest. It saves me from the confusion of wondering whether I’m running the current build or a stale version that Minikube cached days ago.

Hope this saves you some time and spares your keyboard from any unnecessary frustration. Happy coding!

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的 API 修改，我竟然每次都乖乖地把 Image docker push 到 Docker Hub，然後再讓 Minikube 去 pull 下來。那天網路慢到我想哭，看著終端機顯示 ImagePullBackOff 的那一刻，我真的差點把鍵盤砸了，心想：「難道工程師的命運就是要把時間浪費在等待上傳嗎？」

其實問題的核心很單純，Minikube 是一個運行在虛擬機或容器裡的獨立環境，它根本看不到你電腦主機（Host）上的 Docker Daemon。當你在終端機打 docker images 時，你看到的是你電腦裡的倉庫，但 Minikube 的那台虛擬機心裡想的是：「我根本沒聽過這個 Image 啊！」所以當你沒指定 imagePullPolicy: Always 或者網路不通時，它就會直接放棄治療。

後來我終於發現，根本不需要那麼麻煩。最快的方法就是直接告訴 Minikube：「嘿，這東西就在你家裡，不用去外面找了。」只要在編譯 Image 之前，先執行 eval $(minikube docker-env)，接著你的 Docker 指令就會直接對著 Minikube 內部的 Docker Daemon 下手，這時候你再 docker build -t my-app:v1 .，Minikube 就能秒速讀取到這個 Image。


# 讓當前的終端機環境指向 Minikube 的 Docker Daemon
eval $(minikube docker-env)

# 然後直接 build，這樣 Image 就會留在 Minikube 裡面了
docker build -t my-app:v1 .

如果你是用 Docker Desktop 當作 Driver，或者不想每次都切換環境變數，其實還有個更懶人的做法，就是用 minikube image load 指令。這招就是直接把電腦裡的 Image 打包丟進去，雖然稍微慢一點點，但完全不用動腦，也不會影響到你本地環境的其他設定。


# 直接把本地的 image 推進去
minikube image load my-app:v1

為了不讓這種「改一行程式碼要等半小時」的悲劇重演，我現在的做法是統一在 deployment.yaml 裡把 imagePullPolicy 設定成 IfNotPresent。這樣一來，只要我用上述方法把 Image 丟進去過，Kubernetes 就會優先使用本地的複本，徹底解決了那種無謂的網路等待。

學會這招之後，我的開發流程真的順暢太多了，不用再為了測試一個小功能搞得像在進行跨國傳輸一樣。希望這點小撇步能拯救你的開發效率，祝大家寫 Code 順手，Bug 永遠少一隻！
