How to Fix "Hydration failed" Errors in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I encountered the dreaded "Hydration failed" error in React 18. I was pushing a critical update for a client, feeling confident about my new SSR implementation, only to refresh the browser and see my console turn into a sea of red text. I spent three hours—yes, three full hours—staring at my code, convinced I’d broken the laws of physics, only to realize I had a simple date-formatting library generating a different string on the server than it did on the client.

The reason this happens is actually quite logical once you stop pulling your hair out. Next.js renders your component to HTML on the server to give the user a fast, initial view. Once that HTML reaches the browser, React takes over and "hydrates" it by attaching event listeners and turning it into an interactive app. If the HTML the server sent doesn't match exactly what the client-side React code generates during that first render, React throws its hands up and gives you that hydration mismatch error. It’s essentially React saying, "Hey, this isn't the page I was promised," and since it can't guarantee a consistent UI, it forces a re-render.

To fix this, you need to ensure that the content is consistent between environments or delay the rendering of the dynamic content until the component has mounted. I usually reach for a simple useEffect hook to toggle a local state once the component is safely in the browser. By checking if the component has mounted, I can render the "client-only" content only after the initial hydration is complete, effectively silencing the mismatch.


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <span>This renders only on the client!</span>
      ) : (
        <span>Loading...</span>
      )}
    </div>
  );
}

This approach works like a charm because the server renders the "Loading..." state, and the client renders the same, then immediately updates to the dynamic content once it's safe to do so. You’ll stop seeing those annoying errors, and your app will feel much more stable.

To prevent this from becoming a recurring nightmare, my golden rule is to always keep track of environment-dependent logic. If you're using libraries that rely on window, localStorage, or random number generators, force them to wait for the mount. If you aren't sure if something is safe for SSR, put it behind a typeof window !== 'undefined' check or the useEffect pattern above.

I hope this helps you get back to building without the constant console spam. Let me know if you run into any other weird edge cases!

搞定 React 18 Hydration Error：別讓 SSR 把你的 UI 搞瘋了

來源：Stack Overflow ↗ · 341 票

那天我正準備把一個舊專案升級到 Next.js 搭配 React 18，想說這下效能應該會起飛吧？結果一跑起來，瀏覽器 Console 直接噴出一堆紅色警告：「Hydration failed because the initial UI does not match what was rendered on the server」，畫面甚至還會閃爍一下才變正常，當時我真的差點對著螢幕崩潰，心想：「大哥，伺服器渲染出來的 HTML 跟瀏覽器拿到的不一致，這是在跟我開玩笑嗎？」

其實問題的核心很簡單，就是「資訊落差」。伺服器在執行第一次渲染時，它是根據當下的環境（比如沒辦法拿到瀏覽器的 window 物件）來產出 HTML 的，但當 React 在瀏覽器端接手準備進行 Hydration（水合）時，它會拿伺服器給的 HTML 跟自己重新計算出來的 UI 比對。如果這時候你用了什麼依賴瀏覽器環境的變數（比如 new Date()、隨機數、或是 localStorage），兩邊的結果對不上，React 就會發飆，直接無視伺服器給的 HTML，強制在瀏覽器重渲染一遍，這就是為什麼你的畫面會閃爍，甚至效能直接掉漆。

最痛苦的時刻莫過於我對著幾百行的組件除錯，卻發現兇手居然是一個不起眼的 new Date().toLocaleDateString()，這種隱藏在細節裡的「不確定性」，真的是開發者的惡夢。要解決這個問題，其實就是要確保第一次渲染時，伺服器和瀏覽器看到的「起跑線」是一樣的。我後來最常用的解法就是利用 useEffect 來處理這類依賴瀏覽器的邏輯，因為 useEffect 只會在瀏覽器端執行，伺服器根本不會管它。

如果你的組件裡有這種「非同步」或「瀏覽器專屬」的數據，可以試著這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>現在時間是：{new Date().toLocaleString()}</p>
      ) : (
        <p>載入中...</p>
      )}
    </div>
  );
}

這樣一來，在伺服器渲染時，它只會看到「載入中...」，這跟瀏覽器第一次渲染的結果是完全一致的，Hydration 就會順利通過。等到瀏覽器準備好後，useEffect 觸發，畫面才會自動切換成正確的日期，完全無痛解決。

以後遇到這種問題，建議大家在寫 UI 時多問自己一句：「這行程式碼在伺服器上跑，會不會跟瀏覽器不一樣？」只要保持這種警覺，善用 useEffect 或 suppressHydrationWarning（如果有些小誤差真的沒差的話），基本上就不會再被這個錯誤糾纏了。

希望這篇心得能幫你少掉幾根頭髮，下次寫 React 記得心平氣和，Bug 總會解決的！
