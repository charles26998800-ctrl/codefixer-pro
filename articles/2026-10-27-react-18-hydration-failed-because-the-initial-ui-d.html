Solving the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw that dreaded "Hydration failed" warning flashing in my console; I was convinced my entire production build was corrupted. I spent a good four hours down a rabbit hole, meticulously checking my API routes and database queries, only to realize that the culprit was a simple Date object being rendered in a component. It’s one of those infuriating React errors that makes you question your sanity because your code looks perfectly fine in your IDE, but the browser just refuses to play along.

The reason this happens is actually quite logical once you peel back the layers of how Next.js handles server-side rendering. When your app runs on the server, it generates the HTML based on the state at that exact millisecond. If your client-side component tries to render something different—like a random number, a timestamp, or data pulled from localStorage—the React reconciliation process notices the mismatch. React expects the server-rendered HTML and the initial client-side render to be identical. When they don't match, React panics and throws that hydration error because it can't safely bridge the gap between the static HTML and the dynamic application state.

To fix this, I’ve learned that the cleanest approach is to delay the rendering of the mismatched content until the component has officially mounted on the client. I usually create a simple state check to ensure the component only renders its dynamic parts once the client is ready. Here is how I usually handle it in my projects:


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      <h1>My Page</h1>
      {isClient ? (
        <p>Current Time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By adding that isClient flag, I ensure that the server renders the "Loading..." state, which prevents the mismatch. Once the browser takes over, the useEffect fires, updates the state, and the actual time is rendered. It’s a small extra step, but it saves me from those cryptic console warnings that keep me up at night.

If you want to prevent this from happening in the future, my best advice is to audit your dependencies for anything that relies on browser globals like window, document, or localStorage. If you’re pulling data from those sources, don’t try to render it during the initial component execution; always wrap that logic in a useEffect or a custom hook that checks for the client environment first.

Hope this helps you clear those console errors and get back to shipping features. Happy coding!

React 18 Hydration Error：那個讓我熬夜到凌晨兩點的「伺服器與客戶端不對盤」

來源：Stack Overflow ↗ · 341 票

還記得剛升級到 React 18 那陣子，我滿心期待地想體驗 SSR 的效能提升，結果專案一跑起來，瀏覽器 Console 就直接噴出一大串紅通通的 Hydration failed 錯誤。當時我真的差點崩潰，明明程式碼看起來沒什麼毛病，但伺服器渲染出來的 HTML 跟瀏覽器第一次掛載的 DOM 就是對不起來，導致整個頁面閃爍甚至直接崩潰，那種「我明明寫對了，為什麼電腦要搞我」的無力感，真的是工程師生涯中數一數二的痛苦時刻。

其實這個問題的核心概念並不複雜，簡單說就是 React 在執行 SSR 時，伺服器會先產生一份靜態 HTML，接著瀏覽器下載 JS 並嘗試「接手」這份 HTML 的過程（也就是 Hydration）。如果這時候伺服器生成的內容與瀏覽器第一次渲染的內容有一丁點誤差，例如日期時間、亂數，或是瀏覽器因為某些擴充套件修改了 DOM，React 就會因為「對不上帳」而直接拋出錯誤。這在 React 18 之後變得特別嚴格，因為 React 團隊希望確保 UI 的一致性。

要解決這個問題，最直覺的做法就是確保「伺服器」和「客戶端」在初始渲染時拿到一樣的資訊。如果你的組件裡有依賴於環境變數、隨機數或時間戳記的邏輯，記得把它們移到 useEffect 裡處理。因為 useEffect 只會在瀏覽器端執行，這能確保伺服器渲染出來的是一份「乾淨」的初始狀態。我自己通常會寫一個簡單的 useHasMounted hook 來避開這個坑：


import { useState, useEffect } from 'react';

export function useHasMounted() {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  return hasMounted;
}

// 在組件中使用
function MyComponent() {
  const hasMounted = useHasMounted();

  if (!hasMounted) {
    return <div>載入中...</div>; // 伺服器端渲染這個
  }

  return <div>{new Date().toLocaleString()}</div>; // 客戶端掛載後才渲染這個
}

為了預防這種問題再次發生，我現在養成了一個好習慣，就是儘量把會變動的資料處理邏輯放在 useEffect 或者 useLayoutEffect 中，並且在開發環境中特別留意那些會受到瀏覽器行為影響的 UI。只要記住「伺服器端只做靜態渲染，動態邏輯留給客戶端」這個原則，基本上就能避開 90% 的 Hydration 地雷。

希望這些經驗能幫你省下幾個小時的除錯時間，別讓這些紅字毀了你的週末，我們下次見！
