How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours banging my head against the wall because my pods were stuck in an ImagePullBackOff loop, even though I could see my image right there in my terminal using docker images. I felt like I was losing my mind, convinced that Kubernetes was gaslighting me, until I realized that Minikube lives in its own little bubble and has no idea what’s happening on my host machine’s Docker daemon.

The root of the problem is that Minikube runs inside a virtual machine or a separate containerized environment. When you build an image on your laptop, it stays in your host’s Docker daemon. When your Minikube cluster tries to pull an image, it looks inside its own internal registry, not yours. It’s like trying to grab a coffee from your kitchen while you’re sitting in your neighbor's living room; the proximity doesn't matter if you aren't in the same house.

To fix this, you don't need to push your images to Docker Hub or a private registry just to test a one-line code change. The most efficient way I’ve found to handle this is to point your local terminal directly at the Docker daemon running inside the Minikube VM. Just run this command in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build commands you execute will happen directly inside the Minikube environment. You’ll be able to see the image immediately when you run docker images inside the Minikube shell, and your Kubernetes deployments will find the image without any external network traffic. Just remember that this only applies to the current terminal session, so if you open a new tab, you'll need to run it again.

If you find yourself frequently switching between projects and forgetting which environment you're pointing at, my biggest piece of advice is to add a small indicator to your shell prompt. I use a simple script in my .zshrc that checks if the DOCKER_HOST environment variable is set to the Minikube socket and displays a tiny "K8s" icon in my terminal. It saves me from accidentally building images on my host machine and wondering why my pods are still failing to start.

Hope this saves you a few hours of debugging—happy coding!

別再把 Image 推上 Docker Hub 了！Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，我為了測試一個小小的 API 改動，每次都要執行 docker build，接著 docker push 到 Docker Hub，然後再到 Minikube 裡執行 kubectl rollout restart。最慘的一次是網路慢到懷疑人生，光是等那個幾百 MB 的 Image 上傳下載，我就在那邊盯著螢幕發呆了快半小時，心裡只想著：「我只是改了一行 log 啊，為什麼要這麼折磨我？」那種看著 terminal 跑條卡住的痛苦，真的是會讓人想直接把電腦關了回家睡覺。

後來我才搞懂，Minikube 其實是一個跑在虛擬機（或容器）裡的獨立環境，它的 Docker daemon 跟我們本機電腦的 Docker daemon 根本就是兩條平行線。當你興高采烈地在本機 build 出一個 Image，然後在 Deployment yaml 寫上 imagePullPolicy: Always 時，Minikube 跑到遠端去拉取，當然找不到你剛做好的那個寶貝，這就是為什麼它總是噴 ErrImagePull 或 ImagePullBackOff 的原因。

其實解決這件事超級簡單，不需要花錢買私有倉庫，也不用浪費網路頻寬。最直接的方法就是讓你的終端機「暫時切換」到 Minikube 內部的 Docker 環境。你只要在 terminal 輸入這行指令：


eval $(minikube docker-env)

執行完之後，這時候你在本機下的 docker build -t my-app:v1 . 指令，就會直接在 Minikube 的虛擬機裡執行。接著，記得把 Deployment 裡的 imagePullPolicy 改成 IfNotPresent，這樣 Kubernetes 就會乖乖用你剛剛 build 出來的本地版本，而不會跑去外面找了。這招用下去，那個開發速度簡直是飛天般的體驗。

如果你覺得每次都要 eval 很麻煩，或者怕忘記切換，我強烈建議乾脆把這個指令寫進你的 .zshrc 或 .bashrc 裡，或者乾脆養成一個習慣：每次開工前先檢查 docker context。不過最保險的預防方式，還是把 imagePullPolicy: IfNotPresent 這行寫進你的測試用 YAML 模板裡，這樣就算哪天你不小心忘了切換環境，也不會因為 Kubernetes 強迫去拉遠端 Image 而導致部署失敗。

好了，現在趕快去試試看，把那些浪費在等待上傳的時間拿去多喝杯咖啡吧！
