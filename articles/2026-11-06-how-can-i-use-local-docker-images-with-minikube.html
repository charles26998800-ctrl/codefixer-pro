Stop Pushing to Docker Hub: How to Use Local Images with Minikube

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours—yes, three full hours—cursing at my terminal because my pod kept stuck in ImagePullBackOff. I was convinced my YAML was broken, but it turned out I was just dutifully pushing every single tiny code change to Docker Hub, waiting for the upload, and then pulling it back down just to test a one-line change. It was a massive waste of bandwidth and an even bigger waste of my patience.

The reason this happens is actually pretty straightforward: Minikube runs inside its own isolated virtual machine or container. When you run docker build on your laptop, that image lives in your host’s Docker daemon. Minikube, however, is looking at its own internal Docker daemon. It has no idea your image exists on your machine, so it tries to reach out to the internet to find it, fails, and gives up. It’s like trying to grab a coffee from a kitchen that isn’t even in your house.

The cleanest way I’ve found to fix this is by pointing your host’s shell directly at the Docker daemon running inside the Minikube VM. Instead of pushing to a registry, you just run a quick command to sync your environment. You’ll want to run this in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube cluster. Now, when you run your deployment, Kubernetes will see the image locally and start the container instantly. If you’re on a newer version of Minikube, you can also use the image loading utility, which I find even more convenient if I don't want to mess with my shell environment:


minikube image load my-image-name:latest

This command grabs the image from your local Docker engine and pushes it into the Minikube environment, which is a lifesaver if you have multiple terminal tabs open and don't want to re-export your environment variables every time.

To stop running into this in the future, always set your imagePullPolicy to IfNotPresent in your Kubernetes manifest files. This ensures that if the image already exists inside the Minikube node, Kubernetes won't try to go out to the internet to find a newer version, which keeps your local dev loop snappy and prevents those annoying "pull failed" errors.

Hope this saves you from the same three-hour headache I dealt with back in the day. Happy coding!

為什麼 Minikube 總是抓不到我的 Local Docker Image？別再傻傻推送到 Docker Hub 了！

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了測試一個小功能，反覆修改程式碼、打包成 Image，然後再 Push 到 Docker Hub，等候那該死的網路傳輸速度，最後在 Minikube 裡執行 kubectl apply。結果呢？我盯著螢幕看著 ImagePullBackOff 的錯誤訊息，心臟差點沒停掉。當下真的覺得自己像個白癡，明明檔案就在我筆電裡，為什麼還要繞地球一圈才抓得到？那種看著進度條跑不動的焦慮，簡直是開發者的惡夢。

其實這個問題的核心在於架構的隔離。Minikube 預設運行在一個獨立的虛擬機（或是容器）裡，它擁有自己的 Docker Daemon。簡單來說，你的電腦是一個世界，Minikube 又是另一個世界，它們彼此「互不相識」。當你在終端機輸入 docker build 時，Image 是存在你電腦的 Docker Daemon 裡，但 Minikube 的 Pod 在執行時，是向它自己的 Docker Daemon 索取鏡像，兩邊根本沒同步。

我後來發現，其實根本不需要什麼推送到遠端伺服器，最快的方式就是直接把環境變數指過去。只要在執行 build 之前，先執行這行指令：


eval $(minikube docker-env)

執行完這行後，你的終端機就會連上 Minikube 內部的 Docker 環境。這時候你再跑一次 docker build -t my-app:v1 .，這個 Image 就會直接寫進 Minikube 的肚子裡。接著你只需要把 Deployment 設定檔裡的 imagePullPolicy 改成 IfNotPresent，Minikube 就會很聰明地優先使用你剛才 Build 好的本地鏡像，而不會傻傻地跑去網路上抓，這感覺真的爽快多了，節奏感完全回來了！

為了避免以後又因為忘記切換環境而崩潰，我現在習慣在專案裡寫一個簡單的 Makefile。這樣我只要打 make build，它就會自動幫我處理好環境變數切換和打包的步驟。或者如果你用的是比較新版的 Minikube，其實直接用 minikube image load my-app:v1 指令也可以把鏡像丟進去，不用切來切去反而更乾淨。

希望這些經驗能幫你省下那段漫長的等待與無謂的挫折，畢竟工程師的時間應該花在寫程式，而不是跟網路連線搏鬥啊！下次碰到類似的坑，記得深呼吸，通常問題都比你想像中簡單多了。
