How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 689 votes

I still remember the first time I set up a local Kubernetes cluster with Minikube. I spent three hours banging my head against the wall because my pods kept stuck in ImagePullBackOff, despite me staring directly at the local image in my terminal. I felt like I was losing my mind, convinced I had mistyped the tag or the image name, only to realize that Minikube and my host machine were living in two completely different universes.

The reason this happens is actually quite simple once you peek under the hood: Minikube runs inside its own isolated virtual machine or container. When you build an image on your host machine, it lives in your host's Docker daemon. Minikube, however, has its own internal Docker daemon. It doesn't look at your host's library, so when you tell Kubernetes to pull my-app:latest, it blindly checks the public Docker Hub, fails to find it, and throws a tantrum. It’s a classic case of the "it works on my machine" syndrome, but for your cluster.

To fix this, you don't need to push your code to a remote registry just to test a tiny change. The most efficient way I’ve found to handle this is by pointing your local Docker environment directly at the Minikube daemon. You can do this by running a single command in your terminal before you build your image:


eval $(minikube docker-env)

Once you run that, your terminal is effectively "hooked" into the Minikube VM. Now, when you run docker build -t my-app ., the image is built directly inside the Minikube environment. Kubernetes will see it immediately because it's already sitting right where it needs to be. Just remember that if you open a new terminal tab, you’ll need to run that command again, as it only affects your current shell session.

If you’re using the newer Minikube drivers or just want a more modern approach, you can also use the minikube image load command. This is honestly cleaner if you don't want to mess with environment variables. You just build your image locally like you always do, and then push it into the cluster with:


minikube image load my-app:latest

This effectively copies the image from your host daemon into the Minikube environment. It takes a few extra seconds, but it’s incredibly reliable and avoids any weird side effects with your shell environment.

To keep your sanity, my biggest tip is to always set your Kubernetes deployment's imagePullPolicy to IfNotPresent. By default, if your tag is latest, Kubernetes might try to pull it from the web every time, which is exactly what you’re trying to avoid. With IfNotPresent set, K8s will see your local image and skip the registry entirely.

Hope this saves you those three hours of frustration I had to deal with. Happy coding, and may your pods stay in the Running state!

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的神級技巧

來源：Stack Overflow ↗ · 689 票

剛開始玩 Kubernetes 的時候，我真的差點崩潰。當時我寫好了一個微服務，想說在 Minikube 跑跑看，結果為了測試一個小小的 bug，我得先 docker build，然後 docker push 到 Docker Hub，再等 Minikube 把那個肥大的 image 下載回來。光是這段「上傳、下載」的過程，我就不知道浪費多少時間在盯著終端機發呆，甚至還因為網路不穩，搞到最後整個人火氣都上來了，心想：「我明明就在同一台電腦上，為什麼要搞得像跨國傳輸一樣麻煩？」

其實這背後的原因很單純，因為 Minikube 本身是一個跑在虛擬機（或是容器）裡的獨立環境，它根本看不見你宿主機（Host）裡面的 Docker daemon。對 Minikube 來說，它是一個封閉的小世界，你電腦裡的 Docker 環境對它而言就是外太空，所以你沒指定路徑，它當然找不到你的 image，只能乖乖去遠端倉庫抓。

如果你不想再經歷那種「改一行程式碼、等五分鐘下載」的地獄，其實最快的方法就是讓 Minikube 直接用你當前的 Docker 環境。只要在執行 kubectl 之前，先跑這行咒語：


eval $(minikube docker-env)

執行完之後，你的終端機就會連上 Minikube 內部的 Docker daemon。這時候你在這個視窗執行 docker build -t my-app:latest .，這個 image 就會直接進到 Minikube 的肚子裡。接著你的 Kubernetes YAML 記得把 imagePullPolicy 改成 IfNotPresent，這樣它就不會笨笨地跑去遠端抓，直接用你剛才編譯好的版本，速度快到讓你懷疑人生。

要預防這種慘劇再次發生，我建議大家養成一個習慣，就是把這個指令直接寫進你的 .zshrc 或 .bashrc 裡，或者乾脆寫在開發用的 Makefile。像我自己就會在 Makefile 裡加一個 build-local 的指令，把這兩個步驟綁在一起，這樣以後要部署測試時，只要下個 make build-local 就搞定，再也不用擔心網路慢或是權限問題了。

以後遇到這種「本地開發」的坑，千萬別傻傻地一直往 Docker Hub 推，把時間省下來去喝杯咖啡還比較實在！
