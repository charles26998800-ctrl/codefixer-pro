How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27240 votes

I still remember the first time I accidentally committed a massive .env file containing my local database credentials to a repo. My heart sank, I broke into a cold sweat, and I spent a good two hours panicking while searching for a way to delete the commit before the automated CI/CD pipeline picked it up and deployed my secrets to the world. It’s a rite of passage for every developer, but that sinking feeling never really goes away until you learn the magic of the git reset command.

The reason this happens is usually just a simple lapse in focus—you ran git add . when you meant to be more selective, or you committed code that wasn't quite ready for prime time. Git is designed to be a ledger of your work, and by default, it treats every commit as a permanent entry in that history. When you make a mistake, Git doesn't automatically know you "didn't mean it," so it keeps the commit right there in your branch history. As long as you haven't pushed those changes to the remote server, you're in the clear; you’re basically just editing your own local diary before you show it to the rest of the team.

To fix this, I always reach for git reset. The command you need depends entirely on whether you want to keep your file changes or wipe them out entirely. If you want to undo the commit but keep your work in your staging area so you can fix the files and commit them again, you’ll want to run a soft reset. This is my go-to move because it’s low-risk:


git reset --soft HEAD~1

This command moves your branch pointer back by one commit, but leaves all the files from that commit staged and ready for a new, corrected commit. If you realized you committed a total disaster and you just want to throw those changes into the trash, you can use the hard flag instead. Be careful with this one, because it will permanently delete any uncommitted work in those files:


git reset --hard HEAD~1

If you just want to unstage the files but keep the changes in your working directory so you can choose exactly what to include next time, use git reset HEAD~1 without any flags. It’s the perfect middle ground for when you realize you included too many files in a single commit.

To prevent this from becoming a recurring headache, I’ve started using the -p or "patch" flag with my add command. Instead of blindly running git add ., I use git add -p. It forces me to review every single hunk of code I’m staging, which acts as a built-in safety net against accidentally committing files I didn't intend to touch. It adds a few seconds to my workflow, but it’s saved me from countless "oops" moments.

Hope this saves you some stress the next time you hit a snag. Happy coding and may your git history always stay clean!

手殘把垃圾塞進 Git 了？別怕，這招教你神不知鬼不覺地反悔

來源：Stack Overflow ↗ · 27240 票

說真的，我第一次遇到這狀況時，心臟真的停了半拍。那天我趕著下班，沒檢查就直接 git commit，結果才發現把一堆測試用的 log 檔跟不該公開的設定檔全塞進去了，甚至還包含了一個剛寫好一半、完全不能跑的廢棄功能。看著終端機顯示 commit 成功的訊息，我當時真的很想直接把筆電闔上裝作沒事發生，那種「完了，我是不是要把整個專案重拉一次」的絕望感，真的會讓人想原地離職。

其實這背後的道理很單純，Git 就像是一個時光紀錄器，它記錄了你每一個版本的狀態。當你執行 commit 時，Git 只是把這些改變「鎖」在本地的儲存庫裡。只要你還沒執行 git push 把這些髒東西推送到遠端伺服器，你的這些變更其實都還在你的掌握之中，Git 只是把它們放在一個叫做 HEAD 的指標後面，我們只要把指標往回撥，這些 commit 就會像沒發生過一樣消失。

如果你只是想撤銷最近的一次 commit，但又想保留剛剛修改過的那些檔案內容（這樣你才能繼續改），這招 git reset --soft HEAD~1 是我的救命稻草。執行這行指令後，那個 commit 會被拆掉，但你改動過的檔案會直接回到「已暫存（Staged）」的狀態，你只要把那些垃圾檔案 git reset 掉，重新調整就好。如果你的情況更糟，連檔案都改爛了，想把一切恢復成 commit 之前的清白模樣，那就用 git reset --hard HEAD~1，這會直接把所有改動炸掉，還你一個乾淨的目錄。不過要小心，這招是真的會把你的心血結晶直接刪除，用之前記得確認你真的不想留戀那些程式碼了。

為了避免這種心跳加速的時刻，我後來養成了一個習慣，就是在敲下 git commit 之前，一定會先來個 git status 檢查到底有哪些檔案要進去。真的不放心的話，我推薦大家去裝一些視覺化的 Git 工具，或者乾脆設定一個 alias，強制自己在 commit 前跑一下 git diff --cached。看著螢幕上顯示的差異，確認沒有不該出現的檔案，再去執行 commit，這幾秒鐘的檢查真的能省下後面一小時的除錯時間。

以後如果不小心又手殘，記得冷靜深呼吸，Git 的時光機功能強大到讓你懷疑人生，千萬別直接把整個專案資料夾刪掉重來啊！
