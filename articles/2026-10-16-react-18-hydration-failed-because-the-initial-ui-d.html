Solving the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours deep into a late-night debugging session, convinced I had broken the entire build pipeline, only to realize I was just rendering a localized timestamp that changed the millisecond the page hit the client. I stared at my screen for a good ten minutes, questioning my life choices, before I finally understood that React is just a bit of a perfectionist when it comes to the server and client being on the same page.

The root cause of this headache is actually pretty simple once you pull back the curtain. When you use Next.js, the server generates the initial HTML of your page and sends it to the browser. Once that HTML arrives, React takes over to "hydrate" it, attaching event listeners and making it interactive. If the HTML the server sent doesn't perfectly match what React generates on the client during that first render, React panics and throws a hydration error. This usually happens because of dynamic data like Date.now(), random numbers, or browser-only APIs like localStorage that simply don't exist in the Node.js environment during the initial build.

To fix this, I’ve learned that you need to delay the rendering of that dynamic content until the component has actually mounted in the browser. I usually handle this by using a state variable to track the mounting status. By initializing the state as false and flipping it to true inside a useEffect hook, I ensure that the problematic code only runs on the client side, where the environment is consistent.


import { useState, useEffect } from 'react';

export default function MyDynamicComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Now this will only render after hydration */}
      The current time is: {new Date().toLocaleTimeString()}
    </div>
  );
}

The best way to prevent this in the future is to keep a close eye on your useEffect hooks and any global variables that rely on browser-specific objects. If I find myself reaching for window or document inside a component, I immediately wrap the usage in a check or a custom hook to ensure it’s only firing after the client-side mount. It’s a small extra step, but it saves me from those late-night debugging marathons.

Hope this clears up the confusion and saves you some time. Happy coding, and may your hydration always be successful!

被 React Hydration Error 搞到懷疑人生？其實兇手通常只有這幾個

來源：Stack Overflow ↗ · 341 票

那天我正準備把剛寫好的 Next.js 專案部署上線，信心滿滿地打開瀏覽器預覽，結果一進到控制台（Console），整排紅字直接炸開，那個「Hydration failed」的錯誤訊息簡直比我的期末考成績還刺眼。我盯著螢幕看了半小時，心想：「我程式碼明明寫得好好的，為什麼伺服器渲染出來的 HTML 跟瀏覽器剛跑起來的 React 元件長得不一樣？」當時真的差點把鍵盤摔了，那種「明明眼看要收工卻被卡住」的無力感，相信每個開發者都懂。

其實這問題的根本原因說穿了，就是 React 在「搞分裂」。簡單來說，Next.js 先在伺服器端把 HTML 給渲染出來傳給瀏覽器，但瀏覽器接手後，React 發現自己跑出來的結果跟伺服器給的不一樣。這通常是因為你用到了一些「只有瀏覽器才有的東西」。最常見的罪魁禍首就是 new Date()、隨機數產生器，或是根據使用者系統設定（像是 window.matchMedia）來動態改變 UI 的邏輯。因為這些數值在伺服器跑的時候是一個樣，到了瀏覽器又變成了另一個樣，React 一比對發現「咦？怎麼對不上？」，它就會直接報錯並選擇放棄治療，乾脆把整個 DOM 重刷一遍。

後來我發現，最直接的解決方法就是確保伺服器跟瀏覽器的第一次渲染必須「完全同步」。如果你的 UI 真的必須依賴瀏覽器環境的資料，那就乾脆等元件掛載（Mount）完成後再渲染。我通常會寫一個簡單的 useEffect 來處理這種情況，只要確保狀態在元件掛載後才更新，就能避開這個坑。程式碼大概長這樣：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>現在時間是：{new Date().toLocaleTimeString()}</p>
      ) : (
        <p>載入中...</p>
      )}
    </div>
  );
}

要預防這種鳥事再次發生，最好的習慣就是把「會變動的瀏覽器原生 API」跟你的 UI 渲染邏輯嚴格拆開。盡量不要在元件的最外層直接去撈 window 或 localStorage，而是把它們封裝在 useEffect 或者自定義的 Hook 裡。只要讓伺服器渲染時拿到的是一個「預設值」，等瀏覽器接手後再透過 Hook 更新成實際數據，Hydration 就再也不會來煩你了。

搞定這個 bug 之後，終於可以安心去泡杯咖啡休息一下，希望大家都能順利避開這些讓人抓狂的報錯！
