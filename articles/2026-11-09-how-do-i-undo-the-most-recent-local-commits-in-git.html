How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27251 votes

I’ll never forget the first time I accidentally committed a massive .env file containing my local database credentials to a repo. I was halfway through a third cup of coffee, feeling like a genius, until I realized I’d just pushed my secrets into the local history; I spent a solid two hours sweating bullets, convinced I’d just compromised the entire production environment before I even finished my morning stand-up. It’s a rite of passage for every developer, and if you’re reading this, you’ve likely just had that same sinking feeling in your gut.

The root cause of this panic is usually just a simple disconnect between the staging area and the commit history. When you run git commit, you’re essentially taking a snapshot of everything currently in your index and locking it into the project history. If you realize immediately afterward that you included a file you didn’t mean to, or if you simply made a typo in the commit message, Git doesn't automatically know you made a mistake—it treats every commit as a intentional milestone. The good news is that because you haven't pushed to the remote server yet, your local history is still completely under your control and easy to rewrite.

To fix this, I always reach for git reset. If I want to undo the commit but keep the changes I made to the files so I can fix them, I use the --soft flag. This moves the HEAD pointer back one step, effectively "undoing" the commit while leaving all your hard work sitting in your staging area, ready for a follow-up commit.


git reset --soft HEAD~1

If you realize the changes were a total disaster and you just want the files to go back to exactly how they were before you started working, I use the --hard flag instead. Just be careful with this one—it’s the "nuclear option" because it nukes your local changes, and there’s no easy way to get that code back once you run it.


git reset --hard HEAD~1

I’ve learned the hard way that the best way to prevent this specific headache is to adopt a strict "git status" habit. Before I run any commit command, I force myself to type git status one last time just to see exactly what’s green and ready to go. It adds two seconds to my workflow, but it’s saved me from countless "oops" moments where I accidentally added a build folder or a config file I didn't intend to track.

Hopefully, this gets you back on track without too much stress. Happy coding, and try to keep those commits clean!

該死的 Git commit！還沒推送到遠端，怎麼把剛才那次 commit 救回來？

來源：Stack Overflow ↗ · 27251 票

記得有一次，我趕著下班去接小孩，心急火燎地把程式碼 commit 進去，結果一回頭才發現，我竟然把一堆還在測試階段的 debug log 和亂七八糟的設定檔全都給 commit 了，甚至連不該放進去的 API 金鑰都差點一起打包。當下那個心跳加速的感覺真的超崩潰，腦袋瞬間一片空白，心想這要是推送到公司的主分支，明天肯定要被主管叫去「喝咖啡」，那種冷汗直流的痛，我到現在都還記得。

其實這個問題會發生，通常就是因為我們對 Git 的指標機制還沒那麼熟。當你在本機執行 git commit 時，Git 其實只是把這些變動記錄在你的本機資料庫裡，它就像是在你的開發歷史上蓋了一個章。因為你還沒 git push，這個「章」還在你的領土範圍內，所以我們完全有權力把它撕掉、重來，根本不需要擔心會影響到遠端伺服器上的同事。

當時我冷靜下來後，發現其實只要用 git reset 就能解決，這招真的救了我好幾次。如果你只是想撤銷最後一次 commit，但想保留你寫好的檔案變動（畢竟還要改嘛），你可以直接打：


git reset --soft HEAD~1

這樣一來，那個 commit 的紀錄會消失，但你剛才改的那些檔案會留在暫存區（Staging Area），你可以直接修正後再重新 commit。但如果你的情況更慘，發現剛才做的根本就是垃圾，想把檔案通通還原到 commit 之前的狀態，那就用這個狠一點的指令：


git reset --hard HEAD~1

這招下去，所有改動會直接灰飛煙滅，請務必確認你真的不要那些程式碼了再按 Enter，不然真的會欲哭無淚。

為了避免下次再發生這種「手滑」的慘劇，我現在養成一個習慣：在 commit 之前，一定會先跑一次 git status 看一下到底有哪些檔案被選中，或者乾脆用 git diff --cached 再掃一眼。甚至如果你真的很常忘記，可以考慮安裝一些 Git GUI 工具，視覺化看到底哪些檔案會被送進去，這樣真的會安全很多。

希望這招能幫你從崩潰邊緣拉回來，以後 commit 前多看一眼，心臟會健康很多。
