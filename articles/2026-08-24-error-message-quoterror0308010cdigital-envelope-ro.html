How to Fix the "digital envelope routines::unsupported" Error in React

Source: Stack Overflow ↗ · 2572 votes

I still remember the first time this error popped up on my terminal. I had just upgraded my local Node.js environment to version 17, feeling all productive and updated, only to have my entire React project refuse to start with that cryptic "digital envelope routines" message. I wasted a good two hours convinced I’d somehow corrupted my node_modules or messed up my IntelliJ configuration, constantly nuking and reinstalling my project before I realized it was a fundamental shift in how Node handles security.

Essentially, this happens because Node.js v17 and newer moved to OpenSSL 3.0. This update introduced stricter security standards that don't play nice with the older hashing algorithms used in many popular Webpack versions and legacy React scripts. Your project is trying to use an algorithm that Node now considers "unsupported," and it throws this tantrum to protect you from what it perceives as a security risk, even though it's usually just a compatibility mismatch in your build tools.

The quickest way I’ve found to resolve this—without downgrading your entire Node installation—is to force Node to use the legacy OpenSSL provider. You can do this by setting an environment variable before your start script runs. If you’re on macOS or Linux, you’ll want to modify your package.json file like this:


"scripts": {
  "start": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

If you’re working on a Windows machine, the syntax is slightly different because of how the command prompt handles environment variables:


"scripts": {
  "start": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

If you don't want to mess with your package.json every time, you can also just run the command directly in your terminal before starting your dev server, or add it to your global shell configuration if you’re tired of typing it out.

To keep this from biting you again, I’ve learned to always check the Node version compatibility of my dependencies before jumping on the latest LTS release. Keeping a tool like nvm (Node Version Manager) installed is a lifesaver, as it lets you toggle between Node versions on a per-project basis whenever you run into these weird build-time ghosts.

Hope this saves you a bit of the headache I went through. Happy coding and may your builds stay green!

又被 Node.js 版本陰了？解決 error:0308010C 的崩潰時刻

來源：Stack Overflow ↗ · 2572 票

記得那天我剛接手一個舊專案，想說先跑個 npm start 確認環境沒問題，結果終端機螢幕瞬間噴出一大串紅通通的錯誤訊息，最後卡在那個鬼魅般的 digital envelope routines::unsupported。當時我真的差點把咖啡噴在螢幕上，心想：「我明明什麼都沒動啊，為什麼昨天還能跑的程式，今天就直接原地爆炸？」那一刻我盯著螢幕發呆了十分鐘，心裡充滿了懷疑人生，感覺就像是剛裝好的系統被什麼隱形力量給詛咒了一樣。

其實這問題的罪魁禍首就是 Node.js 的升級。簡單來說，Node.js 17 版本之後引入了新的 OpenSSL 3.0，這玩意兒對加密演算法的安全性要求變高了，但我們很多舊專案用的 Webpack 4 或者一些依賴套件，還在用舊版的加密演算法（比如 MD4）。當 Node.js 發現這些「老古董」演算法時，就會直接跳出來大喊：「這不安全，我不准你跑！」這就是為什麼你會看到那串看起來很專業、其實只是在鬧脾氣的錯誤代碼。

我當時試過重灌 node_modules、刪掉 package-lock.json，結果通通沒用，最後才發現只要在啟動指令前加個環境變數就能繞過檢查。如果你跟我一樣急著要讓專案跑起來，直接在 package.json 的 scripts 區塊動點手腳就行了。如果是 Windows 使用者，請用 set，像這樣：


"scripts": {
  "start": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

如果你是在 macOS 或 Linux 跑專案，寫法則是加上 export：


"scripts": {
  "start": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

這樣設定之後，等於是告訴 Node.js 說：「拜託，讓我用舊版的加密機制吧」，專案通常就能順利起飛了。

說真的，這種環境問題最磨人，為了避免下次換台電腦又崩潰一次，我現在養成了一個好習慣，就是嚴格使用 .nvmrc 或 .node-version 檔案來鎖定專案的 Node 版本。只要確保團隊每個人開發環境的 Node 版本一致，這種「我的電腦可以跑，你的卻不行」的靈異事件就能少掉一大半。

希望這招能救你脫離苦海，別再為這種環境設定氣到長皺紋啦！
