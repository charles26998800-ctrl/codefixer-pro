Fixing React 18 Hydration Errors in Next.js: A Practical Guide

Source: Stack Overflow ↗ · 341 votes

I remember the first time I saw the "Hydration failed" error in a React 18 project; I was staring at a perfectly fine-looking dashboard, only to watch it flicker and crash the moment the JavaScript bundle kicked in. I spent three hours refactoring my entire component tree, convinced I’d broken some complex state logic, only to realize it was just a tiny, innocent Date object causing the mismatch. It’s one of those bugs that makes you want to throw your monitor out the window because the UI looks identical to the naked eye, yet React is screaming that it’s fundamentally different.

At its core, this error is React’s way of saying that the HTML generated on your server doesn't match the HTML generated by the client during the initial render. When you use Server-Side Rendering (SSR) in Next.js, the server sends a static snapshot of your page. Once that reaches the browser, React tries to "hydrate" it by attaching event listeners and making it interactive. If your server-side code uses something that changes on the fly—like Math.random(), a local storage check, or even just the current timestamp—the client-side React tree will differ from the server's static output. Since the DOM tree doesn't match the virtual DOM snapshot, React gives up and throws the error to prevent silent UI bugs.

To fix this, you need to ensure that the initial render is identical across both environments. The most common solution is to defer the rendering of the dynamic content until the component has actually mounted on the client. I usually handle this by using a simple useEffect hook to track the mounting state. If the component hasn't mounted yet, I return a fallback or null, which forces the client to wait for the JavaScript to execute before showing the dynamic part.


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a simple skeleton loader
  }

  return (
    <div>
      {/* This only renders after hydration is complete */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
};

By adding that isMounted check, you’re telling React, "Hey, don't worry about matching these specific dynamic parts during the first pass; let the client handle it once it's ready." This keeps your server and client in sync and makes that nasty red console error disappear instantly.

The best way to prevent this in the future is to keep your server-side logic strictly deterministic. Whenever you find yourself reaching for a browser-only API like window or localStorage inside the body of a component, try to wrap that logic in a custom hook or a client-side-only component. If you can keep your server-rendered HTML clean and predictable, you’ll avoid these hydration headaches entirely.

Hope this saves you a few hours of debugging time this week. Happy coding and let me know if you run into any other weird React quirks!

崩潰！React 18 Hydration Error 到底在搞什麼鬼？

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地把專案搬到 Next.js 上，結果一打開瀏覽器，控制台（Console）那紅通通的一片報錯直接讓我原地石化。螢幕上寫著：「Hydration failed because the initial UI does not match what was rendered on the server」，我當時心想：「大哥，我明明什麼都沒改啊，為什麼伺服器渲染出來的東西跟瀏覽器長得不一樣？」那種明明寫得好好的程式碼，卻因為莫名其妙的同步問題導致 UI 一片空白，真的會讓人想把鍵盤直接丟出窗外。

這問題的根本原因，其實就是 React 18 對「一致性」的要求變嚴格了。簡單來說，Next.js 會先在伺服器端把 HTML 畫出來傳給瀏覽器，然後瀏覽器再接手把它「掛載（Hydrate）」成互動式的 App。如果你的程式碼裡用了 new Date()、隨機數 Math.random()，或是根據瀏覽器特定的 window 物件來決定 UI 顯示什麼，那伺服器算出來的結果跟瀏覽器算出來的一定會有誤差。React 一比對發現：「咦？伺服器給我的跟瀏覽器現在算的長得不一樣」，為了保險起見，它乾脆直接報錯給你看。

我後來發現，最常見的兇手就是這些會「隨環境變化」的邏輯。要解決它，最快的方法就是讓 React 知道這個元件「先不要在伺服器渲染」，等到瀏覽器載入完畢後再顯示。我通常會寫一個簡單的 useMounted Hook，或是乾脆用 useEffect 來控制渲染時機。只要確保這個元件只在客戶端渲染，問題就迎刃而解了：


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) return null; // 或者你可以放個 Loading spinner

  return <div>這裡放那些會導致錯誤的邏輯，例如 {new Date().toLocaleString()}</div>;
};

為了避免哪天又踩到這種雷，我現在養成一個習慣：只要涉及到瀏覽器特有 API（像是 localStorage、window.innerWidth）或是會變動的日期時間，我一律會先把元件包在判斷式裡，或是直接封裝成 Client Component。盡量不要在元件的頂層直接使用這些不穩定的數值，這樣就能避開大部分的 Hydration 惡夢。

搞定這個之後，看著控制台終於變回乾淨的白色，那種心情真的比喝到冰美式還爽。希望這些經驗能幫你省下幾個熬夜抓蟲的夜晚，大家一起加油吧！
