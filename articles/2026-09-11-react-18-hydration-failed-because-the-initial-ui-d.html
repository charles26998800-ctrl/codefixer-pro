Fixing the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" warning pop up in my console after upgrading a project to React 18. I spent three hours staring at my perfectly valid-looking component, convinced that React had finally lost its mind, only to realize I was just being careless with my dynamic date rendering. It’s one of those infuriating bugs that makes you feel like you’re losing your grip on reality, especially when the code looks absolutely identical in both the editor and the browser.

Essentially, this error happens because the HTML generated by your server doesn't match the initial HTML rendered by your browser. Next.js does a "dry run" during hydration where it compares the DOM structure it received from the server against the virtual DOM it calculates on the client. If your server renders a timestamp or a random value that changes by the time the browser parses the JavaScript, React panics because the nodes don't align. It’s a classic mismatch between "what I thought I sent" and "what I’m seeing now."

I finally solved this by ensuring my dynamic content is only rendered after the component has mounted. Since the server has no concept of the client's current time or specific browser environment, you have to tell React to wait for the client-side lifecycle before injecting those variable pieces of UI. I usually handle this by using a simple useEffect hook to toggle a state variable, which forces the component to render the dynamic part only on the client side.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    // Render a placeholder or nothing at all during SSR
    return null; 
  }

  return (
    <div>
      {/* Now this will only render on the client, avoiding the mismatch */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

The best way to prevent this from ruining your day is to avoid using browser-only APIs like window, localStorage, or new Date() directly in your render logic. If you absolutely need to use them, always wrap that specific logic in a client-side check or a useEffect hook to ensure the server and client stay in sync during that initial render phase. Keeping your rendering pure and predictable is the secret sauce to avoiding these headaches entirely.

Hope this saves you from pulling your hair out as much as I did. Good luck debugging!

React 18 Hydration Error：那個讓我熬夜到凌晨兩點的「UI 不一致」惡夢

來源：Stack Overflow ↗ · 341 票

還記得那天晚上，我正信心滿滿地要把舊專案升級到 Next.js 和 React 18，想說享受一下 SSR 的極致效能，結果打開瀏覽器控制台一看，整排紅通通的 Hydration failed 錯誤訊息直接把我從椅子上嚇醒。最讓我崩潰的是，網頁看起來明明就長得一模一樣，為什麼 React 就是堅持說伺服器端渲染的結果跟瀏覽器端不一樣？我當時盯著螢幕，眼球差點要掉出來，心想：「大哥，我程式碼就長這樣，你是哪裡看走眼了？」

其實這問題的根源說穿了就是「資訊不對稱」。當 Next.js 在伺服器端生成 HTML 時，它會根據當下的環境（比如伺服器時間、隨機產生的 ID、或是瀏覽器特有的 API）渲染出一份結構。等到這份 HTML 傳到瀏覽器，React 開始執行 hydrate 動作時，它會再次執行同樣的程式碼，如果這時候因為環境變了、時間跳了一秒、或者隨機亂數變了，導致瀏覽器產生的 DOM 樹跟伺服器給的不一樣，React 就會直接大崩潰，報出這個經典錯誤。這真的是開發者最不想看到的畫面之一，因為它通常意味著你的組件在兩個環境下的執行結果對不起來。

我當初花了整整兩小時才抓到兇手，原來是我在組件裡用了 new Date().toLocaleDateString()。因為伺服器跟瀏覽器的時區或執行時間微小差異，導致渲染出的文字長度或內容對不上，這簡直是隱形刺客。解決方法其實很單純，就是確保在「第一次渲染」時，雙方都拿到一樣的資料。我通常會利用 useEffect 來處理這類只存在於瀏覽器的邏輯，像這樣：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? new Date().toLocaleDateString() : 'Loading...'}
    </div>
  );
}

透過這種方式，伺服器第一次渲染時會統一輸出「Loading...」，等到瀏覽器接手後才執行真正的時間渲染，這樣就不會發生不一致的問題了。除此之外，我也強烈建議大家在寫組件時，養成檢查是否使用了 typeof window === 'undefined' 的習慣，或者乾脆確保所有依賴外部狀態的邏輯都延後到 useEffect 裡執行。

以後只要看到控制台跳出這類的錯誤，先別急著懷疑人生，通常都是這些「只有瀏覽器才知道」的小東西在搗蛋。希望這篇筆記能幫你省下幾個小時的睡眠，咱們下次踩坑再見啦！
