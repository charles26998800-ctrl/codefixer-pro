Fixing the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in React 18; I was three hours deep into a late-night debugging session, convinced my API routes were broken or my database connection had vanished. After refreshing my browser for the twentieth time and double-checking every single line of my server-side logic, I realized the data was perfectly fine, but my UI was essentially having an identity crisis. It’s one of those bugs that makes you question your sanity for a second, but it usually boils down to a classic mismatch between what the server thinks the world looks like and what the browser sees the moment it wakes up.

The root of this problem is actually quite logical once you stop pulling your hair out. When you’re using Server-Side Rendering (SSR), React generates the initial HTML on the server and sends it to the client. Once the browser receives that HTML, it tries to "hydrate" it by attaching event listeners and making it interactive. If the component renders something different on the client than it did on the server—like a random number, a date, or even a browser-specific check like window—React freaks out. It compares the server-generated DOM to the client-rendered output, sees they don't match exactly, and throws the hydration mismatch error to prevent potential UI bugs.

To fix this, you need to ensure that the content is identical during the initial render pass. I usually solve this by using a useEffect hook to trigger client-side-only code. Since useEffect only runs after the component has mounted on the client, it’s the perfect place to handle logic that involves the browser environment. For example, if you’re trying to render a date or a component that relies on window or localStorage, keep it hidden until the component is fully mounted.


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This only shows up after hydration: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By wrapping your client-only logic in this isClient check, you guarantee that both the server and the client start with the exact same "Loading..." state. Once the browser takes over, the state updates, and your dynamic content renders safely without triggering that annoying console error.

The best way to prevent this from happening again is to get into the habit of treating your components as "server-first." Whenever I’m writing a component that might need browser-specific APIs, I automatically ask myself, "Does this need to be visible on the very first paint?" If the answer is no, I force it to wait for the client-side mount, which saves me a ton of headaches during development.

Hope this clears things up and saves you from the same late-night frustration I dealt with. Happy coding!

被 React Hydration Error 搞到懷疑人生？其實這不是你的錯

來源：Stack Overflow ↗ · 341 票

那天凌晨兩點，我正盯著螢幕修一個 Next.js 的 SSR 專案，原本以為大功告成準備收工了，結果打開瀏覽器控制台一看，整排紅通通的「Hydration failed」警告直接跳出來，那一刻我真的是差點把咖啡噴在鍵盤上。明明程式碼看起來邏輯完全沒問題，伺服器渲染出來的 HTML 卻跟瀏覽器第一次跑 React 的結果對不上，那種「我明明寫得沒錯，為什麼你就是不聽話」的無力感，真的會讓人崩潰到想直接把電腦關掉去睡覺。

其實說穿了，Hydration 失敗的原因很單純，就是伺服器（Server）跟客戶端（Client）對「初始畫面」的認知有落差。React 在渲染時，會先要求兩邊產出的 DOM 結構必須一模一樣，如果你的程式裡用了 Date.now()、隨機數，或是像 typeof window !== 'undefined' 這種只有瀏覽器才有的判斷，伺服器因為拿不到這些數值，產出的 HTML 就會跟瀏覽器跑出來的不一樣。最常見的痛苦時刻就是：你在開發環境明明沒事，一上線或是做完 Build 之後，網頁直接閃爍一下，甚至因為結構錯誤導致樣式跑版，那種「明明開發時好好的」感覺真的很想罵髒話。

我後來發現最笨的解法就是硬幹，但其實只要讓 React 稍微「緩一下」就能解決。我通常會用一個小技巧，就是透過 useEffect 來延遲渲染那些只在客戶端才需要的內容。與其讓伺服器去猜那些不確定的變數，不如直接告訴 React：「嘿，先幫我留個空位，等瀏覽器準備好再把東西塞進去」。程式碼大概長這樣：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <span>現在時間是：{new Date().toLocaleTimeString()}</span>
      ) : (
        <span>載入中...</span>
      )}
    </div>
  );
}

這樣處理之後，伺服器渲染時只會看到「載入中...」，不會去嘗試計算那些會導致錯誤的時間差，等瀏覽器執行 useEffect 後才會顯示正確內容，問題瞬間就沒了。

要預防這種鳥事再次發生，最簡單的建議就是：保持你的 UI 元件儘量純淨（Pure）。如果真的必須使用瀏覽器特有的 API，請養成習慣把這些邏輯包在 useEffect 裡，或者乾脆限制它們只在 isClient 為 true 時才執行。只要讓伺服器和瀏覽器在第一次對接時達成共識，這類莫名其妙的錯誤自然就會少很多。

好了，希望這招能救你脫離苦海，趕快把這個雷排掉，早點關機休息吧！
