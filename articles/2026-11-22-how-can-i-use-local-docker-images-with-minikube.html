How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 690 votes

I remember back when I was first getting comfortable with Kubernetes, I wasted an entire afternoon pulling my hair out because I kept changing a single line of code in my Go service, rebuilding the image, and wondering why my pod wouldn't update. I spent three hours verifying my deployment YAML, convinced I had a typo, only to realize that Minikube had no idea my local image even existed because it was looking at a remote registry that hadn't been updated yet. It was one of those moments where you stare at the screen and just have to laugh at your own stubbornness for assuming the cluster could read your mind.

The root of this frustration is simple: Minikube runs inside its own isolated environment—usually a virtual machine or a separate container—that has its own Docker daemon. When you run docker build on your laptop, that image lands in your local host's daemon. However, when you tell Kubernetes to pull an image, it asks the Minikube daemon for it. If that image isn't there, Minikube tries to fetch it from a remote registry like Docker Hub or ECR. Since your local image is effectively invisible to the cluster, you end up stuck in a loop of building locally and struggling to see your changes reflected in your pods.

The cleanest way to bridge this gap without cluttering up a public registry with "test-v1-final-v2" tags is to point your local terminal directly to the Minikube Docker daemon. Before you run your build command, you just need to execute one quick command in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. After that, you'll want to make sure your Kubernetes deployment manifest has imagePullPolicy: IfNotPresent set. This tells Kubernetes to check for the image locally first and only attempt a remote pull if it can't find it. If you ever need to switch back to your host's Docker daemon, you can just run eval $(minikube docker-env -u). It’s a total game-changer for local development cycles.

To keep this from biting you again, always get in the habit of checking your deployment's imagePullPolicy. If you leave it at the default Always, Kubernetes will try to reach out to the internet every time a pod restarts, which will fail if your image only exists inside the Minikube daemon. Keeping that policy set to IfNotPresent is the best insurance policy you can have for a smooth local workflow.

Hope this saves you from the same three-hour headache I had. Happy coding, and may your pods always hit Running on the first try!

還在把 Docker Image 推上 Docker Hub？教你如何直接在 Minikube 本地開發

來源：Stack Overflow ↗ · 690 票

剛開始學 Kubernetes 那陣子，我真的是被 Minikube 的 Image 拉取機制搞到懷疑人生。記得有次趕專案進度，我明明在本地電腦 docker build 了一個 Image，結果在 Minikube 裡部署時，Pod 一直卡在 ImagePullBackOff。我當時盯著螢幕，看著那個錯誤訊息，心裡真的是一萬隻草泥馬奔騰而過，心想「老兄，我就在你的宿主機旁邊啊！為什麼還要跑去 Docker Hub 找？難道我們之間這麼有距離感嗎？」。為了測試一個小改動，我不斷地要把 Image push 到 Docker Hub 再 pull 下來，來來回回浪費了超多時間，差點就直接把鍵盤砸了。

會發生這種事，其實是因為 Minikube 本質上是一個跑在虛擬機（或容器）裡的獨立環境，它有自己的一套 Docker Daemon。當你寫下 image: my-app:latest 時，Minikube 預設會去外面的 Registry 找，它根本不知道你電腦裡還有個「隱藏版」的 Image。這就像是你把東西放在自家的客廳，卻叫外送員去總倉庫找一樣，他當然找不到啊。

後來我發現，其實根本不需要那麼麻煩。最直覺的方法就是直接把你的終端機環境切換到 Minikube 內部的 Docker Daemon。只要在終端機輸入這行指令：


eval $(minikube docker-env)

只要執行這行，接著你在同一個視窗執行 docker build -t my-app:latest .，這個 Image 就會直接寫進 Minikube 的容器空間裡。這時候你再去跑 K8s 的 YAML 設定檔，Pod 就會像裝了導航一樣，瞬間抓到本地的 Image，完全不用經過網路傳輸，速度快到讓你懷疑人生。記得喔，這只對你當前的終端機視窗有效，如果開了新視窗，記得要重新執行一次。

如果你懶得每次都切換環境，或者覺得這招太麻煩，我強烈建議養成一個習慣：把 Deployment 的 imagePullPolicy 設為 IfNotPresent。這樣一來，只要 Image 已經在 Minikube 裡面了，它就不會再去網路上浪費時間重抓。雖然這只是個小細節，但長期下來真的能省掉不少等待的時間，也不會因為網路慢而導致部署失敗。

搞懂這個之後，開發效率真的提升不只一個檔次，再也不用為了改一行 Code 等半天傳輸了。希望這篇能救你一命，別再傻傻地把 Image 丟上雲端測試啦！
