How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27240 votes

I still remember the first time I accidentally committed a massive folder of local build artifacts and sensitive config files to a repo. I was halfway through my morning coffee, feeling productive, when I realized I’d just pushed a "work in progress" commit that included things that definitely shouldn't be in version control. I spent a solid hour frantically googling commands, terrified I was going to delete my entire project history, only to realize that Git is actually much more forgiving than it looks.

The root of this frustration usually comes down to how Git separates the "staging area" from the "commit history." When you run git commit, you’re essentially taking a snapshot of your current index and locking it into the repository's history. If you realize you included the wrong files or forgot to add a crucial change, you’re stuck with that commit hanging out in your local branch. Since you haven't pushed it to the server yet, the history is still malleable, but it feels incredibly permanent because the standard git commands don't always make the "undo" process obvious to newer developers.

When I need to fix this, I reach for git reset. The way you use it depends entirely on what you want to do with the work you already did. If I just want to undo the commit but keep my changes staged (maybe I forgot to add one tiny file), I use a soft reset. This moves the branch pointer back one commit but leaves all my files exactly where they were, sitting in the staging area ready to be recommitted.


git reset --soft HEAD~1

If I realized the commit was a complete disaster and I want to keep the changes in my working directory but unstage them, I use a mixed reset. This is my go-to when I want to rework the files before committing them again.


git reset HEAD~1

However, if I’ve completely botched the work and just want to wipe the slate clean as if that commit never happened, I use a hard reset. Be careful with this one, because it discards all your local changes in that commit, and there’s no easy way to get them back.


git reset --hard HEAD~1

The best way to prevent this headache is to adopt the habit of running git status right before you hit enter on that commit command. It takes two seconds, but it acts as a final sanity check to make sure you aren't accidentally dragging in hidden files or build artifacts that don't belong in the repo.

Hope this helps you save your progress and keep your git history clean. Happy coding, and try not to commit those build folders!

手滑 Commit 了怎麼辦？教你如何優雅地「後悔」 Git 操作

來源：Stack Overflow ↗ · 27240 票

記得有一次凌晨三點，我正趕著把一個後端功能修好準備上線，腦袋已經呈現當機狀態。我以為我只改了核心邏輯，結果一鼓作氣 git commit -am "fix bug" 下去之後，才發現我不小心把幾百個測試用的 Log 檔案，甚至是包含測試用假帳號密碼的設定檔全給包進去了。那一刻看著終端機畫面，真的差點崩潰，心想這要是推上去給同事看到，我不只要請喝飲料，簡直是要社死現場了。

其實這類問題的本質很單純，就是我們對 Git 的「暫存區」與「本地版本庫」的互動太心急了。當你執行 git commit 時，Git 就像是幫你的檔案拍了一張定格照片放進相簿裡。如果你還沒執行 git push，這些「照片」其實還只是躺在你電腦裡的個人相簿，並沒有對外公開。所以，我們需要的不是什麼複雜的還原術，而是單純地把那張拍壞的照片抽出來重拍。

我當時救命的解法就是 git reset。如果你只是想撤銷最後一次 commit，但想保留檔案修改的內容（畢竟辛苦寫的程式碼不能丟），你可以直接下這行指令：


git reset --soft HEAD~1

這行指令的意思是把指標往回移動一個位置，但把原本 commit 的檔案全部留在「暫存區（Staged）」。這樣你就可以針對剛剛手滑選錯的檔案進行 git restore --staged <檔案名稱>，把它們移出暫存區，然後再重新 commit 一次正確的內容，簡直是完美掩蓋犯錯痕跡的神器。但如果你是連檔案內容都想直接作廢，徹底回到 commit 之前的樣子，那就用 git reset --hard HEAD~1，不過這一招真的要小心，用了之後檔案改動會直接消失，別怪我沒提醒你喔。

為了避免這種心驚膽跳的時刻再次發生，我現在養成了一個習慣，就是在 commit 之前，一定會先補上一句 git status 看一眼到底放了什麼東西進去。如果懶得看，我強烈建議你改用 GUI 工具，像是 Sourcetree 或 VS Code 內建的 Git 面板，它們能讓你一眼看出哪些檔案被勾選要進去 commit，視覺化的呈現真的能拯救不少像我這種愛亂打指令的工程師。

希望下次你手滑的時候，記得這招「原地後悔法」，別再對著螢幕乾著急啦！
