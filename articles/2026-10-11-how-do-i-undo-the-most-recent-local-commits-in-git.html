How to Undo Your Most Recent Local Git Commits Without Panicking

Source: Stack Overflow ↗ · 27243 votes

I remember the first time I accidentally committed a massive, half-baked feature branch to my local repository right before a demo. I had git add . running on reflex, hit git commit, and suddenly realized my "work-in-progress" debug statements were now part of the permanent history. I spent about an hour sweating, convinced I’d ruined the entire codebase, only to realize that Git is actually much more forgiving than it looks when you haven't pushed your changes to the server yet.

It happens because Git treats your local history as a flexible timeline rather than a rigid ledger. When you run a commit, you’re essentially creating a pointer to a snapshot of your files. If you haven't pushed that commit to a remote repository like GitHub or GitLab, that snapshot only exists on your machine. You aren't actually deleting history from the world; you’re just moving your local pointer backward to a previous state. It’s a common point of confusion because the command line feedback makes it feel like you’re "destroying" work, when really, you’re just hitting the undo button.

To fix this, I always reach for git reset. The beauty of this command is that it lets you decide what happens to the files you just "un-committed." If you just want to undo the commit but keep your changes in your staging area so you can tweak them, I use the soft reset:


git reset --soft HEAD~1

If you want to go a step further and completely unstage those files—effectively taking them back to the state they were in before you ran git add—I use the mixed reset, which is the default:


git reset HEAD~1

Now, if you’re like me and you realize you committed a bunch of garbage code that you don't even want to look at anymore, you can use the hard reset. Just be careful, because this will permanently discard any changes in those files:


git reset --hard HEAD~1

To stop this from becoming a recurring nightmare, I started using the -p flag with git add whenever I’m working on multiple things at once. By running git add -p, Git walks me through each "hunk" of code, letting me choose exactly what I want to stage and what I want to leave behind. It forces me to slow down and look at what I’m actually committing, which has saved me from accidentally shipping a stray console.log more times than I care to admit.

Hopefully, this saves you from the same panic attack I had back in the day. Happy coding, and may your git history stay clean!

該死，我剛剛 Git commit 了什麼？教你如何優雅地「反悔」

來源：Stack Overflow ↗ · 27243 票

我記得那是週五下午四點，我剛改完一個超複雜的 bug，整個人處於一種「今天終於能準時下班」的亢奮狀態，手指飛快地打下 git commit -am "fix everything"。結果按下 Enter 的那一秒，我突然意識到我的開發分支裡還夾帶了一堆測試用的垃圾 log，甚至還不小心把某個硬編碼的測試 API Key 給 commit 進去了。那個瞬間，我的心跳直接漏了一拍，看著終端機上的訊息，差點崩潰到想直接把電腦丟出窗外。

其實這真的不能怪我們太粗心，Git 的設計哲學就是「盡可能記錄下你所有的足跡」。當你執行 commit 時，Git 會把這些變更凍結在本地的倉庫裡，這就像是你在寫日記，一旦寫上去，它就成為歷史的一部分了。如果我們還沒把這些東西 push 到遠端伺服器，那一切都還有救，但很多人第一次遇到時，會因為害怕把「歷史」弄壞而不敢亂動，這才是最讓人痛苦的時刻——明明檔案就在那裡，卻覺得自己像個被鎖在門外的笨蛋。

如果你發現自己 commit 錯了，千萬別慌，最常用的救命稻草就是 git reset。如果你只是想撤銷最後一次 commit，但想保留你辛苦寫的程式碼，只要輸入這行指令：


git reset --soft HEAD~1

這行指令會把你的 commit 拆掉，但原本修改過的檔案會乖乖地留在你的暫存區（Staging Area），你可以直接修改那些不該進去的檔案，然後再重新 commit 一次，完全沒人會發現你剛剛犯了蠢。但如果你是連修改的內容都不想要了，想徹底讓檔案回到 commit 前的乾淨狀態，那就用這個狠一點的：


git reset --hard HEAD~1

這招下去，那些改動就真的掰掰了，所以用之前一定要確認你真的不想要那些變更，不然你會跟我當年一樣，對著螢幕發呆半小時，然後默默打開資源回收桶（雖然 Git 裡沒這東西）。

為了避免這種心臟病發作的時刻，我現在養成了一個習慣，就是 commit 前一定會先打 git status 看一下清單，或者乾脆用 git add -p 來一個一個檔案檢查確認。這雖然稍微麻煩一點，但比起之後在那邊拆解 commit，這點時間絕對花得很值得。

希望這招能救你一命，下次別再讓這種小失誤毀了你的週末心情啦！
