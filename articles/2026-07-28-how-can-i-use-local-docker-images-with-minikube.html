How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up Minikube, thinking I was being clever by building my images locally and immediately trying to deploy them. I spent three hours wondering why my pods were stuck in ImagePullBackOff hell, convinced my YAML was broken, only to realize that Minikube had no idea my local Docker daemon even existed. It’s a classic rite of passage for every Kubernetes dev, and trust me, there's nothing quite as humbling as watching a cluster stare blankly at a local image it can't see.

The reason this happens is actually quite straightforward once you peek under the hood: Minikube runs inside its own isolated virtual machine or container. When you run docker build on your host machine, those images are living in your host's Docker daemon, which is completely invisible to the Docker daemon running inside the Minikube node. Unless you push your images to a registry like Docker Hub or ECR, your cluster is essentially blind to your local workspace.

The most efficient way I’ve found to fix this without cluttering up a registry is to point your local terminal directly at the Docker daemon living inside Minikube. By running the minikube docker-env command, you tell your shell to route all your docker commands into the cluster's internal engine. If you're on Mac or Linux, just run this in your terminal:


eval $(minikube docker-env)

Once you’ve done that, any docker build -t my-app:latest . command you run will build the image directly inside the Minikube environment. Now, when you update your Kubernetes deployment to use imagePullPolicy: IfNotPresent and reference that tag, the cluster will find it instantly because it's already sitting locally on its own disk. Just remember that if you open a new terminal tab, you'll need to run that eval command again, or your commands will go back to hitting your host's local Docker instead.

To prevent this headache in the future, I highly recommend adopting a strict naming convention for your local development images, like prefixing them with dev/. More importantly, if you find yourself doing this constantly, look into using skaffold or tilt. These tools automate the process of syncing your local code changes directly into the cluster, which saves you from manually running build commands every time you tweak a line of code.

Hope this saves you from the same three-hour rabbit hole I fell down. Happy hacking and keep those deployments smooth!

別再推送到 Docker Hub 了！在 Minikube 裡使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 688 票

記得剛開始用 Minikube 做開發時，我真的快崩潰了。那時候我寫完一個小功能，為了測試它在 K8s 裡的運行情況，傻傻地把映像檔推送到 Docker Hub，再從 Minikube 裡面 pull 下來。結果那個下午，我大部分時間都在看著「Downloading」的進度條發呆，網路一慢簡直讓人想把螢幕砸了，更慘的是，為了修正一個拼字錯誤，我得重複這個過程整整五次，那種「我到底在幹嘛」的無力感，相信很多人都懂。

其實這背後的道理很簡單，Minikube 雖然是一個模擬的 K8s 環境，但它本質上是一個獨立的虛擬機（或容器），它有自己的一套 Docker Daemon。所以當你在自己電腦的終端機執行 docker build 時，映像檔是存在你本機的 Docker 裡，Minikube 的節點根本看不見，它只會去公共的 Registry 找。這也是為什麼你把 imagePullPolicy 設定成 IfNotPresent 卻一直報 ErrImagePull 的原因，因為它真的找不到啊！

解決這個問題最快、最不折騰的方法，就是直接讓 Minikube 用你當前的 Docker 環境。如果你是用 Mac 或 Linux，最順手的方式就是執行這行指令：


eval $(minikube docker-env)

這條指令會把你的終端機環境變數指向 Minikube 內部的 Docker Daemon。設定好後，你在同一個視窗執行 docker build -t my-app:v1 .，這個映像檔就會直接被塞進 Minikube 的肚子裡。接著，你只要在 Deployment 的 YAML 檔裡把 imagePullPolicy 改成 Never，告訴 K8s「不要去網路上找，直接用本地的」，這樣部署速度快到讓你懷疑人生，幾乎是秒啟動。

不過要提醒一下，這個設定只對「當前」的終端機視窗有效。為了預防下次又忘記，或是換個視窗開發又踩到坑，我現在習慣在專案的 Makefile 裡寫一個簡單的 build 指令，或是直接把這個設定寫在 .bashrc 或 .zshrc 的 alias 裡。或是乾脆養成習慣，只要打開開發專案，第一件事就是執行 eval $(minikube docker-env)，久了就變成肌肉記憶了。

說實話，自從用了這個方法，我開發測試的效率至少提升了三倍，再也不用看著進度條發呆了。希望這招能拯救你接下來的開發時光，趕快去試試看吧！
