How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27237 votes

I still remember the first time I accidentally committed a .env file containing my local database credentials to a public repo. I panicked, sweating through my hoodie as I realized I’d already hit enter, and I spent a solid two hours trying to figure out how to "un-do" the last commit without nuking my entire project directory. It’s a rite of passage for every developer, and honestly, if you haven’t felt that brief, heart-stopping terror of a bad commit, you probably aren’t pushing enough code.

The reason we run into this mess is that Git is designed to be a persistent history tracker. When you run git commit, you’re essentially telling Git to cement your current file state into the repository's timeline. Because Git is so good at preserving what you’ve done, it doesn’t have an "undo" button that’s as obvious as the one in your text editor. You’re essentially asking the version control system to perform a rewrite of the timeline, which can feel intimidating until you understand that your local commits are just pointers in a graph.

When I need to fix a local commit that hasn't been pushed to the remote server, I reach for git reset. If you just want to undo the commit but keep your work in the staging area so you can tweak the files, I use --soft. It’s the safest option because it leaves your files exactly as they were, just without the commit record. You’d run:


git reset --soft HEAD~1

If you’ve completely botched the files and just want to throw the entire commit away—effectively acting like it never happened—you use --hard. Just be careful here, because this will permanently delete any uncommitted changes in your working directory. I’ve definitely nuked a few hours of work by being too aggressive with this command, so double-check your status first:


git reset --hard HEAD~1

If you’re worried about losing your changes, you can always run git stash before doing anything. This tucks your current work away in a safe place, allowing you to reset your branch to a clean state, and then you can git stash pop your changes back once you’ve sorted out the mess.

To prevent this from becoming a recurring nightmare, I started using the --amend flag whenever I realize I’ve missed a file or made a typo in a commit message. Instead of making a new commit, git commit --amend lets you add the forgotten files to the previous commit, keeping your history clean and saving you from having to perform a reset in the first place.

Hope this helps you save some time and keeps your Git history looking professional. Happy coding, and try not to commit those API keys!

手殘黨救星：還沒推上遠端前，如何優雅地「吃掉」剛做的 Commit？

來源：Stack Overflow ↗ · 27237 票

記得有次半夜趕工，我為了修一個緊急上線的 bug 搞得焦頭爛額，最後終於把程式碼搞定，想都沒想就直接 git commit -am "Fix everything"。結果一按下 Enter，我才驚覺自己把還在測試階段的 Debug Log 跟一堆亂七八糟的臨時檔案全給塞進去了！那一刻我真的是心跳漏掉半拍，看著那個剛剛產生的 Commit ID，腦袋瞬間一片空白，心想：「完了，這下要是推上去肯定被同事笑死，甚至搞壞主分支。」

其實這種情況之所以發生，通常是因為我們對 Git 的運作機制太過自信，或者只是單純的「手滑」。Git 的核心概念其實就是一個版本歷史的鏈結，當你執行 commit 時，它就像是在這條鏈上又掛了一個鉤子。還沒 Push 到遠端時，這些鉤子都還只存在你的筆電裡，這就是為什麼我們有機會「反悔」。對 Git 來說，你的 local 環境就像是一個可以隨意塗改的草稿紙，只要沒公開，你怎麼改都不會有人發現。

當時我冷靜下來後，發現其實只要用 git reset 指令就能搞定。如果你只是想把 commit 撤銷，但想保留剛剛寫好的程式碼內容（也就是讓檔案回到 commit 前的「已暫存」狀態），我會推薦你用這行：

git reset --soft HEAD~1

這行指令的意思是把指標往回移一個位置，但檔案變更會乖乖留在你的暫存區。如果你更狠一點，連那些檔案都不想要了，想直接回到 commit 前的乾淨狀態，那就用：

git reset --hard HEAD~1

不過要特別小心，--hard 是真的會把你的改動全部刪除，我第一次用時因為誤判，結果剛寫好兩小時的邏輯直接蒸發，那種看著螢幕發呆、想撞牆的痛苦，我到現在都還記憶猶新。

為了避免這種慘劇重演，我後來養成一個壞習慣……不，是好習慣，就是每次 Commit 前一定要打 git status 看一下。真的，不要嫌麻煩，多看一眼就能避開把敏感檔案或多餘的 log 檔送進歷史紀錄的風險。另外，如果你的改動比較複雜，建議善用 git add -p，這樣你可以一行一行檢查到底加了什麼進去，確認沒問題再 Commit，這樣真的會安心很多。

下次如果不小心手滑，記得先深呼吸，只要還沒 Push，一切都還有救，別自己嚇自己啦！
