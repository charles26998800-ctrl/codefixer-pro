How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 690 votes

I remember the first time I set up a local Kubernetes cluster, I spent about three hours convinced my code was broken because my pods kept throwing ImagePullBackOff errors. I had built my image, verified it was sitting right there in my local Docker daemon, but Minikube just couldn't see it. I ended up pushing a "test-v1" image to Docker Hub just to get it working, only to realize later that I had wasted an entire afternoon waiting for uploads and downloads for something that lived on my own machine.

The reason this happens is actually pretty straightforward: Minikube runs inside its own virtual machine or container, which has its own isolated Docker daemon. When you run docker build on your host machine, that image stays in your host's Docker daemon. Since Minikube’s environment is effectively a separate computer, it doesn't have access to your host's image cache. It's looking for the image in its own internal registry or out on the web, and since your local image isn't there, it fails.

The cleanest way I’ve found to fix this is by pointing your local terminal directly at the Minikube Docker daemon. Instead of trying to move the image, you tell your shell to build the image inside the Minikube environment. Just run this command in your terminal before you build:


eval $(minikube docker-env)

Once you run that, any docker build commands you execute will happen directly inside Minikube. You can then verify it by running docker images and seeing your build listed there. Just remember that if you open a new terminal tab, you’ll need to run that command again, or your docker commands will revert to your host machine. If you’re already using an image, you can also use minikube image load to copy an existing image from your host into the cluster, which is a lifesaver if you don't want to rebuild from scratch.

To prevent this from becoming a recurring nightmare, I always set my Kubernetes deployment manifests to use imagePullPolicy: IfNotPresent. This ensures that Kubernetes checks for the image locally before trying to reach out to a remote registry. It’s a small tweak, but it saves you from those annoying pull errors even after you’ve successfully moved your images into the cluster.

Hope this saves you the hours of frustration I went through! Happy coding and enjoy your local cluster.

為什麼 Minikube 總是讀不到我剛打包好的 Docker image？

來源：Stack Overflow ↗ · 690 票

記得剛開始玩 Kubernetes 的時候，為了測試一個新功能，我興沖沖地寫好 Dockerfile、跑了 docker build -t my-app:v1 .，結果部署到 Minikube 時，Pod 直接原地爆炸，丟給我一個 ErrImagePull。我當時看著螢幕簡直要崩潰，心想：「大哥，我明明就在同台電腦上啊，你為什麼還要跑去 Docker Hub 找？難道你要讓我每次改一行代碼就推一次 Docker Hub 再拉下來嗎？這開發體驗也太折磨人了！」那個下午，我光是為了等那個幾百 MB 的 image 上傳下載，就浪費了兩個小時在滑手機，真的會氣死。

會遇到這種情況，其實是因為 Minikube 的運作機制跟我們一般的 Docker 環境不太一樣。當你啟動 Minikube 時，它其實是在你的電腦裡開了一個獨立的虛擬機（或是 Container），這意味著 Minikube 有自己的 Docker daemon。當你輸入 docker build 時，你是在「宿主機」的 Docker 環境操作，但 Minikube 的 Kubernetes 節點卻是在它的虛擬機環境裡找 image，兩者根本是雞同鴨講，它當然找不到你剛打包好的那個寶貝 image。

後來我終於找到最省事的解法，根本不需要去設定什麼私有 Registry。最直接的做法就是告訴你的 terminal：「嘿，你現在的 Docker 指令請直接對準 Minikube 的環境」。只要執行下面這一行，你的 docker 指令就會自動切換到 Minikube 內部的 Docker daemon：


eval $(minikube docker-env)

執行完這行之後，你再跑一次 docker build -t my-app:v1 .，這次 image 就會直接被建立在 Minikube 內部。之後你在寫 Deployment yaml 時，記得把 imagePullPolicy 設定成 IfNotPresent，這樣 Kubernetes 就會優先使用本地已經有的 image，而不會傻傻地跑去網路上撈。

為了避免以後又踩到同樣的坑，我現在養成了一個習慣，就是把這個環境切換的指令直接寫在我的 .zshrc 或者 .bashrc 裡當成一個 alias，或者乾脆在開工前就養成檢查 minikube status 的習慣。另外，如果你的專案很大，不想每次都 build，也可以考慮用 minikube image load 指令把已經建立好的 image 直接推送到 Minikube 裡，這樣就不會發生那種明明 build 好卻怎麼都抓不到的窘境了。

希望這些經驗能幫你省下不少等候上傳下載的時間，少掉幾根頭髮！
