How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27251 votes

I still remember the first time I accidentally committed a massive, half-baked debugging session filled with console.log statements and API keys to my production repo. I sat there staring at the screen for a solid ten minutes, sweating through my shirt, convinced I’d just nuked my entire project history before even pushing it to GitHub. I spent way too long trying to "undo" it manually by copy-pasting code into Notepad before I realized that Git actually has a built-in safety valve for exactly this kind of panic attack.

The root cause of this headache is usually just a lack of attention during the staging process. We’ve all been there—you run git add . to save time, accidentally dragging in a bunch of temporary files or half-finished features you didn't mean to include. Because Git tracks snapshots rather than just files, once you run git commit, that state is etched into your local history. It feels permanent because the command line makes it look like it's already "done," but since you haven't pushed those changes to a remote server yet, you’re still the only one who knows about your little mistake.

When I need to walk back a commit, I reach for git reset. It’s the surgical tool that keeps my repository clean. If I just want to undo the commit but keep all my work staged and ready to tweak, I run git reset --soft HEAD~1. This effectively "un-commits" the last change, leaving all my files in the staging area so I can fix the mess and commit again properly. 


# Undo the commit, but keep the files staged
git reset --soft HEAD~1

If I realized the entire commit was a complete disaster and I want to wipe the slate clean—meaning I want to lose all the changes in that commit and go back to exactly how things were before I started—I use the hard reset. I have to be careful with this one, though, because it’s destructive; it will permanently delete any work you had in that commit.


# Undo the commit AND destroy the changes in those files
git reset --hard HEAD~1

To keep this from happening again, my best advice is to stop using git add . as your default workflow. I started using git add -p (the patch mode) years ago, and it changed my life. It forces you to review every single hunk of code you’re about to commit, which makes it nearly impossible to accidentally include files you didn't intend to push. It takes an extra five seconds, but it saves me hours of troubleshooting later.

Hope this saves you from a heart attack next time you hit that commit button a little too early. Happy coding!

手滑 commit 了機密檔案？教你如何優雅地把 Git 歷史時光倒流

來源：Stack Overflow ↗ · 27251 票

記得有次半夜趕工，我為了偷懶直接 git add .，結果不小心把一堆包含測試用 API Key 的設定檔給 commit 進去了。當下看著終端機顯示的「commit successful」，心臟真的漏跳一拍，冷汗瞬間冒出來，腦袋裡只有一個念頭：「完了，如果這串指令推上去，我明天是不是要直接打包回家？」那種感覺真的很想找個洞鑽進去，畢竟誰都不想因為這種低級失誤被同事在 Code Review 時公開處刑。

其實這問題發生的根本原因很單純，就是 Git 的設計哲學是「記錄你當下的所有變更」。當你執行 git commit 時，Git 就像是按下了一次快照，把暫存區的所有東西都封裝起來。但如果你還沒執行 git push，這些歷史其實都還只存在你的電腦裡，這就是為什麼我們還有救，因為這是一個還沒對外公開的「私密錯誤」。

我當時冷靜下來後，發現其實 Git 給了我們一個非常強大的後悔藥，那就是 git reset。如果你只是想撤銷最後一次 commit，但想保留檔案修改，讓它們回到暫存區的話，直接打這行就對了：


git reset --soft HEAD~1

這指令好用到不行，它會把 commit 撤銷掉，但你的檔案還會在，這樣你就能把那些錯的檔案移出暫存區，或者把該刪的機密檔案修掉。但如果你是那種連檔案都不想要了，想徹底毀屍滅跡，讓整個工作目錄回到 commit 前的乾淨狀態，那就用這個：


git reset --hard HEAD~1

不過要特別小心，--hard 是會直接把你的修改全部丟掉的，千萬不要在沒備份檔案的情況下亂用，不然當你發現程式碼不見時，那種慘叫聲可是會吵到鄰居的。

至於怎麼預防這種災難再次發生？我後來養成了「檢查狂」的習慣，在 commit 之前一定會先打 git status 看一眼到底加了哪些檔案進去。另外，強烈建議大家去設定 .gitignore，把那些該死的設定檔、環境變數或是 log 檔通通丟進去。只要養成這個好習慣，基本上就不會再發生這種「手殘誤送」的驚魂記了。

以後遇到這種情況別慌，Git 的時光機功能其實挺可靠的，只要還沒推上去，一切都還有救。
