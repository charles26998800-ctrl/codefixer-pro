Fixing React 18 Hydration Errors in Next.js: A Practical Guide

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I encountered the dreaded "Hydration failed" error in a React 18 project. I was convinced my code was perfect, yet my console was screaming at me with a wall of red text that basically said the server and client were speaking two different languages. I spent three hours refactoring my entire component tree, only to realize I had a stray

tag inside a

that was being conditionally rendered based on a browser-only API. It was one of those moments where I wanted to throw my laptop out the window, but it taught me exactly how strict React 18 is about the DOM matching perfectly.

When you see this error, it’s because the initial HTML generated by your server doesn't match the HTML generated by your browser during the initial render. React expects the "hydration" process to be a seamless handoff, where the client takes the static HTML from the server and attaches event listeners to it. If the server renders something like Hello and the client suddenly decides it should be

Hello
—or if you're using something like Date.now() or localStorage that differs between environments—React throws its hands up in frustration. It doesn't know which version is the "truth," so it defaults to the client-side version and nukes the server-rendered content, which defeats the whole purpose of using Next.js.

To fix this, you need to ensure that your component renders exactly the same content on both the server and the client during the first pass. If you have components that rely on browser-specific data, you have to wait for the component to mount before rendering that data. I usually handle this by using a local state variable to track the mounting status. Here is the pattern I use to suppress the mismatch:


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a skeleton loader
  }

  return (
    <div>
      {localStorage.getItem('user-token')}
    </div>
  );
};

By returning null or a loading skeleton on the server (and during the first client render), you avoid the mismatch entirely. Once the component mounts on the client, useEffect triggers, state updates, and React re-renders the component with the browser-specific data. This forces the client to catch up to the state you need without confusing the hydration process.

The best way to prevent this in the future is to be incredibly disciplined about your useEffect hooks. Never access window, document, or localStorage directly in your component body. If you treat your component as a pure function that should return the same output every single time it runs on the server, you’ll rarely see this error again.

Hope this saves you a few hours of debugging and keeps your console clean. Let me know if you run into any other weird hydration quirks!

React 18 Hydration 錯誤：那個讓我半夜加班的「幽靈」不匹配問題

來源：Stack Overflow ↗ · 341 票

記得有次凌晨兩點，我正趕著上線一個 Next.js 的 side project，想說最後優化一下 SEO 就去睡覺。結果一重新整理頁面，瀏覽器 Console 直接跳出一整排紅通通的「Hydration failed」，頁面還瞬間閃爍了一下。當下我真的差點崩潰，明明程式碼跑起來完全沒問題，為什麼 SSR 的結果跟客戶端渲染出來的長得不一樣？那天晚上我盯著螢幕，感覺自己像個傻瓜一樣在跟虛無縹緲的 HTML 字串搏鬥。

其實這個錯誤的根本原因很單純，說穿了就是「溝通不良」。React 在伺服器端（SSR）預先渲染了一份 HTML，但當這份 HTML 到了瀏覽器，React 嘗試要把它「激活」（Hydrate）並接管成互動式的 UI 時，發現瀏覽器端產生的 DOM 結構跟伺服器給的不一樣。這通常是因為我們在元件裡用了依賴於瀏覽器環境的變數，像是 window、localStorage，或者是隨機數 Math.random()，甚至是根據時間戳記顯示的內容。因為伺服器端沒有這些變數，導致兩邊的畫面產生了「時空錯亂」，React 覺得這太危險了，為了保險起見，它乾脆直接報錯。

我後來發現，解決這個問題最快的方法，就是讓 React 「先別急著渲染」。既然問題出在伺服器端沒有瀏覽器環境，那我們就強制讓這段容易出錯的邏輯，只在瀏覽器端掛載完成後才執行。我會透過一個簡單的 useEffect 來判斷元件是否已經掛載（mounted），這樣就能確保第一次渲染時，兩邊的內容是完全一致的靜態結構。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    // 這裡回傳一個空的 div 或預設的骨架屏 (Skeleton)
    return <div>Loading...</div>;
  }

  // 這裡放那些會用到 window 或 localStorage 的複雜邏輯
  return <div>{window.location.href}</div>;
}

為了避免以後再被這個問題搞到想摔鍵盤，我現在養成了個好習慣：只要是會用到瀏覽器原生 API 的元件，我一律會給它一個預設的「靜態顯示狀態」。與其讓 React 去猜伺服器跟客戶端為何不同，不如直接在 useEffect 之前統一給它一個固定的初始值。這樣不僅能避開 Hydration 錯誤，還能順便把頁面的載入體驗做得更好，何樂而不為呢？
