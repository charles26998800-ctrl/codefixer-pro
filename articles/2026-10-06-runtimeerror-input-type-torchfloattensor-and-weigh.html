Troubleshooting RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor)

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a GPU training loop in PyTorch. I thought I was clever by defining a device variable and moving my model over, but as soon as I hit run, my terminal exploded with that classic "Input type and weight type should be the same" error. I spent three hours staring at my screen, convinced my GPU drivers were fried or that I’d somehow installed a corrupted version of PyTorch, only to realize I’d completely forgotten to move the incoming data to the device.

The reason this happens is actually pretty straightforward once you look past the intimidating error message. PyTorch is extremely strict about data locality; your model weights and your input tensors need to live in the same memory space to perform operations. If your model is sitting on the GPU (the cuda device) but your data is still sitting on your CPU RAM, PyTorch refuses to bridge that gap automatically. It’s a safety mechanism to prevent you from accidentally triggering massive, slow data transfers between your system RAM and GPU VRAM during every iteration of your training loop.

The fix is simple, but you have to be intentional about it. Since your model is already on your device, you just need to explicitly move your inputs and labels to that same device inside your training loop. I’ve found that the cleanest way to do this is to call .to(device) on your tensors as soon as you pull them from the DataLoader. Here is what your loop should look like:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move inputs and labels to the same device as the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

Once you add those two lines, the error disappears instantly. If you’re dealing with a complex project, the best way to prevent this from ever happening again is to write a small helper function or a custom dataset wrapper that handles the device placement automatically. Honestly, just getting into the habit of keeping your device variable visible at the top of your training script makes it much harder to lose track of where your tensors are living.

Hopefully, this saves you that three-hour headache I had to deal with. Happy coding!

PyTorch 報錯：Input type 和 weight type 不一致的崩潰日常

來源：Stack Overflow ↗ · 202 票

記得剛開始碰 PyTorch 的時候，那天晚上趕著要把模型訓練跑起來，結果終端機跳出那行經典的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。我當時盯著螢幕看了半天，心想「明明模型都 .to(device) 了啊，到底還想怎樣？」，那種半夜兩點被這行紅字卡住、想睡又睡不著的挫折感，真的會讓人想直接把筆電闔上放棄人生。

其實這個錯誤的邏輯很單純，就是 PyTorch 在檢查運算時，發現你的模型參數已經乖乖跑到 GPU 上了，但你的輸入數據（inputs）卻還停留在 CPU 的記憶體裡。簡單來說，就是「模型在 GPU 喝著咖啡，輸入數據還在 CPU 跑腿」，兩個傢伙根本沒在同一個頻道上溝通，PyTorch 當然就不給你算，直接丟出例外拒絕工作。

要解決這個問題，其實只要在迴圈裡多加一行扣板機就好。當你在 for data in dataloader: 讀取資料時，記得要把 inputs 和 labels 也順手推到跟模型同一個 device 上。像我後來寫的時候，都會習慣養成這樣寫：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵，把資料搬到 GPU
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就可以正常計算 loss 了

為了避免哪天又忘記這件事，我現在寫程式有個小撇步，就是直接寫一個簡單的 to_device 函式，或者乾脆在定義完 device 後，讓自己養成習慣先把資料接過來轉一下。甚至如果你是用比較新的 PyTorch 版本，也可以考慮把資料處理流程寫進 Dataset 的 __getitem__ 裡，或者在訓練迴圈剛開始時就強制檢查一下輸入的裝置，這樣就能省下不少除錯的時間。
