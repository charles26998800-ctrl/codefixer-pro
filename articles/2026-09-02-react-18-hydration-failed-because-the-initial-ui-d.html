How to Fix the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time React 18 threw the "Hydration failed" error in my face. I was building a dashboard that relied heavily on local browser storage for user preferences, and I spent a solid three hours convinced that my server-side logic was completely broken because the browser console kept screaming that the UI didn't match. It turned out my code was perfect, but my assumptions about the state were dead wrong, and I felt like pulling my hair out until I finally understood what was happening behind the scenes.

If you’re staring at this error, it’s because React is trying to be smart. When you use Next.js, the server renders your HTML and sends it down to the browser. Once that HTML lands, React "hydrates" it, meaning it attaches event listeners and makes the page interactive. The problem happens when the server renders one thing (like a timestamp or a localized string), and the client renders something else (like a default value) because it doesn't have access to the same context. React compares the two, sees a mismatch, and throws a tantrum because it’s terrified of updating the DOM incorrectly.

The most common way I’ve fixed this is by forcing the component to wait until it’s actually mounted on the client before rendering the "mismatched" part. You can easily do this by using a simple useEffect hook to track whether the component has mounted. By setting a local state variable, you ensure that the server renders a neutral version, while the client renders the dynamic content once it's safe to do so.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    // Render a skeleton or null to keep the server/client match
    return null; 
  }

  return (
    <div>
      {/* This will only render on the client, avoiding the mismatch */}
      {window.localStorage.getItem('my-key')}
    </div>
  );
}

If you don't care about the content being visible during the initial server render, you can also use suppressHydrationWarning on the specific HTML element that's causing the fuss. This tells React, "I know this will be different, please just ignore it." It's a quick hack, but be careful—only use it for things like timestamps that change every millisecond, otherwise, you might end up with weird UI flickers that confuse your users.

To keep this from haunting your codebase in the future, my best advice is to keep your server-side logic strictly deterministic. If you need to use browser-specific APIs like window, localStorage, or navigator, always wrap them in a check that ensures they only execute after the component mounts. Getting into the habit of thinking "Will this value be the same on the server as it is on the client?" before I write a single line of state code has saved me countless headaches.

Hopefully, this gets your app back on track so you can get back to building cool stuff. Let me know if you run into any other weird edge cases!

React 18 Hydration 錯誤：那個讓你懷疑人生的「不一致」

來源：Stack Overflow ↗ · 341 票

記得上次為了搞定 Next.js 的 SSR，我整個人簡直快崩潰。當時我正準備把一個舊專案升級到 React 18，想說應該只是改個版本號而已，結果一執行，瀏覽器控制台直接噴出一堆紅通通的 Hydration failed。看著那行「Server 和 Client 渲染出來的 UI 不一樣」的警告，我真的盯著螢幕發呆了半小時，心想：「我程式碼明明寫得好好的，為什麼電腦要這樣對我？」

其實這個問題的核心在於 React 18 的「水合（Hydration）」機制太嚴格了。簡單來說，Next.js 會先在伺服器端把 HTML 跑一遍，然後把這個靜態 HTML 傳給瀏覽器；接著 React 在前端接手，要把這些 HTML 變成可以互動的組件。如果伺服器算出來的結果，跟瀏覽器第一次跑出來的結果有一丁點出入，比如一個隨機數、當下時間，或是像 typeof window !== 'undefined' 這種判斷式，React 就會覺得：「這根本不是同一個東西啊！」然後直接放棄治療，噴出錯誤給你。

我當時遇到的最痛苦時刻，就是因為我在組件裡寫了一個簡單的 new Date().toLocaleTimeString() 來顯示當前時間。伺服器渲染時是 10:00，傳到瀏覽器時變成 10:01，這短短一秒的誤差就足以讓 Hydration 崩潰，讓我的頁面變成一片混亂。

要解決這個問題，最直覺的方法就是讓這個組件「晚點再渲染」。我後來學乖了，利用 useEffect 來處理這種只在瀏覽器端才需要的邏輯，因為 useEffect 只會在組件掛載（mount）到瀏覽器後才執行，完全避開了伺服器端的渲染衝突。

你可以試著這樣寫：


import { useState, useEffect } from 'react';

function TimeComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? new Date().toLocaleTimeString() : '正在載入中...'}
    </div>
  );
}

這樣一來，伺服器只會拿到那個「正在載入中...」的純文字，等到瀏覽器真的跑起來了，才會把真實的時間換上去。React 看到前後一致，就不會再跟我鬧脾氣了。

至於怎麼預防這種惡夢再次發生，我現在養成了一個習慣：只要是用到了瀏覽器專屬 API 的功能，或者會隨時間、環境變動的內容，我一律預設把它丟進 useEffect 裡處理，或者乾脆用 dynamic import 並設 ssr: false。只要把這些「不穩定因素」隔離在伺服器渲染流程之外，你的開發體驗真的會順暢很多。

處理 Hydration 錯誤確實很煩，但只要搞懂了它是怎麼運作的，下次再看到紅字就不會想砸鍵盤了，大家一起加油吧！
