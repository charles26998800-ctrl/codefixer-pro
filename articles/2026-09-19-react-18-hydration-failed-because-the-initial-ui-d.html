React 18 Hydration Errors: Why Your Server and Client Aren't Talking

Source: Stack Overflow ↗ · 341 votes

I still vividly remember the first time I upgraded a project to React 18. I thought it would be a smooth afternoon of bumping package versions, but instead, I spent four hours staring at a console full of angry red text screaming about hydration mismatches. I was convinced I’d broken the entire architecture, only to realize that my server-rendered HTML and my client-side bundle had a fundamental disagreement about what a simple timestamp should look like.

The root cause of this headache is actually quite simple: React expects the HTML generated by your server to be identical to the HTML generated by the client during that initial "hydration" phase. When you use something that changes based on the environment—like new Date().toLocaleTimeString() or checking typeof window—the server renders one thing, and the browser calculates something slightly different the millisecond it takes over. React sees this discrepancy, panics, and throws the "Hydration failed" error because it can't guarantee a stable UI. It’s essentially a trust issue between your backend and your frontend.

When I finally tracked this down, the fix was to delay the rendering of the dynamic content until the component has actually mounted in the browser. You don't want the server trying to guess what the client-side state is, so you force the component to wait for the useEffect hook, which only runs on the client. Here is how I handle it now:


import { useState, useEffect } from 'react';

export default function DynamicComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>The time is: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By introducing that isClient state, I ensure that the server renders a static placeholder, and the client only injects the dynamic time once it’s safely in the browser's domain.

To prevent this from happening in the future, my golden rule is to treat any data that depends on the browser environment (like local storage, window dimensions, or current time) as "client-only" by default. If you keep your server-side logic strictly deterministic and delay any browser-specific API calls until after the initial mount, you’ll save yourself a massive amount of debugging time.

Hope this helps you clear those console errors and get back to shipping features. Happy coding!

React 18 Hydration 錯誤：那個讓你懷疑人生的「UI 不匹配」惡夢

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 的那個週末，我原本想著只要換個版本就能享受效能提升，結果打開瀏覽器主控台一看，整排紅通通的 Hydration failed 直接讓我原地石化。最崩潰的是，頁面明明看起來沒問題，但控制台卻在那邊歇斯底里地喊著「伺服器產出的 HTML 跟客戶端渲染的不一樣」，那一刻我真的覺得自己寫了幾年的 React 都白學了，甚至一度想把整個 node_modules 刪掉重灌。

其實這個問題的核心很簡單，就是「時差」造成的認知落差。當你使用 Next.js 或 SSR 時，伺服器會先幫你渲染好一份 HTML 送到瀏覽器，但如果你的程式碼裡包含了一些「隨機變數」，例如 new Date()、Math.random()，或是從 localStorage 讀取資料，伺服器跑出來的結果就會跟瀏覽器第一次執行 React 時跑出來的結果不同。React 發現兩邊長得不一樣，為了怕畫面亂掉，它就會直接報錯，甚至乾脆放棄治療，重頭渲染一次畫面，這就是為什麼你的頁面會閃爍一下才出現。

我當時遇到的情況就是把日期處理直接寫在元件裡，後來我學乖了，學會了如何「按兵不動」。最直接的解法就是確保第一次渲染時，兩邊的內容是完全一致的。你可以利用 useEffect 這個鉤子，因為它只會在瀏覽器端執行，伺服器端理都不理它。只要把會變動的內容藏在 useEffect 裡，就能避開這個坑。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? new Date().toLocaleTimeString() : '載入中...'}
    </div>
  );
}

透過這種方式，伺服器端永遠只會輸出「載入中...」，等到瀏覽器接手後，useEffect 才會觸發並更新時間。這樣前後端內容對齊了，React 也就閉嘴了，不會再跳出那惱人的錯誤訊息。

至於怎麼預防這種問題再次發生，建議大家養成一個好習慣：只要牽涉到瀏覽器特有的物件，像是 window、document 或者本地端儲存空間，一律統一放到 useEffect 裡處理，或者乾脆使用 Next.js 提供的 dynamic 引入並設定 ssr: false。只要把「會變動的邏輯」跟「靜態 UI」拆得夠乾淨，這種莫名其妙的錯誤自然就會離你遠去。

祝大家的專案都能跑得順順利利，別再被這些 hydration 錯誤搞到掉頭髮啦！
