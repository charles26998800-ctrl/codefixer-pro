Troubleshooting RuntimeError: Input type and weight type should be the same in PyTorch

Source: Stack Overflow ↗ · 202 votes

I remember the first time I hit this error while working on a custom CNN architecture late on a Tuesday night. I had spent nearly three hours debugging my data augmentation pipeline, convinced the issue was a corrupted tensor shape, only to realize I had completely forgotten to move my input data to the GPU after setting up the model. It’s one of those classic PyTorch "gotchas" that makes you want to stare at the wall for a few minutes, but once you understand the underlying requirement, it becomes second nature to handle.

The reason this error pops up is that PyTorch is incredibly strict about hardware consistency. When you move your model to the GPU using model.to(device), you are loading those weight tensors into VRAM. However, when you iterate through your DataLoader, PyTorch defaults to creating those input tensors on your CPU's RAM. Your model is basically standing there with its arms open waiting for data on the GPU, while your CPU is still holding onto the data, resulting in a type mismatch between the torch.FloatTensor on your CPU and the torch.cuda.FloatTensor inside your model.

To fix this, you have to explicitly move your input tensors to the same device as your model during your training loop. I’ve found that the cleanest way to do this is to call .to(device) on your inputs and labels right as you pull them from the loader. Here is how I update my training loops to ensure everything stays in sync:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Explicitly move inputs and labels to the active device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you’re worried about forgetting this in the future, the best habit I’ve developed is to write a small helper function or a custom wrapper that handles the device movement automatically. Alternatively, if you're feeling fancy, you can use a dictionary or a custom collate function in your DataLoader to map all tensors to the device before they even hit your training loop. Just keeping that device variable handy and applying it consistently is usually enough to stop the headache before it starts.

Hope this helps you get back to training your models without the constant runtime crashes. Happy coding!

救命！PyTorch 又報錯：Input type 和 weight type 不一樣？

來源：Stack Overflow ↗ · 202 票

那天凌晨兩點，我剛寫完一個複雜的模型架構，滿心期待按下執行鍵，結果螢幕上那行紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same 直接讓我原地崩潰。我盯著螢幕看了十分鐘，心想：「明明都已經把模型 to(device) 了啊，到底還想怎樣？」那種好不容易寫完代碼，卻被這種低級錯誤卡住、甚至還得熬夜抓蟲的絕望感，真的會讓人想把鍵盤給拆了。

說穿了，這問題其實就是 PyTorch 在「鬧脾氣」。簡單來說，就是你的模型已經乖乖搬到 GPU（cuda）上工作了，但你餵給它的數據卻還留在 CPU（FloatTensor）裡。想像一下，你的大廚（模型）在餐廳廚房（GPU）裡準備好要炒菜了，你卻把食材（inputs）丟在遙遠的家裡（CPU）叫他炒，這兩邊根本不同步，PyTorch 當然就會跳出來報錯，告訴你兩邊的「語言」不通，沒辦法進行運算。

我後來發現，最常見的坑就是我在迴圈裡忘了把數據也搬過去。解決方法其實超級簡單，你只需要在讀取資料時，順手把 inputs 和 labels 也推送到同樣的 device 就行了。我現在寫迴圈時都會習慣這樣寫：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！把數據也送過去
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也記得要在同一個 device 上喔

為了避免以後再因為這種蠢問題浪費時間，我現在養成了一個習慣，就是把裝置設定寫在最前面，然後在定義好 device 後，直接寫一個小工具函式或是檢查點，確保所有 tensor 在進入模型前都已經過 to(device) 的洗禮。只要養成「只要是 Tensor，進模型前先檢查所在位置」的反射動作，基本上就能告別這個惱人的錯誤了。

希望這篇能救回你的凌晨兩點，下次寫 code 記得先把資料餵對地方，別讓 GPU 空轉啊！
