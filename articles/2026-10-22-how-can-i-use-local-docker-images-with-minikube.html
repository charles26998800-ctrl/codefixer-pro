How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours staring at an ImagePullBackOff error, convinced that my YAML files were cursed, only to realize that Minikube was trying to reach out to the Docker Hub for an image that was sitting right there on my machine. I felt like a complete amateur, but it turns out this is one of the most common "gotchas" when you're first moving from standard Docker containers to a local K8s development workflow.

The reason this happens is actually quite straightforward once you peek under the hood: Minikube runs inside its own isolated virtual machine or container. Because it’s a separate environment from your host machine, it has its own independent Docker daemon. When you build an image on your laptop, it’s stored in your host's Docker daemon, but Minikube has no idea that image exists. When Kubernetes tries to pull the image by name, it checks its internal registry, fails to find it, and tries to reach out to the internet, which is why your local builds seem invisible to your cluster.

The quickest way I’ve found to bridge this gap—without setting up a private registry or pushing to Docker Hub—is to point your local shell directly to the Minikube Docker daemon. Before you run your build command, execute this in your terminal:


eval $(minikube docker-env)

Once you run that, your local docker commands are now talking directly to the Docker engine inside your Minikube cluster. Now, when you run docker build -t my-app:latest ., the image is built directly inside the Minikube environment. You don't need to push anything anywhere. Just remember that if you open a new terminal window, you'll need to run that command again, or your terminal will revert to talking to your host's Docker daemon. After you've built your image, make sure your Kubernetes deployment sets imagePullPolicy: IfNotPresent (or Never), otherwise K8s will still try to pull from the remote registry even if the image is right there.

To keep your sanity, my best advice is to use a specific tag for your local development images, like dev or latest, and keep your imagePullPolicy strictly set to IfNotPresent. This prevents K8s from trying to reach out to the registry if you’ve already got the image built locally. It’s a small configuration change that saves me from constant ImagePullBackOff headaches every time I iterate on a feature.

Hope this saves you a few hours of debugging time today. Happy coding and good luck with your cluster!

別再把 Image 推到 Docker Hub 了！Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 時，我為了測試一個簡單的 API 改動，流程竟然是：改程式碼 -> Build Docker Image -> 推送到 Docker Hub -> 回到 Minikube 拉取最新映像檔。那個「等待推送與拉取」的過程簡直是惡夢，有次為了改一行 log，我坐在電腦前看著進度條跑了五分鐘，那種「我到底在幹嘛」的崩潰感，真的會讓人想直接把電腦砸了。

其實會卡住是因為 Minikube 本質上是一個跑在虛擬機（或容器）裡的獨立環境，它根本看不到你電腦本地 Docker Daemon 裡的那些映像檔。你以為你在 Terminal 下了 docker build 就萬事大吉，但在 Minikube 的眼裡，它的「本地」是虛擬機內部的 Docker，而不是你開發機的 Docker。所以就算你 build 了一百次，Minikube 還是會去網路上找，找不到就報 ImagePullBackOff 給你看，這真的會讓人懷疑人生。

要解決這個問題，最快的方法就是直接把 Minikube 的 Docker 環境「指向」你的開發機。只要執行這行指令，你的 Terminal 就會直接跟 Minikube 裡面的 Docker 對話：


eval $(minikube docker-env)

執行這行之後，你再跑一次 docker build -t my-app:v1 .，這次它就會直接把映像檔塞進 Minikube 的肚子裡。之後你只要在 Kubernetes 的 YAML 檔裡把 imagePullPolicy 設定成 IfNotPresent，Minikube 看到本地已經有這張圖，就不會再去網路上下載了，開發效率直接起飛。

不過要注意，如果你是用 Mac 或 Windows 且開啟了 docker-desktop，有時候環境切換會讓你搞混到底 build 在哪裡。我後來養成一個習慣，就是每當我要開始開發特定專案時，一定會先確認 docker context 是不是正確的，或者乾脆在 ~/.zshrc 裡設個 alias，讓我能一鍵切換環境。

以後別再為了測試一行程式碼，就把映像檔丟到網路上繞一圈了，直接用本地環境測試才是工程師該有的優雅。祝大家除錯順利，早點下班！
