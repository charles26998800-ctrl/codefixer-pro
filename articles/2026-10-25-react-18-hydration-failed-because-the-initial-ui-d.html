Debugging the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still vividly remember the first time I saw the dreaded "Hydration failed" error in a React 18 project. I had just migrated a legacy dashboard to Next.js, feeling pretty proud of my performance metrics, only to refresh the page and see my console flooded with bright red warnings. I spent three hours refactoring my entire component tree, convinced I’d broken some complex state logic, before realizing it was just a simple mismatch between my server-rendered date and the client-side clock.

The reason this happens is actually quite logical once you peek under the hood of React 18. When you use Server-Side Rendering (SSR), the server generates the initial HTML based on the state it sees at that exact moment. Then, when the browser loads the JavaScript bundle, React tries to "hydrate" that static HTML by attaching event listeners and making it interactive. If the HTML the browser receives doesn't match exactly what the client-side React component renders on that very first pass, React throws its hands up and declares a hydration mismatch. It’s essentially saying, "Hey, what I got from the server doesn't match what I’m seeing right now, so I’m just going to force a re-render to fix it," which is terrible for performance and can cause some really weird flickering.

To fix this, I usually look for dynamic values that change immediately upon execution, like Date.now() or random number generators. If you’re rendering something that varies between the server and the client, you need to wait until the component has actually mounted in the browser before rendering it. I’ve found that the cleanest way to handle this is by using a simple useEffect hook to track the mounting state.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Now this only renders once the client is ready */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

By returning null or a loading state until isMounted becomes true, you guarantee that the server renders a neutral placeholder, and the client-side React takes over to render the dynamic content. This keeps the server and client in sync during that critical hand-off phase.

If you want to prevent this from happening in the first place, my biggest tip is to be extremely careful with browser-only globals like window, document, or localStorage inside your render logic. I make it a rule of thumb to never touch those outside of useEffect or useLayoutEffect. If you follow that one simple discipline, you’ll save yourself a massive amount of debugging time down the road.

Hope this helps you get your app back on track without the headache. Happy coding!

React 18 Hydration Error：那個讓我熬夜到凌晨兩點的「UI 不匹配」地獄

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 的那個週末，我原本想著趕快把 SSR 搞定就能去睡個好覺，結果打開瀏覽器控制台一看，整排紅通通的 Hydration failed 錯誤直接把我炸醒。我看著螢幕上那一串又臭又長、說什麼伺服器端渲染跟客戶端 UI 不一致的警告，真的差點把鍵盤砸了，心想：「明明程式碼長得一模一樣，到底哪裡不匹配啦！」最慘的是，我為了找這個錯，把所有元件拆開又重組，甚至還懷疑過是不是 Next.js 的快取壞了，整整在電腦前乾耗了三個小時，那種「明明覺得自己寫對了卻被系統狠狠打臉」的無力感，真的是工程師生涯最痛苦的時刻之一。

其實會發生這種狀況，說穿了就是「時差」問題。React 18 在 SSR 時，伺服器會先產生一份 HTML，當瀏覽器收到這份 HTML 後，React 會嘗試進行「補水（Hydration）」，也就是把事件綁定上去。如果伺服器渲染出來的內容，跟客戶端第一次執行 React 時算出來的結果有那麼一點點不一樣，比如因為時間戳記、隨機亂數，或是瀏覽器特有的 API（像 window.localStorage），React 就會直接原地崩潰，因為它不允許這種「前後不一致」的狀況發生。

後來我發現，最常見的兇手就是我在元件裡直接用了 new Date() 或者是讀取 localStorage。當伺服器跑的時候，時間是伺服器的時間，等瀏覽器執行時，時間已經過了幾毫秒，這細微的差異就成了壓垮駱駝的最後一根稻草。解決方案其實很直覺，就是要確保「第一次渲染」時，雙方的產出必須是一致的。我通常會利用 useEffect 來處理那些只有瀏覽器才有的邏輯，因為 useEffect 只有在瀏覽器端才會執行，這樣就能避開伺服器端的渲染衝突。

這是我後來處理這類問題的標準寫法：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    // 只有在瀏覽器端才會執行這段
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>現在時間是：{new Date().toLocaleTimeString()}</p>
      ) : (
        <p>載入中...</p>
      )}
    </div>
  );
}

為了預防這種惡夢再次發生，我現在養成了一個習慣，就是只要用到瀏覽器獨有的 API，我一定會先檢查 typeof window !== 'undefined'，或者乾脆統一用 useEffect 來延後渲染那些依賴環境變數的 UI。不要試圖在元件的頂層直接讀取那些會隨時間或環境變化的值，把它們丟進 useEffect 裡準沒錯。

希望這招能幫你省下幾個熬夜的夜晚，畢竟好好的週末拿來除錯這種「靈異現象」實在太不划算了！
