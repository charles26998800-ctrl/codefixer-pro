How to Undo Your Most Recent Local Git Commits (Without Losing Your Work)

Source: Stack Overflow ↗ · 27233 votes

I still remember the first time I accidentally committed a massive folder of local build artifacts and sensitive environment variables to a repo. I was halfway through a coffee, feeling confident about my progress, when I realized I’d just pushed a "Work in Progress" mess that included secrets I definitely shouldn't have tracked. I spent a solid hour sweating over the command line, terrified that I was about to delete my entire project history, only to realize that Git is actually much more forgiving than it looks.

The root cause of this panic is usually just a lack of familiarity with how Git manages state. When you run git commit, you aren't just saving files; you're creating a snapshot in your local history. If you haven't pushed that snapshot to a remote server like GitHub or GitLab yet, your local repository is essentially your personal sandbox. Git keeps a pointer to your current work, and undoing a commit is really just moving that pointer backward in time. You’re not actually "deleting" the code; you’re just telling Git to pretend the last commit never happened.

When I need to fix this, I always reach for git reset. The command you need depends entirely on whether you want to keep your changes or wipe them out entirely. If you want to undo the commit but keep your files staged and ready to tweak, run git reset --soft HEAD~1. This keeps your work exactly as it was, but moves the commit out of the way. If you want to keep the changes but unstage everything so you can choose exactly what to commit next, use git reset HEAD~1 instead.

Now, if you’re like me and you realize you committed a total disaster that you just want to vanish, you can use the nuclear option: git reset --hard HEAD~1. Be careful with this one, though—it permanently deletes all the changes in that commit. If you aren't sure, check your status first:


# Undo the commit but keep your changes staged
git reset --soft HEAD~1

# Undo the commit and unstage the files
git reset HEAD~1

# Undo the commit and delete all your changes (Use with caution!)
git reset --hard HEAD~1

To prevent this headache in the future, I started using a .gitignore file religiously from the very first minute of a project. It’s so easy to get lazy and just run git add . without looking, but taking two seconds to verify your staged files with git status before hitting enter on that commit command will save you from a world of hurt.

Hope this saves you some stress next time you have a "git oopsie" moment. Let me know if you run into any other weird edge cases!

手滑提交了不該送出的程式碼？別慌，Git 救命指南來了

來源：Stack Overflow ↗ · 27233 票

記得有一次凌晨三點，我為了趕專案進度，在最後一次 commit 時不小心把測試用的 debug log 跟一堆沒整理好的垃圾檔案全部打包送出去了。按下 git commit 的那一刻，我整個人僵在螢幕前，心跳大概漏了兩拍，腦中閃過無數個「完蛋了，等下推上伺服器肯定會被同事笑死」的念頭。那種眼睜睜看著錯誤被記錄下來，又不知道怎麼把它「抹掉」的無力感，真的是每個工程師的惡夢。

其實這問題發生，通常就是我們對 Git 的「暫存區」跟「歷史紀錄」還沒那麼熟悉。Git 很強大，它把你的每一次更動都當作珍貴的歷史，但問題就在於，當你 commit 的當下，Git 已經把你的檔案狀態寫進了它的資料庫。很多新手（包含當年的我）會以為 git revert 是萬能的，但那其實是「產生一個新的 commit 來抵銷舊的」，如果你只是想把剛剛那筆還沒推出去的 commit 直接當作沒發生過，用 revert 反而會讓紀錄變得很髒。

當我發現自己 commit 錯東西時，我的救星就是 git reset。如果不小心 commit 了但我還想保留剛剛改動的檔案內容，只是想把 commit 撤銷掉重新整理，我會直接輸入：


git reset --soft HEAD~1

這指令超級好用，它會把那個 commit 拆掉，但你剛剛寫好的程式碼通通會留在暫存區（Staging Area），你可以直接修改檔案，重新 add 再 commit 一次，完全不留痕跡。但如果你的情況更慘，是連檔案內容都改壞了，想徹底回到 commit 之前的狀態，那就要用「毀滅性」的這招：


git reset --hard HEAD~1

這招下去，那個 commit 跟裡面所有的檔案變動會直接消失，連渣都不剩，請務必先確認你真的不需要那些檔案了再執行，不然真的會欲哭無淚。

為了不要再經歷這種心臟病發作的時刻，我現在養成了一個習慣，就是每次 commit 前一定會先跑一次 git status，確認一下到底有哪些檔案被改動了。如果專案比較複雜，我強烈建議大家開始練習使用 git add -p，這樣你可以一行一行檢查到底把什麼東西放進了暫存區，確保送出去的每一個 commit 都是乾乾淨淨、邏輯正確的。

希望大家都能平平安安地寫程式，少踩這種讓心跳加速的雷。下次如果不小心又手滑了，記得冷靜下來用 reset 處理，千萬別急著亂下指令喔！
