How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up Minikube, thinking I’d be up and running in ten minutes. Instead, I spent three hours staring at ImagePullBackOff errors, fruitlessly pushing images to a private registry I didn't actually need, just because I didn't realize Minikube was living in its own isolated bubble. It was one of those classic "why is this so hard?" moments that makes you want to throw your monitor out the window, but once I figured out the secret, my local development workflow became instant.

The reason this happens is simple: Minikube runs inside a virtual machine or a containerized environment that doesn't share the same Docker daemon as your host machine. When you run docker build on your laptop, that image ends up in your host's local registry. When your Kubernetes pods try to pull an image, they look inside the Minikube node’s internal registry, which is completely empty. They aren't talking to each other, so the cluster just assumes the image doesn't exist and starts panicking.

The easiest way I fixed this—and the method I use every single day—is by pointing my local terminal directly at the Minikube Docker daemon. Instead of building locally and pushing to a registry, you run a single command that tells your host to route all Docker commands straight into the Minikube environment. Open your terminal and run this:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it worked by running docker images, and you'll see your custom images sitting right there where Kubernetes can actually see them. Just remember that if you open a new terminal tab, you'll need to run that command again, as it only affects the current shell session. After you've built your image, make sure your Kubernetes manifest has imagePullPolicy: IfNotPresent set, otherwise, K8s might still try to reach out to the internet to fetch a version that doesn't exist.

To prevent this from becoming a recurring nightmare, I always keep my imagePullPolicy set to IfNotPresent in my development manifests. It’s a tiny configuration change that saves you from having to deal with registry authentication or slow upload times entirely. By building directly into the cluster's daemon, you keep your feedback loop tight and your sanity intact.

Happy coding, and may your pods always reach the Running state on the first try!

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的省力技巧

來源：Stack Overflow ↗ · 688 票

記得剛開始碰 Kubernetes 的時候，我整個人簡直快崩潰。當時我寫好了一個微服務，想在 Minikube 上測試，結果為了驗證一個小改動，我得先 docker build，然後 docker push 到 Docker Hub，再從 Minikube 裡 kubectl delete pod 等它重新拉取。那一整天我大概花了 80% 的時間在盯著「ImagePullBackOff」那個該死的錯誤訊息看，網路慢一點的時候，我真的會坐在椅子上發呆懷疑人生。

為什麼會搞得這麼累？其實是因為 Minikube 和你電腦上的 Docker 是兩回事。當你啟動 Minikube 時，它其實是在你的電腦上開了一個虛擬機（或是 Container），這意味著 Minikube 裡面的 Docker Daemon 跟你在終端機打 docker build 時用的那個 Docker Daemon 是完全隔離的。所以，不管你在外面 build 了多少次，Minikube 就像個「與世隔絕」的孤島，它根本看不到你本地的這些鏡像，只能乖乖去遠端倉庫抓。

要解決這個問題，其實最快的方法就是讓 Minikube 直接共用你目前的 Docker 環境。只要在執行 kubectl 之前，先執行這一行指令：


eval $(minikube docker-env)

這行指令的魔法在於，它會把你的終端機設定指向 Minikube 內部的 Docker。之後你再執行 docker build -t my-app:v1 .，這個鏡像就會直接出現在 Minikube 的肚子裡了。這時候你只要把 Kubernetes 的 Deployment 設定檔裡的 imagePullPolicy 改成 IfNotPresent，Pod 就會優先使用本地鏡像，完全不需要再經過什麼推送到雲端的操作，速度快到讓你感動落淚。

不過，這種方法有一個小地雷，就是它只針對你當前開的這個終端機視窗有效。如果哪天你想換個視窗開發，記得要重新跑一次指令，不然你會發現不管怎麼 build，Pod 還是會報錯說找不到鏡像，我就曾經因為這點在同一個坑裡跌倒過兩次。

如果不想每次都執行指令，其實最好的做法是建立一個簡單的 alias，或者乾脆在開發階段養成習慣，把這行指令加進你的 .zshrc 或 .bashrc 裡。另外，如果你是用 Docker Desktop 這種比較新的環境，Minikube 也支援 --driver=docker 模式，這樣兩邊的環境會更無縫接軌。

下次開發時別再傻傻地等著 Docker Hub 上傳了，把這招學起來，保證你的開發體驗會好上好幾倍！
