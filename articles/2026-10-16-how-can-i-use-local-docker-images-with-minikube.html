How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 690 votes

I remember back when I was first getting comfortable with Kubernetes, I spent a solid three hours banging my head against the wall because my pods were stuck in an ImagePullBackOff loop. I was convinced I had tagged everything perfectly, but I kept forgetting that my local machine and the Minikube virtual machine are essentially two different worlds that don't know the other exists. It’s incredibly frustrating to sit there waiting for a slow company VPN to upload a 2GB image to a registry just to test a single line of code change.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside its own isolated environment, usually a VM or a container. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Kubernetes, however, is looking for that image inside the Minikube node’s Docker daemon. Since they are disconnected, Kubernetes tries to reach out to a public or private registry to find the image, fails, and gives up.

To fix this, you don't need to push your images anywhere. The easiest way I’ve found to bridge that gap is to point your local terminal directly at the Minikube Docker daemon. By running the eval command, your local docker CLI talks to the engine inside Minikube, meaning any image you build is instantly available to your clusters.


# Run this in your terminal to point your shell to Minikube's Docker
eval $(minikube docker-env)

# Now, build your image as you normally would
docker build -t my-local-app:latest .

Once you’ve run that eval command, you just need to make sure your Kubernetes deployment manifest has the imagePullPolicy set to IfNotPresent. If you leave it as Always, Kubernetes will still try to reach out to a remote registry, which will fail because your image only exists locally.


spec:
  containers:
  - name: my-app
    image: my-local-app:latest
    imagePullPolicy: IfNotPresent

If you ever want to switch back to your local machine's Docker daemon, just run eval $(minikube docker-env -u).

To keep your workflow clean and prevent future headaches, I highly recommend adopting a tagging strategy that explicitly separates your local development images from production ones. I always tag my local builds with :dev or :local, which helps me avoid accidental mismatches when I finally do push to a real registry for production deployments.

Hopefully, this saves you those extra hours of debugging I had to endure. Happy coding, and may your pods always reach the Running state on the first try!

別再為了測試把 Docker Image 推上雲端了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 那會兒，為了測試一個簡單的 API 改動，我每次都要把 Docker Image build 好，然後推到 Docker Hub，再從 Minikube 裡面 pull 下來。當時網路慢到想哭，有一次為了等那個 500MB 的 image 下載完，我連泡麵都吃完了，結果最後發現程式碼打錯一個字，那種「想把鍵盤吃掉」的崩潰感，相信各位工程師一定都懂。

其實這個問題的核心在於，Minikube 雖然跑在你的電腦上，但它其實是一個獨立的虛擬機（或容器），它有自己的一套 Docker Daemon。所以你在本機終端機輸入 docker build 時，那個 image 是存在你本機的 Docker 環境裡，Minikube 的節點根本看不見它，這就是為什麼你明明 build 好了，部署時卻一直噴 ImagePullBackOff 的原因。

要解決這個問題，最快的方法就是直接讓你的終端機「指揮」Minikube 內部的 Docker。你只要執行下面這行指令，就能把當前的 shell 環境切換到 Minikube 的 Docker Daemon：


eval $(minikube docker-env)

執行完之後，你再輸入 docker build -t my-app:v1 .，這時候的 image 就會直接建置在 Minikube 的環境裡了。接下來在你的 Deployment YAML 檔裡，記得把 imagePullPolicy 設定成 IfNotPresent，這樣 K8s 就會優先使用本地已經存在的 image，不用再去網路上辛苦尋找了。

不過要提醒大家，每次關掉終端機這個設定都會跑掉，如果你不想每次都手動執行，或者覺得這樣切換環境很麻煩，我建議乾脆在 .bashrc 或 .zshrc 裡面幫它加個 alias，甚至乾脆直接養成在開發環境用 minikube image load 指令的習慣。這招的好處是你不需要切換環境變數，直接把本機的 image 推進去就好，指令長這樣：


minikube image load my-app:v1

這招對我來說簡直是救命稻草，以後測試改動再也不用看著進度條發呆了。希望這些小心得能幫大家省下不少除錯的時間，我們下次見！
