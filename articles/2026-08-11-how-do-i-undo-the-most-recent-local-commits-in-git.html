How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27237 votes

I still remember the first time I accidentally committed a massive folder of local environment logs and API keys to my main branch. I had been coding for six hours straight, my brain was basically mush, and the second I hit enter on that git commit, my stomach dropped through the floor. I spent the next two hours sweating over whether I had just permanently exposed my production credentials to the cloud, cursing my lack of a .gitignore file.

The reason we get into this mess is that Git is designed to be a persistent history tracker. When you run git commit, you’re essentially carving your changes into stone. Git doesn't "know" you made a mistake; it just assumes you’re an expert who meant to include every single staged file. Since we’re all human, we often get ahead of ourselves, stage everything with a lazy git add ., and finalize a commit before double-checking what actually went into the index.

If you haven’t pushed your work to a remote repository yet, the fix is actually quite straightforward thanks to the git reset command. The command you’ll want to reach for is git reset --soft HEAD~1. This effectively moves the "pointer" of your branch back one step, undoing the commit while keeping all your changes staged and ready in the index. If you realize you included files you didn't mean to, you can use git reset HEAD~1 (the "mixed" reset) to unstage the files entirely, leaving your work in your working directory so you can selectively re-add only the files that belong there.


# Undo the commit, but keep the changes staged
git reset --soft HEAD~1

# Undo the commit AND unstage the files (safest for cleaning up)
git reset HEAD~1

If you really messed up and want to nuke the last commit and all changes associated with it—meaning you want to act like that work never happened—you can use git reset --hard HEAD~1. Just be careful, because this will permanently delete any uncommitted work in those files, and I’ve definitely lost a few hours of progress by being too trigger-happy with that command.

To prevent this nightmare in the future, I started using the -p (patch) flag whenever I stage my files. Instead of running git add ., I run git add -p. This forces Git to show me every single hunk of code I’m about to stage, letting me review the changes piece by piece before I commit. It takes an extra ten seconds, but it has saved me from countless "oops" moments.

Hope this saves you some of the panic I felt back in the day. Happy coding, and keep those commits clean!

手殘把垃圾塞進 Git 了？別怕，這招幫你救回還沒 Push 的 Commit

來源：Stack Overflow ↗ · 27237 票

那天半夜兩點，我正趕著要下班，腦袋已經呈現當機狀態，隨手就把一堆還在測試中的 Debug Log 和沒寫完的半成品 git commit 了下去。按下 Enter 的那一瞬間，我看著終端機顯示的「commit 成功」訊息，心臟直接漏跳一拍，因為我才剛意識到，我把不該上傳的敏感設定檔也一起打包進去了。那種「完了，我是不是要重寫整個專案」的恐慌感，真的只有半夜趕工的工程師才懂，簡直比看到 Production 環境掛掉還心酸。

其實 Git 會發生這種悲劇，通常就是因為我們太習慣 git commit -a 這種無腦指令，或是對當前所在的狀態沒看清楚。簡單來說，Git 就像是一個時光膠囊，當你執行 commit 時，它已經把你的變更打包進本地的歷史記錄裡了。如果你還沒執行 git push 把這些爛攤子推到遠端伺服器，那這一切都還有救，因為這些變更目前還只是在你的電腦裡「自嗨」而已，還沒影響到團隊的進度。

遇到這種情況，我通常會直接祭出 git reset 這個神器。如果你的目標只是想撤銷最後一次 commit，但想保留你剛才辛辛苦苦改好的檔案（也就是讓它們回到「還沒 commit，但是已經在暫存區」的狀態），我會執行這行：

git reset --soft HEAD~1

這行指令會把你的最後一次 commit 拆掉，檔案變更會回到你的 Stage 區，讓你能夠補救或是把那幾個不該進去的檔案移除。但如果你是那種「我剛剛改的東西全是垃圾，我只想通通刪掉，當作沒發生過」的情況，那就更狠一點，直接用 --hard：

git reset --hard HEAD~1

請務必小心，用了 --hard 之後，你剛剛寫的那些代碼是真的會憑空消失，想救都救不回來，千萬別在恍神的時候亂敲。

為了不要再經歷這種心臟病發作的時刻，我現在強迫自己養成一個好習慣：在 commit 之前，絕對會先輸入 git status 看一下到底有哪些檔案被變更了。甚至我會習慣用 git add -p 來一個檔案一個檔案檢查，雖然麻煩了一點，但這多花的那十秒鐘，真的能省下後續好幾個小時除錯的眼淚。

祝大家寫 code 順利，永遠都不用用到這些復原指令啦！
