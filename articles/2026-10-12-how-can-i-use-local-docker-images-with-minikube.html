How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the day I spent three hours debugging a ImagePullBackOff error, convinced that my YAML was fundamentally broken. I was sitting at my desk, caffeine-fueled and deeply annoyed, because I had a perfectly good image sitting right there in my terminal, but Kubernetes was stubbornly trying to reach out to the Docker Hub to find it. It’s one of those classic "aha!" moments in local Kubernetes development that makes you realize just how isolated your Minikube node really is from your host machine.

The reason this happens is simple: Minikube runs inside its own virtual machine or container environment. When you run docker build on your laptop, that image lives in your host's Docker daemon. Minikube has its own separate Docker daemon inside its node, and it has no idea what’s happening outside its own bubble. If you try to deploy a pod with imagePullPolicy: Always (which is often the default), K8s will try to look for that image in a remote registry, fail to find it, and leave you staring at a crash loop.

The fastest way I’ve found to bridge this gap without setting up a private registry is to point your local terminal directly to the Minikube Docker daemon. Instead of building the image on your machine and trying to push it, you just run a single command to redirect your shell, and then build inside the Minikube environment. On macOS or Linux, it’s as easy as running this:


eval $(minikube docker-env)

Once you’ve run that, any docker build command you execute will build the image directly inside the Minikube node. You can then verify it by running docker images in that same terminal, and you’ll see your custom image listed right there. Just make sure your Kubernetes deployment uses imagePullPolicy: IfNotPresent so it doesn't try to check a remote registry for the tag. If you’re using Windows, the process is slightly different because you’ll need to use PowerShell, but the concept remains the same—you're just telling your local tools to talk to the Minikube engine instead of your host engine.

To keep your sanity in the future, my biggest tip is to always use specific tags instead of relying on :latest. When you’re iterating quickly, it’s easy to get confused about which version of the image is actually sitting in the Minikube cache. By tagging your images with a version number or a short git hash, you’ll immediately know if the deployment is using the fresh build you just created or some stale relic from last week.

Hope this saves you from the same three-hour headache I dealt with back in the day. Happy coding, and let me know if you run into any other weird K8s behavior!

為什麼 Minikube 總是找不到我剛打包好的 Docker Image？

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，我為了測試一個簡單的 API 改動，反覆地在本地執行 docker build。結果每次把 YAML 丟進 Minikube，它就給我報一個 ImagePullBackOff 的錯誤，搞得我滿頭大汗。我當時心想：「大哥，我明明就在同台機器上啊，你是在跟我開什麼玩笑？」最崩潰的是，我一度以為是 Minikube 的網路連線有問題，還在那邊笨笨地去改 Docker Registry 設定，結果最後發現，原來這傢伙根本沒在看我電腦裡的倉庫。

這個問題的根本原因其實很單純：Minikube 本質上是一個跑在虛擬機（或容器）裡的獨立環境，它有自己的一套 Docker Daemon，跟我們宿主機（Host）上的 Docker 是完全隔離的。所以，當你用電腦上的 Docker 指令打包好映像檔後，Minikube 的節點根本「看不到」這些檔案，它只會習慣性地去 Docker Hub 或是指定的遠端倉庫抓取。如果你沒把東西推到網路上，它自然會抓不到，這就是為什麼你會看到那個討厭的錯誤訊息。

後來我學乖了，與其在那邊傻傻地推到 Docker Hub 再拉下來，不如直接把本地的 Docker 環境「指向」Minikube。你只要在終端機輸入這一行指令，就能讓當前的終端機直接操作 Minikube 內部的 Docker：


eval $(minikube docker-env)

執行完這行之後，你再跑一次 docker build -t my-app:v1 .，這時候產生的映像檔就會直接存進 Minikube 的肚子裡了。接著，記得把你的 Kubernetes YAML 裡的 imagePullPolicy 改成 IfNotPresent，這樣 Kubernetes 就會優先使用本地已有的映像檔，而不會再跑去外面瞎找。

為了避免以後又遇到這種「明明有圖卻讀不到」的詭異狀況，我現在習慣在開發時直接用 minikube image load 指令，或者乾脆養成習慣，在開始開發前先確認一下環境變數。只要記住，當你切換到不同專案或重啟 Minikube 時，環境變數可能會失效，這時再重跑一次 eval 就能省下大把除錯的時間。

希望這招能拯救你的開發效率，別再為了這種鬼打牆的問題浪費生命啦！
