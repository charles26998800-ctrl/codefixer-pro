Fixing RuntimeError: Input type and weight type should be the same in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a GPU training loop in PyTorch. I felt like a wizard after moving my model to the GPU with model.to(device), but then my terminal slapped me in the face with that dreaded RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same. I spent a good three hours convinced my GPU drivers were toast or that my PyTorch installation was corrupted, only to realize I’d completely forgotten to move the actual data tensors to the same device as the model.

The root cause here is actually quite simple, even if the error message sounds cryptic. In PyTorch, your model weights and your data tensors must live on the same hardware to perform matrix multiplications. When you move your model to the GPU using .to('cuda'), the model parameters are living on your graphics card's memory, but your inputs and labels are still sitting comfortably in your CPU's RAM. When you feed that CPU-bound data into the GPU-bound model, PyTorch throws a type mismatch error because it can’t perform operations between two different memory spaces.

To fix this, you need to be explicit about moving your data inside your training loop. I usually handle this by defining my device once at the top of my script and then calling .to(device) on every batch of data as soon as I pull it from the dataloader. Here is how I usually structure my loop to ensure everything stays in sync:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move the inputs and labels to the same device as the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    # Now the forward pass will run without issues
    outputs = model(inputs)
    ...

If you’re working with complex objects or custom datasets, it’s easy to miss a tensor hidden inside a dictionary or a list. To prevent this headache in the future, I’ve started writing a tiny helper function or a simple utility class that recursively moves any PyTorch tensors found in a batch to the target device. It saves me from having to manually move every single field in my data pipeline, and it’s a total lifesaver when you're refactoring your code for larger projects.

Hope this clears things up so you can get back to training your models without the constant debugging. Happy coding!

PyTorch 報錯解密：為什麼我的 Tensor 和 Model 總是在鬧分居？

來源：Stack Overflow ↗ · 202 票

記得剛開始碰 PyTorch 的時候，為了趕一個重要的 Deadine，我熬了整晚把模型架構刻出來，想說總算可以跑訓練了，結果按下 Run 的那一瞬間，螢幕噴出一長串紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。當時我真的差點把鍵盤砸了，心想：「我不是明明已經把 model 搬到 GPU 了嗎？你到底還想怎樣！」

其實這個錯誤的核心原因很單純：PyTorch 對硬體管理非常嚴格，它不允許你的模型在 GPU 上跑，但輸入的資料卻還留在 CPU 的記憶體裡。想像一下，你的模型就像個身價高貴的 GPU 貴族，而你的資料就像還在 CPU 泥地裡的平民，PyTorch 規定這兩者必須在同一個「場域」才能進行運算。當你只寫了 model.to(device)，卻忘了把每個 batch 的 inputs 和 labels 也推過去，它們就會因為身分（device）不符而拒絕溝通。

我當時是在那個 for 迴圈裡卡了半天，後來才意識到，寫 model.to(device) 只是把模型搬家，但資料是動態的，每一個迴圈進來的資料都是新的個體。要解決這個問題，你必須在迴圈內手動把資料也搬過去。我後來改成了這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵：把資料也移到同一個 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就可以正常計算 Loss 了

只要確保資料進迴圈後第一件事就是 .to(device)，這類問題基本上就能迎刃而解。為了避免下次又因為趕時間忘記這一步，我後來養成了一個習慣：我會直接寫一個小小的 helper function 或者乾脆用 data = [d.to(device) for d in data] 這種寫法來統一處理，甚至在寫專案設定檔時，就會把 device 設為一個全域變數，強迫自己寫 code 時隨時意識到它。

希望這篇心得能幫你省下寶貴的除錯時間，別再為了這種「空間錯位」的錯誤熬夜啦！
