Why React 18 Hydration Errors Are Driving You Crazy (And How to Fix Them)

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a Next.js project. I had just migrated a legacy app to React 18, feeling pretty smug about my performance gains, only to have the entire UI turn into a mess of console errors the moment I refreshed the page. I spent three hours—yes, three full hours—staring at my components, convinced I’d broken the laws of physics, only to realize I was just trying to render the current time on the server.

The core issue here is actually pretty simple once you stop pulling your hair out. When you use Server-Side Rendering (SSR), React generates the HTML on the server and sends it to the browser. Then, the client-side JavaScript kicks in to "hydrate" that static HTML and make it interactive. If the HTML the browser receives doesn't perfectly match the HTML the client-side React code generates on the first pass, React freaks out. It assumes something is fundamentally wrong and throws the hydration mismatch error. This often happens because of things like Date.now(), Math.random(), or local storage checks that return different values on the server versus the client.

To fix this, I’ve learned that you need to delay the rendering of the component until the app has actually mounted on the client. By using a simple useEffect hook, you can ensure that the part of your UI causing the mismatch only renders after the initial hydration is complete. Here is how I usually handle it in my projects:


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This renders only on the client: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By setting that isClient state inside useEffect, you’re telling React, "Hey, don't worry about this part until we're officially in the browser environment." Since useEffect doesn't run on the server, the server will render the "Loading..." fallback, and then the client will swap it out for the dynamic content immediately after mounting. It's clean, it's predictable, and it stops those nasty console errors from cluttering your logs.

The best way to prevent this in the future is to keep your server and client logic strictly separated. If you find yourself reaching for a browser-specific API like window or localStorage inside your render function, stop and move that logic into a useEffect or a dedicated client-side hook. If you can keep your server components pure and predictable, you'll rarely see that hydration error ever again.

Hope this helps you get your app back on track without losing your mind. Happy coding!

React 18 Hydration Error：那個讓人崩潰的 UI 不一致地獄

來源：Stack Overflow ↗ · 341 票

記得那天晚上，我正準備把一個好不容易刻完的功能推上線，結果一打開瀏覽器，控制台（Console）直接噴出一整排刺眼的紅色錯誤訊息：「Hydration failed because the initial UI does not match what was rendered on the server」。我當時盯著螢幕看了半天，心想：「這不是明明寫得好好的嗎？為什麼伺服器渲染出來的東西，跟瀏覽器跑出來的長得不一樣？」那種「我寫的 code 難道有自己的想法？」的無力感，真的是差點讓我直接把鍵盤砸了。

其實這問題的根本原因，就是 React 18 的「嚴格模式」在搞鬼。簡單來說，伺服器先在後端跑了一次程式碼，產生了靜態 HTML 給瀏覽器，但當瀏覽器接手進行 Hydration（水合）時，它發現這兩邊渲染出來的 DOM 結構竟然對不上。最常見的兇手就是我們喜歡寫的 new Date()、Math.random()，或是從 localStorage 讀取資料的邏輯。因為這些值在伺服器跑的時候是一個樣，到了瀏覽器執行時又變成了另一個樣，React 發現兩邊對不起來，就會直接跳出這個警告，甚至乾脆讓你的 UI 整個炸掉。

我後來發現，最簡單也最有效的解法，就是讓 React 先「裝傻」。既然伺服器不知道瀏覽器那邊的狀態，那我們就乾脆讓這個組件在掛載（Mount）完成後再渲染，確保兩邊的初始狀態一致。我通常會搭配 useEffect 來處理，像這樣：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>現在的時間是：{new Date().toLocaleTimeString()}</span> : null}
    </div>
  );
}

透過這種方式，伺服器渲染時只會看到一個空的佔位符（或 null），等到瀏覽器把 JavaScript 下載並執行完畢後，isClient 變成 true，組件才會真正渲染出內容。這樣一來，伺服器和瀏覽器就再也不會吵架了。

至於要怎麼預防下次再踩進這個坑？我建議大家養成一個好習慣：只要用到瀏覽器獨有的 API（像是 window、localStorage、或者任何會變動的隨機值），永遠不要直接放在組件的頂層初始化。盡量把這些邏輯封裝在 useEffect 裡面，或者乾脆用 typeof window !== 'undefined' 來做個簡單判斷。只要心裡多惦記著「這段 code 會不會在伺服器上跑？」這個問題，基本上就能避開 90% 的 Hydration 地獄。

希望這些經驗能幫你少掉幾根頭髮，下次遇到這種錯誤別太氣餒，其實它只是 React 在跟你鬧脾氣而已。
