Solving the "Hydration failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed because the initial UI does not match what was rendered on the server" error pop up in my console. I had just migrated a project to React 18 and felt like a genius until I opened the browser, only to see my app flickering and throwing a wall of red text that made me want to throw my coffee across the room. I spent three hours debugging my CSS and state management, convinced I’d broken the entire architecture, only to realize I was just trying to render a timestamp on the server that didn't match the one on my client.

At its core, this error is React's way of telling you that the HTML generated by your server didn't match the HTML generated by your client during the initial "hydration" phase. Next.js does a great job of pre-rendering your pages on the server, but when your client-side JavaScript kicks in, it tries to rebuild that same component. If you’re using something like new Date().toLocaleTimeString() or checking localStorage before the component mounts, the server renders one value, the client renders another, and React throws its hands up in frustration because it can't figure out which version is the "truth."

To fix this, the trick is to make sure your component doesn't attempt to render the dynamic data until it has officially mounted in the browser. I usually handle this by using a simple useEffect hook to toggle a "mounted" state. By initializing this state to false, I force the component to render a placeholder (or nothing at all) on the server, ensuring the client and server start on the same page. Once the component mounts on the client, the useEffect fires, updates the state, and the dynamic content finally renders where it belongs.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or return a loading skeleton
  }

  return (
    <div>
      Current Time: {new Date().toLocaleTimeString()}
    </div>
  );
}

If you really want to avoid this headache in the future, my best piece of advice is to be extremely careful with browser-only globals like window, document, or localStorage inside your render logic. Whenever you need to access those, wrap that specific logic in a custom hook or a conditional check that ensures the code path is only executed after the component has successfully mounted. It’s a small change, but it saves you from the nightmare of fighting the DOM during the hydration process.

Hopefully, this saves you from the same three-hour rabbit hole I fell down. Let me know if you run into any other weird hydration quirks!

被 React Hydration Error 搞到懷疑人生？其實兇手通常只有這幾個

來源：Stack Overflow ↗ · 341 票

那天半夜兩點，我正盯著螢幕準備把那個花了兩週重構的 Next.js 專案上線，結果一打開瀏覽器 Console，滿江紅的「Hydration failed」直接把我的睡意嚇飛。我心想：「明明本地跑得好好的，為什麼一上 SSR 就跟我玩這齣？」那一刻我真的差點把鍵盤給摔了，明明程式碼邏輯看起來完全沒問題，為什麼 React 這麼傲嬌，一定要因為伺服器渲染出來的 HTML 跟瀏覽器第一次產出的 DOM 不一樣就直接罷工？

其實說穿了，React 的 Hydration 機制就像是一個極度龜毛的強迫症患者。當你在伺服器端渲染（SSR）時，React 會先把 HTML 丟給瀏覽器，但當瀏覽器下載好 JS 並開始執行時，React 會再次檢查：「欸，我生成的 HTML 跟瀏覽器現在看到的結構一樣嗎？」只要有一丁點出入，比如伺服器給的是

但瀏覽器這端因為某些邏輯變成了 ，或者更常見的——時間戳記、隨機數、甚至是瀏覽器特定的 API 導致的渲染差異，它就會直接跳出那個惱人的錯誤，甚至乾脆把整個頁面重刷一遍，讓你的 SSR 優化瞬間變成了笑話。

我後來發現，最常踩的坑就是把 new Date() 或者 Math.random() 直接寫在元件的渲染邏輯裡。解決這個問題最直接的方法，就是確保元件在「伺服器端」和「客戶端第一次渲染」時拿到的是完全一樣的資料。如果你必須使用那些會變動的數值，那就把渲染的時間點往後推。我通常會用一個簡單的 useEffect 來處理，先讓元件保持初始狀態，等瀏覽器這端載入完畢後，再把真正的內容補上去：


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? new Date().toLocaleTimeString() : '載入中...'}
    </div>
  );
};

這樣做的好處是，React 在伺服器端會先渲染出「載入中...」，瀏覽器第一次接收到的也是「載入中...」，兩邊對上了，就不會報錯。等到頁面掛載好之後，useEffect 觸發，畫面才會變成正確的時間，這才是最安全的做法。

要預防這種鳥事再發生，建議大家平時開發時，盡量避免在元件頂層直接依賴 window 或 localStorage 這類只有瀏覽器才有的東西。我現在養成習慣，只要是跟瀏覽器環境高度綁定的邏輯，一律先用 typeof window !== 'undefined' 判斷，或者乾脆統一丟進 useEffect 裡處理。只要你把「伺服器端要跑的」跟「瀏覽器端要跑的」區分乾淨，基本上就不會再被這個 Hydration 錯誤折磨了。

希望這篇筆記能救你一命，下次遇到這種紅色錯誤訊息，先深呼吸，別急著懷疑人生！
