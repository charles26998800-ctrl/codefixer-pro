How to Fix the "Hydration failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I encountered this error while migrating an old project to React 18. I spent three hours late on a Tuesday night staring at my console, convinced that my server-side rendering logic was perfectly fine, only to realize I had a rogue Date.now() call tucked inside a component that was causing the server and client to disagree on what time it was. It’s one of those bugs that makes you want to throw your keyboard out the window because the app looks like it’s working, yet the console is screaming at you that everything is broken.

The reason this happens is actually quite logical once you peek under the hood of how Next.js works. When your app renders on the server, it generates the HTML and sends it to the browser. Once that HTML arrives, React takes over on the client side to "hydrate" it—basically attaching event listeners and turning it into a dynamic app. If the HTML the server generated doesn't match the HTML the client creates on its first render, React throws its hands up in frustration. It doesn't know which version to trust, so it gives you that hydration mismatch error rather than risking a janky UI.

To fix this, you need to ensure that the content being rendered on the initial pass is identical on both sides. The most common culprit is using browser-specific APIs like window, localStorage, or dynamic values like random numbers or timestamps during the initial render. My go-to solution is to delay the rendering of that component until the client has finished mounting. You can do this by using a simple useEffect hook to toggle a state variable.


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a simple skeleton/loading state
  }

  return (
    <div>
      {/* Now it's safe to use browser APIs or dynamic values here */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

By returning null or a static loading state on the server, you ensure that the server-rendered HTML is consistent. Once the component mounts on the client, isMounted becomes true, and the component re-renders with the dynamic data. This prevents the mismatch because the server doesn't even try to guess the dynamic content; it just waits for the client to handle it.

The best way to prevent this from happening in the future is to keep your components as "pure" as possible during the initial render. If you find yourself reaching for window or localStorage inside your main component body, stop and move that logic inside a useEffect or use a custom hook that checks for the window object's existence. Keeping your UI deterministic is the secret to a smooth, error-free React 18 experience.

Hope this saves you from the same headache I had, and happy coding!

救命！React 18 的 Hydration Error 到底要怎麼解？

來源：Stack Overflow ↗ · 341 票

還記得那天深夜，我正準備把改好的功能推上 Production，結果瀏覽器控制台突然跳出一堆紅色的 Hydration failed 錯誤訊息，整個頁面看起來簡直像被炸過一樣，排版亂得慘不忍睹。當時我盯著螢幕，內心真的只有無數個髒話，明明在本地端跑得好好的，為什麼部署到伺服器就開始跟我鬧脾氣？那種「明明程式碼沒錯，但它就是不聽話」的無力感，真的是每個前端工程師的惡夢。

其實這個問題的根本原因，說穿了就是 React 的「認知失調」。當你使用 Next.js 做 SSR（伺服器端渲染）時，伺服器會先產生一份 HTML 發送給瀏覽器，但 React 在瀏覽器啟動時，會執行一次 hydrate 過程，把事件綁定上去。如果伺服器算出來的 HTML 結構，跟客戶端瀏覽器第一次渲染的結果長得不一樣，React 就會嚇得直接報錯。最常見的兇手通常是時間戳記、隨機亂數，或者是像 typeof window !== 'undefined' 這種判斷式，導致兩邊邏輯出現了時間差。

我當時踩過最痛的一次坑，是因為我在元件裡直接用了 new Date().toLocaleTimeString()，這東西在伺服器跑的時間跟瀏覽器執行時根本對不上，那一瞬間崩潰的心情真的難以言喻。後來我發現，要解決這類問題，最乾淨的方法就是把這些「不確定因素」移到 useEffect 裡，因為 useEffect 只會在瀏覽器端執行，伺服器根本不會去碰它。

例如，如果你有個元件需要顯示當前時間，千萬不要直接寫在渲染邏輯裡，試試看這樣改：


import { useState, useEffect } from 'react';

function TimeComponent() {
  const [time, setTime] = useState(null);

  useEffect(() => {
    // 這樣伺服器只會拿到 null，等到瀏覽器載入後才補上真實時間
    setTime(new Date().toLocaleTimeString());
  }, []);

  return <div>當前時間: {time ?? '載入中...'}</div>;
}

透過這種方式，伺服器端渲染出的 HTML 就會保持一致，等到瀏覽器把 JavaScript 載入完成，useEffect 才會觸發，這時候再把內容補上去，React 就不會因為結構不匹配而瘋狂報錯了。

至於怎麼預防這種問題再次發生，我現在養成了習慣，只要涉及到瀏覽器特有 API（像是 window、localStorage 或隨機數），我一定會強制規定自己把它們隔離在 useEffect 或 useLayoutEffect 裡面，或者直接使用 dynamic import 並設置 ssr: false。只要養成這種「伺服器端渲染要保持純粹」的思維模式，基本上就能避開 90% 的 Hydration 坑。

希望大家之後再看到這串紅字時，能像我一樣冷靜地把它解決掉，然後準時下班去喝杯咖啡！
