How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27251 votes

I’ll never forget the time I spent three hours refactoring a complex utility function, only to realize I’d accidentally staged and committed a massive, auto-generated build folder along with my changes. I hit the "commit" button with such smug confidence, then immediately felt that sinking pit in my stomach when I saw the file list. I was convinced I’d just nuked my progress and would have to manually revert every single line of code, but thankfully, Git is a lot more forgiving than it looks at first glance.

The root of this frustration usually comes down to how Git separates the "staging area" from the "commit history." When you run git commit, you’re essentially snapping a permanent photo of your index. If you haven't pushed that photo to a remote server yet, you’re in a unique position of power; your local history is still malleable. It’s not that you’ve broken anything—you’ve just created a "checkpoint" that you didn't actually want. The good news is that git reset is specifically designed to roll back that pointer to a previous state, effectively "undoing" the commit while keeping your files safely in your working directory.

To fix this, I always reach for git reset --soft HEAD~1. This command is my go-to because it moves the branch pointer back by one commit, but it leaves all your hard work sitting in your staging area, ready for you to tweak, unstage, or commit again properly.


# This undoes the commit but keeps your files staged and ready
git reset --soft HEAD~1

If you realize that you actually messed up the files entirely and want to wipe the changes from that commit completely—as if it never happened—you’ll want to use the --hard flag instead. Just be careful, because this will discard all the work you did in that commit.


# This is the "nuke it" option—be very careful!
git reset --hard HEAD~1

If you just want to unstage the files but keep the changes in your working directory so you can selectively re-add them, you can use git reset HEAD~1. It’s essentially the default behavior, and it’s a lifesaver when I’ve lumped too many unrelated changes into one big, messy commit.

To keep this from happening again, I’ve started making it a habit to run git status right before I hit that commit button every single time. It sounds simple, but that five-second pause to scan the list of files has saved me from so many "oops" moments that I can’t even count them anymore.

Hope this saves you some of the panic I felt during my first few months with Git. Let me know if you run into any other weird edge cases!

手滑把不該 commit 的檔案推上去了？別慌，Git 救得回來

來源：Stack Overflow ↗ · 27251 票

記得剛當菜鳥工程師那會兒，有次為了趕下班，想說把手邊的功能 commit 一下，結果沒注意看 git status，直接 git add . 然後 git commit -m "update" 就送出了。直到我瞄到終端機噴出一堆包含敏感金鑰和測試用垃圾檔案的紀錄，心臟差點沒停掉，那種冷汗直流、覺得自己明天就要被開除的崩潰感，真的這輩子忘不了。

其實這問題的根本原因很簡單，就是我們太依賴「全選」這個動作了。Git 的 commit 就像是幫你的專案拍了一張快照，一旦按下了快門，那個當下的所有變更都會被鎖進紀錄裡。重點是，只要你還沒把這些髒東西 git push 到遠端伺服器，你的 Git 紀錄其實都還只是「私人檔案」，想怎麼改、怎麼刪，完全是你說了算，根本不用擔心會搞壞團隊的進度。

當時我發現這個慘案後，第一時間就是先深呼吸，然後用 git reset 把這顆「地雷」拆掉。最常用的招式就是 git reset --soft HEAD~1，這行指令會直接把剛剛那個 commit 撤銷，但神奇的是，你剛剛辛苦寫的程式碼變更，會乖乖留在你的暫存區（Staging Area）裡，讓你還有機會把不該加進去的檔案移出清單。如果你連程式碼都不想要了，想徹底回到 commit 之前的樣子，那就狠一點用 git reset --hard HEAD~1，這招直接把檔案狀態重置到上次 commit 的樣子，操作前記得確認你真的不想留任何東西，不然真的會欲哭無淚。

為了避免下次再發生這種「手滑悲劇」，我現在養成了習慣，在 commit 之前一定會先打個 git status，確認一下到底有哪些檔案被標記成綠色的。如果懶得一個一個檢查，我強烈建議裝個 Git 的 GUI 工具，或是直接在編輯器裡看變更清單，把「全選」的習慣戒掉，改用「選取特定檔案」來 commit。畢竟預防勝於治療，多花那五秒鐘檢查，絕對比事後在那邊冷汗直流要划算得多。

總之，Git 的後悔藥其實挺好吃的，只要還沒 push 出去，天都塌不下來，下次遇到別慌，冷靜執行指令就好啦！
