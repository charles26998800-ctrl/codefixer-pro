How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a training loop on my brand-new GPU rig. I was so excited to see those iterations fly by, but the second I hit run, my terminal turned into a wall of red text screaming about a RuntimeError. I spent three hours—yes, three full hours—debugging my model architecture and checking my data loaders, only to realize I’d completely forgotten to move the input tensors to the device. It’s one of those classic "welcome to deep learning" moments that makes you want to throw your keyboard out the window.

The reason this happens is actually pretty straightforward, even if it feels like a headache at the time. PyTorch is very strict about where your data lives. When you call model.to(device), you’re successfully moving all your model parameters and buffers onto the GPU. However, the data coming out of your DataLoader defaults to the CPU. Since the GPU can't perform math on data that's still sitting in your system RAM, PyTorch throws a type mismatch error because it’s trying to do arithmetic between a FloatTensor (CPU) and a cuda.FloatTensor (GPU). It’s essentially a language barrier between your hardware components.

To fix this, you have to explicitly move your input tensors onto the same device as your model during every iteration of your training loop. I usually handle this right after pulling the data from the loader. Here’s the snippet that saves the day:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move the inputs and labels to the device before passing them to the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # Proceed with your loss calculation...

If you’re working with a complex data structure like a dictionary or a list, you might need to iterate through them and move each one individually, but for most standard pipelines, the approach above does the trick.

If you want to prevent this from ever ruining your day again, my biggest tip is to write a small helper function or a custom collate_fn that handles device placement automatically. Better yet, get into the habit of writing a generic to_device utility that checks the type of your data and moves it recursively. Once you build that into your boilerplate code, you’ll never have to worry about this specific runtime error again.

Hope this clears things up so you can get back to training your models. Happy coding, and may your loss curves always trend downward!

救命！PyTorch 的 GPU 裝置不匹配地獄：RuntimeError: Input type and weight type should be the same

來源：Stack Overflow ↗ · 202 票

還記得剛開始接觸 PyTorch 的時候，我滿心歡喜地把模型搬到 GPU 上，想說終於可以享受飛快訓練的快感，結果按下執行鍵不到三秒，螢幕直接噴出一大串紅色錯誤訊息。當下我真的差點崩潰，明明 model 都已經 .to(device) 了，為什麼程式還在那邊跟我吵說輸入的 FloatTensor 跟權重的 cuda.FloatTensor 不一樣？看著那行該死的錯誤訊息，我坐在電腦前盯了半小時，心裡想著：「這不是已經丟進 GPU 了嗎？到底是在演哪齣？」

其實說穿了，這就是 PyTorch 對「裝置一致性」的潔癖。簡單來說，PyTorch 要求參與計算的所有物件——無論是模型權重還是你餵進去的數據——必須住在同一個「房間」裡。如果你把模型搬到了 GPU（cuda），但你的數據還留在 CPU（main memory）上，它們就像兩個不同時空的人，根本無法對話。這就是為什麼你的模型在 GPU 裡大喊「給我資料」，而你的資料卻還在 CPU 裡慢吞吞地排隊，最後系統只好報錯中斷。

解決這個問題的方法其實很單純，就是要把每一批進來的 inputs 和 labels 同步搬到跟模型一樣的地方。我後來養成了習慣，在 for 迴圈讀取資料的時候，順手加一行 .to(device)，問題就迎刃而解了：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！把資料也強制遷移到跟模型同一個裝置
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也要確保 labels 在正確的裝置上
    loss = criterion(outputs, labels)

為了避免以後再被這個問題搞到心態爆炸，我後來寫程式時會習慣把 device 設定設成全域變數，或是寫一個小工具函式來統一處理搬移。最保險的做法，就是永遠不要假設資料會自動跟著模型走，只要看到 inputs，心裡就要有個反射動作：「這傢伙搬家了沒？」

這坑我當年可是踩得夠深，希望你們看完這篇能少走點彎路，早點下班回家休息。祝大家模型訓練順利，GPU 永遠不會報錯！
