How to Fix the "digital envelope routines::unsupported" Error in React

Source: Stack Overflow ↗ · 2572 votes

I still remember the day I upgraded my Node.js version on a whim, thinking I was doing my future self a favor by staying current. Within minutes, every single one of my local development servers started spitting out that cryptic error:0308010C:digital envelope routines::unsupported message, and I honestly thought I’d nuked my entire environment. I spent three hours digging through node_modules, convincing myself I had some sort of dependency hell, only to realize it was just a massive breaking change in the underlying crypto library.

The reason this happens is actually quite straightforward once you peel back the layers. When Node.js bumped up to version 17 and beyond, they switched to OpenSSL 3.0 as the default. This version is much stricter about the algorithms it allows, and it essentially deprecated the older, less secure hashing algorithms that many older Webpack versions and React scripts rely on. Because your project is trying to use an algorithm that OpenSSL 3.0 no longer trusts, it throws this "unsupported" error as a security guardrail. It’s frustrating because it’s usually not your code that's broken—it's the build tools you're using.

Fixing this is a breeze if you know where to look. Since we don't want to downgrade our entire Node.js installation just to keep an old project running, we can use an environment variable to tell Node to use the legacy provider. If you're on a Mac or Linux machine, you can patch this directly in your package.json file by modifying your start script:


"scripts": {
  "start": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

If you’re working on Windows, the syntax changes slightly because of how the command prompt handles environment variables, so you'll want to use set instead:


"scripts": {
  "start": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

Once you save that file and run your command again, the error should vanish instantly. If you find yourself doing this across a dozen projects, you can even set this as a global environment variable in your .bashrc or .zshrc file, though I usually prefer keeping it scoped to the specific project so I don't forget why I did it later.

To keep this from biting you in the future, my best advice is to embrace version managers like nvm (Node Version Manager). Instead of relying on the global Node version installed on your system, keep a .nvmrc file in the root of your React projects. That way, whenever you cd into a project folder, you can just run nvm use and ensure you're working in an environment that actually matches your project's dependencies. It saves so much headache when you're jumping between legacy codebases and modern ones.

Hope this saves you those hours of debugging I wasted! Happy coding and keep your dependencies clean.

救命！React 專案噴出 error:0308010C，Node.js 版本更新後的崩潰日常

來源：Stack Overflow ↗ · 2572 票

還記得某個週五下午，我正準備把剛寫好的 React 小功能推上測試環境，結果才剛敲下 npm start，終端機就噴出一堆紅通通的錯誤訊息，那個 error:0308010C 直接映入眼簾。當下我真的差點崩潰，心想「不是啊，昨天才好好的，今天怎麼連專案都跑不起來？」，這簡直是工程師最不想在週末前夕遇到的靈異事件。

其實這背後的原因一點都不玄學，主要就是 Node.js 在 v17 版本後，底層的加密演算法換成了 OpenSSL 3.0，這傢伙對於安全性要求比較高，導致以前舊版 Webpack 用的一些加密方式直接被判定為「不安全」或是「不支援」。簡單來說，就是你的舊專案還在用比較舊的打包工具，但你的 Node.js 已經跑得太快，兩邊語言不通，才會蹦出這個「數位信封常式不支援」的怪錯。

當初我發現這個問題時，第一個反應就是去查 Stack Overflow，發現這真的是全球工程師的共同痛點。解決方法其實不難，最直接的手段就是告訴 Node.js：「嘿，請你暫時放寬一點標準，用回舊版的加密模式吧！」如果你是用 Mac 或 Linux，只要在啟動專案的指令前加上環境變數設定就好，像這樣：


export NODE_OPTIONS=--openssl-legacy-provider
npm start

如果你是 Windows 用戶，那就要稍微改一下 package.json 裡的 scripts，把啟動指令改成：


"scripts": {
  "start": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

改完之後再跑一次，看著熟悉的編譯畫面跑出來，那種感動真的無法言喻。不過說實話，這只是治標不治本，最根本的預防方式還是要乖乖面對現實。建議大家平時開發時，儘量使用 nvm (Node Version Manager) 來管理版本，針對不同的老舊專案，切換成當時合適的 LTS 版本執行，才不會因為強行升級 Node.js 而讓舊程式碼原地爆炸。

以後遇到這種莫名其妙的錯誤，先別急著重灌電腦，通常都是版本更新惹的禍。希望這招能幫你省下不少找 bug 的頭髮，我們下次見！
