How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still vividly remember the first time I encountered this error back when I was training my first ResNet model on a local GPU. I had spent nearly three hours debugging my custom dataset loader, convinced that my preprocessing pipeline was the culprit, only to realize I’d completely forgotten to move my tensors to the device. I honestly felt like throwing my keyboard out the window when I saw that cryptic mismatch error pop up for the tenth time, but it’s a classic rite of passage for every PyTorch developer.

The reason this happens is actually quite straightforward once you stop seeing it as a wall and start seeing it as a mismatch in memory location. PyTorch is extremely strict about where your data lives; if your model parameters are sitting comfortably on your GPU (the cuda device), but your input data is still hanging out in your system's RAM (the cpu device), the underlying C++ code hits a wall. The CPU and GPU operate in different memory spaces, and PyTorch won't implicitly move your data across that bridge for you because that operation can be a silent performance killer. It forces you to be explicit about where your data is living so you don't accidentally tank your training loop's throughput.

To fix this, you need to ensure that the tensors you pull from your dataloader are explicitly sent to the same device as your model. I usually handle this inside the training loop right after I unpack my batch. It’s a quick one-liner that saves you a massive headache. Here is the snippet I use to keep things running smoothly:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the line that solves the mismatch
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you want to prevent this from ever ruining your day again, my best tip is to write a small helper function or a custom wrapper for your training step that automatically handles the device transfer. Instead of manually calling .to(device) everywhere, I often define a simple move_to(obj, device) utility that recursively checks for tensors and moves them. Keeping that logic centralized means you’ll never have to hunt down a dangling FloatTensor in a massive codebase ever again.

Hope this helps you get your model training without any more crashes. Happy coding, and may your gradients always converge!

PyTorch 的老朋友：RuntimeError: Input type and weight type should be the same

來源：Stack Overflow ↗ · 202 票

還記得剛開始接觸 PyTorch 那陣子，為了訓練一個模型，我興沖沖地把筆電插上電，寫好訓練迴圈後按下 Run，心想這下總算能看見 Loss 下降了吧。結果螢幕一閃，噴出一長串紅通通的錯誤訊息 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same，當時我盯著螢幕看了十分鐘，心裡只有一句：「這不是已經把 model 送進 GPU 了嗎？你到底還想怎樣！」

其實這問題發生得特別冤。簡單來說，PyTorch 是一個非常講究「門當戶對」的框架。雖然你把模型（weights）放到了 GPU 上，但你的資料（input）卻還懶洋洋地待在 CPU 的記憶體裡。當模型準備好要運算時，它發現自己手上的參數是 CUDA 版本，但你餵給它的卻是普通的 FloatTensor，兩邊根本不在同一個頻道上，就像你拿著台幣去買要用美金結帳的商品，系統當然會直接拒絕交易。

我當初被這個坑卡了整整一個下午，後來才發現解決方法其實簡單到讓人想笑。你不需要在每次迴圈裡重新搬移模型，只要在讀取資料時，順手把 input 和 label 也「打包」送進同一個 device 就行了。我現在的寫法通常會這樣處理：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就在這裡，要把資料丟進跟模型一樣的 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... 後續的訓練步驟

後來為了避免再發生這種低級錯誤，我養成了一個習慣，就是永遠不要在程式碼各處硬寫 cuda()，而是定義好 device 後，不管是模型定義還是資料讀取，全部統一透過 .to(device) 來處理。這樣就算哪天換了伺服器，或者要在沒有顯卡的機器上跑測試，只要改一行 device 的定義，整套邏輯就都能跑得通，再也不用為了這些瑣碎的型別不一致崩潰了。

希望這招能幫你省下寶貴的除錯時間，快回去把模型跑起來吧！
