How to Fix "Hydration failed" Errors in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error staring back at me in the browser console. I had spent three hours meticulously crafting a dynamic dashboard, only to have the entire app flicker and explode the moment it loaded, leaving me with a screen full of garbled text and a deep sense of existential dread. It felt like I was fighting the framework rather than building with it, but once I wrapped my head around the lifecycle of server-side rendering, it all started to click.

The root cause of this headache is actually quite logical: React is trying to be efficient by comparing the HTML generated on the server with the HTML generated by your client-side code. When your server sends down one version of the DOM—usually because it doesn't have access to browser-specific APIs like window or localStorage—and your client-side React tries to render something slightly different, the reconciliation process breaks. It’s essentially a mismatch in the "source of truth," and because React 18 is much stricter about these differences than previous versions, it throws a hydration error rather than trying to patch the DOM and potentially causing performance issues.

The most common fix I’ve found for this is to delay the rendering of the component until the client has fully mounted. If you have code that relies on browser-only data, you should use a useEffect hook to toggle a state variable. By default, you render nothing (or a loading skeleton), and once the component mounts on the client, you switch that state to true to render your actual UI. 


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This only shows up after hydration: {window.innerWidth}px</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
};

Another trick I use when I’m dealing with third-party libraries that inject their own markup is the suppressHydrationWarning attribute. If you have a timestamp or a dynamic value that you know will change immediately on the client and you don't care about the initial server-side match, you can add suppressHydrationWarning={true} to the specific HTML tag. Just be careful with this one, as it’s a bit of a "nuclear" option that ignores the mismatch entirely.

To keep this from biting you in the future, my best advice is to embrace the "Server-First" mindset. Whenever you're writing a component, ask yourself if the data you're using is truly available on the server. If it isn't, don't try to force it into the initial render. Instead, build your components to handle a "loading" state by default, and only inject the browser-specific logic once the client takes over.

Hope this saves you a few hours of debugging and lets you get back to building cool stuff. Good luck with the code!

React 18 Hydration 錯誤：那個讓我懷疑人生的「UI 不匹配」惡夢

來源：Stack Overflow ↗ · 341 票

我還記得那天晚上，為了趕一個專案的 Demo，我興沖沖地把 Next.js 升級到 React 18，結果一打開瀏覽器，控制台直接炸出一片紅字：「Hydration failed because the initial UI does not match what was rendered on the server」。我當時盯著螢幕看了十分鐘，心裡想著：「我程式碼明明都長一樣啊，到底是在不匹配什麼？」那種明明寫對了卻被系統打臉的無力感，真的是工程師職涯中最想原地退休的時刻之一。

其實這個問題說穿了，就是 React 的「雙胞胎機制」鬧脾氣。在 Next.js 的 SSR 架構下，伺服器會先渲染一份 HTML 給瀏覽器，等 JavaScript 下載完後，React 會在客戶端進行「Hydration（注水）」，把事件綁定上去。問題是，如果伺服器算出來的結果，跟瀏覽器第一次跑 React 時算出來的結果有一丁點細微的差異——比如時間戳記、隨機亂數，或是瀏覽器特有的 window 物件——React 就會崩潰，覺得這兩份東西根本不是同一個，乾脆直接報錯給你看。

我後來發現，最常見的兇手就是我們在渲染時用了 new Date() 這種會變動的東西，或者是在組件裡直接呼叫了 typeof window !== 'undefined' 來判斷環境。解決這個問題最乾淨的做法，就是讓 React 先跳過第一次的渲染差異。我後來學乖了，把需要依賴客戶端狀態的組件包裝起來，確保它們只在掛載完成後才顯示。我通常會寫一個簡單的 useEffect 來處理這個狀態，像這樣：


import { useState, useEffect } from 'react';

function ClientOnlyComponent({ children }) {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null; // 或者你可以放個簡單的 loading skeleton
  }

  return <>{children}</>;
}

這樣一來，伺服器端渲染時只會拿到一個乾淨的空殼，等到瀏覽器真的準備好要「注水」時，組件才正式顯現，這樣兩邊的 UI 就會乖乖對齊了。

至於怎麼預防這種惱人的狀況再次發生？我現在養成一個習慣，就是盡量在組件內少用那些會跟瀏覽器環境綁定的邏輯，如果真的非用不可，一定要加上 useEffect 來確保它只在客戶端執行。另外，檢查你的 HTML 結構也很重要，像是不小心在
