How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 690 votes

I remember the first time I set up a local Kubernetes cluster, I spent a good three hours staring at ImagePullBackOff errors, absolutely convinced my YAML was perfect. I kept rebuilding my image locally, tagging it, and wondering why my Minikube pod refused to see the changes, only to realize I was essentially trying to look for a book in a library that didn't know the shelf existed. It’s one of those classic "aha!" moments that makes you feel like a genius and an idiot at the same time.

The reason this happens is actually quite simple: Minikube runs inside its own isolated virtual machine or container. When you run docker build on your laptop, that image lives in your host machine's Docker daemon. Minikube’s internal Kubernetes node has no idea that your host exists, so when you tell it to pull an image, it checks its own internal registry, fails to find it, and tries to reach out to Docker Hub. Since your image isn't public, the pull fails, and your deployment sits there in a state of perpetual sadness.

The cleanest way I’ve found to fix this is to point your local terminal directly at the Docker daemon running inside Minikube. By running a single command, you can make your host's Docker client talk to the one inside the cluster. Open your terminal and run this:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. You don't need to push or pull anything; just build your image, update your deployment, and Kubernetes will see it immediately. Just keep in mind that this only applies to the current terminal session, so if you open a new tab, you'll need to run it again. Also, make sure your Kubernetes deployment's imagePullPolicy is set to IfNotPresent or Never, otherwise, K8s might still try to reach out to an external registry and fail.

To prevent this headache in the future, I highly recommend adding a small alias to your .bashrc or .zshrc file. Whenever I'm starting a new session, I just type eval-minikube to sync my environment instantly. It saves me from having to remember the exact syntax every time I switch projects, and it keeps my local development loop lightning fast.

Happy coding, and may your pods always reach the Running state on the first try!

別再把 image 推上 Docker Hub 了！在 Minikube 使用本地 Docker 映像檔的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，為了測試一個簡單的 API 改動，我傻傻地每次都把 image build 好、標上 tag，然後推送到 Docker Hub，再從 Minikube 裡 pull 下來。那時候網路慢得要命，我光是盯著那個 ImagePullBackOff 的錯誤訊息發呆，就浪費了人生中好幾個小時，搞到最後差點要把筆電砸了，心想：「難道我每改一行 code 都要經歷一次這種折磨嗎？」

其實這一切都是因為 Minikube 本質上是一個跑在虛擬機（或是容器）裡的獨立環境。當你在終端機執行 docker build 時，你是在「宿主機」的 Docker daemon 裡建構映像檔，但 Minikube 根本看不見那邊啊！它就像個被關在圍牆裡的小圈圈，只能存取自己內部的 registry。所以當你呼叫它去 pull 一個它根本沒聽過的 image 時，它當然只能兩手一攤給你報錯。

要解決這個問題，最直覺的做法就是把你的環境變數直接「指」向 Minikube 內部的 Docker daemon。只要在終端機輸入這行魔法咒語：


eval $(minikube docker-env)

執行完這行之後，你的終端機就會暫時「借用」Minikube 內部的 Docker 環境。這時候你再執行 docker build -t my-app:v1 .，這個 image 就會直接被 build 進 Minikube 的肚子裡。之後在 Kubernetes 的 YAML 檔裡，記得把 imagePullPolicy 改成 IfNotPresent，這樣它就不會笨笨地跑到外面去抓，直接用你剛剛建立好的在地映像檔，開發效率瞬間提升十倍！

不過，這種方法有一個小缺點，就是你每次開新的終端機視窗都要重新跑一次 eval。如果你想一勞永逸，或者不想每次都切換環境，其實可以直接用 minikube image load 這個指令。舉個例子，先在外面 build 好 image，然後直接把它「投遞」進去：


minikube image load my-app:v1

這招我覺得更乾淨，因為它不需要修改你的 shell 環境變數，也不會搞亂你本機原本的 Docker 設定。

至於怎麼預防這種鬼打牆的情況再次發生？我強烈建議你把這些 build 的流程寫成 Makefile。只要在 Makefile 裡包裝好 minikube image load 的指令，以後不管你是誰來接手這個專案，只要執行 make build-and-load，一切就自動搞定。別再手動去記這些指令了，把時間花在寫程式上，而不是花在跟 Kubernetes 的存取權限搏鬥，這才是工程師該有的生活品質啊。

下次如果又看到 ErrImagePull，記得先深呼吸，那通常只是因為你忘了告訴 Minikube 你的寶貝 image 放在哪裡而已！
