How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27229 votes

I still remember the first time I accidentally committed my local .env file—complete with real API keys—to a repo I was just about to push to production. My heart sank when I saw that "1 commit ahead" notification, and I spent a solid hour frantically googling how to fix it without nuking my entire project history. It’s a classic rite of passage for every developer, and if you’ve found yourself staring at your terminal with that same pit of dread, don't worry, you’re definitely not alone.

The reason we get into this mess is usually just a lack of attention during the git add process. We tend to get lazy and run git add . or git add -A when we’re in a rush, inadvertently staging files we never intended to track. Git is designed to be a ledger of your work, and once you run git commit, that snapshot is officially recorded in your local database. Because Git is so good at keeping history, it doesn't just "forget" what you did, which is why you have to explicitly tell it to roll back the clock.

If you’re in this spot, the command you’re looking for is git reset. The beauty of this is that it lets you choose exactly what happens to the files you just committed. If I want to undo the commit but keep all my changes in the staging area (so I can fix the file list), I use a soft reset.


git reset --soft HEAD~1

This command moves your branch pointer back by one, effectively "undoing" the commit while leaving all your files right where they were, sitting in your staging area ready to be adjusted. If you want to go a step further and completely unstage everything so you can start the selection process from scratch, I go with a mixed reset instead:


git reset HEAD~1

This keeps your actual file changes intact in your working directory, but it removes them from the staging area. Now you can use git status to see exactly what’s going on, remove the files you didn't mean to include, and make a clean commit. Just remember, never use --hard unless you’re absolutely certain you want to destroy every change you’ve made since that commit, because there’s no easy way to get that code back once it’s gone.

To prevent this from becoming a regular habit, I’ve started using git add -p (the patch flag) instead of adding everything blindly. It forces me to review every single hunk of code I’m about to commit, which has saved me from committing debug logs and wrong configs more times than I care to admit.

Hope this gets your repo back in shape and saves you some stress today. Happy coding!

手殘救星：還沒推上遠端前的 Git Commit 到底怎麼刪？

來源：Stack Overflow ↗ · 27229 票

記得有一次凌晨三點，我正趕著把一個重要功能上線，腦袋已經快要當機。我一個手滑，把一堆還在測試中的 Debug Log 和亂七八糟的設定檔通通 commit 進去，甚至還不小心把剛寫好的 API 密鑰也一併送進了版控。那一刻心臟真的是停了一拍，螢幕上那一串「commit 成功」的訊息簡直像是在嘲笑我的無知，我當時真的差點崩潰，想說這下完蛋了，要是直接推上去，明天大概就要去人事部報到了。

其實這背後的道理很單純，Git 的 commit 就像是你在玩遊戲時的存檔點。當你執行 git commit 時，Git 只是在你的本地倉庫把這些變更紀錄起來，還沒有傳到遠端的伺服器（像是 GitHub 或 GitLab）。所以只要這些髒東西還沒離開你的電腦，我們就有絕對的掌控權，可以透過「時光倒流」的方式把這些紀錄抹掉，就像這一切從來沒發生過一樣。

我當時冷靜下來後，用的就是 git reset 這個最強大的指令。如果你只是想把剛剛那次 commit 撤銷，同時想把改過的檔案保留在工作目錄，好讓你重新整理一下再 commit，我建議你用這招：


git reset --soft HEAD~1

這行指令的意思是「把指標往回推一個位置」，而且 --soft 參數會幫你把剛剛 commit 的那些檔案全部留在「暫存區（Staging Area）」。這樣你就可以直接修正檔案，不用擔心檔案消失。如果你連這些檔案都不想要了，想徹底毀屍滅跡，那就直接改用 git reset --hard HEAD~1，不過這一招要小心，因為它會讓你剛剛做的所有修改直接蒸發，我以前就因為手快用了這招，結果把辛辛苦苦寫了一整晚的程式碼弄丟，盯著螢幕發愣了五分鐘才回過神來，那個痛苦真的是刻骨銘心。

為了避免這種心跳加速的情況再度發生，我現在養成了一個習慣：在 commit 之前，一定會先下 git status 檢查到底有哪些檔案要被送進去。如果真的怕檔案太多管不過來，我強烈建議你用 git add -p，它會一個區塊一個區塊地問你：「這個改動要不要加進來？」，這樣就能確保你不會因為一時粗心，把不該出現的檔案給包進去。

學會這幾招以後，下次手滑也不用怕了，Git 的強大就在於它給了我們無數次改過自新的機會。祝大家寫扣順利，再也不用凌晨三點在那邊冷汗直流！
