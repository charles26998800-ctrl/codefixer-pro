How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 688 votes

I remember the first time I set up Minikube, I felt like a genius until I tried to deploy a custom Go microservice. I spent three hours banging my head against the wall because my pod kept stuck in ImagePullBackOff, despite seeing my image staring back at me right there in my local docker images list. It’s infuriating when you’re just trying to iterate quickly and the tooling feels like it’s actively conspiring against your productivity.

The reason this happens is actually quite simple: Minikube runs inside its own isolated virtual machine or container. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Minikube, however, has its own internal Docker daemon that has no idea what’s happening outside its own borders. It’s like keeping your groceries in your neighbor’s fridge and wondering why you can’t find them in your own kitchen; they’re just not in the same environment.

The cleanest way I’ve found to solve this—without setting up a private registry or pushing to Docker Hub—is to point your local shell directly at the Minikube Docker daemon. Before you run your build command, you just need to run one line of code in your terminal:


eval $(minikube docker-env)

Once you run that, your local terminal is effectively "hooked" into the Minikube environment. Any docker build command you run now will build the image directly inside Minikube’s internal daemon. You can verify it worked by typing docker images, and you'll see your local image listed right there. Now, when you update your Kubernetes manifest, set the imagePullPolicy to IfNotPresent so K8s doesn't try to go out to the internet looking for an image that only exists locally.

To prevent this headache in the future, I highly recommend adding an alias to your .bashrc or .zshrc file. Whenever I'm starting a new session, I just type eval-minikube to sync my environment instantly. It’s a small quality-of-life change, but it’s saved me from countless hours of debugging deployment loops.

Hope this saves you some time today—happy coding!

別再把 Docker Image 推上 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 688 票

記得剛開始碰 Kubernetes 的時候，我真的快被 Minikube 搞瘋了。那時候我寫好一個微服務，想說在本地測試一下，結果每次改完程式碼，都要先 docker build，然後 docker push 到 Docker Hub，再回頭去 Minikube 下載。重點是，那個網路慢到我想哭，我花在等待上傳下載的時間，比實際寫程式還久。最崩潰的一次，我明明只是改了一行 log，結果為了測試，硬生生等了十分鐘才看到結果，那種想把電腦砸了的無力感，相信你一定懂。

其實會發生這種狀況，是因為 Minikube 本身是一個跑在虛擬機（或是另一個容器環境）裡的獨立世界。當你在你的 Mac 或 Windows 終端機打 docker build 時，那個 Image 是存在你本機的 Docker Daemon 裡，但 Minikube 的 Pod 根本看不到那個空間。對它來說，你沒把圖檔推到公開或私有 Registry，它就只能兩手一攤說「ImagePullBackOff」，完全找不到東西。

後來我發現，其實根本不需要繞遠路。最簡單的方法就是直接用 Minikube 內建的環境變數，把你的終端機「指向」Minikube 內部的 Docker Daemon。只要執行下面這一行：


eval $(minikube docker-env)

執行完之後，你現在下的任何 docker build 指令，都會直接在 Minikube 的環境裡打包。這時候你再跑 kubectl apply，它就能直接抓到剛建好的 Image，根本不需要什麼推送到遠端的步驟，速度快到讓你懷疑人生。如果你是用 Windows 的 PowerShell，記得要改成 minikube docker-env | Invoke-Expression。

為了避免以後又忘記，或者哪天換了個視窗又在那邊鬼打牆，我現在習慣在 ~/.zshrc 或 ~/.bashrc 裡加一個 alias。反正只要記得，每當我開一個新終端機要開發 K8s 專案時，先確認一下環境對不對就好。還有，如果哪天你發現 Docker 指令怎麼突然變慢了，或者連不上，記得檢查一下是不是還在 Minikube 的環境裡，這時候只要把環境變數切回來，或者重開視窗就沒事了。

希望這些小撇步能幫你省下不少等候時間，別再為了傳輸 Image 而浪費生命啦！
