Next.js Hydration Errors: Why Your Server and Client Aren't Talking

Source: Stack Overflow ↗ · 341 votes

I still vividly remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours deep into a late-night debugging session, convinced my logic was bulletproof, only to realize that a simple new Date() call was causing my entire application to crash the moment it hit the browser. I genuinely wanted to throw my laptop out the window because the UI looked perfectly fine for a split second before the React error overlay slapped me in the face.

The root cause of this frustration is actually quite logical once you peel back the layers of how Next.js works. When you use Server-Side Rendering (SSR), the server generates the initial HTML based on the state it has at that exact microsecond. When that HTML hits the client, React tries to "hydrate" it by attaching event listeners and turning those static elements into an interactive application. The problem triggers when the server-rendered HTML doesn't match the HTML generated by the client during that very first render. Since the server and client are essentially living in two different timelines, any discrepancy—like a localized timestamp, a random number, or a browser-specific check—causes React to panic and bail out of the hydration process.

To fix this, I stopped trying to force the server to guess the client's environment. The most reliable way to handle this is to defer the rendering of content that depends on browser-only state. I usually use a useEffect hook to set a piece of state once the component has officially mounted on the client side. By initializing that state to false and flipping it to true inside useEffect, I can ensure the UI only renders the problematic content after the hydration mismatch is no longer a risk.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>Rendered on the client: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

This approach works because useEffect only runs in the browser, meaning the server will always render the "Loading..." fallback, and the client will then update to show the actual data once it's safe to do so.

If you want to prevent this nightmare from happening again, my biggest tip is to always watch out for non-deterministic data in your initial render pass. If you're using libraries that rely on window, localStorage, or dynamic time stamps, wrap them in a custom hook or a simple boolean flag like the one above. It’s a small bit of extra boilerplate, but it saves you from the headache of fighting with React’s internal consistency checks.

Hope this clears up the confusion and saves you from a few hours of head-scratching. Happy coding, and may your builds stay green!

React 18 Hydration 錯誤：為什麼我的頁面又崩潰了？

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那個週末，我正想在 Next.js 專案裡大展身手，結果一打開瀏覽器，控制台那行紅通通的 "Hydration failed" 直接讓我心臟漏跳半拍。我看著畫面明明長得一樣，但網頁就是硬生生報錯，那種「我到底寫錯了什麼」的無力感，真的會讓人想把鍵盤直接丟出窗外，尤其是當你以為一切邏輯都寫得很完美的時候。

其實這問題的核心很單純，就是 React 在「伺服器端渲染出的 HTML」跟「瀏覽器第一次跑起來的 HTML」對不上。想像一下，你在伺服器端產生了一段 HTML，結果瀏覽器下載下來一跑，因為某些動態變數（像是 Date.now()、隨機亂數，或是瀏覽器特有的 localStorage）導致兩邊的結果有差異，React 就會覺得：「欸，這不是我當初送來的東西啊！」然後它就會直接放棄治療，報錯給你看。最痛苦的是，有時候只是因為 HTML 結構裡多了一個空格，或是你在 p 標籤裡面塞了個 div，這種隱形殺手往往花了我好幾個小時才抓到。

要解決這個問題，最直覺的作法就是確保該區塊「只在客戶端渲染」。我後來發現最穩的做法是利用 useEffect 來處理那些會變動的內容。當 React 偵測到組件掛載後，再把真正的資料填進去，這樣伺服器跟客戶端第一次的對接就不會吵架了。你可以試試看這樣的寫法：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>現在時間是：{new Date().toLocaleTimeString()}</p>
      ) : (
        <p>載入中...</p>
      )}
    </div>
  );
}

這個邏輯很簡單，就是先讓伺服器吐出一個佔位符，等瀏覽器執行完 JS 後，再把真正的內容補上，這樣兩邊的初始 UI 就會完全一致了。

至於怎麼預防這種鬼打牆的狀況，我現在養成一個習慣：只要看到跟時間、隨機數、或是用戶端存取相關的邏輯，一律強制用 useEffect 包起來。另外，寫 HTML 結構時也一定要嚴格遵守規範，別把 div 塞進 p 標籤，畢竟瀏覽器對 HTML 的容錯處理跟 React 的嚴謹要求是兩回事，多注意這些細節真的能省下不少加班時間。

希望大家下次遇到這個錯誤時，能比我當年冷靜一點，喝口水再戰吧！
