Fixing the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a React 18 project. I was convinced my code was perfect, yet my console was screaming at me with a wall of red text that made no sense. I spent three hours refactoring my entire component architecture, only to realize the culprit was a simple Date() call that was rendering differently on the server than it was on my laptop. It’s one of those bugs that makes you want to throw your keyboard out the window, but once you understand the mechanism, it becomes much easier to squash.

The core reason this happens is that React expects the HTML generated by your server to be an exact twin of the HTML generated by the browser during the first render. When you use Next.js, the server pre-renders your page into static HTML and sends it to the client. When React kicks in on the browser, it tries to "hydrate" that static HTML by attaching event listeners. If your component relies on data that changes between the server-side render and the client-side render—like a timestamp, a random number, or even local storage—React notices the mismatch and throws its hands up in frustration. It’s essentially saying, "Hey, this DOM node doesn't look like what I was promised," and since it can't guarantee a consistent UI, it forces a re-render.

To fix this, I’ve learned that the best approach is to defer the rendering of mismatch-prone content until after the component has mounted. I usually use a useEffect hook to toggle a state variable once the component is safely in the browser environment. Here is how I typically structure this pattern to keep things clean:


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      <h1>Welcome</h1>
      {isClient ? (
        <p>Current time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
};

By initializing isClient to false, the server renders the "Loading..." state. Once the browser takes over and the component mounts, the useEffect fires, updates the state to true, and React renders the actual dynamic content. Because the server and the initial client render now both agree on the "Loading..." state, the hydration process completes without a hitch.

The best way to prevent this in the future is to keep your components as pure as possible and be extremely mindful of browser-only APIs. If you find yourself needing to access window, localStorage, or dynamic timestamps, always wrap them in a check that ensures the code only executes after the component has mounted. It’s a bit of extra boilerplate, but it saves you from those late-night debugging sessions when you just want to ship your code.

Hope this helps you clear up those console errors and get back to building. Let me know if you run into any other weird hydration quirks!

React 18 Hydration Error：那個讓我加班到凌晨三點的「伺服器 vs. 客戶端」幽靈

來源：Stack Overflow ↗ · 341 票

還記得剛升級 React 18 那陣子，我滿心期待地想體驗 SSR 的效能優化，結果一跑起來，瀏覽器 Console 直接噴出一整排刺眼的紅色警告：「Hydration failed because the initial UI does not match what was rendered on the server」。當下我真的傻眼，明明程式碼看著都沒錯，怎麼伺服器渲染出來的 HTML 跟瀏覽器拿到的不一樣？那晚我看著螢幕，心裡想著「這不就是同樣的 Component 嗎？到底在不一致什麼啦！」結果為了查這問題，原本想早點下班追劇的我，最後直接跟螢幕對看熬到凌晨。

其實這個問題的核心很簡單，就是伺服器和瀏覽器這兩個「當事人」對同一段網頁內容有不同解讀。當 Next.js 在伺服器跑完渲染後，會把 HTML 丟給瀏覽器，瀏覽器在進行「Hydration（注入）」時會檢查內容是否跟伺服器產出的一模一樣。最常見的兇手就是我們用了 Date 物件、隨機數 Math.random()，或者是依賴了 window 或 localStorage 這類瀏覽器專屬的物件。因為伺服器根本沒有這些東西，所以一開始渲染時產生了空值或預設值，等瀏覽器接手後又填入了真實數據，React 一比對發現「咦，怎麼不一樣？」，於是就炸給你看了。

當時我發現自己是因為在 component 裡直接寫了 new Date().toLocaleDateString()，導致伺服器渲染時的時間戳跟瀏覽器執行時慢了幾毫秒，這細微的差異就成了壓垮駱駝的最後一根稻草。解決方案其實很直覺，就是確保在 Hydration 完成之前，兩邊看到的內容是一樣的。我後來學會了用 useEffect 來處理這類依賴瀏覽器環境的邏輯，或者乾脆強制讓元件只在客戶端渲染。你可以試著用一個簡單的 flag 來判斷：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? new Date().toLocaleDateString() : 'Loading...'}
    </div>
  );
}

透過這種方式，伺服器第一次渲染會顯示「Loading...」，等瀏覽器載入完成後，useEffect 觸發再把真正的日期換上去，這樣就不會跟伺服器渲染出來的 HTML 產生衝突。當然，如果你的專案很大，也可以考慮使用像 next/dynamic 配合 { ssr: false } 來直接跳過特定元件的伺服器渲染，這招在處理一些第三方 UI 套件時特別好用，省去不少麻煩。

要預防這種鳥事再發生，最有效的習慣就是養成「防禦性渲染」的思維。以後只要看到要存取 window、localStorage 或者任何會隨時間變動的資料，我都會反射性地先問自己：「這東西在伺服器上有嗎？」只要心裡有這個警鐘，通常就能在把 code 推上去前就把 bug 抓出來。

寫程式就是這樣，雖然偶爾會被這種 Bug 搞到懷疑人生，但解開那一刻的爽感還是挺值得的，下次遇到這類問題，記得先深呼吸再檢查這兩邊的狀態一致性就好啦。
