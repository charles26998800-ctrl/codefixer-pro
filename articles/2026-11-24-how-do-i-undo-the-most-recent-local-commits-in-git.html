How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27249 votes

I’ll never forget the time I spent three hours debugging a production build only to realize I’d accidentally committed my local .env file containing sensitive API keys to a public repo. I felt that cold wave of panic wash over me, convinced I’d just ruined my career before lunch, until I realized I hadn't pushed the changes yet. It’s a rite of passage for every developer, and if you’ve landed here, you’re likely staring at your terminal with that same pit in your stomach.

The reason this keeps happening is that Git is designed to be a ledger of your work, and by default, it assumes every commit you make is exactly what you intended to save. When you run git commit, you’re telling Git to create a permanent snapshot of your current state. Because Git tracks the history of your files so strictly, it doesn’t have a simple "undo" button in the GUI sense; you’re effectively telling the repository to rewrite its own history by moving the pointer back to a previous state.

To fix this, I always reach for git reset. The command you need depends on whether you want to keep your changes or throw them away entirely. If you want to undo the commit but keep your work in your staging area so you can fix the file selection, run:


git reset --soft HEAD~1

This moves the branch pointer back one commit, but leaves all the files you "committed" sitting in your staging area, ready to be adjusted. If you’ve made a complete mess of things and just want to wipe the last commit and all the file changes associated with it off the face of the earth, use the hard reset:


git reset --hard HEAD~1

Just be careful with that hard reset—it’s permanent, and you’ll lose any code changes you had in that commit. I usually stick with the --soft flag unless I’m absolutely certain I want to throw my work in the trash.

If you want to stop this from becoming a regular occurrence, start using the --patch flag when you add your files. Instead of running git add . like a madman, run git add -p. It forces you to review every single hunk of code you’re about to commit, which is a massive safety net that has saved me from committing debug logs and accidental config changes more times than I can count.

Hopefully, this gets you back on track without the stress. Happy coding, and try to double-check those diffs before hitting enter next time!

手殘把敏感檔案 commit 進去 Git 了？別慌，教你幾招救回來

來源：Stack Overflow ↗ · 27249 票

記得有次半夜趕工，想說把寫好的功能 commit 一下準備去睡覺，結果腦袋當機，竟然把整個 node_modules 資料夾和一堆 API key 的設定檔通通加進去 commit 了。當下看到那個 git commit 成功的訊息，我整個人差點從椅子上彈起來，心臟漏跳好幾拍，那種「完了，這下要被資安組抓去喝咖啡」的恐懼感，真的是這行最痛苦的時刻之一。

這其實就是 Git 設計上的一個特性：它非常誠實地記錄了你所有的變更。當我們執行 git commit 時，Git 就像一個忠實的書記官，把當下的狀態凍結在歷史裡。如果你還沒把這些東西推送到遠端伺服器（Push），那其實都好辦，因為這些錯誤還只存在於你自己的電腦，就像是你在日記本上寫錯字，只要還沒撕下來交給別人看，隨時都能用立可白塗掉。

我當時冷靜下來後，發現其實只要用 git reset 就能把這些錯誤抹掉。如果你只是想撤銷最後一次 commit，但想保留檔案的修改內容（畢竟辛苦寫的程式碼不想重打），我會用這一招：


git reset --soft HEAD~1

這行指令會把最後一次的 commit 拆開，檔案會回到「已暫存（Staged）」的狀態。如果你的情況更糟，連檔案內容都想直接丟掉、還原到 commit 之前的乾淨狀態，那就用下面這行，這招殺傷力較強，執行前請確保你真的不要那些檔案了：


git reset --hard HEAD~1

用完之後，你就會發現剛剛那個錯誤的 commit 就像從沒發生過一樣。不過說實話，為了避免這種心跳加速的時刻，我現在養成了一個好習慣，就是在 commit 前一定會先打 git status 看一下清單。如果覺得手動檢查太容易漏掉，也可以在專案根目錄下放一個 .gitignore 檔案，把那些不該進版控的敏感資訊或垃圾檔案通通寫進去，這樣 Git 就會自動忽略它們，想誤觸都難。

以後遇到這種手殘狀況，記得深呼吸，只要還沒 push 出去，這都不算什麼大事啦！
