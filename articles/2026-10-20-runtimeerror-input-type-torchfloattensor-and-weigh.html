How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a custom training loop in PyTorch. I felt like a total genius until I hit that dreaded RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same. I spent three hours staring at my screen, convinced my GPU was broken or my drivers had spontaneously combusted, only to realize I’d simply forgotten to move my data to the device I had so carefully moved my model to.

The root cause here is actually quite simple, though it’s a classic "gotcha" for anyone working with heterogeneous hardware. PyTorch is extremely strict about data locality; if your model’s parameters are living on your GPU (the cuda device) but your input tensors are still sitting in your system RAM (the cpu device), the internal CUDA kernels simply won't know how to talk to them. It’s like trying to put a key into a lock that’s in a different building—the computation just can't happen until both pieces of the puzzle are in the exact same memory space.

To fix this, you have to explicitly move your input tensors to the same device as your model inside your training loop. I usually handle this by grabbing the device from one of the model's parameters, which ensures I’m always using the right target. Here is how I update my loops to avoid this headache:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move the inputs AND labels to the device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you’re working with complex objects or custom datasets, you might find yourself doing this repeatedly. To prevent this from ever ruining your day again, I recommend writing a small utility function or a wrapper for your training step that handles device placement automatically. Better yet, if you're using modern PyTorch, you can use a torch.cuda.amp.autocast context or simply make it a habit to check input.device against next(model.parameters()).device during your first iteration of debugging. It saves a massive amount of time when you're deep in the weeds of model architecture changes.

Hope this clears up the confusion so you can get back to actually training your models. Happy coding, and may your gradients always converge!

別再讓 GPU 崩潰了：解決 PyTorch 的 RuntimeError: Input type and weight type should be the same

來源：Stack Overflow ↗ · 202 票

我還記得剛開始接觸 PyTorch 的那天，熬夜把模型架構寫好，滿心期待按下執行鍵，結果螢幕上那行血紅色的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same 直接讓我原地石化。那時候我盯著螢幕看了半小時，心想：「我明明都把 model 丟到 GPU 了啊，為什麼還要跟我吵架？」那種明明程式碼邏輯全對，卻被硬體規格卡住的無力感，真的是每個 AI 工程師心裡的痛，尤其是當時我還以為只要一行 .to(device) 就能解決所有煩惱。

其實這個錯誤的原因很單純，就是「語言不通」。簡單來說，你的模型已經乖乖搬到顯卡（GPU）上待命了，但你餵給它的資料（inputs）卻還懶洋洋地待在 CPU 的記憶體裡。PyTorch 很龜毛，它要求運算時的所有參與者——也就是模型參數和輸入資料——必須在同一個「場域」裡。就像是你把球員都拉到籃球場了，結果球卻還留在更衣室，裁判（PyTorch）當然會跳出來喊停。

解決方法其實沒你想的那麼複雜，只要在迴圈裡多補上一行搬運指令就行了。我當時就是漏掉了把 inputs 和 labels 同步移過去，只要在讀取資料時多做一個動作，把資料也推送到你定義好的那個 device 上，問題就能迎刃而解：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵在這裡：記得要把資料也移到同一個 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就可以安心做 loss 計算了

為了避免以後再被這種低級錯誤搞到崩潰，我後來養成了一個習慣，就是寫一個簡單的工具函式，或者直接在資料載入後統一做一次檢查。如果你想要更優雅一點，可以把搬運資料的動作寫進自定義的 Dataset 或者 DataLoader 的封裝層裡，這樣之後寫訓練迴圈就不用每次都擔心忘記。或者乾脆在程式碼開頭定義一個 device_transfer 的小函數，只要有新資料進來就過一遍，確保它們永遠跟著模型走。

解決完這個 bug 後，看著 GPU 使用率終於開始跳動的樣子，真的會有種莫名的感動。下次遇到這種問題，先別急著懷疑人生，記得檢查一下你的資料是不是還留在 CPU 裡偷懶喔！
