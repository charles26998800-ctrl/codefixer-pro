Solving the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours deep into a late-night debugging session, convinced my API routes were broken or my database connection was acting up, only to realize the culprit was a tiny piece of code relying on Math.random() during the initial render. It’s one of those bugs that makes you want to throw your monitor out the window, especially when your local environment seems to work perfectly fine until you hit that refresh button.

The core issue here is actually pretty logical once you get past the frustration: React expects the HTML sent by the server to be an identical match to the HTML generated by the client during the first render. When you use Server-Side Rendering (SSR) in Next.js, the server pre-renders your page into static HTML. When that HTML hits the browser, React tries to "hydrate" it by attaching event listeners and turning it into a living, interactive application. If the server says "I have a timestamp of 12:00 PM" but the client, running on a different machine or a slightly delayed state, thinks it's 12:01 PM, React panics. It detects a mismatch, throws up its hands, and crashes the hydration process because it can't guarantee a consistent UI.

To fix this, I’ve learned that the secret is deferring the rendering of dynamic content until the component has actually mounted on the client. I usually create a small custom hook or a wrapper component that forces React to wait until the client-side environment is ready. Here is how I typically handle it:


import { useState, useEffect } from 'react';

const useHasMounted = () => {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  return hasMounted;
};

export default function MyComponent() {
  const hasMounted = useHasMounted();

  if (!hasMounted) {
    // Render a skeleton or null to keep the server/client HTML consistent
    return null; 
  }

  return <div>{new Date().toLocaleTimeString()}</div>;
}

By returning null (or a static loading placeholder) during the server render and the initial client pass, you ensure that the server doesn't try to guess what the dynamic content will be. Once the component mounts, hasMounted flips to true, and React renders the actual dynamic output. Since this only happens on the client, the server and client stay perfectly in sync, and that dreaded error message disappears for good.

The best way to prevent this in the future is to keep your server-side components as pure as possible. If you know a piece of data is going to change based on the user's browser environment—like local storage, window dimensions, or randomized timestamps—don't even attempt to render it until you are certain you're in the client-side lifecycle. Treating the server render as a static snapshot and reserving dynamic logic for useEffect will save you hours of head-scratching.

Hope this helps you get your app back on track without too many more headaches. Happy coding, and may your hydration always stay consistent!

被 React 18 的 Hydration Error 搞到懷疑人生？其實兇手通常是這些小細節

來源：Stack Overflow ↗ · 341 票

記得那是個趕專案的週五下午，我正信心滿滿地把一個複雜的元件搬到 Next.js 裡，想說利用 SSR 提升一下 SEO。結果一刷新瀏覽器，控制台（Console）直接炸出一大串紅字：「Hydration failed because the initial UI does not match what was rendered on the server」。當時我真的差點把鍵盤砸了，明明程式碼看著都沒錯，怎麼伺服器渲染出來的 HTML 跟瀏覽器剛跑起來的 React 元件就是對不上？那種「明明眼前的畫面是對的，但就是報錯」的無力感，真的是我工程師生涯中數一數二的痛苦時刻。

其實這問題的根本原因很單純，就是 React 想要達成「無縫銜接」。簡單來說，Next.js 先在伺服器端把 HTML 吐給瀏覽器，然後瀏覽器下載完 JS 後，React 會接手把這些靜態 HTML 變成活生生的互動元件。但如果這時候瀏覽器算出來的初始畫面，跟伺服器給的不一樣（哪怕只是多了一個空格，或者一個隨機產生的 ID），React 就會覺得這太詭異了，直接報錯給你看，乾脆放棄同步，重新渲染整個畫面。最常見的兇手就是我們喜歡用的 Date()、隨機亂數，或是那些依賴瀏覽器 window 物件的判斷邏輯。

我那次排查了好久，最後發現是因為我在元件裡直接寫了 new Date().toLocaleString()，這導致伺服器跑的時間跟瀏覽器跑的時間差了幾毫秒，內容一不一樣，錯誤就噴出來了。解決方案其實很簡單，就是讓這個「不穩定」的內容晚點再出現。我通常會用一個 useState 配合 useEffect 來控制渲染時機，確保只有在瀏覽器跑完第一次渲染後，才顯示這些會變動的資訊。


import { useState, useEffect } from 'react';

function TimeDisplay() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者給一個固定的 Skeleton 畫面
  }

  return <div>現在時間：{new Date().toLocaleString()}</div>;
}

為了預防這種惡夢再次發生，我現在養成了一個習慣：只要是會用到 window、localStorage 或者任何依賴當下瀏覽器環境的邏輯，一律先問自己「這東西在伺服器上有意義嗎？」。如果沒有，就乖乖把它丟進 useEffect 裡處理，或者乾脆用 dynamic import 並設為 ssr: false。只要確保伺服器吐出來的東西是「穩定的」，這類 Hydration 的地雷基本上就踩不到了。

寫程式就是這樣，雖然偶爾會被這種莫名其妙的報錯氣死，但解決之後的成就感還是挺迷人的。祝你的專案跑得順順利利，別再被這些紅字折磨啦！
