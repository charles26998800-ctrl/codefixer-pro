How to Undo Your Last Local Git Commit Without Losing Your Mind

Source: Stack Overflow ↗ · 27243 votes

I still remember the first time I accidentally committed my .env file—along with a bunch of unfinished debug code—to a production branch. I spent nearly two hours sweating in front of my terminal, terrified that I’d somehow permanently borked the repo or deleted my progress. It’s a rite of passage for every developer, but that sinking feeling in your gut when you hit enter on a bad commit is something I wouldn’t wish on my worst enemy.

The root of the problem is that Git is designed to be a persistent history tracker. When you run git commit, you’re essentially carving your changes into stone. The confusion usually stems from the fact that Git has different "layers"—your working directory, the staging area (index), and the commit history. When you realize you’ve made a mistake, you're essentially trying to perform a time-travel maneuver to pull that commit back out of the history without destroying the actual work you did on those files.

If you haven't pushed your changes to a shared server yet, fixing this is actually pretty straightforward. I usually rely on git reset to handle this. If you want to undo the commit but keep your changes in your staging area so you can fix them, I use a "soft" reset. Just run this in your terminal:


git reset --soft HEAD~1

This command moves your branch pointer back one step, but keeps all your modified files ready to be committed again. If you realize the files you committed were a total disaster and you just want them gone entirely—wiping the changes from your workspace—you’ll want to use the "hard" reset instead. Just be careful with this one, because it’s permanent:


git reset --hard HEAD~1

Once you’ve run these, your local history is clean again, and you can get back to work.

To prevent this nightmare in the future, I started using the --patch flag when staging my files. Instead of running a lazy git add ., which grabs everything in sight, I run git add -p. It forces me to review every single hunk of code I’m about to commit. It’s saved me from committing "console.log" debugging lines more times than I care to admit.

Hope this helps you save your progress and your sanity. Happy coding, and try not to sweat the small stuff!

Git 手殘救星：還沒 Push 的 Commit 到底該怎麼撤銷？

來源：Stack Overflow ↗ · 27243 票

記得剛進這行沒多久，有次我在趕一個重要功能的上線，為了測幾個 debug 的 log，順手把一堆亂七八糟的測試檔案給 commit 了進去。結果當我準備要 push 到遠端時，才驚覺「慘了，這些垃圾檔案怎麼也在裡面？」，那一瞬間我真的是冷汗直流，心跳快到快要從喉嚨跳出來，深怕一個不小心把這些髒東西推到正式環境，然後就被主管抓去「懇談」了。

其實會發生這種事，通常就是因為我們太習慣順手執行 git commit -a，或者是一時手滑把不該加入的檔案 git add 了進去。Git 的設計邏輯是把你的修改先打包成一個個「快照」（Commit），但因為還沒推送到遠端伺服器，這些快照其實都還只存在你的本地磁碟裡。這就像是你在寫草稿，只要還沒寄出去，都還有機會把它丟進碎紙機重來一遍。

當下我冷靜了一下，發現這其實超好救。如果你只是想撤銷最後一次 commit，但想保留檔案的修改內容（畢竟那是你辛苦寫的 code，只是不想打包成這次的 commit），直接用 git reset --soft HEAD~1 就行了。這指令會把 commit 給拆掉，但你的檔案還會安安穩穩地躺在 Staging Area，隨時可以再選一次要不要 commit。


git reset --soft HEAD~1

但如果你的情況跟我那次一樣，那些檔案根本就是垃圾，只想把它們「徹底抹除」，讓一切回到 commit 之前的樣子，那就必須用 --hard 這個參數。請注意，這招下去，你所有沒存檔的修改都會直接消失，所以我通常會先深呼吸確認一次。


git reset --hard HEAD~1

為了避免這種心臟病發作的時刻再次發生，我現在養成了每次 commit 前一定會執行 git status 的習慣。即使覺得自己很熟了，多看一眼那個紅色的檔案列表，真的能省下後續大把的除錯時間。如果你跟我一樣容易手滑，也可以考慮設定一個 Git Alias，或者在 IDE 裡安裝那種會顯示未追蹤檔案的插件，畢竟預防勝於治療，少按那一下 Enter 就能少掉好幾根白頭髮。

以後如果不小心又 commit 錯了，記得別慌，Git 是你的工具，不是你的敵人，冷靜下來把 commit 拆掉重來就沒事啦！
