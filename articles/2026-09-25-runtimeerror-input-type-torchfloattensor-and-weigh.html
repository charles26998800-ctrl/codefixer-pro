Fixing the "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I remember the first time I hit this error; I was three hours deep into training a ResNet model, fueled by way too much cold coffee, and convinced I’d finally cracked my loss function. I hit run, watched the progress bar for half a second, and then everything imploded with that dreaded RuntimeError. I spent an embarrassing amount of time checking my CUDA drivers and reinstalling PyTorch, only to realize I had simply forgotten to move my tensors to the GPU.

The root cause is actually pretty straightforward once you stop panic-sweating. In PyTorch, your model weights and your input data have to live on the same device to perform mathematical operations. When you call model.to(device), you’re successfully pushing your model parameters to the GPU, but the data coming out of your DataLoader defaults to the CPU. Essentially, you’re trying to multiply a GPU-resident matrix by a CPU-resident matrix, and PyTorch throws a fit because it can’t perform cross-device operations on the fly. It’s a classic "mismatched types" error that feels way more intimidating than it actually is.

The fix is to ensure that every single batch of data you pull from your DataLoader is explicitly moved to the same device as your model. I usually handle this right inside the training loop. You don't need to change your data loading pipeline at all; just add a .to(device) call when you unpack your batch. It looks like this:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # Move the inputs and labels to the same device as the model
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... proceed with loss calculation

This simple adjustment ensures that your data is sitting right next to your model weights before the forward pass happens. If you’re dealing with multiple inputs or complex custom datasets, just make sure to iterate through them and send each tensor to the device individually.

To stop this from biting you in the future, I always recommend defining a global device variable at the top of your script and being religious about using it. If you build a habit of writing inputs = inputs.to(device) the moment you define your training loop, you’ll never see this error again.

Hope this saves you from the same headache I had! Happy coding, and may your gradients always converge.

又是這個經典錯誤：RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same

來源：Stack Overflow ↗ · 202 票

還記得剛開始接觸 PyTorch 的那陣子，為了趕一個重要的 Demo，我凌晨三點還在實驗室跟 GPU 奮鬥。當我興奮地按下 Run，以為模型終於要開始訓練時，螢幕上卻無情地噴出這行經典的 RuntimeError。那種「我明明都寫了 model.to(device) 啊，為什麼還跟我鬧脾氣？」的崩潰感，真的會讓人想直接把鍵盤砸了。

其實這個問題的核心邏輯很簡單，就是 PyTorch 這位強迫症患者，不允許你的「輸入資料」跟「模型權重」住在不同的星球。當你把模型透過 .to(device) 丟到 GPU 時，它的權重就變成了 cuda.FloatTensor，但你的 inputs 卻還乖乖地待在 CPU 的記憶體裡，也就是普通的 FloatTensor。GPU 就像是一個只會講英文的工程師，你卻硬塞給他一份寫滿中文的原始碼，他當然看不懂，直接給你報錯也是合情合理。

要解決這個問題，其實只要在迴圈開始前，把資料也同步搬過去就好。我當時就是漏掉了這一行，只要在 for 迴圈裡面，順手把 inputs 和 labels 也推向跟模型同一個裝置，問題馬上就迎刃而解了。你可以寫成下面這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就在這裡，要把資料也搬到 GPU
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就是正常的 loss 計算與反向傳播...

為了不讓自己每天都在修這種低級錯誤，我後來養成了一個習慣，就是寫一個簡單的 move_to_device 輔助函式，或者乾脆在 Dataset 的 __getitem__ 處理時就多留意一下。但最推薦的還是直接寫一個小小的 utility function，把所有 tensor 批次搬移。這樣以後不管模型多複雜，只要統一呼叫這個函式，就不會再發生這種「CPU 與 GPU 溝通不良」的慘劇了。

以後看到這個錯誤訊息，別急著懷疑人生，先檢查一下你的資料是不是還留在 CPU 偷懶就行啦。祝大家的模型都能訓練順利，GPU 永遠不報錯！
