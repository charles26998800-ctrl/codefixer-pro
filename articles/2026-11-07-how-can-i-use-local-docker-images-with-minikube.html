How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster with Minikube; I spent a solid three hours convinced that my YAML configuration was broken because my pods kept crashing with ImagePullBackOff. I was staring at my local terminal, seeing the image right there in my Docker daemon, yet Kubernetes kept trying to reach out to the public registry like it was allergic to my machine. It’s one of those classic "gotcha" moments that every developer hits when they first transition from standard Docker workflows to the K8s ecosystem.

The reason this happens is simple: Minikube runs inside its own isolated environment, usually a virtual machine or a separate container. When you run docker build on your laptop, that image exists in your host's Docker daemon, but Minikube is completely blind to it. It’s looking for the image inside its own internal registry, and since it can't find it there, it defaults to trying to pull it from the internet. It’s not actually a bug—it’s just a architectural wall between your host system and the cluster.

To fix this, the most reliable way I’ve found is to point your local terminal's Docker environment directly to the Minikube daemon. By running the following command, you effectively tell your shell to send all your Docker commands straight into the Minikube cluster:


eval $(minikube docker-env)

Once you’ve run that, any docker build -t my-app:latest . command you execute will build the image directly inside the Minikube environment. After that, you just need to make sure your Kubernetes deployment manifest has imagePullPolicy: IfNotPresent (or Never) set. This tells Kubernetes to skip the search for a remote registry and just grab the image that's already sitting right there in the cluster's local storage.

If you don't want to mess with your environment variables every time, the best way to prevent this headache is to adopt a consistent tagging strategy or use minikube image load. Instead of relying on the environment switch, you can simply build your image normally and then run minikube image load my-app:latest. It’s slightly slower because it has to copy the image over, but it keeps your host Docker environment clean and prevents you from accidentally polluting your cluster when you're just trying to test a quick change.

Hope this saves you from the same three-hour rabbit hole I went down. Happy coding, and may your pods always hit Running on the first try!

別再把 Image 推上 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 690 票

我記得剛開始接觸 Kubernetes 的時候，為了測試一個小小的改動，我得把 Docker image 打包、標註版本、推送到 Docker Hub，然後在 Minikube 裡執行 kubectl rollout restart，看著它顯示 ImagePullBackOff 的那一刻，我真的差點要把鍵盤砸了。最痛苦的是，網路慢的時候，為了等那幾百 MB 的 image 下載，我泡了三杯咖啡都還沒跑起來，看著螢幕上卡在那邊的進度條，心裡只想著：「明明檔案就在我的電腦裡，為什麼還要繞地球一圈？」

會發生這種事，其實是因為 Minikube 本質上是一個跑在虛擬機（或容器）裡的獨立環境。當你執行 kubectl 時，K8s 會去問那個虛擬機：「你有這張 image 嗎？」而虛擬機的 Docker daemon 根本看不到你主機（Host）上的 Docker daemon，所以它理所當然地會跑去網路上找。這就像是你明明把鑰匙放在口袋，卻還大費周章地打電話請鎖匠來開門一樣，完全是認知錯位。

其實解決方法簡單到讓人想哭。如果你是用 Minikube 預設的 Docker driver，你根本不需要推送任何東西，只要在你的終端機輸入這行指令，把環境變數切換過去就好：


eval $(minikube docker-env)

執行完這行後，接下來你在這個終端機視窗下 docker build -t my-app:v1 .，這些 image 就會直接被建立在 Minikube 的虛擬機裡面。這時候你只要把 Deployment YAML 裡的 imagePullPolicy 設定成 IfNotPresent，K8s 就會優先使用本地已有的版本，完全不用管網路速度，也不用管 Docker Hub 的權限。如果你是剛建立 Minikube 的新手，記得每次開新的終端機都要跑一次這行，或者乾脆把它塞進你的 .zshrc 或 .bashrc 裡。

為了避免以後又踩到這種「明明有檔案卻抓不到」的坑，我現在養成一個習慣，就是把 image 的 tag 設定得很明確，盡量不要用 latest。因為 latest 太容易讓人混淆，有時候你以為更新了，結果用的還是舊的 cache。另外，如果你的專案比較複雜，建議直接把 image 註冊表（Registry）的邏輯寫進開發流程裡，或者乾脆用 minikube image load 這個指令，直接把主機上的 image 搬進去，這樣就不會被環境變數綁死。

搞定這點之後，開發效率真的快了不只一個檔次，再也不用為了改一行程式碼而苦苦等待推送了。希望這招能拯救你的咖啡時間，別再讓網路延遲成為你寫 code 的絆腳石啦！
