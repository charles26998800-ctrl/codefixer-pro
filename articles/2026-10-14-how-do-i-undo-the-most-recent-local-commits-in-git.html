How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27243 votes

I’ll never forget the time I was working on a high-stakes client project at 2:00 AM, fueled by nothing but cold coffee and poor decision-making. I was rushing to wrap up a feature, ran a frantic git commit -a, and immediately realized I’d accidentally included a massive, autogenerated log file and a half-finished configuration change that would have broken the entire staging environment. I spent a solid hour staring at my terminal, sweating bullets, terrified that I was about to nuke my entire repository just to get rid of those extra files.

The reason this happens so often—even to seasoned engineers—is that Git’s commit command is a bit too eager to capture everything you’ve staged. When you run that command, Git creates a new snapshot of your project and moves the branch pointer forward. If you haven't pushed that commit to a remote server yet, you’re in a "safe zone" where the history exists only on your machine. You aren't actually deleting history from the team's shared source of truth; you're just rewinding your own local timeline to fix a mistake before it becomes a public one.

To fix this, I always reach for git reset. The command you need depends on whether you want to keep your changes or throw them away entirely. If you want to undo the commit but keep the files you worked on in your staging area (so you can fix what you missed), run this:


git reset --soft HEAD~1

If you’re like me and you realized you committed the wrong files and just want to wipe the slate clean, discarding both the commit and the changes inside those files, you’ll want to be a bit more aggressive:


git reset --hard HEAD~1

Using HEAD~1 tells Git to move your current branch pointer back exactly one commit. The --soft flag keeps your work in the staging area, while --hard resets your entire working directory to match the state of the previous commit. Just be careful with that hard reset—anything you didn't commit before that point is gone forever.

The best way to prevent this headache is to stop using git commit -a entirely. I started making it a habit to use git add -p instead. It forces me to interactively review every single hunk of code I’m staging before I commit it. It takes an extra ten seconds, but it’s saved me from countless "oops" moments where I almost committed something I definitely shouldn't have.

Hope this saves you some of the panic I felt that night. Happy coding, and try to get some sleep!

Git 手殘救星：還沒 Push 的 Commit 怎麼優雅地撤銷？

來源：Stack Overflow ↗ · 27243 票

記得有次半夜趕專案，眼看功能終於寫完，我興奮地打下 git commit -m "feat: finish everything"，結果按下 Enter 的瞬間，我才發現自己把一堆亂七八糟的測試 Log 跟沒用的 config 檔也一起 commit 進去了。當時真的差點崩潰，螢幕前的我心跳漏了一拍，心想：「完了，這下歷史紀錄要變得很難看，如果這時候不小心 push 上去，明天一定會被同事笑死。」那種冷汗直流的感覺，真的是每個工程師的共同夢魘。

其實這問題之所以讓人心慌，是因為我們對 Git 的「狀態機」還不夠熟。簡單說，當你執行 commit 時，Git 會把暫存區（Staging Area）的快照鎖進歷史紀錄裡。如果你還沒 push，這些東西其實都還乖乖待在你的電腦上，根本沒有對外公開，所以你其實握有絕對的控制權，隨時可以把它們「抓出來」重新處理。

我當時冷靜下來後，用的就是 git reset 這個最強大的工具。如果你只是想撤銷 commit，但想保留你辛苦寫好的檔案內容（不希望辛苦寫的 code 瞬間蒸發），直接下這行指令就搞定了：


git reset --soft HEAD~1

這行指令的意思是「把指標往回移一個版本，但把變更全部留在暫存區」。執行完後，你會發現剛剛 commit 的檔案全部都回到 Staging Area 了，這時候你可以隨意調整要加入的檔案，或者補個漏掉的 code，再重新 commit 一次，歷史紀錄看起來就像什麼事都沒發生過一樣完美。如果你的情況更糟，連檔案內容都想直接丟掉、回到 commit 前的乾淨狀態，那就改用 git reset --hard HEAD~1，不過這一招一定要小心，因為沒存好的修改是真的會直接消失，別怪我沒提醒你喔！

為了避免這種心驚膽跳的狀況再次發生，我現在養成了一個習慣，就是 commit 之前一定會先打 git status 看一眼。如果有時候改動太大，我會改用 git add -p 來進行互動式挑選，這樣我就能確保自己 commit 的每一行代碼都是經過深思熟慮的。雖然多花幾秒鐘，但比起事後還要在那邊拆解歷史紀錄，這點時間絕對是值得投資的。

學會這幾招，以後就算手殘也不用怕，Git 這條船你還是穩穩的船長啦！
