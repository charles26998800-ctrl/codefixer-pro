How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I encountered this error while training a custom ResNet on a multi-GPU setup. I had spent nearly three hours debugging my data pipeline, convinced my normalization transforms were broken, only to realize I’d simply forgotten to move my tensors to the device. I felt like a total amateur staring at a screen filled with red text, wondering why my GPU was sitting idle while my CPU was screaming for mercy.

The reason this happens is actually quite logical once you peek under the hood of PyTorch. Essentially, PyTorch is very strict about where your data lives. When you call model.to(device), you’re successfully shipping your model weights over to the GPU's memory. However, your input data—the tensors coming straight out of your DataLoader—are still sitting comfortably in your system's RAM (the CPU). When you try to pass that CPU-bound tensor into a model that expects GPU-bound tensors, PyTorch throws this mismatch error because it can’t perform matrix multiplication across two different memory spaces.

To fix this, you have to explicitly move your input tensors to the same device as your model inside your training loop. I usually keep a reference to my device variable handy and call .to(device) on both the inputs and the labels right after I pull them from the loader. Here is how I update my training loop to avoid that headache:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the line that saves the day
    inputs, labels = data[0].to(device), data[1].to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you’re working with complex data structures like dictionaries or lists of tensors, doing this manually can get old fast. My best tip for preventing this in the future is to write a small helper function or a custom collate function that handles the device transfer automatically for you. By centralizing that logic, you stop relying on your memory to catch every single tensor move, which is exactly how I finally stopped seeing this error pop up in my projects.

Hope this saves you from losing as much time as I did. Happy coding!

救命！PyTorch 又在跟我鬧脾氣：關於 FloatTensor 與 cuda.FloatTensor 的愛恨情仇

來源：Stack Overflow ↗ · 202 票

記得剛開始接觸 PyTorch 的那個週末，我為了趕一個專案進度，熬夜訓練模型，結果眼看著程式跑起來了，心想終於可以去睡個覺，沒想到螢幕上直接噴出一行紅字：RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。那一瞬間我真的差點崩潰，明明已經把 model 搬到 GPU 上了，到底還想怎樣？盯著那行錯誤訊息看了半小時，心裡想著這是不是什麼玄學，怎麼電腦跟我的溝通障礙這麼嚴重。

其實說穿了，這問題的核心就是「位置不對」。PyTorch 很死腦筋，它要求進行運算的所有對象——也就是你的模型參數和輸入資料——必須待在同一個「房間」裡。當你用 model.to(device) 把模型送進 GPU（也就是 cuda）時，模型裡面的權重參數就變成 cuda.FloatTensor 了。但你的 inputs 資料還傻傻地留在 CPU 的記憶體裡，還是普通的 FloatTensor。這就像是一個在台北辦公，一個在高雄，兩邊無法同步作業，PyTorch 就會因為兩者型別不匹配而直接罷工。

解決方法其實比你想像的簡單，我當時發現只要在餵資料進模型前，順手把 inputs 也搬到同一個 device 就行了。我後來習慣在訓練迴圈裡加入一行 inputs = inputs.to(device)，就像這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    inputs, labels = data
    # 關鍵就是這行，要把資料搬到跟模型同一個裝置
    inputs = inputs.to(device)
    labels = labels.to(device) 
    
    outputs = model(inputs)
    # 接下來就是後續的 loss 計算啦

為了避免以後再被這種低級錯誤搞到崩潰，我後來養成了寫一個通用設定的習慣，在程式碼最開始定義好 device 後，我就會告訴自己：只要涉及到 Tensor 的運算，都要保持「裝置一致性」。如果你不想每次都手動寫 to(device)，也可以在讀取資料時直接把裝置參數傳進去，或者寫一個簡單的 helper function 來處理這些搬運工作。

真的，這種錯誤踩過一次就夠了，希望大家以後看到這行紅字時，能馬上想起要把資料也一起打包帶走。祝大家的模型都能訓練順利，GPU 永遠不爆炸！
