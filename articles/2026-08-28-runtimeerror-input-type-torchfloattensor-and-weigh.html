Fixing "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a distributed training job for a computer vision project. I spent three hours staring at my terminal, convinced my GPU was fried or my drivers had somehow spontaneously uninstalled themselves, only to realize I had completely forgotten to move my input tensors onto the device. It’s one of those classic PyTorch rites of passage that makes you want to throw your keyboard across the room, but it’s actually a simple mismatch in the memory space where your data lives.

The root cause of this error is that PyTorch is strictly enforcing a "co-location" rule for your tensors. When you move your model to the GPU using model.to(device), you’re essentially telling PyTorch to store the network's weights in the VRAM of your graphics card. However, when you iterate through your DataLoader, the data being pulled from your CPU RAM is still a standard torch.FloatTensor. PyTorch isn't smart enough to automatically bridge that gap for you during the forward pass, so it throws this RuntimeError because it can't perform matrix multiplication between a weight sitting on the GPU and an input sitting on the CPU.

To fix this, you need to manually move your input tensors onto the same device as your model before they hit the network. I usually handle this right inside the training loop. You've already defined your device variable, so you just need to call .to(device) on your inputs and labels tensors. Here is how I structure that loop to keep things clean and error-free:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # Move the data to the same device as the model
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    # Now the forward pass works perfectly
    outputs = model(inputs)
    loss = criterion(outputs, labels)

The easiest way to prevent this from ever ruining your day again is to write a small helper function or a custom wrapper for your training step that handles device assignment automatically. If you're working on a larger codebase, you might even consider creating a simple utility that checks the device of the model parameters and aligns the incoming data accordingly. It saves you from repeating those lines of code and keeps your training script looking professional and robust.

Hope this clears up the confusion so you can get back to actual model training. Happy coding!

PyTorch 報錯：Input type 和 weight type 不一致，別再被這行搞崩潰了！

來源：Stack Overflow ↗ · 202 票

記得剛開始接觸 PyTorch 的時候，我熬夜趕著訓練一個複雜的 CNN 模型，好不容易把架構搭好、資料集處理完，按下執行鍵的那一刻，心裡想著「終於可以去睡覺了」。結果螢幕瞬間噴出一大串紅字，那個 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same 就像在嘲笑我的天真一樣。我當時盯著螢幕看了半小時，明明已經設定了 model.to(device)，到底還有哪裡沒對到？那種明明覺得邏輯全對，卻被一個莫名其妙的型別錯誤卡死在凌晨三點的挫折感，真的會讓人想直接把電腦蓋上。

其實這個錯誤的原因很單純，就是「跑錯場」了。PyTorch 對於資料與權重的存放位置非常嚴格，簡單來說，就是你的模型已經乖乖搬到 GPU（cuda）去待命了，但你的資料（input）卻還懶洋洋地留在 CPU（float）上。當模型準備要運算時，它發現自己手上的參數是 GPU 格式，但你餵給它的輸入卻是 CPU 格式，兩邊「語言不通」，PyTorch 為了避免計算錯誤直接選擇罷工。這就像是你請了一個外籍大廚（GPU 模型），結果你給他一張中文食譜（CPU 資料），他根本看不懂啊！

解決方法其實一點都不複雜，只要在迴圈讀取資料的時候，順手把資料也「推」進去同一個裝置就可以了。我後來都習慣在 for 迴圈的一開始，直接這樣寫：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # 就是這行，把資料也丟到跟模型一樣的地方
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也要記得把 labels 轉過去

只要確保資料在進入模型前，跟模型站在同一個陣線（都在 GPU 或都在 CPU），這個惱人的錯誤就會立刻消失。

為了避免以後再發生這種「資料跟模型不同步」的尷尬狀況，我現在養成了一個習慣，就是定義一個全域的 device 變數，然後在所有的 tensor 操作或是定義模型時，一律用 .to(device) 來處理。如果你的專案很大，甚至可以寫一個小的輔助函式或是類別來統一處理資料搬移，這樣不僅省事，也不會再因為漏掉某個 tensor 沒移動而浪費寶貴的訓練時間。

希望這篇能救你一命，快去把模型跑起來吧，別跟我當年一樣在半夜對著螢幕乾瞪眼！
