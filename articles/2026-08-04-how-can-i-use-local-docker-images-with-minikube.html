How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up Minikube, thinking I was being clever by building my images locally and immediately trying to deploy them. I spent three hours banging my head against the wall because my pods kept stuck in an ImagePullBackOff loop, convinced that because the image was on my machine, Kubernetes should just "know" it was there. It was one of those classic "aha!" moments where I realized I was treating a virtualized cluster like it was just another process running on my laptop.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside its own isolated virtual machine or container. When you build an image on your host machine, it lives in your host’s Docker daemon. Kubernetes, running inside the Minikube node, has no access to that daemon; it’s looking for the image in its own internal registry or a remote one like Docker Hub. Since it can't "see" your local files, it tries to pull from the internet, fails, and leaves you staring at a crash loop.

The fastest way I’ve found to bridge this gap without needing a private registry is to point your local shell directly at the Minikube Docker daemon. Before you build your image, just run this command in your terminal:


eval $(minikube docker-env)

Once you run that, your local docker commands are now talking directly to the Docker engine inside your Minikube cluster. Now, go ahead and build your image as you normally would:


docker build -t my-local-image:v1 .

After the build finishes, you need to make sure your Kubernetes manifest is configured correctly. Set your imagePullPolicy to IfNotPresent in your deployment YAML. If you don't do this, Kubernetes will default to Always and try to reach out to the internet to verify the image, which will fail because your image only exists inside the Minikube environment.


spec:
  containers:
  - name: my-app
    image: my-local-image:v1
    imagePullPolicy: IfNotPresent

To keep this from biting you again, I always make it a habit to check my context before I start a build. If I’m working on a project that requires frequent image updates, I’ll alias the eval command in my .zshrc or .bashrc so I don't have to hunt for it. Just remember that if you open a new terminal tab, you’ll need to run that eval command again, or your builds will end up back on your host machine where the cluster still can't find them.

Hope this saves you the three hours of frustration I went through! Happy coding and good luck with your deployments.

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的神級技巧

來源：Stack Overflow ↗ · 688 票

當年我剛開始摸索 Kubernetes 的時候，真的差點被那個「改一行程式碼就要推上 Docker Hub」的流程搞到崩潰。我當時為了測試一個極小的 Bug，每次修改完都要執行 docker build，接著 docker push，然後在 Minikube 裡 kubectl delete pod 等它重新拉取，光是等待網路傳輸的時間，我就夠喝三杯咖啡了。最痛苦的是，有時候網路不穩，Image 推到一半失敗，或是因為私有庫權限卡住，那種「明明程式改好了，卻因為部署流程跑不通而卡死」的無力感，真的是工程師的惡夢。

為什麼會這樣呢？其實是因為 Minikube 本身是一個跑在虛擬機或 Docker 容器裡的獨立環境。你的電腦主機跟 Minikube 裡面的 Docker Daemon 根本是兩個平行世界。當你在自己的 Terminal 打 docker images 時，你看得到映像檔，但 Minikube 裡面的節點卻是「瞎子」，它完全不知道你本地有這些檔案，所以它只能乖乖去遠端的 Registry 抓取。

其實要解決這個問題超簡單，根本不需要繞遠路。最快的方法就是直接讓你的 Terminal 指向 Minikube 內部的 Docker 環境。只要在終端機輸入這行魔法指令：


eval $(minikube docker-env)

執行完之後，你的 Terminal 就會跟 Minikube 內部的 Docker 綁定。這時候你再跑 docker build -t my-app:v1 .，這個 Image 就會直接被建立在 Minikube 的環境裡。接著，記得把你的 Kubernetes YAML 設定檔裡的 imagePullPolicy 改成 IfNotPresent，不然它還是會雞婆地跑去網路找。這樣一來，你的部署速度簡直是飛天等級，完全不需要再經過 Docker Hub 這個中間商。

為了避免以後又因為忘記切換環境而在那邊鬼打牆，我現在都習慣在專案裡寫一個簡單的 Makefile。把 eval $(minikube docker-env) 包進去，或者在開發初期就養成習慣，打開 Terminal 第一件事就是檢查環境。如果你用的是 Docker Desktop 的 driver，記得 minikube image load 也是個好選擇，直接把本地的 Image 匯入進去，省得環境切來切去搞混。

只要把這招學起來，保證你之後的開發效率會提升好幾個檔次，再也不用看著進度條在那邊慢慢跑了。
