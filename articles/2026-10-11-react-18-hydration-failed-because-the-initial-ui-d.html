How to Fix "Hydration failed" Errors in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error staring back at me in the browser console. I spent about three hours convinced my API was returning bad data, only to realize I was just rendering a random timestamp in a component that was being called on both the server and the client. It’s one of those bugs that makes you want to throw your keyboard out the window, especially when your code looks perfectly fine at first glance.

The root cause of this frustration is actually quite logical once you peel back the layers of how React 18 handles Server-Side Rendering (SSR). When Next.js renders a page on the server, it generates the HTML and sends it to the browser. Once the browser receives that HTML, React "hydrates" it by attaching event listeners and turning it into a fully interactive application. The problem happens when the HTML generated on the server doesn't perfectly match the HTML generated by the client during that first render. If you’re using something like Date.now(), Math.random(), or even checking window properties that don't exist on the server, React panics because it doesn't know which version of the DOM to trust.

I fixed this by ensuring that my component doesn't attempt to render dynamic, client-only content until the component has actually mounted. If you’re dealing with this, the trick is to use a useEffect hook to track the mounting state. By initializing a state variable to false and flipping it to true inside useEffect, you force the component to wait for the client-side hydration to finish before it renders the problematic content. Here is how I usually structure it to keep things clean:


import { useState, useEffect } from "react";

export default function MyComponent() {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null; // Or a static loading skeleton
  }

  return (
    <div>
      {/* Now it's safe to use browser-only APIs like localStorage or random values */}
      <p>The time is: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

To prevent this from haunting your codebase in the future, my biggest tip is to be extremely mindful of your "islands" of interactivity. Try to keep your server-rendered components as pure as possible and move any logic that relies on the window object or volatile data into components that are specifically marked for client-side rendering. If you keep your server-side logic predictable and deterministic, you’ll stop seeing those annoying hydration mismatches for good.

Hopefully, this saves you those three hours I lost staring at my monitor! Let me know if you run into any other weird quirks with React 18.

又被 React Hydration Error 搞瘋了？這其實沒你想的那麼難解

來源：Stack Overflow ↗ · 341 票

還記得上次為了趕專案上線，我熬夜把舊專案升級到 React 18，結果一打開瀏覽器，控制台噴出一大串紅通通的 "Hydration failed" 錯誤，當時真的差點沒把鍵盤砸了。明明程式碼看起來沒什麼毛病，為什麼伺服器渲染（SSR）出來的 HTML 跟瀏覽器第一次載入時長得不一樣？那一刻看著螢幕發呆，感覺自己像個剛學寫 Code 的菜鳥，心裡那個崩潰啊，真的很想直接把 SSR 關掉算了。

其實這問題的根本原因，說穿了就是「溝通不良」。當你使用 Next.js 或其他 SSR 框架時，伺服器會先幫你產生一份 HTML 傳給瀏覽器，但 React 在瀏覽器端接手時，會試圖把狀態「注入」進去（這就是 Hydration）。如果伺服器渲染出來的內容，跟瀏覽器第一次跑 React 時計算出來的 DOM 結構有一丁點不一致——哪怕只是因為 new Date() 的時間差、或是瀏覽器插件往你的 HTML 裡塞了個什麼垃圾標籤——React 就會因為「這跟我預期的不一樣」而報錯，然後直接放棄治療，強制把整個 DOM 重新渲染一遍，導致網頁閃爍。

我當時踩的坑，很多時候是因為用了像 localStorage 或是隨機生成的 ID 這種只存在瀏覽器端的東西，卻在伺服器端渲染時就直接拿來用了。解決的方法其實很簡單，就是告訴 React：「嘿，這部分內容請等到瀏覽器端再渲染就好」。我習慣的做法是建立一個簡單的 useEffect 來處理這種「客戶端限定」的邏輯。當組件掛載完成後，我們再切換狀態，讓 React 知道現在可以安心渲染這些內容了。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>這是在客戶端才會顯示的內容</span> : <span>Loading...</span>}
    </div>
  );
}

至於要怎麼預防下次再被搞瘋？我現在養成一個習慣：只要是涉及瀏覽器特有 API（像是 window、localStorage 或隨機數）的邏輯，我一律會嚴格檢查它們是否在 useEffect 內部執行。另外，盡量避免在渲染邏輯中直接使用 Math.random() 這種會造成伺服器與客戶端不一致的函數，如果非用不可，記得也要等組件掛載後再產生，這樣就能省下不少除錯的時間啦。
