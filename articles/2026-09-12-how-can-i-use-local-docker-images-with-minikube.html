How to Use Local Docker Images with Minikube Without Losing Your Mind

Source: Stack Overflow ↗ · 689 votes

I remember the first time I set up Minikube, I felt like a genius until I tried to deploy my first local image. I spent three hours tweaking my deployment YAML, convinced I had a typo, only to realize that Kubernetes was trying to pull an image from Docker Hub that didn't exist yet. I was pulling my hair out, staring at the ImagePullBackOff error, before finally realizing that Minikube lives in its own little world inside a VM or container, completely isolated from my machine's local Docker daemon.

The reason this happens is actually quite logical once you peek under the hood. When you run docker build on your laptop, those image layers are stored in your host's Docker engine. Minikube, however, runs as a separate node. When you tell Kubernetes to pull an image, it checks the local cache of that Minikube node. Since your Minikube environment has no idea what’s happening on your host machine, it defaults to reaching out to the internet to find the image. If it’s not on a registry like Docker Hub, it’s just going to fail every single time.

The cleanest way I’ve found to bridge this gap is by pointing your local terminal directly at the Docker daemon running inside Minikube. Instead of building locally and then trying to push or move things, you just execute one command to switch your shell's context:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. It’s like magic. You can verify it’s working by running docker images—you should see the Minikube-specific images listed there. After that, just make sure your deployment YAML has imagePullPolicy: IfNotPresent set. This tells Kubernetes to check if the image is already available locally before trying to go out to the web, which is exactly what we want for local development.

If you’re using a newer version of Minikube or a different driver, you might find that minikube image load is even more reliable. I use this when I’ve already built the image and just want to "push" it into the cluster without messing with environment variables:


minikube image load my-local-app:latest

To keep your sanity, the best tip I can give you is to stop relying on latest tags during development. I started tagging my images with unique identifiers or timestamps, which prevents the "wait, is this actually the new code?" headache. It’s a small habit, but it saves you from questioning your sanity when your changes aren't reflecting in your pods.

Hope this saves you those three hours I wasted. Happy coding, and may your pods stay in the Running state!

為什麼 Minikube 總是找不到我的 Image？教你如何不用 Docker Hub 也能秒速部署

來源：Stack Overflow ↗ · 689 票

記得剛開始碰 Kubernetes 時，為了測試一個小功能，我反覆改了幾行程式碼，每次都要 docker build 再 docker push 到 Docker Hub，然後再到 Minikube 裡 kubectl rollout restart。最慘的一次是網路突然不穩，光是上傳那個幾百 MB 的 Image 就耗了我半小時，看著進度條在那邊龜速爬行，我真的差點把鍵盤砸了，心裡只想著：「我明明就在同一台電腦上，為什麼還要繞地球一圈？」

這其實是因為 Minikube 本身是一個跑在虛擬機（或容器）裡的獨立環境，它有自己的一套 Docker Daemon，跟我們平常在開發機上直接執行的 docker 指令根本是兩條平行線。所以當你執行 kubectl apply 時，K8s 跑到 Minikube 裡面去抓 Image，它只會在它自己的那個小圈圈裡找，找不到當然就報 ImagePullBackOff 給你看，那種明明 Image 就在本地，卻硬是被 K8s 說「我找不到」的挫折感，真的是誰試誰知道。

後來我發現，與其在那邊跟 Docker Hub 搏鬥，不如直接讓 Minikube 的 Docker 環境跟我的本機同步。最直覺的做法，就是直接把指令指向 Minikube 內部的 Docker 環境。只要在執行 docker build 之前，先執行下面這行指令，你的終端機就會暫時「變成」Minikube 的 Docker 客戶端：


eval $(minikube docker-env)

執行這行之後，你再跑 docker build -t my-app:v1 .，這個 Image 就會直接被送到 Minikube 的肚子裡。這時候你只要把 Deployment 裡的 imagePullPolicy 改成 IfNotPresent，K8s 就會乖乖用本地的 Image，再也不會跑去網路上亂抓了。如果你是用 Windows 的 PowerShell，記得用 minikube docker-env | Invoke-Expression 也是一樣的效果。

為了避免以後又忘記這件事，我現在習慣把這類開發指令寫成 Makefile。每次要重新 Build 的時候，我就直接打 make build-local，讓腳本幫我處理環境切換，這樣就不會發生「明明 Build 好了卻還是部署失敗」的尷尬狀況。

其實開發過程順不順，真的就差在這些微小的設定細節，搞定這一招，以後測試開發真的會快上不少！
