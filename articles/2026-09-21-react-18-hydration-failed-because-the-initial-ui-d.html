Why React 18 Hydration Errors Are Driving You Crazy (And How to Fix Them)

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a Next.js project. I had just migrated a legacy dashboard to React 18, feeling pretty smug about my performance gains, when suddenly my console turned into a wall of red text. I spent a good three hours convinced that my server-side rendering logic was fundamentally broken, only to realize I was just rendering the current date in the footer. It’s one of those bugs that makes you want to throw your keyboard out the window, but once you understand the "why," it becomes a lot less intimidating.

The root cause of this frustration is actually quite logical: React expects the HTML sent from the server to be an exact match for what the client generates on its first render. When you use server-side rendering, the server sends a static snapshot of your page. As soon as that HTML hits the browser, React tries to "hydrate" it—attaching event listeners and turning it into a living, breathing app. If your code relies on something that changes between the server’s execution and the client’s execution, like new Date(), Math.random(), or even a check against localStorage, React panics. It sees the server’s output, compares it to the client’s output, sees a discrepancy, and decides to dump the whole thing and re-render from scratch, which is exactly what that dreaded error message is complaining about.

To fix this, you need to ensure that the content is identical during that initial hydration phase. If you have dynamic data that simply can't be known on the server, the easiest way I've found to handle it is to wait until the component has actually mounted in the browser before rendering the dynamic part. I usually create a small state variable to track the mounting status. Here is how I typically structure this to bypass the mismatch:


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>Current time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
};

By defaulting to false and only switching to true inside useEffect, you guarantee that the server always renders the "Loading..." state. Since the client will also render "Loading..." on that very first pass before the effect runs, the HTML matches perfectly. Once the component mounts, the effect fires, the state updates, and React swaps in your actual dynamic content without throwing a tantrum.

If you want to prevent this headache entirely, my biggest tip is to be extremely cautious about what you put directly into your render functions. If you need to access browser-only APIs like window, localStorage, or dynamic timestamps, keep them tucked away behind a useEffect hook or handle them in a client-side component specifically designed for that purpose. Keeping your server-rendered components "pure" and deterministic will save you hours of debugging down the road.

Hope this helps you clear those console errors so you can get back to building cool stuff. Happy coding!

React 18 Hydration 錯誤：為什麼我的頁面總是跟伺服器吵架？

來源：Stack Overflow ↗ · 341 票

記得那天我為了趕一個電商專案的發表，熬夜重構了 Next.js 的路由邏輯，結果一跑起來，瀏覽器控制台直接噴出一堆紅通通的 Hydration failed 錯誤，當時我真的差點把鍵盤砸了。明明我在本機開發看起來都很正常，為什麼一到 SSR 階段，React 就開始跟我鬧彆扭，硬說伺服器渲染出來的 UI 跟瀏覽器收到的不一樣？這種「明明沒改什麼卻炸開」的無力感，真的是每個前端工程師的惡夢。

其實說穿了，這個問題的核心就是「時差」。當你使用 Next.js 的 SSR 時，伺服器會先產生一份 HTML 發給瀏覽器，然後瀏覽器端的 React 會嘗試「接手」（Hydrate）這份靜態內容。如果這時候你的程式碼裡包含了一些會變動的邏輯——像是 new Date()、隨機數產生器，或是依賴 window 物件的判斷式，伺服器算出來的結果跟瀏覽器第一次執行時的結果不同，React 就會判定這次的 Hydration 失敗。最痛苦的是，有時候只是因為 HTML 標籤嵌套錯誤（例如在

），React 為了修正結構而導致內容不匹配，這種隱晦的錯誤真的會讓人查到懷疑人生。

要解決這個問題，最直觀的方法就是強制讓這段邏輯「只在瀏覽器端執行」。我通常會利用 useEffect 來處理這類依賴瀏覽器環境的內容，因為 useEffect 只會在元件掛載到 DOM 後才執行，這樣伺服器那邊就不會因為拿不到 window 或亂跑亂數而導致錯誤。你可以像這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>現在時間是：{new Date().toLocaleTimeString()}</span> : <span>載入中...</span>}
    </div>
  );
}

透過這種方式，伺服器會先傳送那個「載入中」的靜態片段，等瀏覽器接手後，再把真正的時間渲染出來，這樣就不會發生「伺服器說 A，瀏覽器說 B」的衝突了。

想要避免這種情況再次發生，建議養成一個習慣：永遠不要在元件的頂層直接呼叫任何會變動的 API。如果你發現某個功能需要用到瀏覽器專屬的物件（像是 localStorage 或 window.innerWidth），一律把它封裝在 useEffect 或是自定義的 Hook 裡面，並且配合 isMounted 狀態來控制渲染時機。只要讓 SSR 階段保持乾淨、可預測，這類的報錯真的會少一大半。

希望這招能幫你從那一堆紅字中解脫，去喝杯咖啡休息一下吧，這問題真的讓人心累！
