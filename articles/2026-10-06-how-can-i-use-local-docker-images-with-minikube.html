How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster with Minikube. I had this perfect little microservice containerized and ready to go, and I spent a good three hours staring at an ImagePullBackOff error, completely baffled as to why K8s couldn't see the image sitting right there on my machine. I kept trying to docker push to a non-existent private registry, feeling like an absolute amateur while my local terminal mocked me with red error text.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside its own isolated virtual machine or container. When you run docker build on your host machine, that image lives in your host's Docker daemon. Minikube, however, has its own separate Docker daemon inside its VM. Because they aren't sharing the same space, your cluster literally has no idea that your image exists. It tries to reach out to the Docker Hub, fails to find your local tag, and gives up.

To fix this, you don't need to set up a private registry or push your code anywhere. The cleanest way I’ve found to handle this is by pointing your local terminal's Docker environment directly at the Minikube daemon. You do this by running a simple command in your current terminal session:


eval $(minikube docker-env)

Once you run that, any docker build or docker pull commands you execute will happen inside the Minikube VM. It’s like magic—you build the image, and then you can immediately reference it in your Kubernetes manifest. Just make sure your deployment's imagePullPolicy is set to IfNotPresent or Never, otherwise, K8s will try to fetch it from a remote registry despite it being local. If you’re using the Docker driver on Linux, you might not even need this, but for most setups, this command is the gold standard.

To prevent this frustration in the future, I highly recommend adopting a tagging strategy that explicitly labels your local builds. Whenever I’m iterating, I always tag my images as my-app:dev and set my deployment to look specifically for that tag. It keeps things organized and ensures you aren't accidentally pulling a stale version from the cloud while you're trying to test your latest local changes.

Hope this saves you a few hours of head-scratching and keeps your dev loop moving fast. Happy coding!

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，我真的快被 Minikube 搞瘋了。那時候我寫好了一個微服務，想說趕快部署上去測試一下，結果每次修改程式碼，就得重新 Build image、Tag、Push 到 Docker Hub，然後再讓 Minikube 把那個 Image Pull 下來。最讓我崩潰的是，網速慢的時候，光是等待這些重複的步驟，我就能去泡兩杯咖啡，甚至還發生過「明明推上去了，Minikube 卻死活抓不到最新版本」的靈異事件，那種看著螢幕發呆的無力感，真的會讓人想直接把電腦砸了。

會發生這種事，其實是因為 Minikube 是一個獨立在你的電腦裡、跑在虛擬機或容器裡的完整 K8s 環境。對 Minikube 來說，它根本看不到你宿主機（Host）Docker Daemon 裡那些已經編譯好的 Image，它只認得自己內部的倉庫。所以當你在 YAML 檔設定 imagePullPolicy: Always 時，它理所當然地會往 Docker Hub 找，找不到當然就給你報一個 ImagePullBackOff 的錯誤，這真的讓人很挫折。

後來我發現，其實根本不需要把 Image 丟到公開或私有的 Registry 去折騰。最快的方法就是直接把 Docker 的環境變數「指向」Minikube 內部的 Daemon。只要在終端機輸入這行指令：


eval $(minikube docker-env)

執行這行之後，你現在這個終端機視窗的 Docker 指令，就會直接對著 Minikube 裡面的 Docker 操作了。這時候你再執行 docker build -t my-app:v1 .，這個 Image 就會直接出現在 Minikube 的肚子裡，接著你在 YAML 檔案裡把 imagePullPolicy 改成 IfNotPresent，Minikube 就會乖乖用你剛才 build 出來的那個版本，完全不用再跑網路傳輸，速度快到讓你懷疑人生。

如果要預防這種事再發生，我強烈建議你在開發初期就養成習慣，把這行指令寫在 Makefile 裡面，或者乾脆設個 alias。但記得一個重點，這個設定只對當前的終端機視窗有效，如果你開了新的分頁，記得要重新跑一次，不然你會發現怎麼 build 了半天，K8s 還是讀不到你最新的程式碼。

以後遇到這種部署卡住的問題，記得先檢查是不是自己又忘了要把 Docker 環境切換過去啦！
