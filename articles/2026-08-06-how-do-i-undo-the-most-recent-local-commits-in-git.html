How to Undo Your Most Recent Local Git Commits Without Losing Your Work

Source: Stack Overflow ↗ · 27234 votes

I still remember the first time I accidentally committed a massive folder of local build artifacts and sensitive config files right before a production deploy. I was so panicked that I started sweating, convinced I’d just permanently mangled the project history, and I spent nearly an hour staring at the terminal like it was going to magically undo my mistake. It’s a rite of passage for every developer, but luckily, Git is much more forgiving than it feels in those high-stress moments.

The reason this happens is usually just a simple lapse in focus or a "git add ." command that was a little too enthusiastic. When you run a commit, Git creates a snapshot of your project and moves the branch pointer forward. If you haven't pushed that commit to a remote server, that history exists only on your machine, which means you have the power to rewrite it without affecting your teammates' workflows. It’s not that you "broke" anything; you’ve just recorded a state you aren't quite ready to share with the world yet.

The fix I always reach for is the git reset command. If I just want to undo the commit but keep all my hard work in the staging area so I can fix the files, I use a "soft" reset. I run git reset --soft HEAD~1, which effectively rewinds the pointer to the previous commit while leaving all my changed files exactly where they are. If I want to completely wipe the commit and unstage everything, I go with git reset HEAD~1 instead.


# Undo the commit, but keep the files staged and ready to tweak
git reset --soft HEAD~1

# Undo the commit and unstage all changes (files stay in your folder)
git reset HEAD~1

If you’re truly feeling like you made a mess of things and just want to throw the entire commit away—losing the changes you made in those files entirely—you can use the "hard" reset flag. Just be careful with this one, because once you hit enter, those local changes are gone for good.


# Nuclear option: Undo the commit AND delete all changes in those files
git reset --hard HEAD~1

To prevent this headache from happening again, I started using git add -p (the patch mode) instead of just blindly adding everything. It forces me to review every single hunk of code I’m staging, which acts as a built-in "wait, is this really what I want to commit?" sanity check. It takes an extra five seconds, but it’s saved me from countless "oops" moments over the years.

Hope this clears up your Git anxiety and gets your repo back in shape. Happy coding, and try not to stress too much—we've all been there!

手滑提交了不該送出的程式碼？Git 撤銷 commit 的實戰指南

來源：Stack Overflow ↗ · 27234 票

記得剛進這行沒多久，有次我在趕一個重要功能的上線，為了測試隨手加了一堆 Debug 用的 console.log 和亂七八糟的測試檔案。結果一個恍神，我竟然直接執行了 git commit -am "fix bugs"，當下看著螢幕上顯示的 commit 成功訊息，我整個人心跳漏了一拍，心想：「完了，這要是推上去給主管看到，我不被笑死才怪。」那種冷汗直流、差點崩潰的感覺，至今我還記憶猶新。

其實會發生這種慘案，通常都是因為我們對 Git 的「暫存區」概念還不夠熟。簡單來說，當你執行 commit 時，Git 就像是一個盡責的快遞員，把你當下所有加入暫存區（Staging Area）的東西打包封箱了。如果你還沒執行 push，這些東西其實都還乖乖待在你的電腦裡，並沒有傳給同事或是伺服器，所以這時候想要「反悔」是完全來得及的。

我當時救命的解法就是 git reset。如果你只是想撤銷最後一次 commit，但想保留檔案改動，讓它們回到「還沒 commit 但已經 git add」的狀態，你可以直接打這行：


git reset --soft HEAD~1

這行指令就像是按下了時光倒流鍵，把那個 commit 拆開，但你的程式碼還會留在暫存區，方便你直接把那些不該有的檔案移除掉。如果你是連檔案都不想要了，想回到 commit 之前的原始狀態，那就把 --soft 換成 --hard：


git reset --hard HEAD~1

不過要特別注意，--hard 是真的會把你的修改直接抹掉，那種「眼睜睜看著自己辛苦敲的程式碼消失在螢幕上」的痛苦感，相信我，你絕對不想體驗第二次。所以操作前，請務必確認你的重要變更都已經備份或是真的不需要了。

為了避免這種手滑悲劇，我現在養成了一個好習慣：在執行 commit 之前，我一定會先打一次 git status。這就像是過馬路前左右看一眼，確認一下到底有哪些檔案被標記為「準備送出」。如果檔案太多太雜，我會習慣用 git add -p 來逐一選擇要提交的片段，這樣就算真的手癢加了什麼奇怪的測試代碼，也能在加入暫存區的階段就發現。

其實 Git 雖然魔鬼，但它給了我們很多後悔藥，只要還沒 push 出去，一切都好說。下次再遇到這種事，先深呼吸，別急著亂打指令，確認好你要的是「保留改動」還是「徹底毀滅」再下手就好啦！
