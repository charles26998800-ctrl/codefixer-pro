React 18 Hydration Failed: Why Your Server and Client Aren't Talking

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw that "Hydration failed" error in React 18. I had just migrated a fairly complex dashboard, and everything looked perfect in my local development environment until I refreshed the browser and saw my beautifully crafted UI flicker and vanish into a wall of red console errors. I spent three hours refactoring my state management logic, convinced I had broken the entire data flow, only to realize it was just a simple mismatch between a timestamp I was generating on the server and the one being rendered by the browser.

The root cause of this headache is actually quite simple, even if it feels like a total nightmare at 2:00 AM. When you use Server-Side Rendering (SSR) with Next.js, the server generates the initial HTML based on the state it sees at that exact moment. When the browser picks up that HTML, it tries to "hydrate" it by attaching event listeners and turning it into a living React application. If the logic running on your server produces even a slightly different result than what runs in the browser—like a date, a randomized string, or a browser-specific API—React throws its hands up. It basically says, "The HTML I received doesn't match the component tree I'm trying to build," and it forces a full client-side re-render, which is exactly the performance hit we're trying to avoid with SSR in the first place.

When I finally tracked this down in my own code, the fix was to ensure that the component doesn't attempt to render the "volatile" content until after the initial mount. You can use the useEffect hook to force a piece of code to only run on the client side. By initializing a state variable as false and flipping it to true inside useEffect, you create a gatekeeper that keeps the server-rendered HTML clean and consistent. Here is how I usually handle this pattern to keep my console clean:


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or return a loading skeleton
  }

  return (
    <div>
      {/* This only renders after hydration is complete */}
      {new Date().toLocaleTimeString()}
    </div>
  );
};

To prevent this from coming back to haunt you, my best advice is to embrace "Client-Side Only" components for anything that relies on browser globals like window, localStorage, or random number generators. If a specific component doesn't strictly need to be rendered on the server for SEO purposes, just wrap it or load it dynamically using next/dynamic with ssr: false. It’s a massive time-saver and keeps your hydration logic predictable.

Hopefully, this saves you from the same three-hour rabbit hole I fell into. Happy coding, and may your console stay error-free!

被 React 18 的 Hydration Error 搞到懷疑人生？這裡有解法！

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地想體驗 SSR 的效能提升，結果專案一跑起來，瀏覽器 Console 直接噴出一整排紅色的「Hydration failed」警告，整個頁面看起來簡直像靈異現象。我當時盯著螢幕，試圖找出伺服器渲染跟客戶端渲染到底哪裡長得不一樣，甚至一度懷疑是不是 React 本身壞掉了，那種明明程式碼看起來沒問題，卻怎麼都修不好的無力感，真的是差點讓我直接把鍵盤砸了。

會發生這種錯誤，其實是因為 React 的「強迫症」。當你開啟 SSR 時，伺服器會先傳送一份 HTML 給瀏覽器，等瀏覽器載入 JavaScript 後，React 會嘗試進行「Hydration（注入）」，把事件監聽器綁上去。問題來了，如果伺服器渲染出來的 HTML 結構，跟瀏覽器執行 JS 後產生的第一幀畫面長得哪怕只有一丁點不同——比如時間戳記、隨機亂數，或是根據瀏覽器環境（如 window 物件）產生的內容——React 就會覺得自己被騙了，直接報錯給你看。

我後來發現，最常見的兇手就是我在元件裡用了 new Date().toLocaleTimeString() 或者某些依賴於當前環境的判斷式。伺服器渲染時的時間是伺服器時間，瀏覽器渲染時的時間又變了，兩邊對不上， hydration 就宣告失敗。我的解決方法其實很簡單，就是讓 React 在初始階段「先裝死」，等到元件掛載完成後再把正確的內容填進去。

你可以寫一個簡單的 Hook，或者直接像下面這樣處理：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  // 在伺服器渲染時，我們只回傳一個靜態的 placeholder
  // 這樣伺服器和瀏覽器第一次看到的結構就會完全一致
  return (
    <div>
      {isClient ? <span>現在時間：{new Date().toLocaleTimeString()}</span> : <span>載入中...</span>}
    </div>
  );
}

為了預防這種地獄輪迴再次出現，我現在養成了一個習慣：只要是用到了 window、localStorage 或是跟時間、亂數相關的邏輯，我一律預設它們會導致 Hydration 錯誤。在寫這類元件時，我都會強迫自己先思考：「如果這段程式碼在伺服器上執行，它會不會吐出跟瀏覽器不一樣的結果？」如果會，就一定要用 useEffect 把這部分邏輯包起來，確保它只在客戶端觸發。

搞定這個問題後，看著 Console 乾乾淨淨、沒有任何錯誤警告的感覺真的太爽了。希望這篇筆記能幫你少走點彎路，別再跟這些紅字奮戰到半夜啦！
