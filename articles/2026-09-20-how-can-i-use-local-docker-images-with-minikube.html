Stop Pushing to Registry: How to Use Local Docker Images with Minikube

Source: Stack Overflow ↗ · 689 votes

I remember the first time I started playing with Minikube, I wasted an entire afternoon pushing images to Docker Hub just to test a single line of code change. I was sitting there, watching my home Wi-Fi choke on a 500MB image upload, thinking, "There has to be a better way than acting like my local machine is a remote server." It felt ridiculous to treat my own laptop like a cloud provider, and honestly, the feedback loop was killing my productivity.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside its own isolated environment—usually a virtual machine or a separate container—that has its own distinct Docker daemon. When you run docker build on your terminal, that image lives in your host’s Docker daemon, not inside the Minikube cluster. Your Kubernetes pods are looking for the image inside the cluster's daemon, and since it can't find it there, it tries to pull it from a remote registry. It’s like trying to find a book in your kitchen that you left in your office; the cluster simply doesn't know it exists in your host's memory.

The cleanest way I’ve found to bridge this gap without needing a private registry is to point your local terminal's Docker environment directly to the Minikube daemon. You can do this by running a single command in your terminal before you build your images:


eval $(minikube docker-env)

Once you run that, your local docker commands are now talking directly to the Docker engine inside your Minikube cluster. Now, when you run docker build -t my-app:latest ., the image is built straight into the cluster’s memory. Just remember to set your Kubernetes deployment's imagePullPolicy to IfNotPresent or Never in your YAML file, otherwise, Kubernetes might still try to reach out to the internet to find a newer version of the image. If you ever need to switch back to your host's Docker daemon, just run eval $(minikube docker-env -u).

To keep things smooth in the future, I highly recommend adopting a tagging strategy that doesn't rely on the latest tag. When you're constantly rebuilding and testing, latest becomes a nightmare because Kubernetes might get confused about whether it actually needs to pull a new version. If you tag your images with a timestamp or a short git commit hash, you'll save yourself from those "why is my old code still running?" headaches.

Hope this saves you from the registry-pushing madness I went through. Happy coding!

別再傻傻推送到 Docker Hub 了！在 Minikube 直接用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 689 票

記得剛開始碰 Kubernetes 時，我為了測試一個小小的修改，每次改完程式碼都要 docker build，然後苦苦等待 docker push 到 Docker Hub，再從 Minikube 那邊 kubectl delete pod 等它重新拉取。那個下午我反覆做了十幾次，看著那個緩慢的進度條，真的差點崩潰把鍵盤砸了，心想：「難道工程師的生命就是這樣浪費在網路頻寬上的嗎？」

後來我才搞懂，這其實是因為 Minikube 預設運行在一個隔離的虛擬機或容器環境裡，它根本看不到你宿主機（Host）裡面的 Docker Daemon。簡單來說，你電腦上的 Docker 和 Minikube 裡的 Docker 是兩條平行線，它們不共用同一個儲存空間，所以你 build 好的鏡像，Minikube 當然找不著，只能乖乖去遠端 registry 拉。

解決這個「白癡迴圈」其實超級簡單，你根本不需要修改任何設定檔，只需要讓 Minikube 的環境變數指向你本地的 Docker Daemon 就行了。只要在終端機輸入這行指令：


eval $(minikube docker-env)

執行完之後，你現在用的 docker 指令就會直接對著 Minikube 內部的環境操作了。這時候你再跑一次 docker build -t my-app:v1 .，鏡像就會直接被塞進 Minikube 的肚子裡。接著，記得把你的 Deployment YAML 裡的 imagePullPolicy 改成 IfNotPresent，這樣 Kubernetes 發現本地已經有了，就不會再跑去網路上下載。記得喔，如果你換回原本的 shell，記得要重新跑一次這行指令，不然你會發現怎麼 build 了半天，Pod 還是報 ImagePullBackOff 的錯誤，那個當下真的會讓人懷疑人生。

如果要預防這種「重複打包」的痛苦，我強烈建議你在開發初期就養成習慣，把這行指令加到你的 .bashrc 或 .zshrc 裡，或者乾脆寫一個簡單的 Makefile。我的做法是寫一個 make build-local 指令，裡面直接串好環境變數設定和 build 指令，這樣以後只要敲一個指令就能搞定，再也不用因為忘記切換環境而在那邊乾瞪眼。

搞定這個之後，開發效率真的會起飛，祝大家部署順利，別再被網路傳輸卡死啦！
