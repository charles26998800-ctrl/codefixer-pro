How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up a local Kubernetes cluster, feeling like a genius until I tried to deploy my first custom image. I spent three hours banging my head against the wall because my pods kept throwing ImagePullBackOff errors, even though I could see my image sitting right there in my local terminal using docker images. I was ready to throw my laptop out the window because I couldn't fathom why I had to push my code to a remote registry just to test a one-line change.

The reason this happens is actually quite simple: Minikube runs inside its own isolated environment, usually a virtual machine or a separate container. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Minikube’s Kubernetes cluster, however, is looking at its *own* internal Docker daemon. They are two completely different islands, and unless you explicitly tell them to talk to each other, Minikube just can't see what's on your local machine.

The fastest way I’ve found to fix this is by pointing your local terminal's Docker environment directly to Minikube’s internal daemon. By running the following command, you’re essentially telling your terminal, "Hey, stop building images for my laptop and start building them directly inside Minikube."


eval $(minikube docker-env)

Once you run that, any docker build command you execute will place the image directly into Minikube’s registry. Now, when you update your Kubernetes deployment YAML, make sure you set your imagePullPolicy to IfNotPresent. If you leave it as the default Always, Kubernetes will still try to reach out to the internet to verify the image, which will fail because your image only exists inside the cluster.


spec:
  containers:
  - name: my-app
    image: my-image:latest
    imagePullPolicy: IfNotPresent

If you’re on a newer version of Minikube, you can also use the minikube image load command. I actually prefer this method for smaller projects because it doesn't require messing with your environment variables. You just build the image locally like you normally would, and then push it into the cluster with a single command:


minikube image load my-image:latest

To keep your sanity in the future, my best advice is to always use specific image tags instead of relying on latest. When you use latest, it’s incredibly easy to lose track of which version of the code is actually running inside the pod, which leads to those "why isn't my change showing up?" moments that drive us all crazy.

Hope this saves you a few hours of debugging time! Happy coding, and may your pods always stay in the Running state.

為什麼 Minikube 總是抓不到我的 Local Image？別再推送到 Docker Hub 了！

來源：Stack Overflow ↗ · 688 票

還記得剛開始接觸 Kubernetes 的時候，為了測試一個簡單的變更，我硬生生在 Docker Hub 上面來來回回 push 了十幾次 image。那時候真的差點崩潰，每次改一行 code 就得等上幾分鐘的網路傳輸，搞到後來我根本不想寫程式，只想對著螢幕發呆。最痛苦的時刻莫過於，明明電腦裡就已經 build 好了 image，結果 Minikube 的 Pod 狀態永遠卡在 ErrImagePull 或 ImagePullBackOff，看著那幾個錯誤代碼，真的會讓人懷疑人生。

其實這背後的邏輯說穿了很簡單，只是當時的我太菜沒搞懂。Minikube 本質上是一個虛擬機（或容器），它和你的本機環境是「隔離」的。當你執行 docker build 時，這個 image 是存在你電腦的 Docker daemon 裡，但 Minikube 裡頭跑的那個 Kubernetes 環境，它根本沒辦法「穿透」到你的本機硬碟去抓東西。對它來說，你沒告訴它去哪裡找，它就只能乖乖去 Docker Hub 找，找不到當然就報錯給你看了。

解決這個問題最快的方法，就是直接把你的 Docker daemon 切換到 Minikube 的環境。只要在終端機輸入下面這行指令，你的 docker 指令就會直接對著 Minikube 的內部環境發號施令：


eval $(minikube docker-env)

切換過去之後，你再執行 docker build -t my-app:latest .，這次 build 出來的 image 就會直接存在 Minikube 的肚子裡。現在你只要把 Deployment YAML 裡的 imagePullPolicy 改成 IfNotPresent，Kubernetes 就會優先使用本地已經存在的 image，再也不用浪費時間跟網路頻寬去跑推送流程了。

當然，如果你不想每次都切換環境，或者覺得這樣太麻煩，還有一個很懶人的做法，就是直接用 minikube image load 指令。你可以先把 image build 好，然後執行 minikube image load my-app:latest，它會自動幫你把映像檔塞進去。這招對於偶爾才要測試一次的開發者來說非常友善，不用擔心切換環境後導致本機其他 Docker 指令跑不動。

為了避免以後又因為這種「明明有圖卻抓不到」的問題抓狂，我現在養成一個習慣：只要是在進行 Kubernetes 的本地開發，我一定會先檢查 imagePullPolicy 是不是設對了。習慣把這個參數設成 IfNotPresent，真的能幫你省下無數次無意義的等待。

希望這些經驗能幫你省下不少 Debug 的時間，趕快去試試看，別再被那個 ImagePullBackOff 給折磨了！
