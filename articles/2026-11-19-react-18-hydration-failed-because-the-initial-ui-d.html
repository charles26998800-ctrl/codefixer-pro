Troubleshooting the "Hydration failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in React 18. I had spent three hours late on a Tuesday night convinced that my server-side rendering logic was flawless, only to be slapped in the face by a console full of red text telling me the server and client were out of sync. It felt like I was losing my mind because the code looked perfectly fine, but every time I refreshed the page, the mismatch error mocked me from the DevTools.

The root cause of this headache is actually quite logical once you peek under the hood of React 18. When you use SSR, Next.js renders your component into HTML on the server and sends that static string to the browser. Once the browser loads the JavaScript bundle, React tries to "hydrate" that static HTML by attaching event listeners and turning it into a dynamic app. If the HTML the server generated doesn't perfectly match the HTML the client generates during that first render, React throws its hands up in frustration. This usually happens because of non-deterministic data, like using Math.random() or new Date() directly in your component body, or because of browser-specific APIs like window that don't exist on the server.

When I finally hunted down my specific mismatch, I realized I was trying to render content based on a condition that was only available on the client. To fix this, you need to ensure that the component doesn't attempt to render the dynamic parts until it's officially mounted on the client. I’ve found that the cleanest way to handle this is by using a simple useEffect hook to toggle a state variable, which acts as a flag for when the component is safe to render on the client side.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      <h1>Welcome</h1>
      {isClient ? (
        <p>This is only rendered on the client: {window.location.href}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

You can prevent these issues from creeping back into your codebase by being extremely disciplined about where you access global browser objects. My golden rule is to never reference window, document, or localStorage directly in your component’s top-level scope. If you absolutely need those values, wrap them in a custom hook or ensure they are only accessed inside a useEffect or an event handler. Keeping your initial render pure and predictable is the best way to keep the hydration monster at bay.

Hopefully, this saves you the three hours of hair-pulling I went through. Happy coding!

Next.js 遇到 Hydration Failed？別慌，這其實是 React 在跟你玩捉迷藏

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 的那個週末，我原本想著把專案架構優化一下就能開心過週末，結果一跑 npm run dev，瀏覽器控制台直接噴出一大串紅字：「Hydration failed because the initial UI does not match...」。當時我整個人愣住，看著那串錯誤訊息，心裡真的是一萬隻草泥馬奔騰，明明程式碼看著都沒錯，為什麼伺服器給的 HTML 跟瀏覽器剛跑起來的畫面就是對不上？那種查了半天卻找不到兇手的無力感，真的是工程師生涯中最想把螢幕砸了的瞬間之一。

其實這背後的道理說穿了也不複雜。簡單來說，Next.js 在伺服器端（SSR）會先渲染出一段 HTML 發給瀏覽器，但當 React 在瀏覽器端接手準備「綁定」事件（Hydration）時，它發現瀏覽器實際跑出來的 HTML 結構跟伺服器給的居然不一樣。這通常發生在我們用了某些會根據環境變數變動的邏輯，例如 new Date()、隨機數 Math.random()，或是判斷 localStorage 的值。因為伺服器端跑的時候這些值可能跟瀏覽器端不同，React 一發現「咦？不對勁」，為了保持 UI 一致性，它就會直接報錯，甚至乾脆把你辛苦渲染的頁面重刷一遍，效能直接掉到谷底。

我當時排查了半天，發現最常見的兇手就是我在元件裡直接用了會隨時間變動的邏輯。解決這個問題的核心技巧其實就是「延遲渲染」。既然伺服器端跟瀏覽器端的結果在初始階段會衝突，那我們就乾脆讓這部分內容在伺服器端先不渲染，等瀏覽器跑起來之後再補上。你可以用一個簡單的 useEffect 來處理，像這樣：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>現在時間是：{new Date().toLocaleTimeString()}</p>
      ) : (
        <p>載入中...</p>
      )}
    </div>
  );
}

透過這種方式，伺服器端只會輸出「載入中...」，而真正的邏輯會等到瀏覽器端 useEffect 觸發後才執行，這樣兩邊的初始 UI 就會完美對接，討厭的紅字也就消失了。

至於怎麼預防這種鬼打牆的狀況再次發生？我現在養成了一個習慣，只要是會用到 window 物件、localStorage 或者任何依賴瀏覽器環境的 API，我一律會把它們封裝成一個自訂的 Hook，並且強制加上一個 isMounted 的判斷。另外，盡量避免在渲染邏輯裡寫隨機數，如果真的需要隨機，考慮把它放在 useEffect 裡更新 State，而不是直接在 render body 裡調用。

搞定這個問題後，看著控制台終於乾乾淨淨，那種舒暢感真的無價。希望這些經驗能幫你省下幾個熬夜的夜晚，趕快去喝杯咖啡休息一下吧！
