Why Your React Project Is Crashing With "digital envelope routines::unsupported"

Source: Stack Overflow ↗ · 2572 votes

I remember sitting down to spin up a quick prototype last year, feeling pretty productive until my terminal suddenly puked a wall of red text at me. I’d just initialized a standard React project, and instead of seeing that familiar "Compiled successfully" message, I was staring at a cryptic OpenSSL error that made me feel like I’d accidentally tried to hack the Pentagon. I spent a good three hours tearing my hair out, convinced I’d somehow corrupted my entire Node environment, only to realize it was just a mismatch between my Node version and my project's dependencies.

The root cause of this headache is actually pretty straightforward: OpenSSL 3.0. When Node.js upgraded to version 17 and beyond, they switched to OpenSSL 3.0, which enforces stricter security standards for hashing algorithms. Many older React projects and common build tools like Webpack use legacy algorithms that OpenSSL 3.0 simply refuses to run. It's not that your code is broken; it's that your environment is suddenly playing by a set of rules that your project wasn't built to follow yet.

To fix this, I found that the quickest way to get back to coding is to tell Node to use the legacy provider for OpenSSL. If you’re on macOS or Linux, you can set the environment variable right in your terminal before you run your start command. Just prefix your usual startup script like this:


NODE_OPTIONS=--openssl-legacy-provider npm start

If you’re stuck on Windows using PowerShell, the syntax is a bit different, so you’ll want to run this instead:


$env:NODE_OPTIONS = "--openssl-legacy-provider"
npm start

For a more permanent fix that saves you from typing that every single time, I just add it to my package.json file. I update the scripts section so that the start command automatically includes the flag, which keeps my terminal history clean and my sanity intact:


"scripts": {
  "start": "react-scripts --openssl-legacy-provider start",
  "build": "react-scripts --openssl-legacy-provider build"
}

The best way to prevent this from popping up in future projects is to keep an eye on your Node version using a version manager like nvm (Node Version Manager). I try to stick to the current Long Term Support (LTS) version, and whenever I start a new project, I verify that my local tools are compatible with the latest dependency requirements. It’s a small habit, but it saves you from these weird "it worked on my machine yesterday" moments.

Hopefully, this gets you back to building your app without any more cryptic errors. Let me know if you run into any other weird issues!

救命，Node.js 升級後 React 專案直接炸掉：error:0308010C 怎麼解？

來源：Stack Overflow ↗ · 2572 票

那天我為了趕一個急件，剛換了一台新電腦，想說把環境重新架設一下。結果才剛用 IntelliJ 跑起一個乾淨的 React 專案，終端機就直接噴出一堆紅字，那串 error:0308010C:digital envelope routines::unsupported 看得我頭皮發麻，當下真的差點要把鍵盤砸了，心想「這不是最基礎的專案嗎？連這都跑不起來是要怎麼下班啦！」

其實這問題簡單來說，就是 Node.js 的版本升級惹的禍。從 Node.js 17 版開始，OpenSSL 3.0 成了預設標準，但很多舊版的 webpack 或是 React 依賴套件還在用舊的加密演算法，兩邊兜不起來，對方覺得你不安全，你覺得對方太龜毛，最後就直接罷工給你看。這種感覺真的很差，就像你明明只是想用舊鑰匙開門，結果房東突然把整棟樓的鎖都換了，完全沒預警。

我當時試了半天，最後發現最快的方法就是告訴 Node.js：「嘿，別管那麼多，先退回到舊模式吧！」最直接的解法是在啟動專案時，強制設定一個環境變數 NODE_OPTIONS。如果你是用 Windows 的命令提示字元，可以這樣打：


set NODE_OPTIONS=--openssl-legacy-provider
npm start

如果你是用 Mac 或 Linux 的終端機，記得要在前面加個 export：


export NODE_OPTIONS=--openssl-legacy-provider
npm start

當然，每次手動打這些也很煩，我後來直接把這段塞進 package.json 的 scripts 區塊，修改 start 那一行，讓它變成這樣：


"scripts": {
  "start": "react-scripts --openssl-legacy-provider start",
  "build": "react-scripts --openssl-legacy-provider build"
}

這樣一改，以後不管怎麼跑都不會再跳出這個惱人的錯誤了。

至於怎麼預防這種坑，建議大家以後在專案開發時，盡量要把 Node.js 的版本控制好。我現在都會在專案根目錄放一個 .nvmrc 檔案，並且在 package.json 裡面加上 engines 欄位，明確規定這個專案該用哪個版本的 Node.js。這樣就算換了電腦或交接給同事，大家都能確保環境一致，不用每次都為了這些底層套件的相容性搞到心態爆炸。

希望這篇能幫你省下半小時崩潰的時間，趕快去把專案跑起來吧！
