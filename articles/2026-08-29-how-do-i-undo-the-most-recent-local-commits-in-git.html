How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27237 votes

I still remember the first time I accidentally committed a massive debug log file full of sensitive API keys to my main branch. I sat there staring at my terminal for a solid ten minutes, sweating bullets, convinced I’d just permanently ruined my repository and would have to delete the whole project and start over from scratch. I spent a good three hours trying to "fix" it by manually editing files before a senior dev walked by, chuckled at my panic, and showed me how trivial it is to roll back local history in Git.

The reason this happens is usually just a simple case of "git commit -a" being a little too eager or forgetting to check your staging area before hitting enter. Essentially, Git keeps a record of everything you do in its internal history, but as long as you haven't pushed those changes to a remote server, that history is entirely within your control. You’re essentially just telling the Git pointer to move backward in time and pretend the last commit never happened. It’s not magic, it’s just pointer manipulation, but it feels like a lifesaver when you realize you’ve made a mistake.

When I need to undo that last commit, I rely on the git reset command. If you want to undo the commit but keep your changes in your working directory—which is what I usually want so I can fix the files I messed up—you should run git reset --soft HEAD~1. This moves the branch pointer back one step, leaving your work perfectly staged and ready to be fixed.


# Undo the last commit, but keep the changes staged
git reset --soft HEAD~1

If you’re feeling confident and you just want to get rid of the commit *and* all the changes inside it because you realized the entire approach was wrong, you use the --hard flag. Just be careful with this one, because it’s a total wipe—there’s no "undo" for a hard reset once you hit enter.


# Undo the last commit AND destroy all changes in those files
git reset --hard HEAD~1

To stop this from becoming a recurring nightmare, I started using the git status command like it’s a religious ritual. Before every single commit, I run git status to verify exactly which files are staged. If I see something that shouldn't be there, I use git reset to unstage it before finalizing the commit. It’s saved me from countless "oops" moments over the years.

Hopefully, this gets you out of your current jam without any lost work. Good luck with the rest of your coding session!

手滑把不該 commit 的檔案推上去了？別慌，救回你的 Git 本地歷史

來源：Stack Overflow ↗ · 27237 票

記得有一次凌晨三點，我為了趕一個緊急的小功能，腦袋已經呈現「當機」狀態，大腦完全沒過濾就直接執行了 git commit -am "fix bugs"。結果按下去的瞬間，我才發現自己居然把一堆正在測試中的測試檔、還有隱藏的設定檔全給包進去了。當下那種心臟漏跳一拍、冷汗直流的感覺，真的會讓人想直接把電腦關了去睡覺，心想這下是不是毀了，會不會被同事發現我這麼粗心。

其實這狀況在 Git 裡非常常見，根本原因就在於我們對「本地提交」與「遠端同步」之間的認知差異。當你只是在本地 commit 而還沒 push 時，這些紀錄其實還只存在於你電腦裡的 .git 資料夾中，根本還沒傳給伺服器，所以你其實握有絕對的控制權，隨時可以把它們「抹掉」或是「修改」。這就像是你在紙上寫錯字，只要還沒拿去影印機發給全公司看，用修正帶塗掉重寫根本沒人會知道。

我當時冷靜下來後，用的就是 git reset 這個神器。如果我只是想把剛剛那次 commit 撤銷，但保留我改好的程式碼，讓它們回到「還沒 commit 但已經修改過」的狀態，我會直接輸入：


git reset --soft HEAD~1

這行指令的意思是說，把 HEAD 指針往回撥一格，但保持我的檔案變更（--soft）。如果你是連檔案都不想要了，想徹底毀屍滅跡，直接用 --hard 就行了，不過這招要小心，因為它會把你辛苦敲的程式碼直接丟進垃圾桶，救不回來的。我個人最常用的是 --soft，這樣我就可以把剛剛漏掉的檔案從暫存區拿掉，調整好之後再重新 commit 一次，看起來就像什麼事都沒發生過一樣完美。

要預防這種手滑悲劇，我現在養成了一個習慣，就是每次 commit 前一定會先敲 git status 看一眼。我還在 Git 設定裡加入了一個小技巧，就是用 git add -p 來取代直接 git add .。這樣 Git 會逐一問我：「這個檔案要加入嗎？」、「那一行要加入嗎？」，雖然多花幾秒鐘，但這幾秒鐘真的救了我無數次，至少不會再讓那種「不該出現的 debug log」跟著程式碼一起進到 repo 裡。

Git 這種工具就是這樣，剛開始用會覺得它處處針對你，但只要搞懂它其實很樂意幫你「後悔」，你就會覺得安心多了。希望下次你手滑時，這招能幫你穩住心態！
