How to Fix RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor)

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a complex training loop in PyTorch, feeling incredibly proud that I’d finally managed to move my model to the GPU. I hit run, watched the progress bar for about two seconds, and then—boom—the console exploded with that dreaded RuntimeError. I spent three hours staring at the screen, convinced my GPU drivers were haunted, only to realize I’d completely forgotten to move the actual input data to the same device as my model.

The reason this happens is actually quite logical once you stop pulling your hair out. PyTorch is very strict about where your tensors live; your model weights are sitting in the high-speed memory of your NVIDIA GPU, but your input data is still chilling in your system's RAM (the CPU). When the model tries to perform matrix multiplication, it can’t reach across the bus to grab those CPU-bound tensors. You’re essentially trying to perform a calculation where the left hand doesn't know what the right hand is doing. The error message is just PyTorch’s way of saying, "Hey, I can't do math with two different types of hardware at the same time."

The fix is straightforward, but it’s a step that’s easy to skip when you’re busy writing data loaders. You need to explicitly push your input tensors to the device you defined earlier. Inside your training loop, right before you pass the data into your model, you just need to call .to(device) on your inputs. Here is what that looks like in practice:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    inputs, labels = data
    # This is the line that fixes the crash:
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training code

Once you add those .to(device) lines, your tensors will migrate to the GPU, and the RuntimeError will vanish.

To prevent this from becoming a recurring headache, I’ve started adopting a "device-agnostic" coding pattern. Instead of hardcoding cuda or cpu everywhere, I define a device variable at the top of my script and create a small utility function or just keep a mental checklist to always move data immediately after pulling it from the batch. If you make it a habit to move your inputs the second they exit the DataLoader, you’ll save yourself a massive amount of debugging time down the road.

Hope this saves you a few hours of frustration today! Happy coding, and may your training runs finish without any more cryptic errors.

救命！PyTorch 又在跟我鬧脾氣：FloatTensor 與 CudaTensor 的不相容地獄

來源：Stack Overflow ↗ · 202 票

還記得剛開始玩深度學習的時候，為了訓練一個模型，我熬夜寫了好幾個小時的程式碼，好不容易把架構搭好，滿心期待地按下執行鍵，結果螢幕上瞬間噴出一大串紅字。看著那行 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same，我當下整個人直接癱在椅子上，心想：「我不是都把模型丟到 GPU 了嗎？你到底還在吵什麼！」那種以為萬事俱備、結果被一個莫名其妙的型別錯誤卡住的無力感，真的是每個煉丹師共同的夢魘。

其實這個錯誤的原因單純到有點好笑，說白了就是「溝通不良」。PyTorch 是一個很嚴格的強迫症患者，當你的模型（Weights）已經被搬到 GPU 上（也就是 cuda.FloatTensor），但你的輸入資料（Inputs）還留在 CPU 的記憶體裡（也就是 FloatTensor），兩個人在做矩陣運算時根本對不上頻率。模型在 GPU 等著吃資料，你卻把資料丟在 CPU 的籃子裡，PyTorch 當然會崩潰給你看，它根本沒辦法跨設備幫你做運算。

要解決這個問題，其實只要讓它們在同一個「房間」裡就好。最直覺的做法，就是當我們從 DataLoader 拿到資料時，順手把這些資料也搬到跟模型同一個設備上。我通常會這樣寫：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！記得把 inputs 和 labels 也搬過去
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也要記得把 labels 放在同一個 device
    loss = criterion(outputs, labels)

至於要怎麼預防下次再踩到這個坑？我後來養成了一個好習慣，就是定義一個全域的 device 變數之後，絕對不要隨便寫死 cuda 或 cpu。在寫程式時，直接把所有會用到的 tensor 都掛上 .to(device)，甚至在寫測試程式時，乾脆把這個動作封裝成一個小函式或是寫在 Dataset 的 __getitem__ 裡處理。只要你心裡隨時記著「模型在哪，資料就要跟到哪」，這種錯誤基本上就再也不會來煩你了。

搞定這個之後，看著 GPU 的使用率終於跳起來，那種成就感真的是無價的，大家加油啦！
