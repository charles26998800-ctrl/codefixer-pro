How to Fix the "digital envelope routines::unsupported" Error in React

Source: Stack Overflow ↗ · 2572 votes

I remember the exact moment I first saw this error while trying to spin up a quick prototype in a new React project. I had just upgraded my Node.js version, feeling all productive and modern, when my terminal suddenly exploded with that cryptic error:0308010C:digital envelope routines::unsupported message. I spent a good hour staring at my screen, convinced I’d somehow broken my entire development environment, only to realize I was just a victim of a breaking change in OpenSSL that I hadn't prepared for.

The reason this happens is actually quite straightforward once you peel back the layers. When Node.js upgraded to version 17 and later, they switched to OpenSSL 3.0, which enforces stricter security standards. Many older Webpack configurations and legacy dependencies rely on algorithms that OpenSSL 3.0 considers outdated or insecure. Because these libraries try to use those legacy hashing methods, Node.js throws a fit and shuts down the build process to protect you. It’s basically the software equivalent of a bouncer refusing to let you into a club because your ID is from a different decade.

Fixing this is luckily a piece of cake once you know the secret handshake. The most reliable way to handle it without having to downgrade your entire Node installation is to tell the environment to use the legacy OpenSSL provider. You can do this by setting an environment variable before your build script runs. If you’re on a Mac or Linux machine, you just need to modify your package.json file like this:


"scripts": {
  "start": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

If you’re working on Windows, the syntax is slightly different because of how the command prompt handles environment variables:


"scripts": {
  "start": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

If you want to avoid editing your package.json every time, you can also just run the export command directly in your terminal before starting your development server. For a more permanent solution across your system, you can add export NODE_OPTIONS=--openssl-legacy-provider to your .bashrc or .zshrc file, but be careful—that applies the setting globally, which might hide issues in other projects that should actually be updated to modern standards.

To prevent running into this again, my best advice is to keep your project dependencies updated. Most modern versions of react-scripts and Webpack have already patched this behavior to be compatible with OpenSSL 3.0. Whenever you see a dependency vulnerability or a build warning, don't just ignore it; take five minutes to bump your packages, as it’s almost always easier to update your stack than to keep patching these "legacy" holes.

Hope this saves you the headache it caused me. Happy coding!

剛裝好 React 專案就噴 error:0308010C？別慌，這其實是 Node.js 版本惹的禍

來源：Stack Overflow ↗ · 2572 票

那天我心血來潮想試用一個新的 IDE 功能，順手點了 IntelliJ IDEA 的「建立 React 專案」按鈕，想說應該五分鐘就能搞定環境，結果終端機一跑下去，螢幕直接跳出一大串紅字，那個 digital envelope routines::unsupported 的錯誤訊息瞬間讓我心涼了一半。我當下真的差點崩潰，想說我明明什麼都還沒寫，連 App.js 都還沒打開，怎麼連啟動專案都過不去？那種「我明明照著教學做，為什麼世界要這樣對我」的無力感，真的是每個工程師的共同夢魘。

其實這背後的原因一點都不神秘，單純就是 Node.js 的版本更新太快，導致「世代隔閡」。簡單來說，Node.js 在 17 版之後升級了底層的 OpenSSL 庫，改用了更嚴格的加密標準，而許多舊版的 Webpack 或 React 腳本還在用舊的那套加密演算法。所以當你的 Node.js 比較新，卻跑著比較舊的專案設定時，它就會像個固執的老人家一樣，大喊著「我不支援這種過時的演算法」然後直接罷工。

解決這個問題的方法其實比想像中簡單，最快的方式就是告訴 Node.js：「嘿，別管那麼多，先退回到舊模式跑跑看吧」。你只需要在啟動專案的指令前加上一個環境變數設定。如果你是用 Mac 或 Linux，直接在終端機輸入：


export NODE_OPTIONS=--openssl-legacy-provider
npm start

如果是 Windows 的 PowerShell 使用者，指令會長這樣：


$env:NODE_OPTIONS = "--openssl-legacy-provider"
npm start

如果你不想每次都要敲這串指令，最乾脆的做法就是直接改掉 package.json 裡的 scripts 設定，把 start 指令改成 react-scripts --openssl-legacy-provider start，這樣以後每次輸入 npm start 就會自動幫你帶上這個參數，省事很多。

為了避免這種踩坑經驗再次發生，我現在養成了習慣，在接手或建立任何舊專案前，一定會先檢查 .nvmrc 檔案，確保我使用的 Node.js 版本跟專案要求的版本是一致的。如果真的沒辦法，至少也會在開發環境的設定檔裡先留一手。畢竟開發者的人生已經夠難了，不需要把時間浪費在處理這種「版本不合」的無謂錯誤上。

希望這些經驗能幫你省下寶貴的除錯時間，趕快回去寫程式吧，別讓這點小阻礙壞了你的開發節奏！
