How to Use Local Docker Images with Minikube: A Practical Guide

Source: Stack Overflow ↗ · 688 votes

I remember the first time I set up Minikube, I felt like a genius until I tried to deploy my first local image. I spent three hours tweaking my YAML files, convinced my imagePullPolicy was wrong, only to realize I was trying to pull an image that literally lived on my laptop, not in the cloud. It was one of those classic "aha!" moments where you realize you're fighting the architecture rather than the configuration.

The reason this happens is pretty straightforward: Minikube runs inside a virtual machine or a separate container environment, depending on your driver. When you run docker build on your host machine, that image lives in your host's Docker daemon. Minikube, however, has its own isolated Docker daemon inside its VM. When your Kubernetes pods try to pull an image, they look inside Minikube's daemon, see nothing, and start looking at Docker Hub. Since your image isn't there, you get that dreaded ImagePullBackOff error every single time.

The cleanest way I’ve found to fix this is by pointing your local shell directly to the Minikube Docker daemon. Instead of building locally and trying to push or move things around, you just run a single command to switch your environment. Before you run your build command, execute this in your terminal:


eval $(minikube docker-env)

Once you run that, your local docker commands are now talking directly to the Docker engine inside your Minikube cluster. Now, when you run docker build -t my-app:v1 ., the image is built directly inside the Minikube environment. You can verify it worked by running docker images, and you'll see your custom image sitting right there ready for your deployment. Just remember that if you open a new terminal tab, you'll need to run that command again, or you’ll be back to building images on your host machine where Minikube can't see them.

To keep your workflow from getting messy, my biggest tip is to always set your imagePullPolicy to IfNotPresent in your Kubernetes deployment manifests. If you don't do this, Kubernetes might still try to reach out to the registry to check for a newer version of the image, even if you’ve successfully built it locally. By keeping that policy set, you're telling the cluster to trust the local image and stop hunting for one that doesn't exist online.

Hope this saves you from the same three-hour headache I dealt with back in the day. Happy coding, and let me know if you run into any other weird K8s quirks!

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 688 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的功能改動，我竟然傻傻地把 Docker Image 打包好、推到 Docker Hub，然後再讓 Minikube 去拉下來。結果光是網路傳輸就花掉我半小時，更別提中間還斷線兩次，當時盯著螢幕上那個 ImagePullBackOff 的錯誤訊息，我真的差點要把鍵盤給砸了，這種「為了改一行程式碼，卻要跟網路速度搏鬥」的感覺，簡直是開發者的噩夢。

其實這問題的根源很簡單，Minikube 預設運作在一個獨立的虛擬環境（VM 或 Docker Container）裡，這就像是你的電腦裡住著另一個小世界。當你在宿主機執行 docker build 時，Image 是存放在宿主機的 Docker Daemon 裡，但 Minikube 的 Kubernetes 節點根本「看不到」這些 Image。它以為你叫它去遠端抓，結果發現哪裡都找不到，當然就直接送你一個 ErrImagePull 當見面禮。

要解決這個問題，最直覺的方式就是把你的 Docker 環境直接導向 Minikube 內部的 Daemon。只要在終端機輸入這行指令，讓你的 shell 暫時「寄生」在 Minikube 的 Docker 環境裡：


eval $(minikube docker-env)

執行完這行後，現在你再下 docker build -t my-app:latest . 指令，這個 Image 就會直接蓋在 Minikube 內部。這時候你的 Kubernetes Deployment 只要記得把 imagePullPolicy 設定成 IfNotPresent，它就不會再去網路上瞎忙，而是直接撈取你剛建好的本地映像檔。這招真的快到讓我懷疑人生，以前那種等傳輸的日子簡直是在浪費生命。

不過要提醒大家，這招是有副作用的，每次你新開一個終端機視窗，都得重新執行一次這行指令，不然你會發現 docker build 怎麼又把 Image 建在外面了。為了避免這種「明明有建檔卻一直報錯」的尷尬情況，我現在習慣在 ~/.zshrc 或 ~/.bashrc 裡加個小別名，或是養成習慣在開發前先檢查 docker info 是否已經連上 Minikube 的環境。

以後開發 Kubernetes 應用，真的不要再走彎路去推 Image 了，把環境指過去，效率直接起飛。
