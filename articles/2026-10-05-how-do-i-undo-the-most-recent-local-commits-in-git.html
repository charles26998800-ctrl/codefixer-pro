How to Undo Your Last Local Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27242 votes

I still remember the first time I accidentally committed a massive directory of environment variables and temporary build artifacts to a production-bound branch. I spent nearly two hours sweating bullets, convinced I’d somehow permanently bricked the codebase before I even realized git reset was a thing. We’ve all been there—you’re moving fast, you run git commit -a, and suddenly you realize you’ve committed half-baked code or files that definitely shouldn’t be in version control.

The reason this happens is usually just a lack of attention to the staging area. When you run git commit, you’re essentially telling Git to take a snapshot of whatever is currently indexed. If you’ve gotten into the habit of using the -a flag or just blindly running git add . without checking the status, you’re bound to accidentally snapshot files that aren't ready for primetime. Git is designed to be a permanent record, so it doesn't make it immediately obvious how to "delete" that record, which is why it feels so intimidating the first time you run into it.

The good news is that as long as you haven't pushed those commits to a remote server, fixing this is incredibly simple. I usually reach for git reset because it’s the cleanest way to move the branch pointer back to a previous state. If you want to undo the commit but keep all your changes in your staging area (so you can fix what you missed), I run this:


git reset --soft HEAD~1

If you realize the changes were a total disaster and you just want to wipe them out completely, essentially acting like that commit never happened, use the hard reset instead. Just be careful, because this will permanently discard your work:


git reset --hard HEAD~1

Once you run the soft reset, your files will be right back in your staging area, waiting for you to unstage or modify them before making a cleaner commit. It’s a lifesaver.

To keep this from happening again, I’ve made it a personal rule to always run git status before I pull the trigger on a commit. It takes an extra three seconds, but seeing exactly which files are staged prevents those "oh no" moments before they actually turn into a headache. I also started using a GUI tool like GitKraken or even just the built-in VS Code staging view for complex commits, as it forces me to look at the diffs one last time before I finalize the snapshot.

Hope this helps you save some time and keeps your commit history looking clean. Happy coding!

剛 Commit 完才發現檔案傳錯了？別慌，Git 救得回來

來源：Stack Overflow ↗ · 27242 票

記得剛開始工作那年，有次趕著下班，沒檢查仔細就直接 git commit -m "update" 了，結果才發現我不小心把一堆還在測試中的 Debug Log 檔和半成品的設定檔全推進了 Local Repo。那種心跳漏一拍的感覺真的超崩潰，深怕如果不小心手滑 push 上去，隔天早上就會被主管抓去喝咖啡，甚至被同事用異樣眼光盯著看。

會發生這種事，通常是因為我們對 Git 的 Commit 機制太過信任，以為按下去就覆水難收。其實 Git 的厲害之處在於它隨時都在記錄你的「版本歷史」。當你執行 commit 時，Git 只是把這些改動鎖定在你的本地記錄裡，在還沒執行 git push 到遠端之前，這些動作其實都還在你的「掌握之中」，只是這層保護膜很多人不知道怎麼觸發罷了。

當下我的做法很簡單，就是利用 git reset 這個強大的指令。如果你只是想撤銷最後一次 commit，但想保留你辛苦修改的程式碼（檔案還在暫存區或工作目錄），你可以直接輸入 git reset --soft HEAD~1。這樣一來，剛剛的 commit 記錄會直接消失，但你的程式碼會完好無損地留在你的工作區，你可以趕快修正那些錯放的檔案，重新 commit 一次就好。

如果你的情況更糟，是連檔案內容都改壞了，想把一切都變回 commit 前的樣子，那就用 git reset --hard HEAD~1。這招非常暴力，它會把你最近一次 commit 的所有修改直接「抹掉」，還原到 commit 之前的乾淨狀態。我第一次用這個指令時手都在抖，因為這代表你沒 commit 的改動會直接蒸發，所以用之前一定要確認你的 IDE 已經存檔，或者真的確定那些改動都是垃圾。

為了避免這種心驚膽跳的時刻，我現在養成了一個好習慣：在 commit 之前一定會先打 git status 看一下。雖然這看起來很笨，但它能強迫我再確認一次到底改了哪些檔案。如果可以的話，裝個像 Oh My Zsh 這種能顯示 Git 分支狀態的終端機工具也很有幫助，它會直接告訴你現在有多少檔案變更，讓你一眼就能發現「奇怪，怎麼改了 50 個檔案？我明明只動了一個功能」。

學會這幾招 reset，以後就算再怎麼手滑也不怕了，反正 Git 本來就是拿來給我們犯錯後修正的嘛！
