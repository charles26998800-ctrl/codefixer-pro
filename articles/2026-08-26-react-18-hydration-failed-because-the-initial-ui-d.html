Debugging React 18 Hydration Mismatches: Why Your Server and Client Aren't Talking

Source: Stack Overflow ↗ · 341 votes

I still vividly remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours into a late-night coding session, convinced my logic was flawless, only to be met with a wall of red text in the browser console telling me my server-rendered HTML didn't match my client-side bundle. It’s one of those bugs that makes you feel like you’re losing your mind because the UI looks perfect for a split second before it completely breaks or jumps around.

The root cause of this frustration is actually quite logical: React expects the HTML generated on the server to be identical to what the client generates during the initial render. When you use server-side rendering (SSR), the server sends a static HTML snapshot to the browser. Once that hits the client, React "hydrates" it by attaching event listeners and managing state. If your code relies on something that changes based on the environment—like a Date object, a local storage check, or even a random number generator—the server and client will generate different DOM trees. React realizes this mismatch immediately, panics, and throws the hydration error because it can't guarantee the integrity of the UI.

To fix this, I’ve learned that the best approach is to force the component to wait until it’s officially mounted on the client before rendering the "mismatched" part. I usually create a simple useEffect hook to track the mounting state. By initializing a state variable to false and flipping it to true inside useEffect, I can ensure that any code causing the mismatch only runs after the initial hydration is complete. Here is how I typically structure that fix:


import { useState, useEffect } from 'react';

function HydrationSafeComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    // Render a skeleton or nothing while waiting for the client
    return null; 
  }

  return <div>{new Date().toLocaleTimeString()}</div>;
}

By returning null or a neutral loading state during the server pass, you prevent the mismatch entirely. Once the component mounts in the browser, the useEffect triggers a re-render, and the client-side logic kicks in safely.

If you want to prevent this headache in the future, my golden rule is to keep your server-side rendering as deterministic as possible. Avoid accessing browser-specific APIs like window, localStorage, or navigator directly in the top-level scope of your component. If you absolutely need those values, treat them as client-side-only data and always wrap them in an "is-mounted" check. It’s a small bit of extra boilerplate, but it saves you from those late-night debugging marathons.

Hope this clears up the confusion so you can get back to building cool stuff. Happy coding, and may your consoles stay clean!

React 18 Hydration Error：那個讓我熬夜到凌晨的「伺服器 vs 客戶端」幽靈

來源：Stack Overflow ↗ · 341 票

我還記得那天晚上，為了趕一個專案的上線進度，我正意氣風發地要把 App 從普通的 React 切換到 Next.js 的 SSR 模式。結果剛跑起來，瀏覽器控制台就像耶誕樹一樣亮起了整排刺眼的紅字：「Hydration failed because the initial UI does not match...」。當下我真的差點要把鍵盤砸了，明明程式碼看起來沒什麼毛病，為什麼伺服器給我的 HTML 跟瀏覽器自己跑出來的結果就是對不上？

其實這個問題的核心說穿了很單純，就是「時差」鬧的鬼。當你使用 SSR 時，伺服器會先幫你把 HTML 生成好傳給瀏覽器，這時候 React 會在瀏覽器端嘗試「接手」並注入互動邏輯，也就是所謂的 Hydration（水合作用）。但問題來了，如果你的程式碼裡用了 window 物件、或是根據當下時間、隨機數字來決定顯示什麼內容，伺服器產出的 HTML 內容跟瀏覽器第一次執行時的內容就會不一樣。React 看著這兩個版本的 UI 不對勁，為了怕崩潰，它只好直接報錯投降，甚至有時候會乾脆把整個 DOM 砍掉重練，這也是為什麼你可能會看到畫面閃爍，或者某些功能點了沒反應的痛苦時刻。

我後來發現，最常見的兇手就是我在組件裡直接用了 typeof window !== 'undefined' 這種判斷，或者是用了像 new Date() 這種會隨著環境變動的值。解決這個問題，最直覺的做法就是強迫 React 等到組件掛載（Mount）完成後才進行渲染。我通常會寫一個簡單的 useMounted hook 來處理，確保只有在客戶端跑完第一次渲染後，才顯示那些會造成差異的內容：


import { useState, useEffect } from 'react';

function useMounted() {
  const [hasMounted, setHasMounted] = useState(false);
  useEffect(() => {
    setHasMounted(true);
  }, []);
  return hasMounted;
}

// 在你的組件中使用：
function MyComponent() {
  const isMounted = useMounted();

  if (!isMounted) return null; // 或者放一個骨架屏 (Skeleton)

  return <div>這裡現在是安全的：{window.location.href}</div>;
}

為了避免以後再踩到這種坑，我現在養成了一個習慣：只要是涉及到瀏覽器特有 API（像是 localStorage 或 window）的邏輯，我一律把它丟進 useEffect 裡，或者乾脆確保伺服器端和客戶端渲染出的初始 HTML 是一致的。如果你在開發時發現畫面有動態效果，記得先確認伺服器產出的 HTML 是否已經預留了空間，不要讓伺服器跟瀏覽器各唱各的調，不然那種除錯的絕望感真的是誰體驗過誰知道。

希望這篇筆記能救你一命，下次遇到這種紅字別急著摔鍵盤，先喝口水，這只是 React 在跟你鬧脾氣而已。
