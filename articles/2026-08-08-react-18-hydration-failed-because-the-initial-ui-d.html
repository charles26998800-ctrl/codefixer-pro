Why Your Next.js App is Crashing: Solving the Hydration Mismatch Error

Source: Stack Overflow ↗ · 341 votes

I remember the first time I saw the "Hydration failed" error in React 18, I stared at my screen for a solid hour, convinced I’d lost my mind. I had a perfectly simple component displaying the current time, but every time the page loaded, the browser console screamed at me like I’d committed a cardinal sin. I spent way too much time refactoring my entire component tree before realizing it was just a tiny, stupid difference between what the server generated and what the client expected.

At its core, this error happens because React is trying to be efficient. When you use Server-Side Rendering (SSR) in Next.js, the server sends a static HTML string to the browser. Once that HTML hits your user's machine, React "hydrates" it, attaching event listeners and turning it into an interactive app. If the HTML the server sent doesn't match exactly what the client-side React code generates on its first pass, React panics and throws a hydration mismatch error. It’s essentially the framework saying, "Hey, I thought this was supposed to be a button, but you gave me a div," and it shuts down to prevent weird UI artifacts.

The most common culprit I see is using browser-specific APIs or dynamic content—like Date.now() or localStorage—during the initial render. Since the server doesn't know what time it is on the user's specific machine, the server-side render and the client-side render result in two different strings. To fix this, I make sure that any code dependent on the browser environment is delayed until after the component has mounted. I usually wrap the logic in a useEffect hook, which only runs on the client.


import { useState, useEffect } from 'react';

function TimeComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? new Date().toLocaleTimeString() : 'Loading...'}
    </div>
  );
}

By initializing the state to a neutral value like null or a loading string and only switching to the dynamic data once the component mounts, you guarantee that the initial server render matches your initial client render. It’s a clean way to keep React happy without sacrificing your dynamic features.

To prevent this from becoming a recurring nightmare in your codebase, get in the habit of checking if you’re accessing window, document, or any local storage variables during render. If you find yourself reaching for those inside a functional component body, stop and move that logic into a useEffect or use a library that handles client-only rendering for you. It’ll save you a lot of hair-pulling in the long run.

Hope this clears up the confusion and saves you from a few hours of debugging. Happy coding, and may your builds stay green!

React 18 Hydration Error：那個讓我熬夜到凌晨兩點的「UI 不匹配」地獄

來源：Stack Overflow ↗ · 341 票

記得那天我剛把專案升級到 Next.js 和 React 18，想說趁著技術債還清的爽感，一鼓作氣把 SSR 效能調好。結果當我打開瀏覽器 Console，迎接我的竟然是一整排紅通通的 Hydration failed 報錯，畫面還閃得跟鬼片一樣。那一刻我真的差點崩潰，明明程式碼邏輯看起來完全沒錯，為什麼伺服器渲染出來的 HTML 跟瀏覽器第一次跑出來的結果就是對不上？我盯著螢幕看了兩小時，連咖啡都冷了，那種「我明明寫對了，但電腦就是不聽話」的無力感，真的是工程師生涯裡最痛苦的時刻之一。

其實這問題的核心很單純，就是 React 18 變得更嚴格了。當你使用 SSR 時，伺服器會先產出一份 HTML，送到瀏覽器後，React 會進行「水分化（Hydration）」來綁定事件。如果瀏覽器第一次渲染的結果，跟伺服器給的那份 HTML 有一丁點差異（哪怕只是時間戳記、隨機亂數，或者是瀏覽器特有的 API），React 就會直接宣告投降，因為它覺得「這不是我要的結果」。這就像是你跟朋友約好要在門口見，結果你跑去後門，對方當然會傻眼說這不是他認識的那個你。

我當時踩到的雷，其實是因為我用了 new Date().toLocaleTimeString() 這種會隨著時間變動的函數，或者是一些依賴 window 物件的邏輯。要解決這個，最快的方法就是讓 React 稍微「冷靜一下」。我後來學乖了，直接利用 useEffect 這個鉤子，因為它只會在瀏覽器端執行，伺服器渲染時會被忽略。我會寫一個簡單的 isMounted 狀態，確保元件真的掛載到瀏覽器後才渲染那些「不穩定」的內容。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者給一個簡單的 Loading 佔位符
  }

  return <div>現在時間是：{new Date().toLocaleTimeString()}</div>;
}

為了避免以後再被這個地獄級別的報錯折磨，我現在養成了一個習慣：只要是用到了任何跟「當下環境」有關的邏輯，例如時間、使用者偏好設定、或是需要存取 localStorage 的東西，我一律預設它們會導致 Hydration 失敗。最好的預防方式，就是把這類邏輯拆分成獨立的 Client-side 元件，或者乾脆確保渲染邏輯在伺服器和瀏覽器端完全一致。不要在渲染路徑上直接塞入會變動的數值，這是保護你髮際線最重要的一步。

希望大家下次遇到這問題時，能少走點彎路，早點關電腦去睡覺！
