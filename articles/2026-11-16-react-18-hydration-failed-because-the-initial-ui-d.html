Fixing the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a React 18 project. I was convinced my code was perfectly fine until I refreshed the page and saw my UI flicker like a broken neon sign before crashing into a sea of red console errors. I spent three hours refactoring my entire component tree, only to realize I had a tiny piece of logic that was rendering differently on the server than it was on my local machine. It’s one of those bugs that makes you want to throw your keyboard out the window, but once you understand the mechanism, it’s actually quite logical.

The root cause of this frustration is a mismatch between the HTML generated by the server and the first render generated by the browser. When you use Next.js, the server pre-renders your components into static HTML and sends them to the client. React then "hydrates" this static HTML by attaching event listeners and turning it into a dynamic app. If the server says "Hey, I rendered this timestamp," but the browser calculates a different timestamp during its first execution, React panics. It assumes the server-side render was corrupted, so it throws the error to prevent rendering unpredictable UI. This often happens with things like Date.now(), random number generators, or local storage checks that fire before the component has a chance to sync with the browser.

To fix this, I’ve learned to defer any client-specific logic until after the component has mounted. By using a simple useEffect hook, I can force the component to wait until it’s safely in the browser environment before rendering the dynamic content. Here is how I usually handle this:


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>The time is: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By adding that isClient flag, I ensure that the server renders a consistent "Loading..." state, and only once the browser takes over does the actual dynamic content appear. It’s a clean way to ensure the server and client are speaking the same language.

If you want to avoid this headache in the future, my best advice is to keep your render logic as pure as possible. Avoid accessing window, localStorage, or fluctuating timestamps directly in your component body. If you absolutely need to use them, wrap them in a custom hook or a conditional check that relies on the component mounting state. It’ll save you a lot of debugging time in the long run.

Hope this clears up the confusion and saves you some time today. Happy coding, and may your hydration always stay consistent!

救命！React 18 的 Hydration Error 到底要怎麼解？

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿懷期待地想體驗一下 SSR 的威力，結果一打開瀏覽器，Console 直接噴出一大串紅通通的 "Hydration failed" 錯誤，當時我整個人原地石化。那種感覺真的很差，明明程式碼在本地跑得好好的，上線後卻因為伺服器渲染出來的 HTML 跟瀏覽器第一次掛載的 DOM 對不上，導致整個頁面直接報錯閃退，真的是差點讓我氣到想把鍵盤砸了。

其實這問題的核心很單純，就是「時差」導致的誤會。伺服器在產生 HTML 時，它讀不到瀏覽器特有的資訊，比如 window 物件、本地儲存的 localStorage，或是隨機生成的 ID。當伺服器渲染了一套內容，瀏覽器載入後卻發現：「欸？怎麼跟我手上的這套不一樣？」React 就會因為這種不一致直接拒絕工作。我當時最痛苦的時刻，就是檢查了老半天，才發現原來只是因為我放了一個 new Date().toLocaleTimeString() 在組件裡，結果伺服器產生的時間跟瀏覽器跑出來的時間差了一秒，整個網頁就這麼掛了。

要解決這個問題，最直覺的做法就是讓 React 先「緩一緩」，等到組件確定已經在瀏覽器端掛載完成（Mounted）之後，再顯示那些會變動的內容。我通常會封裝一個簡單的 ClientOnly 組件來處理這種情況，這樣就能完美避開伺服器跟瀏覽器的認知落差。


import { useState, useEffect } from 'react';

function ClientOnly({ children }) {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null; // 或者你可以放一個簡單的 Loading skeleton
  }

  return <>{children}</>;
}

使用的時候也很簡單，只要把那些會用到 window 或者時間戳記的組件包起來就行了。這樣做之後，伺服器只會看到一個空的佔位符，不會因為預測錯誤而產生不一致的 DOM，等到瀏覽器真的接手後，內容才會自動跑出來。

為了避免以後再被這種問題搞到心累，我現在養成一個習慣：只要是會用到瀏覽器原生 API 的邏輯，我一律強制寫在 useEffect 裡，或者在開發階段就安裝 eslint-plugin-react-hooks 嚴格把關。只要確保組件在初始渲染時保持「純淨」，不依賴任何外部變數，Hydration 的錯誤率真的會大幅下降。

希望這招能救你一命，別再被這該死的報錯折磨啦，趕快去喝杯咖啡休息一下吧！
