How to Fix the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a Next.js project. I was three hours deep into a late-night debugging session, convinced my code was perfect, only to realize the server and the browser were essentially looking at two different versions of my UI. It’s one of those bugs that makes you want to throw your keyboard out the window because the error message is so incredibly vague, yet the solution is usually staring you right in the face.

The root cause of this frustration is a mismatch between your server-side rendered HTML and the initial render on the client. When Next.js pre-renders a page on the server, it generates static HTML. When that page hits the browser, React tries to "hydrate" it by attaching event listeners and state. If your component relies on something that changes between the server and the client—like a random number generator, a timestamp, or browser-only APIs like localStorage—React sees the mismatch and panics. It expects the server's HTML to be an exact match for what it would render on the client; if they differ even by a single character or a nested div, the whole process breaks.

To fix this, you need to ensure that the content is consistent during that critical first pass. If you have content that must be different on the client (like a "Logged in as..." message that requires local storage), you have to delay the rendering of that specific piece until the component has mounted. I usually handle this by using a simple useEffect hook to toggle a "mounted" state. Here is how I typically structure that fix:


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Your client-only logic goes here */}
      <p>Current time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

By returning null or a neutral loading state during the initial server render, you prevent React from trying to reconcile two conflicting versions of the DOM. Once the component mounts in the browser, isMounted becomes true, and React renders the actual client-side content. It’s a clean way to handle the discrepancy without disabling hydration entirely, which would kill your SEO benefits.

The best way to prevent this in the future is to keep your server-side rendering logic pure. Avoid calling Math.random() or accessing browser globals directly inside your component’s main body. Whenever you feel the urge to pull in a browser-specific API, just ask yourself if the server needs to know about it right away; if it doesn't, guard it behind a useEffect hook and you’ll save yourself a world of headache.

Good luck with your debugging, and I hope this saves you from those late-night hair-pulling sessions!

救命！React 18 的 Hydration Error 到底要怎麼解？

來源：Stack Overflow ↗ · 341 票

記得那天我剛把專案升級到 React 18，想說終於能體驗一下新功能了，結果一跑起來，瀏覽器控制台直接噴出一堆慘紅色的「Hydration failed」錯誤訊息。當時我整個人傻掉，明明程式碼看起來沒什麼毛病，但頁面就是瘋狂閃爍，甚至部分 UI 直接消失，那種「我明明寫得沒問題，為什麼電腦要這樣對我」的崩潰感，真的會讓人想當場把鍵盤丟了。

其實會發生這件事，根本原因在於 React 18 的運作機制變嚴格了。當你使用伺服器端渲染（SSR）時，伺服器會先產生一份 HTML 發給瀏覽器，但 React 在瀏覽器上進行「水分補給（Hydration）」時，發現這份 HTML 的結構跟它原本預期的長得不一樣。最常見的兇手就是你在渲染時用了 Date.now()、隨機數字，或者是像 localStorage 這種只有瀏覽器才有的東西。想像一下，伺服器說「我是 A」，結果瀏覽器跑起來變成了「我是 B」，React 一看：「欸？這不對吧？」然後它就乾脆直接放棄治療，報錯給你看。

解決這個問題，最關鍵的原則就是「讓前後端達成共識」。如果你一定要在元件裡用到這些變動的數值，那就必須等到元件真的掛載（Mount）到瀏覽器之後再執行。我當時是透過 useEffect 來解決的，只要把那些不穩定的邏輯丟進去，就能完美避開這個坑。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    // 只有在瀏覽器端才會執行這裡
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <p>現在的時間是: {new Date().toLocaleTimeString()}</p> : <p>載入中...</p>}
    </div>
  );
}

為了預防這種惡夢再次發生，我現在養成了一個習慣：只要是涉及到「瀏覽器特有 API」或者「隨機產生的內容」，我一律會確保它們不在 SSR 的階段執行。最好的做法是在寫元件時，先問自己一句「這東西伺服器知道嗎？」，如果答案是否定的，那就乖乖把它包在 useEffect 裡，或者乾脆用 typeof window !== 'undefined' 做個簡單的保護措施。

搞定這個問題之後，看著控制台終於乾乾淨淨的感覺真的太爽了，大家一起加油吧！
