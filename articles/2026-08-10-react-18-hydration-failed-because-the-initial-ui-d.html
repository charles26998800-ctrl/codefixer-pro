Solving React 18 Hydration Errors: When Server and Client Don't Agree

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I migrated a legacy project to React 18; I felt like a genius until I opened my browser console and saw a sea of red text screaming about hydration mismatches. I spent three hours refactoring components, convinced I’d broken the entire state management system, only to realize I was just rendering the current date. It’s one of those bugs that makes you want to throw your laptop out the window, but once you understand the "why," it becomes a lot less intimidating.

The root cause of this frustration is actually quite logical: React is trying to be incredibly efficient. When you use Server-Side Rendering (SSR), the server sends a static HTML string to the browser. Once that HTML loads, React "hydrates" it by attaching event listeners and turning it into an interactive app. If the HTML the server generated doesn't match exactly what the client-side JavaScript produces on the first render, React throws its hands up. In React 18, the team made this error more explicit because mismatched UI can lead to weird bugs, like buttons not clicking or text flickering as it snaps into place.

The most common culprit I see—and the one that tripped me up—is rendering something dynamic, like the current date, time, or a random number, during the initial render. If the server says it's 10:00 AM and the client code executes a millisecond later and thinks it's 10:00:01 AM, the DOM nodes won't match, and the hydration process fails. To fix this, you need to ensure the component only renders the dynamic content once it's officially mounted on the client. I handle this by using a simple useEffect hook to track the mounting state.


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    // Render a placeholder or null to ensure the server and client 
    // initial render match perfectly.
    return null; 
  }

  return (
    <div>
      Current Time: {new Date().toLocaleTimeString()}
    </div>
  );
}

By rendering null (or a static loading skeleton) on the server and during the first pass on the client, you guarantee that the initial tree is identical across both environments. Once useEffect fires, the client-side React knows it's safe to inject the dynamic content, and the hydration mismatch disappears entirely.

To prevent this from happening in the future, my golden rule is to keep my top-level component renders as "pure" as possible. If you’re pulling data from localStorage or using a browser-only API like window, always gate that logic behind a mount check. It’s a small bit of extra boilerplate, but it saves you from losing your mind during those late-night debugging sessions.

Hope this helps you clear those console errors and get back to shipping features. Good luck with your build!

Next.js 報錯惡夢：Hydration failed 到底在吵什麼？

來源：Stack Overflow ↗ · 341 票

還記得那天深夜，我正興高采烈地要把一個新開發的 Next.js 專案部署上線，結果瀏覽器打開一看，整個畫面閃了一下，Console 立刻跳出那行讓人看了就頭痛的「Hydration failed」。當下我真的差點把鍵盤砸了，心想明明在開發環境跑得好好的，怎麼一進到 SSR 模式就直接翻車，那種「我明明寫對了，但電腦卻跟我唱反調」的無力感，真的是每個前端工程師的成人禮。

其實這個錯誤的核心邏輯很簡單，就是 React 在跟你鬧脾氣。當我們使用 Next.js 做伺服器端渲染（SSR）時，伺服器會先產生一份 HTML 發送給瀏覽器，然後瀏覽器再接手讓頁面「活起來」（這個過程就叫 Hydration）。問題就在於，伺服器產出的 HTML 結構，跟瀏覽器第一次跑 React 時產生的 HTML 不一樣。最常見的原因就是我們在組件裡用了 typeof window !== 'undefined' 這種判斷，或者用了像 new Date() 這種會隨著時間跳動的函數，導致兩邊的內容對不上，React 發現「咦？你給我的東西跟伺服器說的不一樣」，為了安全起見，它就直接報錯給你看。

我後來發現，最常導致這個問題的兇手，其實就是我隨手寫的邏輯錯誤。比如我在組件裡直接判斷了當前時間，或者在 useEffect 之外使用了瀏覽器才有的 API。解決這個問題的秘訣，就是確保組件在「第一次渲染」時，兩邊拿到的東西是一模一樣的。我後來學乖了，如果真的需要用到瀏覽器端的東西，我會先讓它渲染一個空的佔位符，等到確認已經在客戶端執行後，再把真正的內容塞進去。像這樣寫就乾淨多了：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者你可以放個 <div className="skeleton" />
  }

  return <div>這裡放我那些會報錯的瀏覽器專屬邏輯</div>;
}

為了預防這種崩潰再次發生，我現在養成了一個好習慣：盡量避免在組件的頂層直接依賴會變動的狀態，例如隨機數或是當前時間。如果你真的非得要在 SSR 環境下顯示這些東西，記得要麼把它們移到 useEffect 裡處理，要麼就乾脆給它一個預設的靜態值，確保伺服器渲染出來的內容跟客戶端第一眼看到的長得一模一樣。

搞懂這個機制之後，Hydration 就再也沒困擾過我了，希望你們也能順利避開這個坑！
