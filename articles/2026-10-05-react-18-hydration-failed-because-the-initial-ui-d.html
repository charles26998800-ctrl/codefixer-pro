Debugging React 18 Hydration Mismatch Errors in Next.js

Source: Stack Overflow ↗ · 341 votes

I remember the first time I saw that dreaded "Hydration failed" error in my console; I’d just migrated a legacy project to Next.js and felt like a genius until I opened the browser and saw my entire UI flickering like a broken neon sign. I spent three hours staring at my code, swearing that my server-side logic was identical to my client-side logic, only to realize I had a simple Date() call that was rendering different millisecond timestamps on every pass. It's the kind of bug that makes you want to throw your monitor out the window because the error message is technically correct but practically useless at pointing you to the specific line of code.

The root cause of this mess is actually pretty simple: React expects the HTML sent from the server to be a perfect mirror of what the client generates on the initial render. When you use server-side rendering, Next.js ships a static HTML string to the browser, but then React "hydrates" it by attaching event listeners and turning it into a dynamic app. If the browser-rendered version differs from that static HTML—even by a single space, a dynamic timestamp, or an environment-specific variable—React throws its hands up in frustration. It decides the server's version is untrustworthy and replaces the entire DOM tree, which is a massive performance hit and leads to that ugly UI flash.

To fix this, I usually look for anything that changes between the server and the client. The most common culprit is using browser-only APIs like window, localStorage, or dynamic values like Math.random() or new Date() directly in your component body. The secret to squashing this bug is to wait until the component has actually mounted in the browser before rendering those dynamic parts. I typically use a useEffect hook to set a piece of local state once the component is ready.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>Current time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By adding that isClient check, I ensure that the server renders the "Loading..." state consistently, and only after the hydration process is complete does the client-side logic kick in. If you’re dealing with library-specific issues—like a UI component that insists on rendering a random ID—check the documentation for a "suppressHydrationWarning" prop, but use that sparingly because it’s usually just masking the underlying inconsistency.

Moving forward, the best way to prevent these headaches is to adopt a "server-first" mindset where you keep your component logic as deterministic as possible. I’ve started using useEffect for anything that touches browser APIs, and I always check if a component truly needs to be dynamic during that first paint. If you treat the server render as a static snapshot, you’ll find yourself fighting the hydration errors a lot less often.

I hope this helps you save some time so you can get back to building cool stuff instead of debugging the framework. Catch you later, and good luck with the refactoring!

React 18 惡夢：Hydration Failed 到底要搞死誰？

來源：Stack Overflow ↗ · 341 票

前陣子為了把專案升級到 React 18，我熬了兩個晚上改程式碼，結果伺服器一跑起來，瀏覽器 Console 就跳出那串讓人心碎的「Hydration failed」。我看著那滿頁紅通通的錯誤訊息，真的差點把鍵盤砸了，心想明明邏輯都沒動，為什麼伺服器渲染出來的東西跟瀏覽器長得不一樣？那種「我明明寫對了，為什麼電腦覺得我錯了」的無力感，真的是工程師職涯中最想原地退休的痛苦時刻之一。

其實這問題的根本原因說穿了，就是 React 在玩「大家來找碴」。當你使用 Next.js 做 SSR 時，伺服器會先產生一份 HTML，然後傳給瀏覽器；接著 React 會在瀏覽器端嘗試「接手」這份 HTML，這過程叫 Hydration。如果伺服器算出來的初始 UI，跟瀏覽器第一次跑 React 時渲染出來的結果有任何一丁點出入，比如因為時間、隨機數字，或者瀏覽器環境特有的屬性導致結果不一致，React 就會直接大崩潰，認為這份 UI 已經「壞掉了」。

我當時踩到的坑其實很蠢，就是因為我在元件裡用了 typeof window !== 'undefined' 來判斷環境，但渲染邏輯卻因為這判斷產生了差異。要解決這個問題，最簡單暴力的方法就是確保元件「先不要在伺服器端渲染」。我後來學會了用 useEffect 來處理這類依賴瀏覽器環境的邏輯，因為 useEffect 只會在瀏覽器端執行，完美避開了伺服器端渲染不一致的問題。

如果你跟我一樣被這個問題卡住，建議可以試著建立一個簡單的 ClientOnly 元件，把那些會造成不一致的 UI 包起來：


import { useState, useEffect } from 'react';

export default function ClientOnly({ children }) {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null;
  }

  return <>{children}</>;
}

使用的時候，只要把那些會跳錯的元件包進去，例如 ，這樣伺服器只會渲染一個空標籤，等到瀏覽器載入後才把內容補上去，這場 Hydration 的鬧劇自然就結束了。

為了預防下次再被這種問題折磨，我現在養成一個習慣：只要是會用到 localStorage、window 物件或是隨機數產生的 UI，我一律預設它們是「非同步」的，絕對不在初始渲染時強行塞給伺服器處理。把這些內容延後渲染，不僅能解決 Hydration 錯誤，還能讓你的頁面看起來更乾淨，這招真的好用。

希望你們看完這篇能少掉幾根頭髮，下次遇到這種紅色錯誤訊息，深呼吸喝口咖啡再動手吧！
