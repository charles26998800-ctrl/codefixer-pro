How to Undo Your Most Recent Local Git Commits Without Losing Your Work

Source: Stack Overflow ↗ · 27236 votes

I remember the first time I accidentally committed a massive folder of local build artifacts and sensitive config files right before a deadline. I spent a good three hours sweating, convinced I’d somehow corrupted my entire repository or triggered a merge conflict that would take me all weekend to fix. It’s a rite of passage for every developer, and honestly, if you haven’t had that mini-heart attack when you realize you’ve committed the wrong files, you probably just haven't been coding long enough.

The reason this happens is that Git treats your local history as a flexible timeline rather than a permanent ledger. When you run git commit, you’re essentially creating a snapshot in your local branch’s pointer. Because you haven't pushed those changes to the remote server yet, that history exists only on your machine. Git allows you to move that pointer backward, effectively telling your local environment to "forget" that the last snapshot ever happened. It’s not that the code is deleted; it’s just that the commit record is stripped away, leaving your files exactly where they were before you ran that command.

To fix this, I always reach for git reset. The command you need depends on how much "cleanup" you want to do. If you just want to undo the commit but keep all your changes staged and ready to edit, you’ll use the soft reset. Just run git reset --soft HEAD~1 in your terminal. This pops the commit off the stack, but your files remain in the staging area, so you can fix whatever you messed up and commit it again properly.

If you made a total mess and want to completely wipe the changes from that commit while keeping your files in your working directory, use git reset --mixed HEAD~1. This is the default behavior. It un-stages your changes, meaning they aren't ready to be committed anymore, but they’re still sitting in your file explorer waiting for you. If you’re feeling dangerous and want to delete everything from that commit permanently—meaning you’re totally fine with losing all the work you just did—you can use git reset --hard HEAD~1. Be careful with that last one, though, because there’s no "undoing" a hard reset once it’s done.

The best way to prevent this headache is to start using the -p or --patch flag when you add files. Instead of running git add . (which is a recipe for disaster), I always run git add -p. This forces Git to show you each hunk of code you’re about to stage. It takes an extra five seconds, but it acts as a final sanity check that keeps you from committing things you didn't mean to include in the first place.

Hope this saves you the panic I felt during my first run-in with this. Happy coding, and try not to break too much stuff today!

救命！我不小心 commit 了不該 commit 的東西，Git 該怎麼救？

來源：Stack Overflow ↗ · 27236 票

記得剛入行那陣子，有次我在深夜趕工，正準備把一個功能 push 上去，結果手一抖，竟然把還在測試階段、甚至沒寫完的 debug log 還有一些亂七八糟的廢棄檔案全部 commit 進去了。當時看到那串 commit ID 亮在那裡，我整個人心跳漏了一拍，心想：「完了，這要是推上去被同事看到，我的工程師尊嚴豈不是掃地？」那種以為自己要搞砸整個專案的恐慌，真的是每個資深工程師都經歷過的惡夢。

其實發生這種事，通常就是因為我們對 git commit 的機制太放心了，以為只要還沒 push，一切都好說。但 Git 的本質就是一個強大的版本控制工具，它會把你每一次的「提交」都嚴格記錄下來。當你下達 commit 指令時，Git 就像是一個盡忠職守的紀錄員，不管你丟進去的是不是垃圾，它都照單全收。所以，當你發現 commit 內容有誤，其實不用慌，因為這些紀錄都在你本地端，還沒對外「公開處刑」，我們隨時有機會把它們「抹除」或「修正」。

我當下冷靜下來後，用的就是 git reset 這個指令。如果你只是想把 commit 撤銷，但想保留檔案的修改內容（畢竟辛苦寫的 code 不想重打），我會用 --soft 參數：


git reset --soft HEAD~1

這行指令的意思是把 HEAD 指標往回移一個位置，把那個 commit 給拆了，但你修改的檔案依然會留在暫存區（Staging Area），讓你隨時可以重新調整要 commit 的內容。但如果你是像我那次一樣，整包 commit 都是垃圾，連檔案都不想要了，那就更暴力一點：


git reset --hard HEAD~1

這招下去，檔案會直接變回 commit 前的狀態，這就是最痛苦的時刻——因為你剛才修改的內容會直接「人間蒸發」。所以用 --hard 之前，真的要確保你心裡有底，或者確定那些檔案真的沒救了。

為了避免以後再犯這種低級錯誤，我現在養成了一個好習慣：在正式 commit 之前，一定會習慣性地先打 git status 看一下到底有哪些檔案被標記了，甚至會用 git diff --cached 檢查一下 commit 內容到底長什麼樣。雖然這多花幾秒鐘，但比起事後在那邊冷汗直流地撤銷 commit，這點時間成本真的太划算了。

Git 雖然有時候讓人很頭痛，但只要掌握好這些撤銷的小技巧，它其實是你最強大的防護罩。下次如果不小心手滑，記得先深呼吸，只要還沒 push，一切都還有救啦！
