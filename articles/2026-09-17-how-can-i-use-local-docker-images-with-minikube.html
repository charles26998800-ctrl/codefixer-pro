How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 689 votes

I still remember the first time I set up Minikube, thinking I’d be up and running in ten minutes flat. I spent three hours staring at an ImagePullBackOff error, convinced my YAML was broken, only to realize that Minikube had no idea my local Docker images even existed. It’s infuriating when you’re just trying to test a quick code change and you’re forced to push an image to Docker Hub just to pull it back down to your own machine.

The reason this happens is actually quite simple: Minikube runs inside its own isolated environment, usually a virtual machine or a separate container. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Minikube’s internal Kubernetes cluster, however, is looking at its own separate Docker daemon. It’s like keeping your tools in a shed in the backyard while you're trying to fix a sink in the kitchen; the house just can't see what's in the shed.

The cleanest way I’ve found to bridge this gap without needing a private registry is to point your local terminal directly at the Minikube Docker daemon. Before you run your build command, you just need to run one line in your terminal:


eval $(minikube docker-env)

Once you’ve run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it worked by running docker images, and you'll see your custom image sitting right there alongside the standard Minikube components. From that point on, you just need to make sure your Kubernetes deployment manifest has imagePullPolicy: IfNotPresent set. This tells Kubernetes, "Hey, don't go looking on the internet for this; it’s already here, just use it."

To keep this from biting you again, make sure you always set your imagePullPolicy to IfNotPresent in your deployment YAML files. If you leave it at the default—which is usually Always—Kubernetes will ignore your local image and try to pull from a registry anyway, landing you right back in that ImagePullBackOff loop.

Hope this saves you a few hours of head-scratching! Let me know if you run into any other weird Minikube quirks.

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 689 票

記得剛開始碰 Kubernetes 的時候，我真的快被 Minikube 的映像檔管理搞到崩潰。當時我寫好了一個微服務，改了一行 code 就要重新 build，為了讓 Minikube 抓到新版本，我竟然傻傻地把 image 推到 Docker Hub 再拉下來，結果為了等那幾百 MB 的上傳下載，我一天有一半的時間都在滑手機發呆。最慘的一次是，我改了一個極小的 bug，結果因為網路太慢，我足足等了十分鐘才看到結果，那種「明明程式碼改好了，卻被開發環境卡死」的無力感，真的會讓人想直接把電腦砸了。

會發生這種事，是因為 Minikube 本質上是一個跑在虛擬機（或是容器）裡的獨立環境，它有自己的 Docker Daemon。簡單來說，你電腦本機的 Docker 跟 Minikube 裡的 Docker 是兩個完全不同的平行世界。當你在本地 docker build 時，映像檔是存在你電腦的 Daemon 裡，Minikube 根本看不到，所以它才會拼命去 Docker Hub 找，找不到就報 ImagePullBackOff 給你看。

其實解決方法超級簡單，根本不需要繞遠路。最推薦的做法就是直接讓你的終端機「指向」Minikube 內部的 Docker 環境。只要在終端機輸入這一行指令：


eval $(minikube docker-env)

執行完這行後，接下來你在同一個終端機視窗執行的 docker build 指令，就會直接把映像檔塞進 Minikube 的環境裡，完全不需要 push 到雲端。這時候你再執行 kubectl apply，Minikube 就會像看到自家人一樣，直接抓取本地的映像檔，速度快到讓你懷疑人生。如果你想切換回本機的 Docker，只要執行 eval $(minikube docker-env -u) 就行了，是不是方便多了？

至於要怎麼預防下次又踩坑？我的建議是養成檢查 imagePullPolicy 的習慣。在你的 Deployment YAML 檔裡，記得把 imagePullPolicy 設為 IfNotPresent。這樣就算你偶爾忘記切換環境，Kubernetes 也會優先嘗試使用本地已有的映像檔，而不是一有風吹草動就去網路上抓，這算是一個防呆的小動作，能幫你省下不少除錯的時間。

以後遇到這種卡住的問題，記得先確認你的 Docker Daemon 在哪裡，別再跟我當年一樣傻傻地當「網路流量產生器」啦！
