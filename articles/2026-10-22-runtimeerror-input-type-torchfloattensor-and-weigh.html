How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a GPU training loop in PyTorch. I was so proud of myself for finally getting a dedicated machine with an NVIDIA card, only to hit this exact RuntimeError the moment I started the first epoch. I spent three solid hours double-checking my model architecture and imports, convinced I’d broken something deep in the framework, before I realized I was just a victim of a simple device mismatch.

The reason this happens is actually quite straightforward once you stop panicking. PyTorch is extremely strict about where your data lives; it needs your model parameters and your input tensors to be on the exact same device. When you call model.to(device), you’re successfully moving your weights to the GPU, but your dataloader is still fetching data from your CPU's RAM as a FloatTensor. When you pass that CPU-bound tensor into a GPU-bound model, PyTorch throws an error because it doesn't know how to perform operations across different memory spaces. It’s basically like trying to plug a European power cord into an American wall socket—the hardware exists, but they aren't speaking the same language.

Fixing this is a quick one-liner that I usually end up adding to my training loops out of muscle memory now. You need to explicitly move your inputs and labels to the same device as your model inside the loop. I usually do this right after unpacking the data from the loader. Here is how I structure it to keep things clean:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the magic line that fixes the mismatch
    inputs, labels = data[0].to(device), data[1].to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you’re working with more complex structures like dictionaries or lists of tensors, just make sure you iterate through them and send each individual tensor to the device. It feels a bit repetitive, but it’s the standard way to handle device placement in PyTorch.

To prevent this from ever ruining your workflow again, I’ve found that it’s best to define a helper function or a simple to_device utility in your boilerplate code. Whenever I start a new project, I write a quick function that recursively moves objects to a target device. That way, even if my data loaders start returning nested dictionaries or custom objects later on, I just pass them through my helper and I never have to worry about those pesky type mismatches again.

Hopefully, this saves you that three-hour headache I dealt with. Happy coding, and may your GPU utilization stay high!

還記得剛開始接觸 PyTorch 的時候，我整個人充滿雄心壯志，想說終於把模型遷移到 GPU 上跑了，結果按下 Run 的那一刻，螢幕直接噴出一大串紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。當下我真的差點崩潰，明明 model.to(device) 都寫了，為什麼這傢伙還是不領情？當時我盯著螢幕看了半小時，心裡想著「顯卡都買了，你跟我說這程式碼跑不動？」，那種明明離成功只差一步、卻被硬生生卡住的挫折感，真的讓人很想把鍵盤給砸了。

其實會出現這個錯誤，核心問題非常簡單：PyTorch 是個很講究「門當戶對」的框架。我們的模型已經被移到了 GPU 上（也就是 cuda.FloatTensor），但從 DataLoader 讀取進來的資料還待在 CPU 的記憶體裡（預設是 FloatTensor）。當你把 CPU 上的資料餵給 GPU 上的模型時，PyTorch 就像個嚴格的守門員，直接大喊：「你們兩個類型不一樣，不准進來！」這就是為什麼你會看到這段讓人頭痛的錯誤訊息。

要解決這個問題，其實只要在迴圈裡面加一行指令就好。我們必須在把資料餵給模型之前，顯式地告訴 PyTorch：「嘿，把這些資料也丟到 GPU 上去。」我當時寫完這一行，看著 Terminal 終於開始跑 Training Epoch 的時候，那種感動真的難以言喻。你可以直接參考下面這種改法：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就在這裡！要把 inputs 和 labels 通通轉過去
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就是你的 loss 計算了...

為了避免下次再被這個坑絆倒，我現在養成了一個習慣，就是寫一個簡單的 helper 函數，或者直接在處理資料的地方封裝成一個小步驟。其實最簡單的預防方式，就是寫一個 to_device 的小工具，在所有 tensor 進入模型前先過濾一遍，這樣就不怕哪天手滑漏掉某個參數。還有，如果你是在寫比較複雜的專案，記得檢查一下 DataLoader 的 pin_memory=True，這不僅能幫你預防一些奇怪的記憶體傳輸問題，還能順便加速資料讀取，算是個一舉兩得的小撇步。
