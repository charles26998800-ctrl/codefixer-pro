How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I remember the first time I set up a local Kubernetes cluster, I spent a solid three hours banging my head against the wall because my pods were stuck in ImagePullBackOff. I was convinced my YAML was perfect, yet Minikube insisted on looking for my image in the public Docker Hub registry instead of seeing the one sitting right there on my machine. It’s one of those classic "gotcha" moments that every developer hits when they first start containerizing their local workflows.

The reason this happens is actually pretty straightforward: Minikube runs inside its own isolated virtual machine or container environment. Even if you have the Docker daemon running on your host machine, your Minikube cluster has no idea it exists. When you tell Kubernetes to run an image, it checks its own internal registry first, fails to find it, and then tries to reach out to the internet to pull it. Since your image is local to your laptop's Docker daemon, the cluster simply can't "see" it, leading to that annoying error.

The cleanest way I’ve found to fix this is to point your host terminal’s Docker environment directly at the Minikube daemon. Instead of building your image and hoping Kubernetes finds it, you can run a single command that reconfigures your shell to build images directly inside the Minikube environment. Just run this in your terminal before you build:


eval $(minikube docker-env)

Once you run that, your docker build commands will execute inside the Minikube VM. You can verify it’s working by running docker images, and you should see your newly built image listed right there. Now, when you update your Kubernetes deployment manifest, make sure you set the imagePullPolicy to IfNotPresent so that K8s doesn't go looking for a remote version that doesn't exist.


spec:
  containers:
  - name: my-app
    image: my-local-image:latest
    imagePullPolicy: IfNotPresent

To prevent this from becoming a recurring headache, I’ve started using a simple Makefile for my projects. I include a target that runs the docker-env command automatically or reminds me to do it before building. It saves me from those "Why isn't my code changing?" moments, which usually turn out to be me building the image on my host machine while Minikube is still looking at an old, cached layer inside its own internal registry.

Keep grinding and don't let the configuration drift get you down. Happy coding!

別再把 image 推到 Docker Hub 了！Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，我為了測試一個小小的 API 改動，每次都要執行 docker build 然後還要辛苦地 docker push 到 Docker Hub，再從 Minikube 把它 pull 下來。最崩潰的是，網速慢的時候，我光是盯著那個拉取進度條發呆的時間，都夠我泡兩杯咖啡了。有一次我趕著 Demo，結果因為網路不穩 pull 下來一個損毀的 image，看著 Pod 一直出現 ImagePullBackOff 的錯誤訊息，我真的差點要把鍵盤砸了。

為什麼會這樣呢？其實是因為 Minikube 是一個獨立的虛擬機（或是容器環境），它內部的 Docker daemon 跟我們本機電腦的 Docker daemon 根本是兩個不同的世界。當你說 kubectl apply 時，Kubernetes 是去 Minikube 的那邊找鏡像，它根本看不到你本機電腦裡那個剛打包好的 image，當然就找不到東西啦。

後來我發現，其實根本不需要繞遠路去推送到遠端倉庫。最快的方法就是讓你的終端機直接連上 Minikube 內部的 Docker 環境。你只要在終端機輸入這行指令：


eval $(minikube docker-env)

只要執行這行，接著你跑的 docker build -t my-app:latest . 就會直接在 Minikube 內部的 Docker 環境裡進行。這樣一來，當你部署 YAML 設定檔時，只要記得把 imagePullPolicy 設定為 IfNotPresent，Kubernetes 就會乖乖地使用你剛編譯好的本地鏡像，連一秒鐘的網路下載都不用浪費。

為了避免以後忘記，或者又手癢跑去 push，我現在的做法是在專案目錄下放一個簡單的 Makefile。把 eval $(minikube docker-env) 和編譯指令寫在一起，甚至加上自動更新 Deployment 的指令。這樣我每次只要打 make deploy，所有流程就會自動跑完。只要養成「先切換環境再編譯」的習慣，那種看著 ImagePullBackOff 崩潰的慘劇就再也不會發生了。

搞定這個之後，開發效率真的快了不只一個檔次，祝大家都能順利避開這個坑！
