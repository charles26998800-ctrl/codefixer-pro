Debugging the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I upgraded a project to React 18 and saw my entire console turn into a graveyard of red text. I spent three hours—yes, three full hours—trying to figure out why my production build looked like a flickering mess of broken layout shifts, only to realize the server and the client were essentially shouting different sentences at each other. It’s one of those bugs that makes you want to throw your monitor out the window, but once you understand the "why," it actually starts to make a lot of sense.

The core reason this happens is that React 18 is much stricter about the "Hydration" process than previous versions. When you use Server-Side Rendering (SSR), Next.js generates the initial HTML on the server and sends it to the browser. Once the browser loads your JavaScript, React tries to "hydrate" that static HTML by attaching event listeners and turning it into a dynamic app. If the HTML the server sent doesn't match the HTML the browser generates during that first render, React just throws its hands up in frustration and gives you that hydration error. This usually happens because you’re using something like Date.now(), Math.random(), or checking a window property that doesn't exist on the server.

I fixed this by ensuring that my component doesn't attempt to render dynamic, client-only data until the component has actually mounted. If you’re trying to render something that changes based on the user's environment, you need to wait until the client side is ready. I usually reach for a simple useEffect hook to toggle a "mounted" state, which prevents the server from trying to guess what the dynamic content should look like.


import { useState, useEffect } from "react";

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Now it's safe to render your dynamic data */}
      Current time: {new Date().toLocaleTimeString()}
    </div>
  );
}

To prevent this from haunting your future builds, make it a golden rule to never rely on global browser objects like window or localStorage during the initial render phase. If you absolutely need to render something that depends on the client environment, always gate it behind a useEffect or a check for typeof window !== 'undefined'. It’s a small extra step, but it’ll save you from those late-night debugging sessions that make you question your career choices.

Hope this clears up the confusion and helps you get your app back on track. Happy coding, and may your console stay clean!

React 18 Hydration Error：那個讓我熬夜到凌晨三點的「UI 不匹配」地獄

來源：Stack Overflow ↗ · 341 票

記得那天半夜，我正準備把一個折騰了兩週的 Next.js 專案部署上線，滿心期待看到成果，結果瀏覽器打開一看，控制台直接炸出一片紅色的錯誤訊息：「Hydration failed because the initial UI does not match what was rendered on the server」。當下我真的差點崩潰，明明在開發環境跑得好好的，怎麼一進生產環境就開始給我鬧脾氣？為了抓出這個隱形兇手，我盯著螢幕盯到眼睛快脫窗，那種「明明程式碼沒錯，但網頁就是不聽話」的無力感，真的是每個前端工程師的噩夢。

其實這個問題的核心很單純，就是 React 在跟你玩「找不同」。當你使用 SSR（伺服器端渲染）時，伺服器會先把 HTML 生成好傳給瀏覽器，但瀏覽器接手後，發現原本渲染出來的結構，跟它在本地端用 JavaScript 跑出來的結果長得不一樣。這通常發生在我們依賴了瀏覽器獨有的 API，比如 window 物件、localStorage，或是用了像是 Date.now() 這種每次跑都會變的函式。伺服器渲染出來的時間點，跟瀏覽器載入後執行的時間點產生了「時差」，React 一看：「欸？這跟我剛收到的劇本不一樣啊！」然後它就乾脆罷工，直接報錯給你看。

解決這個問題，最快的方法就是讓 React 先「緩一緩」。我當時發現，只要確保組件在伺服器端渲染時不要去碰那些瀏覽器特有的東西，問題就解決了一半。最簡單的手段就是利用 useEffect，因為它只會在瀏覽器端執行，完美避開了伺服器端的渲染過程。我的做法通常是先在組件裡定義一個狀態，初始值設為 false，等組件掛載完成後才切換成 true，這樣就能確保只有在瀏覽器環境下，我才去渲染那些會導致衝突的內容。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <p>現在是瀏覽器環境，我可以顯示時間：{new Date().toLocaleTimeString()}</p> : <p>Loading...</p>}
    </div>
  );
}

想要預防這種讓人心累的 Bug，最好的習慣就是在寫組件時時刻刻提醒自己：「這個元件現在到底在哪裡跑？」如果你的 UI 邏輯會因為當下的時間、隨機數或者特定的瀏覽器環境設定而改變，請務必養成把這類邏輯包在 useEffect 裡，或者乾脆使用 dynamic import 並設定 ssr: false。只要把這些「不確定因素」移出伺服器渲染的流程，你的控制台就會變得乾淨清爽很多。

希望大家之後遇到這個紅字時，能比我冷靜一點，畢竟這只是 React 在跟你確認細節而已。寫程式嘛，偶爾被這些小細節卡住也是修行的一部分，祝各位開發順利，早點下班！
