How to Use Local Docker Images with Minikube Without the Registry Headache

Source: Stack Overflow ↗ · 689 votes

I remember the first time I set up a local Kubernetes cluster, I spent three hours banging my head against the wall trying to figure out why my pods kept crashing with an ImagePullBackOff error. I had my image sitting right there on my machine, staring me in the face, yet Minikube insisted on trying to pull it from Docker Hub, which obviously didn't have my private, unfinished work. It’s one of those rites of passage every Kubernetes engineer goes through, and let me tell you, it's frustrating as hell when you just want to see your code run.

The reason this happens is actually quite simple: Minikube runs inside its own isolated environment, usually a virtual machine or a container. When you run docker build on your host machine, that image stays in your host’s Docker daemon. Minikube’s internal cluster has no idea that image exists because it’s effectively looking at a completely different "world" than your host terminal. It tries to reach out to the internet to find the tag you specified, fails because it’s local, and that’s the end of that.

The fastest way I’ve found to fix this is by pointing your local terminal directly to the Docker daemon running inside Minikube. By doing this, any image you build is injected straight into the cluster’s environment, so there’s no need to push or pull anything. You just run a single command in your terminal:


eval $(minikube docker-env)

Once you’ve run that, any docker build command you execute will build the image inside the Minikube environment. You can verify it worked by running docker images—you’ll see your local images listed alongside the internal Kubernetes system images. Now, when you update your deployment YAML, just make sure imagePullPolicy is set to IfNotPresent or Never, otherwise Kubernetes might still try to go out to the web to check for a newer version of your image.

To prevent this headache in the future, I always stick to a strict naming convention or use a specific profile for my local development. If I'm working on a project that requires constant iteration, I set up a quick alias in my .bashrc or .zshrc file to toggle the environment variable so I don't accidentally build images on my host machine when I meant to target the cluster. It saves me those precious minutes of debugging when I'm deep in the flow.

Hope this saves you from wasting your afternoon like I did. Happy coding!

別再把 image 推到 Docker Hub 了！Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 689 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的 API 修改，我硬是把 Docker image 推到 Docker Hub 再拉下來，來來回回幾十次。當時網路慢得要死，我看著終端機畫面上的進度條緩慢爬升，內心真的是無限崩潰，心想：「難道我每改一行程式碼，就要浪費十分鐘在等待上傳下載嗎？這工程師當得也太窩囊了吧！」

其實這背後的邏輯很簡單，Minikube 雖然跑在你的電腦裡，但它骨子裡是個獨立的虛擬機（VM）或是容器環境。當你執行 kubectl apply 時，Kubernetes 節點會去尋找對應的映像檔，如果它在自己的「私人倉庫」裡找不到，就會乖乖去遠端的 Docker Hub 抓。簡單來說，你的電腦上有 image，但 Minikube 的那台「小電腦」根本不知道這東西的存在。

我後來發現最省事的做法，根本不需要什麼複雜的設定，直接利用 Minikube 內建的 Docker 環境變數就能搞定。只要在開發環境下輸入這行指令：


eval $(minikube docker-env)

這行指令的魔法在於，它會把你的終端機暫時「導向」到 Minikube 內部的 Docker daemon。現在，當你在這個終端機視窗下執行 docker build -t my-app:v1 . 時，這個 image 就會直接被建置在 Minikube 的環境裡。接著，只要把你的 Deployment YAML 裡的 imagePullPolicy 設定為 IfNotPresent，Kubernetes 就會優先使用你剛才建好的那個本地映像檔，完全不用再經過外部網路。

不過，這裡有個小坑要提醒大家，就是 eval $(minikube docker-env) 只對當前的終端機視窗有效。如果你不小心關掉視窗或是開了新的分頁，記得要重新執行一次，不然你會發現 docker build 完，Kubernetes 還是報 ImagePullBackOff 的錯，那種「我明明剛才建好了啊！」的無力感，我真的不想再經歷第二次。

為了防止這種因為忘記環境變數而崩潰的情況，我現在養成了一個習慣：直接把 eval $(minikube docker-env) 加到我的 .zshrc 或 .bashrc 裡，或者乾脆寫一個簡單的 Makefile 來管理啟動流程。這樣下次要重啟開發環境時，只要一個指令就能確保所有環境變數都乖乖就位。

希望這招能幫你省下無數等待上傳的寶貴時間，別再讓網路速度限制你的開發效率啦！
