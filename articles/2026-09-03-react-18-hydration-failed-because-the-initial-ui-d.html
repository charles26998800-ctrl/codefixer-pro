Why Your Next.js App is Crashing: Solving the "Hydration Failed" Error

Source: Stack Overflow ↗ · 341 votes

I still vividly remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours deep into a late-night coding session, convinced I had built a flawless server-side rendered dashboard, only to watch my entire UI flicker and vanish the moment the browser took over. It’s one of those bugs that makes you want to throw your monitor out the window because the code looks perfectly fine in your editor, yet the browser console screams at you like you’ve committed a cardinal sin.

The root cause of this headache is actually quite simple: a mismatch between what the server generated and what the browser built on its first pass. When you use Next.js, the server renders your HTML and ships it to the client. Then, React "hydrates" that static HTML by attaching event listeners and turning it into a dynamic app. If you have code that behaves differently on the server versus the client—like using Date.now(), Math.random(), or checking for window or localStorage—the browser sees something different than what the server sent. React hits a wall, realizes the DOM tree doesn't match the virtual DOM, and throws up its hands in defeat.

I eventually realized my mistake was trying to render content that depended on the user's browser environment before the component had actually mounted. To fix this, you need to ensure that the initial render is identical across both environments. The cleanest way to handle this is by using a useEffect hook to trigger a state update only after the component has mounted in the browser. By initializing a state variable to false and flipping it once the component hits the client, you can safely render your client-specific logic without confusing the server.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This only shows up on the client: {window.location.href}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

If you want to prevent this nightmare from popping up in the future, my best advice is to embrace the "isMounted" pattern for any component that touches browser APIs. Never try to access window, document, or localStorage directly in your component's body. By forcing your code to wait until the client-side lifecycle begins, you keep the server-side output predictable and stop hydration errors dead in their tracks.

Hope this saves you from the same desk-thumping frustration I went through. Happy debugging!

救命！Next.js 報錯 Hydration failed，伺服器跟客戶端到底在吵什麼？

來源：Stack Overflow ↗ · 341 票

還記得上次剛升級到 React 18，想說趁著週末把專案架構優化一下，結果一跑起來，瀏覽器控制台直接跳出一大串紅通通的「Hydration failed」錯誤。我看著那行「initial UI does not match what was rendered on the server」，心裡真的只有崩潰兩個字，明明程式碼看著都沒錯，怎麼伺服器渲染出來的東西，跟瀏覽器第一次接手時看到的完全不一樣？那一刻我真的在電腦前發呆了半小時，心想這專案是不是要毀了。

其實這問題的根本原因，說穿了就是「溝通不良」。當你用 Next.js 這種 SSR 框架時，伺服器會先把 HTML 算好傳給瀏覽器，然後瀏覽器再接手讓 React 進行「水合（Hydration）」。如果這時候你的程式碼裡用了像是 Date.now()、隨機亂數，或者是根據瀏覽器特定的 window 物件來決定 UI，伺服器算出來的結果跟瀏覽器第一次算出來的就不會一樣。React 發現兩邊對不上，就會為了保險起見直接報錯，畢竟它可不想在這種狀況下搞壞你的 DOM。

最經典的痛苦時刻，就是當你放了個「顯示當前時間」的小功能，或者是一個隨機生成的 ID，伺服器渲染的時候是一個時間戳，等到瀏覽器跑起來又是另一個，兩邊一對，直接原地爆炸。我後來發現，要解決這個問題，最乾脆的做法就是讓那個「會變動」的部分先不要在伺服器跑，等瀏覽器準備好再給它。

我後來學會了一招，直接利用 useEffect 來處理這類依賴瀏覽器狀態的邏輯。既然伺服器端永遠沒辦法預知瀏覽器的狀態，那就乾脆在組件掛載（Mount）之後再渲染這些內容。你可以這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者你可以放一個簡單的載入佔位符
  }

  return <div>這裡放那些會導致 Hydration 錯誤的動態內容：{new Date().toLocaleTimeString()}</div>;
}

這樣寫之後，伺服器會先收到一個空的或者簡單的結構，等到瀏覽器一接手，useEffect 觸發了，UI 才會補上去。這就不會有「伺服器跟瀏覽器對不上」的情況了。

至於怎麼預防這種問題再次發生，我現在養成的習慣是，只要看到任何會用到 window、localStorage 或隨機數的組件，我都會下意識地問自己：「這東西在伺服器上跑會出事嗎？」如果會，我一定會把它包在 useEffect 裡，或者乾脆用 next/dynamic 把組件設為 ssr: false。只要養成這種「伺服器端要保持純粹」的直覺，以後開發起來真的會省心很多。

希望大家下次遇到這個錯誤時，先冷靜深呼吸，別像我當初一樣想把螢幕砸了，這問題其實處理起來比想像中簡單得多！
