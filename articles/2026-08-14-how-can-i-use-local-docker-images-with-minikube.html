Stop Pushing to Docker Hub: How to Use Local Images with Minikube

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up Minikube, thinking I was being clever by building a local image and immediately trying to deploy it. I spent about three hours staring at ImagePullBackOff errors, obsessively checking my YAML manifests for typos, only to realize that Minikube had absolutely no idea my image existed because it was living on my host machine, not inside the cluster's isolated environment. It’s one of those classic "aha!" moments that every Kubernetes developer hits early on, and honestly, it makes you feel a bit foolish until you realize just how isolated these environments actually are.

The reason this happens is pretty straightforward: Minikube runs inside a virtual machine (or a separate container, depending on your driver), and that environment has its own private Docker daemon. When you run docker build on your laptop, you’re pushing that image to your host's Docker engine. When your Pod tries to pull an image, the Kubernetes node looks inside its own internal registry, finds nothing, tries to reach out to the internet, fails to find the image tag, and gives up. It’s not a bug; it’s just the architecture doing exactly what it's designed to do—keeping your local host separate from your cluster.

The fix I settled on is actually much cleaner than uploading images to a remote registry like Docker Hub or ECR. The most direct way to bridge this gap is to point your local shell to the Minikube Docker daemon. By running a single environment variable command, you can make your terminal "talk" directly to the Docker engine inside your Minikube VM. Just run this in your terminal:


eval $(minikube -p minikube docker-env)

Once you’ve run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it’s working by running docker images—you’ll see the standard K8s images listed alongside your own. Now, when you deploy your YAML, just make sure your imagePullPolicy is set to IfNotPresent or Never. If you leave it as Always, K8s will still try to pull from the web and fail, which is another trap I fell into more times than I care to admit.

To prevent this headache in the future, I always set my imagePullPolicy to IfNotPresent by default in my development manifests. It’s a small change that saves you from the frustration of a failed deployment just because your cluster tried to reach out to a registry it didn't need to visit.

Hope this saves you a few hours of debugging. Happy coding, and may your deployments always be crash-loop-free!

別再把 Docker Image 推上 Docker Hub 了！Minikube 本地開發的神級技巧

來源：Stack Overflow ↗ · 688 票

還記得剛開始玩 Kubernetes 的時候，為了測試一個小小的修改，我硬是把 Image 推上 Docker Hub 再拉下來，來回折騰了快半小時。當時網路慢到讓我懷疑人生，看著終端機畫面停在 ImagePullBackOff，我真的差點把鍵盤砸了，心想：「難道工程師的時間就是這樣被浪費掉的嗎？」

其實會卡在這裡，是因為很多人忽略了 Minikube 本質上是一個跑在虛擬機或容器裡的獨立環境。當你在電腦終端機打 docker build 時，Image 是存在你主機的 Docker Daemon 裡，但 Minikube 那個小小的 Kubernetes 集群根本看不到你的主機，它只認得自己內部的倉庫。所以當它試著去拉取你的映像檔時，自然會因為找不到而報錯，這就是最經典的「明明就在眼前，卻像隔著天涯海角」的崩潰時刻。

其實解決方案超級簡單，根本不需要走冤枉路。最直覺的方式就是直接把環境變數切換到 Minikube 內部。只要在終端機輸入這行指令：


eval $(minikube docker-env)

執行完後，你現在的 Docker 指令就會直接對著 Minikube 的內部環境作用了。這時候你再執行 docker build -t my-app:v1 .，這個 Image 就會直接出現在 Minikube 的肚子裡。接著，記得把你的 Deployment YAML 裡的 imagePullPolicy 改成 IfNotPresent，這樣 K8s 看到本地已經有這張圖，就不會傻傻地跑去網路上抓，部署速度保證讓你飛起來。

如果之後你想切回原本主機的 Docker，只要輸入 eval $(minikube docker-env -u) 就行了。

為了避免以後又忘記，我現在的習慣是在專案的 Makefile 裡直接寫一個 dev-build 的指令，把這串切換環境的動作包進去。這樣每次要部署時，只要 make dev-build 就搞定，再也不用擔心手殘打錯指令或是忘記切換環境，省下來的時間拿去喝杯咖啡不香嗎？

以後遇到 ImagePullBackOff 別再急著檢查網路了，先看看是不是你的 Image 根本沒進到 Minikube 的家門口吧！
