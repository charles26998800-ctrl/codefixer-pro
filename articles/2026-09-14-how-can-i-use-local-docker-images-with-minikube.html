Stop Pushing to Registry: How to Use Local Docker Images with Minikube

Source: Stack Overflow ↗ · 689 votes

I remember when I first started playing with Minikube, I spent a solid three hours tearing my hair out because my pods were stuck in an infinite ImagePullBackOff loop. I was convinced my YAML was broken, but it turned out I was just dutifully pushing every single micro-change to a public registry like a chump, waiting for the internet to upload bits that were already sitting on my hard drive. It was a massive waste of time, and honestly, it felt like I was trying to mail a letter to my neighbor instead of just walking across the hall.

The reason you’re running into this is that Minikube runs inside its own isolated environment—usually a virtual machine or a separate container—that has no idea what’s happening inside your host machine's Docker daemon. When your Kubernetes cluster asks for an image, it looks at its own internal registry first. Since your local Docker daemon isn't connected to that internal environment, Minikube assumes the image doesn't exist locally and tries to go out to the internet to fetch it.

To fix this, you don't need to change your workflow or mess with registries. The trick is to point your local terminal at Minikube’s internal Docker daemon. By running a single command, your shell environment will start talking directly to Minikube’s Docker socket instead of your host’s. Just run this in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it by running docker images, and you'll see your custom image sitting right there ready for your pods to consume. Now, when you deploy your YAML, make sure to set imagePullPolicy: IfNotPresent in your manifest so Kubernetes doesn't try to go reach out to the web to find a newer version of your local dev image.


spec:
  containers:
  - name: my-app
    image: my-local-image:latest
    imagePullPolicy: IfNotPresent

If you find yourself constantly switching between your host Docker and Minikube, the best way to prevent the headache is to alias these commands in your .bashrc or .zshrc. I personally keep a use-minikube alias that runs that eval command so I never have to remember the syntax when I’m deep in a debugging session.

Hope this saves you from the same registry-upload purgatory I went through. Happy coding!

還在把 Docker Image 推上 Docker Hub 才給 Minikube 用？教你幾招直接搞定！

來源：Stack Overflow ↗ · 689 票

記得剛開始接觸 Kubernetes 的時候，為了測試一個小小的改動，我得把 Docker image 打包好、推到 Docker Hub，然後再切換到 Minikube 去 kubectl rollout restart。那個過程真的會讓人懷疑人生，每次改一行 code 就要等上好幾分鐘的網路傳輸，有時候遇到網路不穩，看著進度條卡在那裡不動，我簡直想直接把鍵盤給拆了。

為什麼會這樣呢？其實說穿了就是因為 Minikube 本身是一個跑在虛擬機或容器裡的獨立環境，它的 Docker daemon 跟我們本機電腦上的 Docker daemon 是完全分開的。當你在終端機打 docker build 時，那個 image 是存在你的電腦上，但 Minikube 根本「看不見」這份檔案，它只會去外面（像是 Docker Hub）抓。所以，你沒把東西推到網路上，Minikube 當然會報 ImagePullBackOff 給你看，這大概是每個剛接觸 K8s 的工程師最想摔滑鼠的時刻。

其實解決這個問題，根本不需要搞得那麼麻煩。最推薦的方式就是直接讓 Minikube 用你本機的 Docker 環境。只要在 build image 之前，先執行下面這行指令，把環境變數切換過去：


eval $(minikube docker-env)

執行完之後，你現在終端機打的任何 docker 指令，其實都是直接操作 Minikube 內部的 Docker daemon。這時候你再跑 docker build -t my-app:v1 .，這個 image 就會直接被建立在 Minikube 的肚子裡。之後你在 YAML 檔裡的 imagePullPolicy 記得設成 IfNotPresent，這樣 Kubernetes 就會優先使用本機現有的 image，完全不用再走網路下載那一套，速度快到讓你懷疑剛才是在浪費什麼時間。

不過要提醒一下，如果你關掉終端機視窗或是換了一個分頁，這個環境變數就會失效，下次要繼續開發記得再執行一次。如果你不想每次都這麼麻煩，建議可以把這個設定寫進你的 .zshrc 或 .bashrc 裡，但要記得加上判斷式，不然沒開 Minikube 的時候會噴一堆錯誤。

說實話，學會這一招之後，我的開發效率至少提升了三倍，再也不用看著 Docker Hub 的上傳進度條在那邊發呆了。希望這篇筆記能幫你省下不少崩潰的時間，趕快去試試看吧！
