How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I remember the first time I set up a local Kubernetes cluster, I spent a solid three hours banging my head against the wall because my pods kept throwing ImagePullBackOff errors. I was sitting there, staring at my terminal, absolutely certain that my image was right there on my machine, yet Minikube was acting like it was invisible. It felt like I was trying to show a painting to someone who was standing in a completely different building, and the frustration of waiting for a slow registry upload just to test a one-line code change was enough to make me want to switch back to bare-metal scripts.

The reason this happens is actually quite straightforward once you peel back the layers: Minikube runs inside its own virtual machine or container environment, which is completely isolated from the Docker daemon running on your host machine. When you build an image on your laptop, it lives in your host's Docker engine. When your Kubernetes pod tries to pull that image, it’s looking inside the Minikube node’s internal registry. Since those two environments aren’t natively linked, Minikube goes out to the public internet to find your image, fails to find it, and gives up.

To fix this, you don't need to push your images to a remote registry like Docker Hub or ECR. Instead, you need to point your local Docker CLI to the Docker daemon running inside the Minikube VM. The easiest way to do this is by running a single command in your terminal before you build your image. If you're on macOS or Linux, run this:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it worked by running docker images, and you should see your image listed there. Now, when you deploy your YAML file, make sure your imagePullPolicy is set to IfNotPresent or Never, otherwise Kubernetes might still try to reach out to the web to check for a newer version.


spec:
  containers:
  - name: my-app
    image: my-local-image:latest
    imagePullPolicy: IfNotPresent

If you ever need to switch back to your host's Docker daemon, just run eval $(minikube docker-env -u).

To keep things clean and prevent future headaches, I always stick to using specific image tags rather than relying on latest. If you keep overwriting the latest tag, Kubernetes can get confused about whether it actually has the most recent version of your code, which leads to those annoying "why isn't my change showing up?" moments. Stick to semantic versioning or git commit hashes, and you'll save yourself a world of pain.

Hope this saves you some time and keeps your local dev loop snappy. Happy coding!

為什麼 Minikube 總是抓不到我的 Local Docker Image？別再推送到 Docker Hub 了！

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了測試一個小功能，反覆修改程式碼、打包 Docker image，然後為了讓 Minikube 抓到，我竟然一次又一次地把 image 推送到 Docker Hub，再從裡面 pull 下來。當時網路慢到我想哭，看著終端機顯示 ImagePullBackOff 的那一刻，我真的差點要把鍵盤砸了，心想：「我明明就在同一台電腦上，為什麼還要繞這麼大一圈？」

這其實是因為 Minikube 是一個運行在虛擬機或容器裡的獨立環境，它有自己的一套 Docker daemon。簡單來說，你電腦本機的 Docker 和 Minikube 內部的 Docker 是兩條平行線，兩邊完全不互通。當你在自己的 terminal 打 docker build 時，鏡像只會存在你電腦的 daemon 裡，Minikube 當然會一臉無辜地跟你說：「我找不到這個 image 啊，大哥！」

其實解決方法超簡單，只要讓 Minikube 的環境「指向」你本機的 Docker 環境就好了。如果你是用 macOS 或 Linux，只要在 terminal 執行這行指令：

eval $(minikube docker-env)

這行指令會把你的環境變數切換過去，之後你再執行 docker build 時，鏡像就會直接被建立在 Minikube 內部的 Docker daemon 裡了。接下來你只要把 Deployment YAML 裡的 imagePullPolicy 改成 IfNotPresent，Kubernetes 就會乖乖直接用你剛 build 好的鏡像，再也不用經過 Registry 的漫長等待。

如果你是用 Windows 或者不想一直切來切去，另一個更乾脆的做法是直接用 minikube image load 指令。假設你已經 build 好了一個叫 my-app:v1 的鏡像，你只要輸入：

minikube image load my-app:v1

它就會自動幫你把鏡像複製進去，雖然多了一個步驟，但對於不想搞亂環境變數的人來說，這簡直是救命稻草。

為了不要再經歷這種「改一行程式碼、等五分鐘上傳」的痛苦，我現在習慣在開發階段直接把 imagePullPolicy 設為 IfNotPresent，這能強迫 K8s 先找本地端。另外，真的強烈建議各位把 eval $(minikube docker-env) 加進你的 shell 設定檔裡，或者乾脆養成習慣，在開發環境直接使用這種方式，能幫你省下大把浪費在等待網路傳輸的時間。

說真的，把時間花在寫程式上比花在處理 Image Registry 上快樂多了，希望這招能拯救你的開發效率！
