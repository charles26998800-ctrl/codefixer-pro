How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 689 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours trying to figure out why my pods kept stuck in ImagePullBackOff for an image I was staring at right there in my local terminal. It felt like I was losing my mind, convinced I had mistyped the tag, only to realize I was trying to serve a local file to a virtual machine that had absolutely no idea it existed.

The reason this happens is pretty straightforward once you peel back the layers: Minikube runs inside its own isolated environment, usually a virtual machine or a container. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Kubernetes, however, is looking for that image inside the Minikube node’s internal registry. Since the two are effectively living in different houses, the cluster can’t "see" what you’ve built, and it defaults to trying to pull the image from a remote registry like Docker Hub, which fails because your image isn't pushed anywhere.

The cleanest way I’ve found to solve this is to point your local shell directly at the Minikube Docker daemon. Instead of moving files around, you just tell your terminal to run Docker commands inside the Minikube environment. You can do this by running eval $(minikube docker-env) in your terminal. Once you run that, any docker build command you execute will build the image directly inside the Minikube VM. It’s like magic—the image is suddenly "there" as far as Kubernetes is concerned. You just need to make sure your deployment YAML has imagePullPolicy: IfNotPresent set, otherwise, K8s will still try to hit the internet to verify the image.


# Point your shell to the minikube docker daemon
eval $(minikube docker-env)

# Now build your image as usual
docker build -t my-app:v1 .

# Deploy to k8s, ensuring the policy doesn't force a remote pull
kubectl apply -f deployment.yaml

If you don't want to mess with your environment variables, you can also use the minikube image load command, which is a bit more explicit. This copies the image from your host daemon into the Minikube cluster. It’s a bit slower for massive images, but it’s great if you prefer to keep your host Docker context separate from your cluster configuration.


minikube image load my-app:v1

To prevent this headache in the future, I always stick a small note in my README.md for every project that uses local images. If you’re working on a team, someone else will inevitably run into this, so just documenting that eval $(minikube docker-env) step saves everyone a massive amount of debugging time.

Hope this helps you save those hours I wasted—happy coding!

救命，Minikube 怎麼死活讀不到我本機剛 Build 好的 Docker Image？

來源：Stack Overflow ↗ · 689 票

當年我剛開始摸 Kubernetes 的時候，為了測試一個新功能，在電腦上瘋狂改 code、瘋狂 docker build，結果信心滿滿地把 YAML 送進去 kubectl apply，螢幕上卻冷冰冰地噴出一句 ErrImagePull 和 ImagePullBackOff。我當時盯著螢幕看了十分鐘，心想：「大哥，這 Image 明明就在我電腦裡啊，你在跟我開什麼玩笑？」那種感覺真的很崩潰，就像是你精心準備了一桌菜，結果廚房門鎖死，餓著肚子看著裡面一樣無助。

其實這背後的原因一點也不複雜。Minikube 本質上是一個跑在你電腦裡的虛擬機（或是容器），它有自己獨立的 Docker Daemon。簡單來說，你電腦上的 Docker 和 Minikube 裡面的 Docker 是兩個平行時空。當你執行 docker build 時，你是把 Image 塞進了你本機的空間，但 Minikube 的 K8s Node 根本看不見那裡，它只會傻傻地去 Docker Hub 上面找，找不到當然就報錯了。

我後來發現，最快、最不折磨人的解法就是直接讓 Minikube 指向你本機的 Docker 環境。只要在執行指令前，先跑這行：


eval $(minikube docker-env)

這行指令的神奇之處在於，它會幫你設定好環境變數，讓你的 Terminal 直接對話到 Minikube 內部的 Docker Daemon。這時候你再執行 docker build -t my-app:v1 .，這個 Image 就會直接出現在 Minikube 的空間裡。接下來你只要確保 YAML 檔裡的 imagePullPolicy 設為 IfNotPresent，K8s 就會乖乖地使用你剛蓋好的那個 Image，不會再傻傻地跑去網路上載了。

為了避免以後又遇到這種「為什麼沒生效」的鬼打牆，我現在養成了個習慣，就是寫一個簡單的 Makefile。把 eval $(minikube docker-env) 和 docker build 綁在一起，每次要測試時就只打 make build。這樣一來，我根本不用去記那些複雜的環境變數，也不會因為切換了 Terminal 視窗就忘記設定，直接從源頭杜絕掉這種讓人抓狂的錯誤。

希望這招能救你脫離 ImagePullBackOff 的地獄，祝大家部署順利、Bug 遠離！
