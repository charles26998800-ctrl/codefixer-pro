How to Fix RuntimeError: Input type and weight type should be the same in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a GPU training loop in PyTorch, feeling like a genius for finally getting my hands on a dedicated machine. I moved my model to the GPU, hit run, and immediately got slapped in the face by that dreaded RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same. I spent three frustrating hours refactoring my entire custom Dataset class, convinced my data loading logic was broken, only to realize I’d simply forgotten to move the input tensors to the same device as my model.

The root cause here is actually pretty straightforward, even if it feels cryptic when you're staring at the stack trace. In PyTorch, your model's weights and your input data act like two magnets that have to be on the same "plane" of existence—either both on the CPU or both on the GPU. When you call model.to(device), you’re shifting the model weights into your GPU's VRAM. However, PyTorch doesn't automatically reach into your dataloader and move your incoming batches to that same device. Your inputs are still sitting in your system RAM as standard FloatTensors, so when you try to perform matrix multiplication against your GPU-resident weights, the system throws a tantrum because it can't perform math across different memory spaces.

Fixing this is a quick one-liner that I now keep in my standard training template. Inside your training loop, you just need to explicitly push your inputs and labels to the device you defined earlier. It’s a common oversight, but once you add this step, the error disappears instantly. Here is how I handle it in my scripts:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the line that saves the day
    inputs, labels = data[0].to(device), data[1].to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

To prevent this from haunting you in future projects, I recommend creating a small utility function or a wrapper that handles device movement automatically. If you're building larger pipelines, you can even subclass your dataset or use a custom collate function to handle the device transfer, but honestly, just getting into the habit of typing .to(device) the moment you unpack your dataloader will save you a world of headaches.

Hope this clears up the confusion and gets your training loop back on track. Happy coding!

被 PyTorch 的裝置不匹配搞到懷疑人生？教你一招解決 RuntimeError

來源：Stack Overflow ↗ · 202 票

記得剛開始用 PyTorch 跑實驗時，好不容易把模型架構寫好，資料也處理完了，按下執行鍵後我就跑去泡了杯咖啡。結果回來一看螢幕，滿滿的紅字直接噴在終端機上，那個 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same 真的讓我瞬間血壓升高。當時我盯著螢幕看了半小時，心想：「明明都把模型丟給 GPU 了啊，為什麼這傢伙還在跟我鬧脾氣？」那種明明以為程式碼寫得很完美，卻被一個莫名其妙的裝置錯誤卡住的無力感，真的是每個 AI 工程師的惡夢。

其實這個錯誤的原因很單純，就是「雞同鴨講」。PyTorch 很講究門當戶對，當你的模型已經被我送去 GPU（cuda）修煉，但我的訓練資料卻還在 CPU（Float）上面晃蕩時，模型吃進資料的那一刻就會崩潰。這就像是你用超級電腦在跑運算，卻硬要塞給它一筆還沒準備好過來的記憶體資料，系統當然會直接報錯抗議，拒絕執行這種跨裝置的運算。

解決方法其實沒那麼複雜，只要記得把資料也「同步」搬到跟模型同一個裝置上就好。在我的訓練迴圈裡，我習慣在讀取資料後，立刻加上 .to(device) 這行指令。就像這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵在這裡！把資料搬到跟模型一樣的裝置上
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就是正常的 loss 計算與反向傳播...

只要確保 inputs 和 labels 都在同一個 device 上，PyTorch 就會乖乖開工了。

為了避免以後又被這種低級錯誤搞到崩潰，我後來養成一個習慣，就是把裝置定義寫成一個共用的函式，或者直接在資料處理的 pipeline 起點就統一處理好。如果你的專案比較大，甚至可以寫一個小的 wrapper 函式，專門負責把任何進來的 Tensor 自動轉移到設定好的 device，這樣就不用每次寫迴圈都提心吊膽。

希望大家下次看到這個紅字時，別跟我當初一樣慌，轉個身把資料也送去 GPU 就沒事了，我們一起加油！
