React 18 Hydration Mismatch: Why Your SSR is Breaking

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the dreaded "Hydration failed" error in a React 18 project. I had just finished migrating a legacy dashboard to Next.js, feeling like a genius, when I opened the console and saw a wall of red text screaming that my server-rendered HTML didn’t match my client-side output. I spent three solid hours debugging what I thought was a complex state management issue, only to realize I was using new Date().toLocaleTimeString() inside my render cycle. It was one of those moments where I wanted to throw my keyboard out the window because the fix was so deceptively simple.

The root cause of this headache is actually quite logical: React expects the HTML generated on the server to be identical to the HTML generated on the client during the first render. When you use dynamic data that changes between the server's build time and the browser's execution—like timestamps, random numbers, or browser-specific local storage values—React gets confused. It sees the server's version, compares it to the client's version, notices the discrepancy, and throws its hands up in the air. Since the server doesn't know the client's environment (or the exact millisecond the page will load), it can't predict what the client will produce, leading to that nasty mismatch error.

To fix this, I’ve learned to defer the rendering of those dynamic elements until the component has officially "mounted" on the client. By using a simple useEffect hook, we can keep the server-side output static while letting the client take over once the page is interactive. Here is how I usually handle it:


import { useState, useEffect } from "react";

export default function DynamicComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      <h1>My App</h1>
      {isClient ? (
        <p>Current Time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By initializing isClient as false, the server renders the "Loading..." fallback. Once the component hits the browser, useEffect fires, updates the state, and triggers a re-render that displays the actual dynamic data. Since both the server and the client agree on the initial "Loading..." state, the hydration process completes without any errors.

Moving forward, the best way to prevent this is to be extremely mindful of browser-only APIs. Whenever I find myself reaching for window, localStorage, or any time-based functions, I treat them as "client-side only" by default. If you can wrap your logic in a client-only check or move that data fetching into a useEffect block, you'll save yourself from ever seeing that hydration warning again.

Hopefully, this saves you from losing as much sleep as I did when I first ran into it. Happy coding, and may your console stay clean!

React 18 Hydration 錯誤搞到我快瘋了：別讓伺服器跟瀏覽器吵架

來源：Stack Overflow ↗ · 341 票

那天凌晨兩點，我正趕著上線一個 Next.js 專案，心想一切都大功告成，結果一重新整理頁面，瀏覽器 Console 直接噴出一整排紅色的「Hydration failed」。我當下真的差點把鍵盤砸了，明明程式碼在本地跑得好好的，為什麼一上線就開始鬧脾氣？那個錯誤訊息就像是在跟我說：「你傳過來的 HTML 跟我想的不一樣喔，你自己看著辦。」在那一刻，我覺得自己簡直是在跟虛無飄渺的伺服器渲染玩猜謎遊戲。

其實這問題的核心很簡單，就是 React 18 的「完美主義」作祟。當我們使用 SSR（伺服器端渲染）時，伺服器會先產生一份 HTML 給瀏覽器，等瀏覽器載入後，React 會進行「Hydration」（注水），把這份靜態 HTML 變成動態的互動頁面。如果伺服器產出的內容，跟瀏覽器第一次執行 JavaScript 時產出的內容有哪怕一丁點誤差，例如時間戳記、隨機亂數，或是瀏覽器因為某些擴充功能自動幫你改了 HTML 結構，React 就會崩潰，覺得這世界不真實了，然後直接放棄治療。

我當初踩到的坑，主要是因為我在元件裡用了 new Date().toLocaleTimeString()，這東西在伺服器跑的時候是一個時間，傳到瀏覽器執行時已經過了好幾毫秒，內容對不上，直接觸發了 Hydration 失敗。解決的方法其實很直覺，就是要確保「第一次渲染」在兩端必須完全一致。我後來採取了「延遲渲染」的策略，讓元件等到瀏覽器端確認載入完成後才顯示。

我會寫一個小 hook 來處理這種狀態，程式碼大概長這樣：


import { useState, useEffect } from 'react';

export function useIsMounted() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  return isMounted;
}

// 在元件中使用
const MyComponent = () => {
  const isMounted = useIsMounted();

  if (!isMounted) return null; // 或者放一個骨架屏 (Skeleton)

  return <div>現在時間是: {new Date().toLocaleTimeString()}</div>;
};

用這種方式，伺服器只會渲染出一個空殼或 Loading 狀態，等瀏覽器接手後，再把真正的內容補上去，這樣就不會產生內容差異，成功避開了那個討厭的錯誤。

要預防這種鳥事再發生，最好的習慣就是把「會變動的內容」與「純靜態 UI」拆得更乾淨一些。盡量避免在 useEffect 以外的地方直接使用會隨環境變化的變數，或者乾脆在開發時就養成習慣，只要是牽涉到時間、亂數或本地儲存的邏輯，一律統一放到 useEffect 之後才進行渲染。

寫這類 SSR 框架真的就是在考驗耐心，修好之後記得去喝杯咖啡犒賞一下自己。
