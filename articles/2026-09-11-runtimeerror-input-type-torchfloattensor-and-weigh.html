How to Fix "RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same"

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a training loop on a multi-GPU server, feeling like a total genius until my terminal exploded with this specific error. I spent three hours staring at my code, convinced that moving the model to the GPU with model.to(device) was enough to solve all my problems. It’s one of those classic PyTorch "gotchas" that makes you want to throw your keyboard out the window, especially when you think you've already handled the device placement correctly.

The reason this happens is actually pretty straightforward once you stop seeing red. PyTorch is extremely strict about the memory location of your tensors; it refuses to perform math operations if one piece of data is sitting on your CPU RAM and the other is waiting in your GPU's VRAM. Even if you’ve moved your model to the CUDA device, your input data remains on the CPU by default when it’s loaded from the DataLoader. You’re essentially trying to perform a matrix multiplication between a CPU-based input and a GPU-based weight matrix, and PyTorch stops you dead in your tracks to prevent a memory mismatch.

To fix this, you need to explicitly move your input tensors to the same device as your model during every iteration of your training loop. I usually handle this right after I pull the data from my dataloader. You don't need to overcomplicate it—just call .to(device) on your inputs and labels before they hit the model. Here’s what my loop looks like now:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # This is the line that saves the day
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you find yourself constantly forgetting this, my biggest tip is to define a helper function or a simple wrapper that handles the device transfer as part of your data pipeline. Better yet, if you're working on a larger project, consider using a high-level library like PyTorch Lightning; it handles these device-agnostic movements under the hood, so you can spend less time debugging hardware mismatches and more time actually tuning your model architectures.

Hope this saves you a few hours of frustration today! Happy coding, and may your gradients always converge.

PyTorch 報錯：Input type 和 weight type 不一致，別再被卡住了！

來源：Stack Overflow ↗ · 202 票

那天深夜，我正準備跑完最後一輪模型的訓練，想說設定好讓它跑個通宵，隔天早上就能看到完美的 Loss 下降曲線。結果，按下執行鍵不到三秒，終端機就噴出一串紅字：RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。我當時真的差點把咖啡噴在螢幕上，心想明明都已經寫了 model.to(device)，到底為什麼這傢伙還是不聽話？

其實這個錯誤的核心原因很單純，就是「跑錯棚了」。PyTorch 非常嚴格，它要求你的模型參數（Weights）和輸入的資料（Inputs）必須待在同一個物理裝置上。如果你的模型已經被我移到了 GPU（cuda），但我的資料卻還留在 CPU（FloatTensor）裡，兩邊就像是隔著太平洋對話，PyTorch 自然就會跳出來說：「喂，你們兩個根本不在同一個頻率上，是要怎麼運算？」這真的很痛苦，尤其當你以為一切都設定好，卻因為少了一行程式碼而在半夜被這種低級錯誤卡住。

要解決這個問題其實很簡單，既然模型已經在 GPU 上了，我們只需要在迴圈讀取資料的時候，順手把資料也「丟」過去就好。我後來習慣在讀取資料的那一刻直接處理，程式碼大概長這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就在這一行，把資料也搬到跟模型一樣的裝置
    inputs, labels = data[0].to(device), data[1].to(device)
    
    outputs = model(inputs)
    # ... 後續的計算

只要確保 inputs 和 labels 都執行了 .to(device)，這個報錯就會瞬間消失。為了不讓這種崩潰經驗重演，我現在寫程式有個小習慣，就是定義一個全域的 device 變數後，寫一個小小的 helper function 或者直接在 DataLoader 外層包個簡單的封裝，確保所有進入模型的 tensor 都會自動檢查所在位置。只要養成「資料進門前先過戶」的習慣，這種 bug 就再也追不上你了。

下次遇到這種莫名其妙的型別報錯，先深呼吸檢查一下「誰在哪裡」就對了，祝大家訓練模型過程順利，別跟我一樣半夜在那邊修這種小 Bug！
