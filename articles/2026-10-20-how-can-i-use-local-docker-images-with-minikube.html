How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I remember the first time I set up a local Kubernetes cluster, I spent a solid three hours banging my head against the wall because my pods were stuck in ImagePullBackOff. I was convinced my YAML was perfect, but I kept forgetting that Minikube lives in its own little bubble—it couldn't see the shiny new image I’d just built on my host machine, and I was stubbornly refusing to push it to a registry just to test a one-line code change.

The reason this happens is actually quite logical once you look under the hood: Minikube runs inside a virtual machine or a separate containerized environment. When you run docker build on your laptop, that image is stored in your local Docker daemon. Your Minikube cluster, however, has its own isolated Docker daemon. When Kubernetes tries to pull an image, it asks the Minikube daemon, "Hey, do you have this?" and since the daemon hasn't seen it, it tries to reach out to Docker Hub, fails, and leaves you staring at an error message.

To fix this, you don't need to mess around with setting up a private registry or wasting bandwidth pushing images. The simplest, most effective way I've found to handle this is by pointing your local shell directly at the Docker daemon inside Minikube. Just run this command in your terminal:


eval $(minikube docker-env)

Once you run that, any docker command you execute in that specific terminal session will talk directly to the Minikube environment. Now, when you run docker build -t my-app:latest ., the image is built straight into the cluster's internal storage. When you deploy your pod, set your imagePullPolicy to IfNotPresent in your deployment manifest. This tells Kubernetes to look for the image locally first, and since it’s already sitting inside the Minikube daemon, it’ll spin up instantly without ever trying to hit the internet.

Moving forward, the best way to prevent this headache is to just make eval $(minikube docker-env) part of your project's startup script or a simple alias in your .zshrc or .bashrc. It saves you from that momentary lapse in memory where you build an image, deploy it, and wonder why Kubernetes is acting like it's never heard of your work before.

Hope this saves you a few hours of debugging—happy coding!

為什麼 Minikube 總是找不到我的 Image？關於本機開發的血淚史

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了部署一個小功能，反覆改了十幾次程式碼。每次我都在電腦上 docker build 好，然後自信滿滿地 kubectl apply，結果回傳的永遠是那句該死的 ErrImagePull。我盯著螢幕看著 ImagePullBackOff 的狀態，心裡想著：「大哥，我明明剛 build 好，你到底在 Pull 什麼東西啦？」那天晚上為了這個問題，我甚至懷疑是不是自己的 Docker 設定跑掉了，差點把整個開發環境重灌。

其實會發生這種事，是因為 Minikube 本質上是一個跑在虛擬機（或容器）裡的獨立環境。當我們在自己的終端機打 docker build 時，那個 Image 是存在你電腦的 Docker Daemon 裡，但 Minikube 的 Node 根本看不到那個空間。簡單來說，Minikube 就像是一個被隔離的「平行時空」，就算你把 Image 存在隔壁房間，只要沒遞給它，它就永遠抓不到。

後來我發現，最快且最不折騰的方法，就是直接讓你的終端機「指著」Minikube 內部的 Docker 環境。只要執行這行指令：


eval $(minikube docker-env)

執行完之後，你再下 docker build 指令，這個 Image 就會直接被建立在 Minikube 的內部空間裡，而不是你電腦的預設空間。這時候你只要把 Deployment 裡的 imagePullPolicy 改成 IfNotPresent，Minikube 就會乖乖地使用你剛蓋好的 Image，再也不會跑去網路上亂抓了。如果你懶得每次開機都打這行，也可以直接用 minikube image load ，雖然稍微慢一點點，但不用切換環境，也算是一種保險。

為了避免這種「明明有圖卻抓不到」的崩潰感，我現在習慣在寫 YAML 檔案時，一定會把 imagePullPolicy 設定為 IfNotPresent。這樣就算哪天我真的把 Image 推上 Docker Hub 了，它也會優先檢查本機有沒有現成的，省去不少等待下載的時間。

以後遇到這種 ErrImagePull 別急著崩潰，先檢查一下是不是跑錯棚就好啦！
