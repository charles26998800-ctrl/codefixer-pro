How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27251 votes

I still remember the first time I accidentally committed a massive debug log file full of API keys to a repository at 2:00 AM. I stared at the screen for a solid ten minutes, sweating bullets, terrified that I’d just permanently screwed up our production branch before even realizing I hadn't pushed anything yet. I spent three hours frantically Googling commands, convinced I was about to delete my entire project history, only to realize that Git is actually much more forgiving than it looks.

The root cause of this panic is usually simple: you got ahead of yourself. You staged files using git add . without checking the status, hit git commit, and realized mid-process that you’d included artifacts, local configs, or just the wrong set of changes. Because Git is designed to be a ledger of your work, it makes "undoing" things feel like you're trying to rewrite history, which is technically what you're doing. As long as you haven't pushed those commits to a shared remote repository, you’re in the clear. You aren't actually deleting history from the world; you’re just shifting your local pointer back to a point in time before you made the mistake.

When I need to fix this, I rely on the git reset command. If I just want to undo the commit but keep my changes in the staging area (so I can fix the file list), I run git reset --soft HEAD~1. This is my go-to move because it leaves my files exactly as they were, just un-committed. If I’m really frustrated and want to completely wipe the changes from that commit because the code was a disaster, I use git reset --hard HEAD~1. Be warned, though: the hard reset destroys your work, so don't use it unless you're 100% sure those changes are garbage.


# Undo the commit and keep changes staged
git reset --soft HEAD~1

# Undo the commit and discard all changes entirely
git reset --hard HEAD~1

If you find yourself doing this often, the best habit I’ve adopted is to always run git status right before I commit. I know it sounds basic, but it forces me to look at the list of staged files one last time, which catches about 90% of my "oops" moments before they ever become a commit.

Hope this helps you clean up your git log without the headache. Happy coding, and try not to commit those API keys next time!

手滑把爛 Code 推上去了？別慌，Git 復原大法在這裡

來源：Stack Overflow ↗ · 27251 票

記得那是一個週五下午，我正準備趕在下班前把最後一個功能修好，結果腦袋一打結，竟然把一堆還在測試中的 Debug 用的 log 跟亂七八糟的廢棄程式碼一起 git commit 了。當下看到螢幕顯示 [master 8a7b6c9] 的時候，我整個人心跳漏了一拍，那種「完了，我是不是要把整個專案搞砸了」的恐懼感，真的是每次遇到都想原地離職。

其實這狀況之所以會發生，通常就是因為我們在 git add . 的時候太豪邁，沒檢查過到底進了什麼檔案，結果就把不該進去的垃圾一起打包了。雖然還沒推送到遠端伺服器（Remote）還算是不幸中的大幸，但要是直接硬幹強行覆蓋，很容易把辛苦寫好的進度也一起弄丟，那種心血付諸流水的痛苦，相信只要是工程師都體驗過，真的會讓人懷疑人生。

好啦，如果你現在也卡在這一關，千萬別急著刪掉資料夾重來。其實 Git 提供了一個超好用的指令叫 git reset。如果你只是想把剛剛那次 commit 撤銷，但想要保留檔案的變更（也就是說，檔案還留在你的工作目錄裡，只是狀態變回還沒 commit 的樣子），你就下這一行指令：


git reset --soft HEAD~1

這行指令的意思是「把指標退回到上一個狀態」，--soft 參數會幫你把改動過的檔案留在暫存區（Staging Area）。如果你是連暫存區都不想要，想把檔案通通變回「還沒 add」的乾淨狀態，那就改用 --mixed，或者更狠一點，直接用 --hard 把剛剛那次 commit 的所有改動通通殺掉（這招真的要小心用，用了就真的救不回來了）。

說到預防，我後來學乖了，每次 commit 之前我一定會養成檢查的好習慣。我現在都會在 commit 前先跑一遍 git status，甚至更推薦大家用 git add -p。這個指令會讓你一段一段地檢查改動內容，就像在過濾器一樣，確認沒問題才放行。只要多花那幾秒鐘檢查，真的能省下後面半小時在那邊心驚膽跳除錯的時間。

Git 雖然有時候很難搞，但只要熟練這些撤銷指令，其實它還是很佛心的。下次再手滑也不要慌，冷靜下來下對指令就沒事了！
