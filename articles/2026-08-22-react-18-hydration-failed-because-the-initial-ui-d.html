Dealing with React 18 Hydration Mismatches: A Survival Guide

Source: Stack Overflow ↗ · 341 votes

I remember the first time I migrated a legacy dashboard to React 18; I thought it would be a smooth weekend project. Instead, I spent four hours staring at a blinking console error screaming about "hydration failed," convinced that my server-side rendering logic had completely betrayed me. It turned out I had a simple random number generator firing on both the server and the client, and that tiny discrepancy sent React into a full-blown existential crisis.

The core reason this happens is actually quite logical: React expects the HTML produced by your server to be an identical twin to the HTML generated by the client during the initial "hydration" phase. When you use server-side rendering, the server sends a static HTML snapshot to the browser. As soon as the JavaScript bundle loads, React tries to "attach" its event listeners and state to that existing DOM. If your code produces different output on the server versus the client—like using new Date(), Math.random(), or even browser-specific local storage checks—React detects the mismatch and throws its hands up. It can't guarantee a consistent UI, so it kills the hydration process to prevent unpredictable behavior.

To fix this, the trick is to postpone the rendering of any non-deterministic content until the component has officially mounted on the client. I’ve found that the cleanest way to handle this is by using a simple useEffect hook to toggle a "mounted" state. By default, I set the state to false, and once the component mounts in the browser, I flip it to true. This ensures the server renders a safe, neutral placeholder, and the client renders the actual dynamic content only after it's safe to do so.


import { useState, useEffect } from "react";

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return <div>Loading...</div>;
  }

  // Now it's safe to use browser-only APIs or random values
  return <div>{new Date().toLocaleString()}</div>;
}

If you really need to render something specific that doesn't rely on state, you can also use suppressHydrationWarning={true} on the specific HTML tag that's causing the fuss, though I usually treat that as a last resort. It’s better to be explicit about your rendering lifecycle than to just silence the warning.

The best way to prevent this in the future is to keep a mental checklist of "server-unsafe" operations. Any time you reach for a browser-specific global like window, localStorage, or even a date-time generator that varies by millisecond, wrap it in a custom hook or a conditional check that confirms the environment. Once you start treating the server and client as two distinct environments that only meet during that hydration handshake, these errors stop being a mystery and start being a standard part of your workflow.

Hope this saves you from losing your mind like I did. Happy coding, and may your console stay clean!

Next.js 遇到 Hydration Failed？別慌，這其實是 React 在跟你玩「找不同」

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地把專案跑起來，結果打開瀏覽器控制台一看，那行紅通通的「Hydration failed because the initial UI does not match what was rendered on the server」直接讓我心跳漏了一拍。我當時盯著螢幕看了半小時，心想：「這程式碼我在開發環境跑得好好的，怎麼一進 Production 就原地爆炸？」那種明明寫對了邏輯，卻被框架報錯折磨的無力感，真的是每個前端工程師的惡夢，差點就想直接把鍵盤砸了。

簡單來說，這個錯誤的本質其實是 React 在玩「大家來找碴」。當你使用 Next.js 做 SSR（伺服器端渲染）時，伺服器會先產生一份 HTML 發給瀏覽器，然後瀏覽器再接手讓頁面「活過來」（也就是 Hydration）。但如果伺服器算出來的 HTML 結構，跟瀏覽器第一次執行 JavaScript 時產生的結果有一丁點不一樣，React 就會崩潰，覺得這世界充滿了欺騙，直接報錯給你看。最常見的兇手通常是像 new Date()、隨機數產生器，或是根據瀏覽器視窗大小決定顯示什麼內容的邏輯，因為伺服器根本不知道瀏覽器現在是幾點、長什麼樣。

要解決這個問題，重點就是「延遲執行」。我們必須確保那些依賴於瀏覽器環境的內容，不要在伺服器渲染階段直接出現，或者確保它們在兩邊的輸出是一致的。我當時最常用的做法就是透過 useEffect 來控制渲染時機，因為 useEffect 只會在瀏覽器端執行，完美避開了伺服器端的混亂。你可以像這樣處理：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者放一個靜態的 loading 狀態
  }

  return <div>這裡放那些會導致錯誤的內容，例如 {new Date().toLocaleString()}</div>;
}

為了預防這種崩潰再次發生，我建議你在寫這類會跟瀏覽器「互動」的組件時，養成一個好習慣：只要涉及 window、localStorage 或任何與時間相關的操作，通通預設把它們包進一個自定義的 Hook 裡，或者乾脆用 isMounted 狀態來保護。只要心裡隨時想著「伺服器看不到瀏覽器」，基本上就不會再被這個問題搞到心累了。

其實這問題搞懂了也就那麼回事，下次再跳出紅字時，就當作是 React 在提醒你該整理一下組件邏輯啦。祝大家開發順利，少遇到這種莫名其妙的 bug！
