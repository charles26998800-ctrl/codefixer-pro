Dealing with React 18 Hydration Mismatch Errors in Next.js

Source: Stack Overflow ↗ · 341 votes

I remember the first time I migrated a legacy app to React 18, I felt like a total pro until I refreshed my browser and saw a console full of red text. I spent three hours staring at my screen, convinced that React was just hallucinating, only to realize I had a simple Date() call that was rendering differently on the server than it was in the browser. It’s one of those bugs that makes you want to throw your keyboard out the window, but once you understand the mechanism, it’s actually quite predictable.

The root cause of this "Hydration failed" error is essentially a mismatch between the HTML sent by the server and the first render generated by the client. When Next.js pre-renders your page, it generates a static HTML snapshot. When that code hits the browser, React attempts to "hydrate" it by attaching event listeners and making it interactive. If the server says "I have a timestamp of 10:00 AM" and the browser immediately calculates "10:01 AM" because it’s running in a different environment, React panics. It assumes the server is wrong or the state is corrupted, so it throws the hydration mismatch error to stop you from shipping a broken UI.

The way I usually fix this is by ensuring that the component doesn't attempt to render dynamic, environment-dependent data until it has officially mounted on the client side. If you have a component that relies on things like local storage, window dimensions, or current timestamps, you need to gate that logic behind a useEffect hook. I typically use a simple state variable to track if the component has mounted.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // or a loading skeleton
  }

  return <div>The client-side time is: {new Date().toLocaleTimeString()}</div>;
}

By returning null or a static placeholder during the initial render, you ensure that the server-side HTML and the client-side initial state remain identical. Once the component mounts, the useEffect triggers, updates the state, and allows React to re-render the dynamic content safely. It’s a clean way to keep your SSR working without triggering those annoying console warnings.

To prevent this from happening in the future, I always try to keep my server-side components as "pure" as possible. If a piece of data doesn't strictly need to be rendered on the server for SEO purposes, keep it behind a client-side flag or a library like react-no-ssr. Getting into the habit of asking "Does this value change based on the user's browser?" before I write a component has saved me from countless late-night debugging sessions.

Hopefully, this saves you a few hours of frustration and gets your app back on track. Happy coding!

救命！React 18 的 Hydration Error 到底要怎麼解？

來源：Stack Overflow ↗ · 341 票

記得那天是週五下午，我正滿心期待地想把剛重構完的 Next.js 專案推上線，結果打開開發者工具一看，滿滿一整排刺眼的紅色 Hydration failed 錯誤訊息。當時我整個人都傻了，明明在本地開發時看起來一切正常，但瀏覽器就是在那邊瘋狂報錯，說伺服器渲染出來的 UI 跟客戶端長得不一樣，當下真的差點把鍵盤直接砸了。

會發生這種事，其實是因為 React 的運作機制。簡單來說，Next.js 會先在伺服器端把 HTML 畫好傳給瀏覽器，然後瀏覽器再接手讓頁面「活起來」（這就是 Hydration）。但如果你的程式碼裡有一些「隨機」的東西，像是用了 new Date()、Math.random()，或者是依賴了只有瀏覽器才有的 window 物件，伺服器算出來的結果跟瀏覽器自己跑出來的結果就會對不上，React 一發現這兩個畫面長得不一樣，就會直接放棄治療並噴出那個讓你崩潰的錯誤訊息。

我後來發現，最常見的兇手就是我們在組件裡直接用了 typeof window 或者 localStorage 之類的東西。要解決這個問題，最乾淨的做法就是確保那個元件「只有在瀏覽器端才渲染」。我自己最常用的解法就是寫一個簡單的 useEffect 來處理，讓元件先渲染一個空的狀態，等掛載完成後再把內容塞進去。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <div>這是只有瀏覽器才看得到的內容</div> : null}
    </div>
  );
}

這樣一來，伺服器端渲染時只會拿到一個空的 div，不會去觸發那些只有瀏覽器才懂的邏輯，等到瀏覽器真的接手後，isClient 變成 true，頁面就會自動補上該有的內容，Hydration 就不會再鬧脾氣了。

至於要怎麼預防下次再被這個雷炸到，我強烈建議大家在寫元件時，養成一個習慣：只要涉及到瀏覽器特定 API 的邏輯，一律把它包裝成 Custom Hook，或者乾脆確保這些邏輯都在 useEffect 裡面執行。不要在 Render 階段直接去讀取 window 或產生隨機數，這絕對是自找麻煩。只要心裡多想一下「這段程式碼在伺服器上跑會變怎樣」，基本上就能避開 90% 的這類問題。

希望這些經驗能幫你省下幾個小時的除錯時間，趕快去把那些紅字消掉然後準時下班吧！
