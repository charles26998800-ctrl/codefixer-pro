Solving the "Hydration Failed" Error in Next.js: A Practical Guide

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the dreaded "Hydration failed" error in a React 18 project. I was three hours deep into a late-night coding session, convinced I had built a perfect component, only to have the browser console scream at me that my server-rendered HTML didn't match the client-side state. I stared at the screen for an eternity, questioning my sanity, before realizing I had carelessly introduced a random number generator directly into my render cycle. It’s one of those bugs that makes you feel like you’re losing your mind because the code looks perfectly valid until it actually runs.

At its core, this error is React's way of telling you that the DOM structure generated by your server doesn't match the one generated by your browser. When you use Next.js, the server pre-renders your page into static HTML and sends it to the user. Once that HTML hits the browser, React "hydrates" it, attaching event listeners and turning it into an interactive app. If the browser tries to render something different—even by a single character or a timestamp—React panics. It can't reconcile the mismatch, so it throws its hands up and declares hydration failed.

The most common culprit is using client-only data, like window, localStorage, or new Date(), directly inside your component body. Since the server doesn't have access to the browser's window object or the user's specific clock, the server renders a default state, while the client renders the "actual" state. To fix this, you need to ensure the component renders the same thing on both sides during the first pass. I usually handle this by using a useEffect hook to trigger the client-side logic only after the initial mount.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>Current time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By adding that isClient flag, you force the component to render a consistent "loading" state on the server, which matches the initial state on the client. Once the browser takes over, the useEffect runs, updates the state, and swaps in your dynamic content. This prevents the mismatch entirely because the server and client start on the exact same page.

To stop this from happening in the future, my golden rule is to treat your top-level component renders as "pure" functions. If you need browser-specific APIs, always hide them behind a useEffect or check for the existence of the object before accessing it. Keep your server and client in sync by being intentional about what renders before the initial mount, and you'll save yourself a massive headache.

Hope this helps you clear those console errors and get back to building cool stuff. Happy coding!

React 18 Hydration Error：那個讓我熬夜到凌晨兩點的「不匹配」惡夢

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿懷期待地想體驗 SSR 的效能提升，結果專案一跑起來，瀏覽器 Console 直接刷出一整排紅通通的 "Hydration failed" 錯誤，當時我盯著螢幕，內心真的只有無數個問號在飛。最讓我崩潰的是，網頁看起來明明長得一模一樣，但 React 就是死活認定伺服器產出的 HTML 跟客戶端渲染出來的結果「長得不一樣」，那種「明明沒錯卻被系統宣告無效」的無力感，真的會讓人想把鍵盤給拆了。

這個問題其實說穿了，就是 React 在玩「大家來找碴」。當你在伺服器端（SSR）產生 HTML 時，React 會把狀態記下來，然後傳給瀏覽器；結果瀏覽器載入 JavaScript 後，重新執行一遍渲染，卻發現某些動態內容（比如時間戳記、隨機亂數，或是瀏覽器特有的 API）跟伺服器給的不一樣。React 為了怕畫面跳動，乾脆直接報錯給你看。最常見的痛苦時刻就是用到 new Date() 或是讀取 window 物件，因為伺服器根本沒有這些東西，或者它們在伺服器跟客戶端跑出來的時間點根本不同。

要解決這個問題，重點在於讓 React 知道「這部分先別急著渲染」。我後來學乖了，如果你的元件真的需要依賴瀏覽器環境，最簡單的解法就是確保它只在客戶端掛載後才執行。我通常會寫一個簡單的 Hook 來判斷，或是利用 useEffect 來處理。你可以試著把會出錯的元件包裝一下，像這樣：


import { useState, useEffect } from 'react';

function ClientOnlyComponent({ children }) {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null; // 或者你可以放一個 loading 的 spinner
  }

  return <>{children}</>;
}

這樣一來，伺服器端永遠只會拿到一個空的殼或是 Loading 狀態，等到瀏覽器真的準備好要接手渲染時，hasMounted 才會變成 true，這樣前後端的內容就能完美對齊，再也不會跳出那該死的錯誤訊息了。

為了預防這種狀況再次發生，我現在養成了一個習慣，就是開發時會特別留意那些「依賴瀏覽器狀態」的邏輯。只要看到 window、localStorage 或 new Date()，我就會下意識地把它們往 useEffect 裡面塞，或者乾脆確保這些邏輯不要在元件的初始渲染階段就被呼叫到。只要把這些「不確定因素」延後到客戶端才處理，Hydration 的錯誤率真的會大幅降低。

希望這招能幫你從崩潰邊緣救回來，別讓這些紅字影響了你寫 Code 的好心情！
