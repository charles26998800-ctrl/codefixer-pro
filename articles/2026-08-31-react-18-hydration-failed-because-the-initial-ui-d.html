Why Your Next.js App is Crashing: Solving the "Hydration Failed" Error

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a Next.js project. I had just finished porting a complex dashboard, feeling pretty clever about my SSR implementation, only to refresh the browser and see my entire UI flicker and collapse into a wall of red text in the console. I spent three hours—yes, actual hours—rearranging my components and questioning my understanding of React, only to realize I was just rendering a localized timestamp that didn't match the server.

The root cause of this frustration is actually quite logical once you peek under the hood of React 18. When you use Next.js, the server renders your page into static HTML and ships it to the browser. Then, React "hydrates" that HTML by attaching event listeners and turning it into a dynamic application. If the HTML the browser generates on the initial render doesn't perfectly mirror what the server sent, React throws its hands up and declares a hydration mismatch. It’s essentially a "spot the difference" game where, if the server says "Hello" and the browser says "Hi," React refuses to play ball because it can't guarantee the state is consistent.

I fixed this by isolating the dynamic parts of my component that were causing the discrepancy. Most of the time, this happens because of Date.now(), Math.random(), or browser-specific APIs like window or localStorage being called during the initial render. The trick is to force the component to wait until it’s safely in the browser environment before rendering that specific piece of data. I started using a simple useEffect hook to toggle a state variable once the component mounts, ensuring the server-rendered HTML remains clean and static.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Now this will only render on the client */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

To prevent this from haunting your codebase in the future, get into the habit of checking for "client-only" logic whenever you touch browser-specific APIs. If you find yourself reaching for window or localStorage inside a component body, stop and wrap that logic in a useEffect or use a library like react-use that handles these lifecycle checks for you. Keeping your initial render deterministic is the single best way to keep these hydration errors at bay.

Good luck with your debugging, and I hope this saves you from the headache I had to endure! Let me know if you run into any other weird edge cases with your build.

React 18 Hydration 錯誤搞得你心很累？這篇救救你

來源：Stack Overflow ↗ · 341 票

記得那天凌晨兩點，我剛把一個 Next.js 專案升級到 React 18，想說順手優化個 SSR 效能，結果 Chrome 控制台直接噴出一大串紅通通的 Hydration failed 錯誤，整頁畫面閃爍個不停。當下我真的差點崩潰，明明程式碼邏輯看起來完全沒問題，伺服器產出的 HTML 跟瀏覽器跑出來的 React 元件卻像在鬧雙胞，這種「明明一樣卻說不一樣」的感覺，簡直比跟另一半溝通還難。

其實這問題的根源很簡單，就是 React 18 對一致性的要求變嚴格了。當伺服器渲染完 HTML 給瀏覽器後，瀏覽器會進行「水分補充（Hydration）」，也就是把事件監聽綁上去。如果瀏覽器第一次渲染的結果，跟伺服器傳來的那個 HTML 有哪怕一丁點差異——比如因為時間戳記、隨機數，或是瀏覽器特定 API（像 window.localStorage）導致的內容不同——React 就會因為「這不是我當初預期的樣子」而直接崩潰。我那時候最痛苦的時刻，就是發現自己用了 Date.now() 直接渲染在元件裡，導致伺服器渲染那一秒跟瀏覽器執行那一秒永遠對不上，找這個 bug 真的找到想把螢幕砸了。

要解決這個問題，最標準的做法就是確保「第一次渲染」時，雙方的資料是一模一樣的。你可以利用 useEffect 來處理那些只有瀏覽器才有的東西，因為 useEffect 只會在元件掛載到瀏覽器後才執行，完全避開了 SSR 的階段。像是我後來就乖乖改成這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>現在時間是：{new Date().toLocaleTimeString()}</span> : <span>載入中...</span>}
    </div>
  );
}

這樣一來，伺服器只會吐出「載入中...」，瀏覽器第一次渲染時也是「載入中...」，雙方達成共識後，再由 useEffect 把正確的時間補上去，錯誤自然就消失了。

至於怎麼預防這種地獄輪迴？我強烈建議大家在寫元件時，隨時提醒自己：「這行程式碼會不會在伺服器上執行時，跟瀏覽器跑出不同結果？」只要涉及到 window 物件、隨機數、或是會變動的時間戳，一律先用 useEffect 包起來或是透過 typeof window !== 'undefined' 做條件判斷。保持靜態渲染的一致性，是維護 React 專案健康的不二法門。

希望這招能幫你脫離苦海，去喝杯咖啡休息一下吧，這 bug 真的不是你的錯。
