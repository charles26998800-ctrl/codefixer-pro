How to Fix the "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 201 votes

I remember the first time I ran into this error back when I was training my first custom CNN. I’d spent an entire afternoon obsessing over my architecture, finally hit "run" on a massive dataset, and watched my terminal spit out a wall of red text less than a second into the first epoch. I sat there for a solid hour convinced my GPU was fried or that I’d somehow broken my PyTorch installation, only to realize I’d completely forgotten to move my input tensors to the device.

At its core, this error is PyTorch’s way of telling you that you’ve got a "type mismatch" between your model and your data. When you call model.to(device), you’re successfully pushing your model weights onto your GPU (the cuda device), but your data is still sitting comfortably in your machine's system RAM as a standard CPU FloatTensor. PyTorch is strictly typed in this regard; it can’t perform matrix multiplication between a weight sitting on the GPU and a tensor sitting on the CPU. It's like trying to plug a European power cord into a US outlet—the two parts just don't speak the same language.

To fix this, you need to be explicit about moving your input data to the same device as your model inside your training loop. I usually handle this by referencing the device object I defined during initialization. Here is how I modify my training loop to stop this error in its tracks:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Explicitly move both inputs and labels to the device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

Once I added those two .to(device) lines, the training started without a hitch. If you’re working with complex data structures like dictionaries or lists of tensors, don't forget that you’ll need to iterate through them and move every single piece to the device individually, as .to() doesn't automatically propagate through nested containers.

To keep this from biting you again, my best advice is to always define a helper function or a small utility class that handles your data movement. Instead of manually calling .to(device) every time, I usually wrap my data loading in a way that ensures everything is already on the target hardware before it even touches the model. It saves you from those late-night debugging sessions where you're staring at the same line of code for way too long.

Happy coding, and may your training loops run without a single crash today!

PyTorch 報錯：Input type 和 weight type 不一致，別再被卡在 GPU 門口了！

來源：Stack Overflow ↗ · 201 票

記得剛開始接觸 PyTorch 的時候，為了跑一個訓練模型，我興沖沖地把筆電接上電源、把模型丟進 GPU，結果程式一跑起來，螢幕直接跳出那行讓人看了就火大的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。那一刻我真的差點崩潰，明明都已經寫了 .to(device)，到底還有什麼是不對的？看著螢幕上那一串錯誤代碼，心裡想著「我不是已經把模型搬進 GPU 了嗎？為什麼資料還是待在 CPU 裡不肯過去？」

這種痛苦時刻真的非常經典，特別是當你訓練一個大型模型，等了老半天終於等到第一個 batch 開始跑，卻在第一行就被這個錯誤攔截，那種「被拒之門外」的無力感，真的是每個煉丹師的必經之路。其實說穿了，這問題的核心就是「你的模型住在 GPU 的豪宅，但你的資料卻還在 CPU 的宿舍」，PyTorch 很嚴格，它不允許這兩個不同空間的傢伙在同一個運算單元裡打架。你雖然把 model 搬過去了，但 inputs 和 labels 這兩位新來的房客，還沒拿到進入 GPU 的通行證。

要解決這個問題其實很簡單，就是要在資料送進 model 之前，手動把它們也踢進去。我在開發時習慣這樣寫，直接在迴圈裡把資料也 .to(device) 一下：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！要把資料搬到跟模型同一個 device
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... 後續的 loss 計算也要記得把 labels 放在同一邊

後來為了避免以後再因為粗心被這個 bug 卡住，我養成了一個小習慣：在定義完 device 後，會寫一個簡單的檢查函數，或是乾脆在寫 DataLoader 的處理邏輯時，強制加上 .to(device) 的習慣。甚至如果你是在做專案規模比較大的開發，建議把這個邏輯封裝進一個簡單的 Trainer 類別裡，這樣每次寫迴圈就不用擔心漏掉這一行，畢竟誰想在訓練過程被這種基礎問題中斷呢？

以後遇到這個錯誤，記得先檢查是不是有哪位資料房客還沒被「搬家」，搞定這個，煉丹之路就順暢多了！
