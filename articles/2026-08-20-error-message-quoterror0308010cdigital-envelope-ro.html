How to Fix the "digital envelope routines::unsupported" Error in React

Source: Stack Overflow ↗ · 2572 votes

I still remember the day I upgraded my local Node environment, feeling all proud about being on the latest version, only to have my entire React project blow up the second I ran npm start. I spent a solid two hours staring at my terminal, convinced I’d somehow corrupted my entire node_modules folder, before I realized it was just a classic case of new software being too smart for its own good. It’s one of those cryptic errors that makes you feel like you’ve broken the matrix, but luckily, the fix is way simpler than it looks.

The root of this headache lies in the jump from Node.js v16 to v17. When Node 17 landed, the team switched over to OpenSSL 3.0, which tightened up security by deprecating a bunch of legacy algorithms. If you’re running an older React project—or even a newer one using outdated build dependencies like older versions of Webpack—those tools are still trying to use the MD4 hashing algorithm, which OpenSSL 3.0 now flags as insecure. Basically, your build script is trying to talk to the crypto library in a language it no longer speaks, and the whole process crashes before it even starts.

I found that the most reliable way to handle this without having to rewrite your entire project’s dependency tree is to tell Node to use the "legacy" provider for OpenSSL. You don't need to downgrade your Node version, which is what I was originally tempted to do. Instead, you just need to set an environment variable called NODE_OPTIONS before your start script fires. If you're on a Mac or Linux machine, you can patch this directly in your package.json file inside the scripts section:


"scripts": {
  "start": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "export NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

If you’re working on Windows, the syntax is slightly different because it doesn't handle the export command the same way. You'll want to use set instead:


"scripts": {
  "start": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts start",
  "build": "set NODE_OPTIONS=--openssl-legacy-provider && react-scripts build"
}

If you don't want to mess with your package.json every time you jump between projects, you can also just run the command directly in your terminal before starting your dev server, or add it to your .bashrc or .zshrc file as a global variable.

To prevent this from popping up in the future, my best advice is to keep your dependencies updated as often as you can stand it. Most of the time, this error only sticks around because the project is relying on an older version of react-scripts that hasn't been maintained to support the newer OpenSSL standards. Running npm outdated or using a tool like npm-check-updates every once in a while will save you from these "deprecated algorithm" traps that seem to hit us every time a new major Node version drops.

Hopefully, this gets your project back up and running so you can get back to writing actual code. Happy hacking!

救命！跑個 React 專案怎麼跳出「digital envelope routines::unsupported」這種鬼錯誤？

來源：Stack Overflow ↗ · 2572 票

記得那天我剛接手一個舊專案，想說先跑個 npm start 確認環境沒問題，結果終端機直接噴出一大串紅字，最後掛著 error:0308010C:digital envelope routines::unsupported。當時我真的差點崩潰，明明幾個月前還能跑的專案，怎麼換了台電腦、升級了一下 Node.js 版本，整個人生就黑白了？那一瞬間真的覺得自己像個菜鳥，連個開發環境都架不起來，心裡滿滿的挫折感。

其實這背後的原因一點都不神秘，就是因為 Node.js 在 v17 版本之後升級了底層的 OpenSSL 3.0，而我們舊專案裡用的 Webpack 版本（通常是 v4 這種老扣扣）還在用舊版的加密演算法。簡單說，就是 Node.js 的新管家不認舊帳號的加密金鑰了，兩邊對不起來，你的 React 專案當然就原地罷工。這真的很煩人，因為這不是你的程式碼寫錯，而是環境升級帶來的「副作用」，當時我還傻傻地去檢查了好幾次 package.json，結果根本是白忙一場。

要解決這個問題，其實不用去大費周章升級整個 Webpack（那簡直是地獄），最快的方法就是告訴 Node.js：「嘿，請你先降級一下安全標準，讓我把專案跑起來吧！」只要在啟動指令前面加上一個環境變數設定就行了。

如果是用 Mac 或 Linux，你可以直接在終端機輸入：


export NODE_OPTIONS=--openssl-legacy-provider
npm start

如果你是用 Windows 的 PowerShell，指令則是：


$env:NODE_OPTIONS = "--openssl-legacy-provider"
npm start

為了不用每次開專案都要手動敲這行，我通常會直接改 package.json 裡的 scripts 設定，把指令寫死進去：


"scripts": {
  "start": "react-scripts --openssl-legacy-provider start",
  "build": "react-scripts --openssl-legacy-provider build"
}

至於要怎麼預防下次再踩到這種坑？說真的，最有效的辦法就是鎖定開發環境的版本。我現在都會在專案根目錄放一個 .nvmrc 檔案，並且在 package.json 裡加上 engines 欄位，強制規定專案必須用哪個版本的 Node.js 執行。這樣不管是誰來接手，只要用 nvm 切換一下版本，就能避開這種跨版本升級帶來的悲劇。

希望這篇筆記能幫你省下幾小時的除錯時間，趕快去把你的專案跑起來吧，別再跟那個錯誤訊息搏鬥了！
