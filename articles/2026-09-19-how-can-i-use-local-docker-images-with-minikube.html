How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 689 votes

I remember back when I was first getting comfortable with Kubernetes, I wasted an entire afternoon scratching my head because my pods kept crashing with an ImagePullBackOff error. I was convinced my YAML was perfect, but I hadn't realized that Minikube was looking for my local image in the cloud instead of right under its nose on my machine. I spent three hours debugging network policies and firewall rules before I realized I was just making things way harder than they needed to be.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside its own isolated virtual machine or container environment. When you run docker build on your host machine, that image lives in your host’s Docker daemon. Minikube, however, has its own separate Docker daemon inside its node. Even if you're on the same laptop, they are essentially strangers to each other. Kubernetes asks the Minikube node to pull an image, the node checks its own internal registry, finds nothing, and fails.

To fix this, you don't need to sign up for a private Docker Hub account or set up a local registry. The simplest way I've found to bridge that gap is to point your terminal's Docker environment directly to Minikube’s internal daemon. Before you run your build command, you just need to execute this line in your terminal:


eval $(minikube docker-env)

Once you run that, your docker commands are now talking directly to the Minikube engine. You can go ahead and build your image as you normally would: docker build -t my-app:v1 .. Now, when you apply your Kubernetes deployment YAML, make sure your imagePullPolicy is set to IfNotPresent or Never. Because the image is now sitting inside the Minikube environment, Kubernetes will find it instantly and skip the external pull attempt.

If you’re worried about this getting messy, the best way to prevent future headaches is to keep your development workflow clean by using a specific tag for your local images. I always use :dev or :local for these builds so I never accidentally deploy a local test image to a production cluster. It’s a small habit, but it’s saved me from deploying broken code more times than I’d like to admit.

Hope this saves you from the same three-hour rabbit hole I fell down. Happy coding!

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 689 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的修改，我竟然乖乖地把 Image 打包、推到 Docker Hub，然後再在 Minikube 裡重啟 Pod 等它下載。那個下午，我盯著終端機看著 ImagePullBackOff 的紅色錯誤訊息循環跑了十幾次，螢幕上的進度條彷彿在嘲笑我的天真，那種「改一行程式碼要等五分鐘才能看到效果」的崩潰感，真的會讓人想把鍵盤砸了。

會發生這種事，其實是因為我們都忘了一個基本邏輯：Minikube 其實是一個跑在你電腦裡的「虛擬環境」。它有自己獨立的 Docker Daemon，跟你電腦本機的 Docker 根本不是同一個世界。所以當你執行 docker build 時，Image 是存在你電腦的 Docker 裡，但 Minikube 的那台虛擬機根本看不到，它當然只能無助地跑去遠端倉庫抓取，抓不到就只能崩潰給你看。

後來我終於受不了這種低效率的開發流程，發現其實根本不需要經過遠端倉庫。最簡單的一招，就是直接把你的 Shell 環境切換到 Minikube 內部的 Docker 環境。只要在終端機輸入這行指令：


eval $(minikube docker-env)

執行完後，你現在輸入的任何 docker 指令，都會直接作用在 Minikube 裡。這時候你再執行 docker build -t my-app:v1 .，Minikube 就會直接「看見」這個 Image。接下來，你只需要在 Kubernetes 的 YAML 設定檔裡，把 imagePullPolicy 改成 IfNotPresent，這樣 Kubernetes 就會優先使用本地已經存在的 Image，而不會再去檢查遠端倉庫了。

為了避免以後又犯這種錯，我現在養成了一個習慣，就是把這些開發用的 Image 加上特定的標籤，並且在開發環境的設定檔裡明確指定 imagePullPolicy: IfNotPresent。這能確保就算哪天我不小心把遠端版本蓋過去，Kubernetes 也會優先使用我手邊剛編譯好的版本，省去很多不必要的網絡等待時間。

現在我的開發流程順暢多了，再也不用為了測一個 API 改動而喝掉三杯咖啡，祝大家的部署之路也能少踩點坑！
