How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 689 votes

I still remember the first time I set up a local Kubernetes cluster. I’d spent all morning crafting a perfect Dockerfile, only to be met with that soul-crushing ImagePullBackOff error the moment I deployed my YAML. I honestly spent three hours convinced my registry credentials were broken, only to realize that Minikube had absolutely no idea my local images even existed because it was living in its own isolated bubble.

The reason you’re running into this is that Minikube runs inside a virtual machine or a separate containerized environment. When you run docker build on your terminal, that image is sitting in your host machine's Docker daemon. Minikube, however, is looking for images inside its own internal Docker daemon. It’s like trying to find a file on your computer while searching inside your neighbor’s laptop—the two environments just aren't talking to each other.

The fastest way I’ve found to fix this is to point your local terminal directly at the Minikube Docker daemon. By running a single command, you can redirect your local Docker CLI to build images straight into the Minikube environment. If you're on Mac or Linux, just run this in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build -t my-app:v1 . command you execute will build the image directly inside Minikube. You can verify it worked by running docker images—you’ll see your local images listed right there in the Minikube context. Just remember that you need to set your Kubernetes deployment's imagePullPolicy to IfNotPresent so that K8s doesn't try to go out to the internet looking for an image that only exists inside your cluster.

To keep things clean and prevent this frustration in the future, get into the habit of using the Minikube image loader utility for quick testing. Instead of switching your entire environment, you can just push an existing local image into Minikube with a single command: minikube image load my-app:v1. It’s saved me so much time when I’m just trying to iterate on a quick fix without reconfiguring my whole shell environment.

Hope this helps you get your cluster running without the headache. Happy coding!

別再為了測試把 Docker Image 推上 Docker Hub 了：Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 689 票

記得剛開始用 Minikube 做本地開發的時候，我真的快崩潰了。那時候我寫完一個微服務，為了測試一點點小改動，我得先 docker build，然後 docker push 到 Docker Hub，再切換回 Kubernetes 執行 kubectl rollout restart。最慘的是，網路慢的時候，我光是等那幾百 MB 的映像檔傳來傳去，半個下午就這麼沒了，有一次因為網路不穩，推到一半斷線，那天我真的差點把鍵盤砸了。

會遇到這種困擾，其實是因為我們對 Kubernetes 的架構有一點誤解。Kubernetes 的節點（Node）其實是一個獨立的環境，當你用 Minikube 啟動時，它其實是在你的電腦裡跑一個虛擬機或容器。簡單說，你電腦本機的 Docker daemon 和 Minikube 裡面的 Docker daemon 是「兩個世界的人」。當你叫 K8s 去拉一個映像檔時，它只會去它的那個小圈圈找，找不到就往外面的 Registry（像 Docker Hub）跑，根本看不到你電腦裡剛剛 build 好的那個影像。

後來我發現，其實不用那麼麻煩。最快的方法就是直接告訴 Minikube：「嘿，你要用的影像就在這裡，不用去外面找」。如果你是用 Docker 作為 Minikube 的 driver，最直覺的做法就是把你的環境變數指向 Minikube 內部的 Docker daemon。只要在終端機執行這行指令：


eval $(minikube docker-env)

執行完之後，你的終端機就會暫時「借用」Minikube 內部的 Docker 環境。這時候你再執行 docker build -t my-app:v1 .，這個影像就會直接出現在 Minikube 的肚子裡。接著，記得把你的 Deployment YAML 裡的 imagePullPolicy 改成 IfNotPresent，這樣 K8s 就會乖乖用本地的那個版本，不會再傻傻地跑去網路上抓了。

當然，如果你跟我一樣懶，不想每次開新視窗都要打一次指令，我強烈建議直接把它寫進你的 .zshrc 或 .bashrc 裡，或者乾脆養成習慣，在開發階段把 imagePullPolicy 設為 Never。這樣只要你一試圖拉取不存在的網路影像，K8s 就會直接報錯提醒你，避免你又浪費時間在等待上。

學會這招之後，開發速度真的快了不只一個檔次，希望你們也能早日脫離「推上去再拉下來」的無間地獄。
