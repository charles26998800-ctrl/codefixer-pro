React 18 Hydration Mismatch: Why Your SSR Is Breaking and How to Fix It

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in React 18; I was three hours deep into a Friday afternoon coffee-fueled coding session, convinced I’d finally perfected my server-side rendering setup. I spent the better part of two hours tearing my hair out, checking every single API call and prop, only to realize the culprit was a simple timestamp being generated differently on the server than on the client. It’s one of those classic "works on my machine" moments that makes you question your sanity until you realize the browser and the server are just seeing two different versions of the truth.

The reason this happens is actually quite logical once you peel back the layers of React 18. When you use SSR, the server generates the initial HTML and sends it to the browser. React then "hydrates" that HTML by attaching event listeners and turning it into a fully interactive app. The problem kicks in when the HTML the server sent doesn't perfectly mirror what the client-side code generates on its first pass. Maybe it's a random number, a date, or a browser-specific check like window.localStorage. If the server renders one thing and the client sees something else during that first render, React throws its hands up in frustration and wipes the server-rendered DOM to replace it with its own, which is exactly the performance hit we were trying to avoid in the first place.

When I finally tracked down the issue in my own project, I realized that I was trying to render a component that relied on the current time immediately upon mounting. To fix this, I had to ensure that the component didn't try to render client-specific logic until it was actually mounted in the browser. The most reliable way to handle this is by using a useEffect hook to toggle a state that tells React, "Hey, we’re actually on the client now."


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>{new Date().toLocaleTimeString()}</span> : <span>Loading...</span>}
    </div>
  );
};

By adding that isClient check, I ensured the server always renders the "Loading..." placeholder, which matches perfectly with the initial client render before the useEffect fires. Once the client takes over, the state updates, and the real content renders without triggering that nasty mismatch warning. It’s a simple pattern, but it’s saved me from countless headaches since.

The best way to prevent this from creeping back into your codebase is to audit your components for any "non-deterministic" data. If you’re using window, localStorage, or dynamic dates, wrap those specific pieces of UI in a client-only check or a custom hook that delays rendering until the hydration phase is complete. Keeping your server-rendered HTML strictly static until the hydration is finished is the golden rule for keeping React happy.

Hopefully, this saves you that Friday afternoon headache I had to endure. Let me know if you run into any other weird edge cases!

React 18 Hydration Error：那個讓我熬夜到凌晨的「伺服器與客戶端不對盤」惡夢

來源：Stack Overflow ↗ · 341 票

我還記得那天晚上，為了趕在產品上線前修好最後一個 SSR 功能，我滿懷自信地把程式碼推上測試機，結果瀏覽器控制台直接跳出一整片刺眼的紅字：Hydration failed because the initial UI does not match what was rendered on the server。當下我真的差點崩潰，明明在開發環境跑得好好的，怎麼一進到生產模式就變成了這種「伺服器說一套、瀏覽器做一套」的尷尬局面？那種看著螢幕發呆、懷疑是不是瀏覽器快取壞掉，結果發現是自己架構問題的無力感，真的是工程師職涯中最想刪除的記憶之一。

其實這問題的根本原因很單純，就是 React 18 變嚴格了。當我們使用 SSR 時，伺服器會先產生一份 HTML 發送給瀏覽器，然後瀏覽器端的 React 會嘗試「接管（Hydrate）」這份 HTML。但如果伺服器渲染出來的內容，跟瀏覽器第一次執行 JavaScript 後產生的內容有哪怕一點點不同，React 就會直接翻臉，認為這是不合法的狀態，乾脆直接重刷整個畫面。最常見的兇手就是 Date()、隨機數、或是依賴瀏覽器特有 API（像是 localStorage 或 window 物件）的邏輯，因為這些東西在伺服器跑的時候根本不存在或是值不一樣，結果導致兩邊的畫面兜不起來。

我那次踩坑後才發現，最簡單的解法就是讓元件「誠實」。既然我們知道瀏覽器端的邏輯在伺服器上會出錯，那就乾脆在伺服器渲染時先給它一個「安全」的預設值，等元件真的掛載（mount）到瀏覽器上後，再進行真正的渲染。我後來習慣用 useEffect 來處理這類依賴環境的邏輯，確保只有在瀏覽器環境下才會執行。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <span>這是只有瀏覽器才看得到的正確資料：{localStorage.getItem('key')}</span>
      ) : (
        <span>載入中...</span>
      )}
    </div>
  );
}

想要預防這種地獄輪迴再次發生，我現在寫元件時只要涉及到「可能會跟伺服器端結果不一致」的邏輯，都會下意識地先檢查環境。你可以試著安裝 use-is-browser 這類小工具，或是乾脆養成習慣，只要是瀏覽器特有的 API，一律包在 useEffect 或是 typeof window !== 'undefined' 的判斷式裡。只要讓伺服器跟瀏覽器在第一次碰面時看到一樣的內容，這討厭的紅字基本上就不會再來找你麻煩了。

祝大家寫程式都能順利一次編譯通過，別像我當年一樣在凌晨三點跟瀏覽器說悄悄話啊！
