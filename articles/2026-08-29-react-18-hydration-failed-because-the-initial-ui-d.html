Why React 18 Hydration Errors Are Driving You Crazy (And How to Fix Them)

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the dreaded "Hydration failed because the initial UI does not match" error in a React 18 project. I had just finished refactoring a dashboard to use Server-Side Rendering for that sweet SEO boost, and I was feeling pretty proud of myself until I refreshed the browser and saw my console turn into an absolute graveyard of red text. I spent three hours staring at my code, convinced I’d broken the entire build pipeline, only to realize I was just trying to display a dynamic timestamp that was literally a millisecond off between the server and the client.

The reason this happens is actually quite logical once you stop pulling your hair out. React expects the HTML generated by your server to be an exact, byte-for-byte match of what the client-side JavaScript produces when it first boots up. If you're using something like Date.now() or checking typeof window !== 'undefined' to conditionally render content, the server outputs one version, but the browser—having a slightly different environment—outputs another. When React tries to "hydrate" that static HTML into an interactive app, it sees the mismatch, panics, and throws the error instead of trying to guess which version is right.

When I finally tracked down the culprit in my own app, the fix was surprisingly simple: I had to delay the rendering of the mismatched content until the component had officially mounted on the client. By using the useEffect hook, I could force the component to wait until the hydration process was complete before injecting that dynamic data. Here is how I usually handle it now:


import { useState, useEffect } from "react";

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>Current time: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By setting a local state variable isClient to true only after the component mounts, I ensure that the server renders the "Loading..." state, and the client renders the exact same "Loading..." state initially. Once the hydration is finished, the client-side effect kicks in and swaps it for the actual dynamic content. It keeps the DOM trees perfectly synced, and the error disappears instantly.

To prevent this from becoming a recurring nightmare in your codebase, my best advice is to adopt a "server-first" mindset for your UI layout. If you absolutely need to render browser-specific data, like local storage values or dynamic timestamps, always wrap those specific elements in a client-only component or a guard clause that waits for the useEffect lifecycle. If you treat the server-rendered HTML as the "source of truth" and only layer interactivity on top of it, you’ll avoid these hydration mismatches almost entirely.

Good luck with the debugging, and I hope this saves you from those late-night frustration sessions. Catch you later!

React 18 Hydration 錯誤：當伺服器與瀏覽器「雞同鴨講」的崩潰時刻

來源：Stack Overflow ↗ · 341 票

記得幾個月前，我剛把專案升級到 Next.js 搭配 React 18，原本以為能享受效能提升的快感，結果打開網頁一看，Console 直接噴出一大串紅通通的 "Hydration failed" 錯誤。當下我真的差點崩潰，明明在開發環境看起來好好的，怎麼一到生產環境，UI 就直接原地爆炸？最痛苦的是，當你瘋狂重新整理頁面，想要抓出那個不一致的元素時，那個錯誤訊息就像在嘲笑你一樣，完全看不出到底是哪一行程式碼在搞鬼。

其實會發生這件事，最根本的原因就是「信任危機」。Next.js 在伺服器端渲染（SSR）時會先產生一份 HTML，然後送到瀏覽器端，React 再嘗試把這份靜態 HTML「掛載（Hydrate）」上互動邏輯。如果瀏覽器第一次渲染出來的內容，跟伺服器給的不一樣——哪怕只是多了一個空白字元、一個隨機生成的 ID，或是根據時間變化的內容——React 就會因為「這跟我預期的長得不一樣啊！」而直接放棄治療，噴出這個錯誤。這就像是你寄了一封信給朋友，結果信件在轉運過程中被修改了一個標點符號，朋友收到後覺得這根本不是你寫的，直接把信撕了。

我後來發現，最常見的兇手就是我在元件裡用了 new Date() 或者隨機數。因為伺服器渲染的那一毫秒跟瀏覽器執行時的毫秒一定不同，結果就是兩邊的 DOM 結構永遠對不起來。解決方法其實不難，就是讓 React 在第一次渲染時「閉嘴」，等瀏覽器確定準備好之後再顯示這些動態內容。我通常會寫一個簡單的 Hook 來處理：


import { useState, useEffect } from 'react';

function useHasMounted() {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  return hasMounted;
}

// 在元件中使用：
function MyComponent() {
  const hasMounted = useHasMounted();

  if (!hasMounted) return null; // 或者放個 Loading

  return <div>現在時間是：{new Date().toLocaleTimeString()}</div>;
}

透過這種方式，我們強迫 React 在伺服器端先別渲染那些會變動的內容，等到瀏覽器環境確定了，再把它們補上去，Hydration 錯誤自然就消失了。

要避免這種情況再次發生，建議大家平時在寫元件時，盡量保持「純粹」。如果你的元件輸出內容會受到環境變數、時間或隨機亂數影響，一定要習慣用這種「延遲渲染」的模式。另外，千萬別在元件的根目錄直接放那種會隨著環境改變的邏輯，不然下次又遇到這種整頁變成白畫面的慘劇，真的會想把電腦砸了。

希望這招能幫你脫離苦海，下次遇到這種莫名其妙的 bug 時，記得深呼吸，反正最後總會修好的啦！
