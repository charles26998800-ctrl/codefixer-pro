How to Fix the "digital envelope routines::unsupported" Error in React

Source: Stack Overflow ↗ · 2572 votes

I still remember the day I pulled a fresh React project from a legacy repository and tried to spin up the dev server, only to be slapped in the face with that cryptic OpenSSL error. I spent a good three hours convinced that my entire Node environment was corrupted, fruitlessly reinstalling everything from nvm to my global packages, before realizing it was just a simple compatibility mismatch. It's one of those classic "works on my machine" moments that turns out to be a total trap if you’ve recently upgraded your Node version.

This annoying error pops up because of a significant change in how Node.js handles encryption. When you updated to Node 17 or higher, the project’s build tools—specifically Webpack—started trying to use an older, less secure hashing algorithm that Node decided to deprecate in favor of OpenSSL 3.0. Because your project’s dependencies are likely relying on older scripts that haven't been updated to support these modern security standards, the whole build process just crashes before it even has a chance to start.

The quickest way I’ve found to resolve this without needing to downgrade your entire Node environment is to force Node to use the legacy OpenSSL provider. You can do this by setting an environment variable called NODE_OPTIONS before your start command runs. If you’re on a Mac or Linux machine, just open your package.json file and modify the start script like this:


"scripts": {
  "start": "react-scripts --openssl-legacy-provider start",
  "build": "react-scripts --openssl-legacy-provider build"
}

If you’re working on Windows using PowerShell, the syntax is a bit different, and you might prefer setting the variable globally for the terminal session by running $env:NODE_OPTIONS = "--openssl-legacy-provider" before you execute your build command. Once you add that flag, your build tools will stop complaining and the dev server should fire right up.

Moving forward, the best way to prevent this headache is to keep a close eye on your project's engines field in your package.json file. By explicitly defining the Node version your project requires, you ensure that you or your teammates don't accidentally jump to a newer version of Node that isn't compatible with your current build configuration. It’s a small bit of configuration that saves a massive amount of debugging time down the road.

Hope this gets your project back on track and saves you that three-hour headache I dealt with. Happy coding!

救命！跑個 React 專案怎麼就炸了？Node.js 的 OpenSSL 升級之亂

來源：Stack Overflow ↗ · 2572 票

那天我剛接手一個舊專案，想說先跑個 npm start 確認環境沒問題，結果終端機直接噴出一大串紅字，最後一行寫著 error:0308010C:digital envelope routines::unsupported。我看著那行錯誤訊息，心裡真的是涼了半截，原本想說五分鐘就能搞定的環境建置，結果在那邊卡了一整個下午，甚至一度懷疑是不是我電腦壞了，還重裝了兩次 Node.js，那種「明明程式碼沒動，為什麼就是跑不動」的無力感，真的是工程師最想摔鍵盤的瞬間。

其實會發生這個問題，是因為 Node.js 17 版本之後升級了底層的 OpenSSL 3.0，但我們平常在用的那些 Webpack 舊版本（通常是 v4）還在使用舊版的加密演算法。簡單來說，就是 Node.js 換了一套更嚴格的資安標準，但我們舊專案的打包工具還在用「老派」的寫法，兩邊溝通不良，Node.js 一看覺得這加密方式太老舊直接拒絕執行，這才導致了這場災難。

好在解決方法其實很單純，我們只需要告訴 Node.js：「嘿，請暫時放寬一點標準，讓我跑一下這舊專案」。最快的解法就是設定一個環境變數 NODE_OPTIONS，讓它強制使用舊版的加密模式。如果你是用 Mac 或 Linux，直接在終端機輸入這行：


export NODE_OPTIONS=--openssl-legacy-provider

如果是 Windows 的 PowerShell 使用者，指令會長這樣：


$env:NODE_OPTIONS = "--openssl-legacy-provider"

設定完之後，再試著跑一次 npm start，通常就能順利起飛了。當然，如果你不想每次開終端機都要敲一次指令，直接把這行加到 package.json 裡的 scripts 區塊，像是 "start": "react-scripts start" 改成 "start": "react-scripts --openssl-legacy-provider start" 也是個不錯的懶人作法。

為了避免以後再被這種環境問題搞到崩潰，我現在都會養成習慣，在專案目錄下放一個 .nvmrc 檔案，明確指定該專案對應的 Node.js 版本。畢竟與其在那邊修補加密模組的相容性，不如直接用適合的版本來跑，才是最穩當的做法。

希望這招能幫你從紅字地獄中解脫，趕快去把專案跑起來吧！
