How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 690 votes

I remember back when I was first getting comfortable with Kubernetes, I spent a solid three hours banging my head against the wall because my pods kept stuck in ImagePullBackOff. I was convinced I’d mistyped the tag, but no—I had simply built the image on my laptop and assumed Minikube would magically "see" it inside its own isolated VM. It’s a classic rite of passage for every K8s developer, and honestly, it’s one of the most annoying hurdles when you’re just trying to iterate quickly on a local feature.

The reason this happens is pretty straightforward: Minikube runs inside its own isolated environment, usually a virtual machine or a separate container. When you run docker build on your host machine, that image lives in your host's Docker daemon. Minikube, however, has its own internal Docker daemon. They aren't talking to each other by default, so when your pod tries to pull an image, the Kubelet looks inside the Minikube environment, finds nothing, and tries to reach out to a remote registry that doesn't have your local changes.

The cleanest way I’ve found to bridge this gap is by pointing your local terminal directly at the Docker daemon inside Minikube. Instead of building on your machine and trying to move the image, you just tell your shell to use the one living inside the cluster. You can do this by running a simple command:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside Minikube’s environment. After that, you just need to make sure your Kubernetes deployment manifest has imagePullPolicy: IfNotPresent set. This tells Kubernetes to check for the image locally before trying to pull it from the internet, and since it’s already sitting there, your pod will spin up instantly. Just remember that if you open a new terminal window, you’ll need to run that eval command again, as it only affects your current session.

To keep this from becoming a recurring headache, I’ve started using a simple naming convention for my local images. I always prefix them with something like local/ or dev/ and explicitly set the imagePullPolicy to IfNotPresent in all my development YAML files. It’s a small habit, but it saves me from accidentally pulling an old version from Docker Hub when I’m deep in a debugging session.

Hope this saves you the three hours of frustration I went through. Happy containerizing!

別再把 image 推到 Docker Hub 了！Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，我為了測試一個小小的修改，每次改完程式碼都要 build 一次 image，再瘋狂 push 到 Docker Hub，然後在 Minikube 裡重新 pull 下來。最崩潰的是，網速慢的時候，我看著終端機顯示 Pulling image... 那幾行字，真的會氣到想去泡杯咖啡甚至直接把電腦蓋起來。有一次我為了改一行 log，重複這個流程搞了整整兩小時，最後才發現只是少加了一個環境變數，當下真的差點要把鍵盤給砸了。

會發生這種「白忙一場」的慘劇，其實是因為 Minikube 本質上是一個跑在虛擬機（VM）或容器裡的獨立環境。你電腦上的 Docker daemon 跟 Minikube 內部的 Docker daemon 根本是兩個不同的世界，當你執行 docker build 時，映像檔存在你本機的 Docker，但 Minikube 的節點根本看不見，它只會乖乖去遠端 Registry 找。如果你沒設好，它當然找不到，然後拋出那個讓人心煩的 ImagePullBackOff。

後來我發現，其實根本不用這麼麻煩，只要讓 Minikube 的環境變數直接指向你本機的 Docker daemon 就行了。最簡單的方法，就是在 build image 之前，先在終端機執行下面這行指令：


eval $(minikube docker-env)

執行完後，你現在所在的終端機視窗就會直接跟 Minikube 內部的 Docker 溝通。這時候你再執行 docker build -t my-app:v1 .，這個映像檔就會直接「變」進 Minikube 的環境裡。記得要在你的 Deployment YAML 檔裡面，把 imagePullPolicy 設定成 IfNotPresent，不然 Kubernetes 還是會雞婆地想去遠端抓圖，導致你的本地映像檔被忽略。

為了以後不要再為了這種環境設定浪費生命，我現在都會養成一個習慣：只要是在開發階段，我會直接把這個 eval 指令寫在我的 Makefile 裡，或者乾脆用 Skaffold 這類工具來自動化處理。這樣不管怎麼改程式碼，只要我打個 make deploy，Skaffold 就會幫我處理好同步，不用再手動去切換環境變數，真的省心不少。

反正開發嘛，時間就是要花在寫 code 上，而不是花在跟 Docker daemon 鬥智鬥勇，希望能幫大家省下那些無謂的等待時間囉！
