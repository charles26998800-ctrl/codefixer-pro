How to Fix the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the dreaded "Hydration failed" error in my terminal; I was mid-coffee, thinking I’d finally nailed my SSR implementation, only for my browser console to explode in red text. I spent three hours chasing ghosts, convinced my API routes were broken, before realizing it was just a simple mismatch between what my server thought the time was and what my browser decided to render. It’s one of those bugs that makes you feel like you’re losing your mind because the code looks perfectly fine, yet React is throwing a tantrum.

The reason this happens is actually quite logical once you peek under the hood. When you use Server-Side Rendering (SSR) in Next.js, the server generates the initial HTML based on the state of your application at that exact moment. When that HTML hits your browser, React tries to "hydrate" it—basically attaching event listeners and turning that static HTML into a living, breathing React component. If the code running in the browser produces even a slightly different output than what the server sent—like a timestamp, a random ID, or a conditional check based on window or localStorage—React panics. It sees the mismatch, assumes the server-rendered content is stale or wrong, and throws the hydration error to protect you from a broken UI state.

I fixed this by realizing that I needed to force the component to wait until it was safely mounted on the client before rendering the dynamic content. If you have code that relies on browser-only APIs or dynamic data that isn't available during the build/request phase, you have to defer that render. I usually implement a simple useEffect hook to toggle a state variable once the component has mounted. Here is how I usually structure the fix:


import React, { useState, useEffect } from "react";

const MyComponent = () => {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      <h1>Welcome to my site</h1>
      {isClient ? (
        <p>This will only render on the client: {new Date().toLocaleTimeString()}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
};

By adding that isClient check, I ensure the server renders the "Loading..." fallback, and the browser replaces it with the dynamic content immediately after the first paint. This keeps the server and client in perfect sync, which is exactly what React needs to stay happy.

To prevent this from becoming a recurring headache, my best advice is to treat your top-level component renders as "pure" as possible. If you need to use browser-specific logic, keep it strictly inside useEffect or within components that you know won't be rendered until after the initial mount. If you stick to that, you'll save yourself a world of debugging pain.

Hope this clears up the confusion and helps you get your app back on track. Happy coding!

被 React Hydration Error 搞到懷疑人生？其實兇手通常只有這幾個

來源：Stack Overflow ↗ · 341 票

那天我為了趕在週五下班前把 SSR 功能搞定，對著螢幕瘋狂除錯，結果一打開瀏覽器控制台，滿滿的紅色「Hydration failed」警告直接噴我一臉。我當下心裡真的只有一個想法：「明明程式碼看著都沒問題，為什麼伺服器給的 HTML 跟瀏覽器跑出來的不一樣？」那種看著螢幕發呆、懷疑自己是不是寫錯程式語言的無力感，真的是工程師職涯中最想原地消失的時刻之一。

其實這問題的根本原因很單純，就是 React 在玩「大家來找碴」。當你在使用 Next.js 或其他 SSR 框架時，伺服器會先產生一份 HTML 傳給瀏覽器，然後瀏覽器端的 React 會嘗試「接手（Hydrate）」這份頁面。如果伺服器渲染出來的內容，跟瀏覽器第一次執行 JavaScript 產生的內容有一丁點誤差，React 就會直接大崩潰，拋出這個錯誤給你。最常見的兇手通常是時間戳記、隨機亂數，或是瀏覽器特有的 API（像是 window 或 localStorage），因為這些東西在伺服器端跟客戶端跑出來的結果絕對不同，React 一比對發現「咦？怎麼不一樣？」，就直接報錯了。

我後來發現，最快解決的方法就是讓那些「會變動的內容」延後渲染。我會用 useEffect 來確保元件只在客戶端掛載完成後才顯示。舉個例子，如果你要在頁面上顯示當前時間或是使用者是否登入，千萬不要直接在 JSX 裡寫 new Date().toLocaleString()，這保證會掛。你可以像我這樣寫：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? <span>現在時間是：{new Date().toLocaleString()}</span> : <span>載入中...</span>}
    </div>
  );
}

這樣一來，伺服器只會拿到那個「載入中...」的純文字，而真正的動態內容則留給瀏覽器去跑，兩邊的基準點對齊了，惱人的錯誤訊息也就跟著消失了。

至於要怎麼預防下次再踩進這個坑？我覺得最有效的一招就是養成檢查「伺服器端依賴」的習慣。只要你用到 window、document 或者任何會隨時間變動的邏輯，心裡就要響起警報聲，立刻把這些邏輯丟進 useEffect 裡處理。只要確保渲染邏輯在伺服器跟客戶端是一致的，你就能省下大把的時間，不用再跟這些莫名其妙的報錯搏鬥啦。

希望這篇能幫你少掉幾根頭髮，下次遇到這種問題先別慌，檢查一下是不是哪裡偷用了瀏覽器專屬的變數就好。
