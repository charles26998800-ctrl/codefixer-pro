How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster with Minikube. I had this perfectly crafted container image sitting right there on my machine, and for some reason, I spent three hours fighting ImagePullBackOff errors because I didn't realize Minikube was looking at a remote registry instead of my local daemon. I actually ended up pushing a private image to Docker Hub just to test a two-line code change, which is honestly the most embarrassing thing I’ve done as a developer.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside its own isolated virtual machine or container. Because it’s an isolated environment, it doesn't automatically "see" the images stored in your host machine’s Docker daemon. When you run kubectl apply, your Minikube node tries to pull the image from a remote registry like Docker Hub or ECR. If the image isn't there, it fails, completely ignoring the fact that you’ve got the exact same image tag sitting right on your laptop.

The absolute cleanest way I’ve found to solve this is by pointing your local terminal directly to the Docker daemon running inside the Minikube virtual machine. By doing this, any docker build command you run will build the image directly inside the Minikube environment, making it immediately available to your pods. Before you run your build command, just execute this in your terminal:


eval $(minikube docker-env)

Once you run that, your local shell is "hooked" into the Minikube Docker socket. Now, when you run docker build -t my-app:latest ., the image is built inside the VM. You can verify it by running docker images—you'll see your custom image listed there, and your Kubernetes deployment will pick it up instantly. Just remember that if you open a new terminal tab, you’ll need to run that eval command again because it only affects your current session.

To keep things running smoothly and prevent these headaches in the future, my biggest tip is to always set your deployment's imagePullPolicy to IfNotPresent. By default, if your image tag is latest, Kubernetes will try to pull it from the registry every single time. If you use IfNotPresent, it’ll check the local cache first, which saves you from those annoying connectivity issues and makes your local development cycle feel lightning-fast.

Hope this saves you from the same three-hour rabbit hole I went down. Happy coding, and may your deployments always stay in the Running state!

別再把 Image 推上 Docker Hub 了！在 Minikube 使用本地映像檔的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的 API 改動，我竟然傻傻地先把 Image 推送到 Docker Hub，然後再讓 Minikube 從遠端拉下來。那時候網路慢得要命，看著終端機顯示 ImagePullBackOff 的紅色錯誤訊息，心裡真的是滿滿的無奈，當時差點直接把筆電闔上不幹了。這種「改一行程式碼、等五分鐘下載」的開發循環，簡直就是浪費生命的極致，後來我才發現，原來自己一直都在走冤枉路。

其實問題的核心很單純，Minikube 是一個跑在虛擬機或容器裡的獨立環境，它的 Docker Daemon 和你本機電腦上的 Docker Daemon 根本是兩碼子事。當你在本地終端機輸入 docker build 時，映像檔是存進了你電腦的 Docker，而 Minikube 根本看不見那邊，它只認得自己肚子裡的那些映像檔。所以不管你在外面蓋得再漂亮，Minikube 只要去自己的倉庫找不到東西，就會跑去遠端抓，這就是為什麼我們老是卡在下載進度條的原因。

最快、最不囉唆的解法其實就是直接把你的 Docker 環境「導向」給 Minikube。只要你在終端機執行下面這行指令，你的 docker 指令就會暫時變成在控制 Minikube 內部的 Docker 環境：


eval $(minikube docker-env)

執行完之後，你現在下的 docker build -t my-app:v1 . 就會直接把映像檔蓋進 Minikube 的肚子裡，完全不需要經過網路傳輸。接著，記得把你的 Kubernetes Deployment YAML 檔案裡的 imagePullPolicy 改成 IfNotPresent，這樣 K8s 就會優先使用你剛才蓋好的本地版本，不會跑去網路上亂抓。

如果哪天你不想用這個模式了，或者怕它影響到你本機開發其他專案，只要重開一個終端機視窗，或者執行 eval $(minikube docker-env -u) 就可以切換回來。

為了避免以後又被這種問題搞到心態炸裂，我現在養成一個習慣，就是只要在開發階段，我會習慣把 imagePullPolicy 設為 IfNotPresent 作為標準配置。這樣就算哪天網路斷了，或者我忘了切換環境，也不會一直噴出那些煩人的錯誤訊息。

學會這招之後，開發速度真的快了不只一個檔次，希望你們也能早日脫離「等待下載」的苦海！
