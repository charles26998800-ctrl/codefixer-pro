How to Undo Your Last Git Commit Without Losing Your Work

Source: Stack Overflow ↗ · 27236 votes

I still remember the first time I accidentally committed a massive config file containing my local database credentials. I spent three hours sweating, convinced I’d just exposed my entire dev environment to the internet, all because I typed git commit -a instead of checking my staged files. It’s a rite of passage for every developer, but that sinking feeling in your stomach when you realize you’ve committed the wrong thing is something I never want to experience again.

The root cause of this panic is usually just a lack of attention to the staging area. We often get into a "flow state" where we’re smashing keys, running git add . without a second thought, and firing off commits before we’ve actually verified what’s going into the history. Git assumes you know what you’re doing, so when you tell it to commit, it blindly bundles up whatever you’ve staged. Since these commits are only living in your local repository, the good news is that you have total control to rewrite that history before anyone else sees it.

When I need to fix this, I rely on git reset. If you just want to undo the commit but keep the files you changed sitting in your working directory—so you can fix them or unstage them—you want a "soft" reset. I run this command in my terminal:


git reset --soft HEAD~1

This command moves your branch pointer back one step, effectively vaporizing the commit, but it keeps all your hard work right there in the staging area. If you realize you shouldn't have touched those files at all and you want to completely destroy the changes from that commit, you use the "hard" reset. Just be careful, because this is destructive:


git reset --hard HEAD~1

Using the --hard flag tells Git to discard everything in that commit and reset your working directory to match the state of the previous commit. I only use this when I'm absolutely sure that I don't want to see those changes ever again.

To keep this from happening, I started using the git status command like a nervous tick. Before I run any commit, I force myself to type git status to see exactly which files are staged. It takes five seconds, but it’s saved me from countless headaches and late-night reverts.

Hope this saves you some stress on your next deployment. Happy coding!

不小心 Commit 了垃圾檔案？別慌，Git 救得回來

來源：Stack Overflow ↗ · 27236 票

記得剛入行那年，有次趕著下班，沒檢查就直接 git commit -am "fix bugs"，結果一送出才發現我把幾百個測試生成的 log 檔和隱私設定檔全塞進去了。當時看著終端機視窗，心臟差點跳出來，那種「慘了，我該不會把公司機密傳到遠端吧」的崩潰感，真的會讓人冷汗直流。最痛苦的是，我已經 Commit 下去了，看著 Git 歷史紀錄裡那個孤零零的錯誤 Commit，真的會覺得人生好難。

其實這問題的本質很單純，Git 的架構讓我們在 Commit 到遠端伺服器前，本地端的歷史紀錄其實是「可塑的」。當你執行 git commit 時，Git 只是把你的修改打包在本地的倉庫裡，只要你還沒執行 git push，這些錯誤就還在你的電腦上，隨時可以把它們「拆掉」。

如果你只是想撤銷最後一次 Commit，但想保留檔案修改（也就是讓檔案退回到還沒 Commit 的狀態，繼續在工作區待著），我最常用的指令就是 git reset --soft HEAD~1。這個指令就像是按下時光倒流鍵，把那個 Commit 拆開，但你的程式碼全都完好無缺地留在原地，你可以重新 git add 正確的檔案，再一次乾乾淨淨地 Commit。

如果你的情況更糟，連檔案內容都想直接丟掉、不想留任何痕跡，那就用 git reset --hard HEAD~1。這招非常兇狠，它會直接把那個 Commit 以及該次修改的檔案全部刪除，讓你的程式碼回到上一個 Commit 的狀態。每次下這個指令我都會深呼吸一次，因為如果檔案沒備份好，是真的會直接消失的，那種眼睜睜看著程式碼蒸發的感覺，真的會讓人懷疑人生。

要預防這種慘劇，我後來養成了一個壞習慣，就是每次 Commit 前一定要打 git status 看一下清單。如果覺得手動檢查太麻煩，其實可以善用 git commit -p（patch mode），它會一個一個問你哪些修改要加入，這樣就算想偷懶全選，也會在確認過程中發現自己不小心加了什麼奇怪的檔案進去。

學會這幾招後，至少下次手滑的時候，不用再對著螢幕乾瞪眼了。祝大家以後的 Git 紀錄都乾乾淨淨，再也不用體驗那種心臟漏跳一拍的恐懼感啦！
