How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster with Minikube, feeling pretty proud of myself until I tried to deploy my first custom image. I spent three hours banging my head against the wall because my pods kept stuck in ImagePullBackOff, despite me staring directly at the local image in my terminal. I was convinced I’d messed up my registry credentials or some obscure networking config, only to realize I was essentially trying to show a photo to someone standing in a different room while holding it behind my back.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside its own isolated virtual machine or container environment. When you run docker build on your host machine, that image lives in the Docker daemon on your laptop, but the Minikube cluster has its own, separate Docker daemon inside its VM. When Kubernetes tries to pull an image, it asks the Minikube daemon, which naturally looks at its own internal list, finds nothing, and tries to reach out to the external registry. Since your image isn't pushed to Docker Hub or ECR, the whole thing falls apart.

The most straightforward way I’ve found to fix this is by pointing your local terminal to the Docker daemon running inside Minikube. By running a single command, you can make your host's Docker CLI talk directly to Minikube's engine, meaning any build you perform happens right where the cluster can see it. Just run this in your terminal before you build your image:


eval $(minikube docker-env)

Once you’ve run that, go ahead and build your image as usual: docker build -t my-app:v1 .. Now, when you deploy your YAML file, make sure your imagePullPolicy is set to IfNotPresent or Never. If you leave it as Always, Kubernetes will try to reach out to the internet to verify the image, which will fail because your image is local to the VM, not the public web.

To prevent this headache in the future, I always stick to a simple rule: keep your image tags explicit. If you're constantly iterating, don't just use latest because Kubernetes might get confused if it sees a local image and tries to reconcile it with a remote one. If you ever find yourself getting frustrated with the eval command, you can also use minikube image load my-app:v1, which copies the image from your host daemon into the Minikube environment without needing to switch your environment variables.

Hope this saves you a few hours of debugging and gets your pods running on the first try. Happy coding!

別再把映像檔推到 Docker Hub 了！Minikube 本地開發的省力技巧

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 那陣子，為了測試一個簡單的 API 改動，我傻傻地把 Docker Image build 完就 push 到 Docker Hub，然後再在 Minikube 裡 pull 下來。結果那天網路剛好慢到想哭，光是等待上傳下載，我就在電腦前喝了三杯咖啡，甚至還懷疑人生地想著：「難道這就是雲端原生開發的代價嗎？」那種明明程式碼只改了一行，卻要花十分鐘等部署的無力感，真的會讓人想直接把電腦砸了。

會遇到這種卡關，其實是因為 Minikube 本質上是一個跑在虛擬機或容器裡的獨立環境。當你在終端機打 docker build 時，映像檔是存在你本機的 Docker Daemon 裡，但 Minikube 根本看不見這個「隔離區」。對它來說，它只認得 Registry 裡面的東西，所以除非你透過網路下載，否則它就是會報 ErrImagePull 給你看，看著那個錯誤訊息不斷閃爍，真的會讓人滿肚子火。

後來我發現，其實根本不需要繞遠路。最快的方法就是直接把你的 Docker 環境指向 Minikube 內部的 Daemon。只要在終端機輸入這行指令：


eval $(minikube docker-env)

執行完之後，你再跑 docker build -t my-app:v1 .，這個映像檔就會直接「長」在 Minikube 的肚子裡了。這時候你只要把 Deployment YAML 檔裡的 imagePullPolicy 改成 IfNotPresent，Kubernetes 就會乖乖地優先使用本地映像檔，完全不需要經過網路傳輸。這感覺就像是把檔案直接丟進去一樣順暢，再也不用浪費時間跟 Docker Hub 的伺服器磨蹭。

如果不想每次開新視窗都要打一次指令，建議直接把它寫進你的 .zshrc 或 .bashrc 裡，或者乾脆養成習慣，在開始開發前先執行一下這行。另外，為了避免 Kubernetes 真的跑去網路上抓舊版本，記得一定要把 imagePullPolicy 設為 IfNotPresent，這是我踩過最多次坑的地方，沒改這行的話，就算你本地已經 build 了最新版，它還是會因為抓不到最新的 tag 而在那邊跟我鬧脾氣。

學會這招之後，開發效率真的快了不只一個檔次，總算不用再為了測試一個改動而浪費一整天的生命了。
