Stop Pushing to Docker Hub: How to Use Local Images with Minikube

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster. I spent three hours pulling my hair out because I kept changing a single line of code in my Go service, rebuilding the image, and watching Kubernetes sit there in ImagePullBackOff hell. I was convinced something was wrong with my YAML, not realizing I was essentially trying to bake a cake in a different kitchen than the one I was standing in.

The root cause of this headache is simple: Minikube runs inside its own isolated environment, usually a virtual machine or a separate container. When you run docker build on your laptop, that image lives in your host’s Docker daemon. Minikube’s node, however, has its own independent Docker daemon. When you ask Kubernetes to pull my-app:latest, it looks inside its own internal registry, fails to find it, and tries to reach out to a public registry like Docker Hub. Since you haven't pushed your experimental changes yet, the pod simply fails to start.

The cleanest way I’ve found to fix this is to point your local terminal directly at the Docker daemon living inside the Minikube node. Instead of fighting with registries, you can run a single command to sync your shell environment. Just execute this in your terminal:


eval $(minikube docker-env)

Once you run that, any docker build command you issue will actually build the image directly inside the Minikube cluster. Now, when you run your kubectl apply command, the cluster sees the image is already present locally and starts your pods instantly. Just remember that if you open a new terminal window, you’ll need to run that command again, or your builds will go back to your host machine. If you’re on a newer version of Minikube, you can also use the minikube image load command, which is a bit slower but works perfectly if you don't want to mess with your environment variables.

To keep this from biting you again, always set your imagePullPolicy to IfNotPresent in your deployment YAML files. By default, if you use the latest tag, Kubernetes often tries to pull the image from the registry every time the pod restarts. Setting this policy forces the cluster to check its local cache first, which is exactly what you want during local development.

Happy hacking, and enjoy the speed boost you get from skipping those registry pushes!

為什麼 Minikube 總是抓不到我的 Local Image？教你優雅解決這場災難

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了測試一個微小的程式碼改動，硬是把 Docker image 推到 Docker Hub 再重新 pull 下來，來回折騰了快半小時。當時我看著終端機顯示 ImagePullBackOff 的紅字，整個人簡直快崩潰，心想：「我明明就在這台電腦上把 Image 建好了，為什麼 Minikube 就是裝作沒看到它！」那種感覺就像是你在家裡明明把鑰匙放在桌上，出門前卻怎麼找都找不到，最後才發現它一直都在你的口袋裡。

其實這背後的道理很簡單，Minikube 雖然是跑在你的電腦上，但它骨子裡其實是一個獨立的虛擬機（或是容器環境），它有自己獨立的 Docker daemon。當我們在開發機的終端機執行 docker build 時，Image 是存在你主機的 Docker 裡，而 Minikube 那邊的 Docker 根本看不見你的主機。這就是為什麼你明明 build 好了，K8s 卻還是堅持要從遠端倉庫抓取，然後因為抓不到而崩潰。

解決這個問題最快的方法，就是直接把你的 Docker 環境「導向」到 Minikube 裡面。你只要在終端機輸入這一行指令：


eval $(minikube docker-env)

執行完之後，你現在下的任何 docker build 指令，都會直接在 Minikube 的環境裡產生 Image，K8s 就能直接讀取到它們。不過要記得，如果你想切換回本機的 Docker 環境，記得要重開一個終端機視窗，或者執行 eval $(minikube docker-env -u)。另外，如果你不想每次都切換環境，也可以在寫 Deployment 的時候，把 imagePullPolicy 設定成 IfNotPresent，這樣只要 Image 已經在 Minikube 的快取裡，它就不會再去網路上瞎忙了。

說到預防這類問題，我現在養成了一個習慣，就是把 Image 的 tag 標註得非常清楚。千萬不要只用 latest，因為當你用 latest 的時候，K8s 有時候會因為快取的緣故，即便你更新了 Image，它還是會抓到舊的版本，那種「明明改了卻沒生效」的挫折感，真的會讓人想把鍵盤拆了。給每個版本一個明確的編號，你會發現開發體驗真的會順暢很多。

希望這招能幫你省下不少推送到 Docker Hub 的時間，別再讓 ImagePullBackOff 佔用你的寶貴開發時光了！
