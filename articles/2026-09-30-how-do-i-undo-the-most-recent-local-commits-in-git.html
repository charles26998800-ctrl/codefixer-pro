How to Undo Your Most Recent Local Git Commits Without Losing Your Mind

Source: Stack Overflow ↗ · 27242 votes

I still remember the first time I accidentally committed a .env file containing my actual AWS production keys. My heart sank into my stomach, and I spent a solid hour frantically Googling commands while sweating through my shirt, convinced I was about to be fired for a security breach. It’s a rite of passage for every developer, and if you haven’t had that "oh no" moment yet, just wait—you’ll get there eventually.

The reason this happens is pretty simple: Git is designed to be a persistent history tracker. When you run git commit, you’re essentially snapping a permanent picture of your project state in your local history. Git doesn't "know" that you made a mistake; it just assumes you’re an expert who meant to include those specific files. Because you haven't pushed to the remote server yet, your local history and the remote branch have diverged, and that’s where the confusion usually starts.

When I need to fix this, I rely on git reset. The command you use depends entirely on whether you want to keep the work you did or throw it away completely. If I just made a typo in the commit message or forgot to add a single file, I use the --soft flag. This keeps your changes staged and ready to commit again, which is a lifesaver when you just need a quick do-over:


git reset --soft HEAD~1

If I messed up more significantly and want to keep my changes in the working directory but unstage them—essentially "un-committing" but keeping the files modified—I go with the default mixed reset:


git reset HEAD~1

However, if I realize the code I just wrote is total garbage and I want to nuke the entire commit and the files associated with it, I use the hard reset. Be careful here, because this is the nuclear option. Once you run this, those changes are gone forever:


git reset --hard HEAD~1

To prevent this from happening again, I’ve made it a habit to use git status like it’s a nervous tic. Before I run any commit command, I double-check the list of files under "Changes to be committed." If you’re really paranoid, you can also set up a pre-commit hook that scans for sensitive patterns, but honestly, just slowing down for five seconds to read the terminal output has saved me more times than any script ever could.

Hope this helps you clean up your git history without any more panic attacks. Happy coding!

救命！我不小心 commit 了不該 commit 的東西，怎麼辦？

來源：Stack Overflow ↗ · 27242 票

還記得那是個週五下午，我正準備趕在下班前把最後一個功能收尾，結果手滑加上腦袋當機，直接把一大堆還在測試中的 Debug Log 和敏感設定檔全都 commit 上去了。當我按下 git commit 的那一刻，看著螢幕上顯示的「1 file changed, 50 insertions」，心臟真的漏跳了一拍，那種「完了，這下要爆炸了」的恐懼感，真的是身為工程師最想刪除的人生片段之一。

其實會發生這種慘案，通常就是我們對 Git 的「暫存區（Staging Area）」太過自信。當我們使用 git add 把檔案送進去，再用 git commit 封裝起來時，Git 就會把這些變更凍結成一個版本。問題就在於，我們往往以為 commit 就像發送訊息一樣不可逆，但其實 Git 的強大之處就在於它允許你「假裝這件事沒發生過」，前提是你還沒把它推送到遠端伺服器（Remote）。

如果只是想撤銷最後一次 commit，但想保留剛剛寫好的那些代碼變更，方便你重新整理後再提交，我最常用的指令就是 git reset --soft HEAD~1。這一招就像是按下「復原」鍵，它會把那個 commit 拆掉，讓你所有的檔案變更回到「已暫存」的狀態，這時候你就可以安心地把那些不該出現的檔案從暫存區移出來。


# 撤銷 commit，但保留檔案變更在暫存區
git reset --soft HEAD~1

但如果你今天是因為剛剛寫了一坨垃圾代碼，想徹底斷絕關係，連檔案變更都不想要了，那就要狠一點，直接用 git reset --hard HEAD~1。這指令會把你的狀態直接拉回上一個 commit，所有還沒送出去的改動都會瞬間蒸發，這時候真的會有一種「世界清靜了」的感覺。不過要提醒一下，用 --hard 之前一定要確認裡面真的沒東西是你之後還會想找回來的，否則你會哭出來。

為了避免這種心驚膽跳的時刻，我現在養成了一個習慣，就是每次 commit 前一定會先打 git status 看一眼。雖然聽起來很基本，但真的能救命；如果還是怕手殘，可以試著用 git add -p 來逐行檢查變更，這樣就算真的改壞了，至少你也是在檢查的當下就發現，而不是等到 commit 完才在電腦前崩潰。

Git 的指令雖然有時候很讓人頭大，但搞懂這些撤銷操作後，真的會覺得人生輕鬆不少。大家以後手滑的時候先別慌，冷靜下來把 commit 拆掉就沒事了！
