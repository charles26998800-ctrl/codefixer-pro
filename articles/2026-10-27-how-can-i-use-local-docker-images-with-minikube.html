How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 690 votes

I remember back when I first started tinkering with Kubernetes, I spent a solid three hours banging my head against the wall because my pods were stuck in ImagePullBackOff. I was convinced my YAML was perfect, only to realize I was trying to reference a local image that Minikube had absolutely no idea existed. It’s one of those classic "aha!" moments that every developer hits when they move from standard Docker workflows to local K8s clusters, and it’s honestly incredibly frustrating until you realize how the architecture actually talks to itself.

The reason this happens is simple: Minikube runs inside its own virtual machine or container, which is completely isolated from your host machine's Docker daemon. When you build an image on your laptop, it sits in your host's Docker engine. When you tell Kubernetes to pull an image, it looks inside the Minikube node’s internal registry, not your local one. Since the image isn't there, K8s tries to pull it from a remote registry like Docker Hub, fails, and leaves you staring at a crash loop.

To fix this, you don't need to waste time pushing images to a remote registry just to pull them back down five seconds later. The easiest way to bridge this gap is to point your local shell to the Docker daemon running inside Minikube. By running the following command in your terminal, you tell your local Docker client to talk directly to the Minikube engine:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube environment. You can verify it worked by running docker images—you should see your freshly built image right there in the list. Now, when you deploy your Kubernetes manifest, make sure your imagePullPolicy is set to IfNotPresent or Never. If you leave it as Always, Kubernetes will try to reach out to the internet to verify the image, which will break everything all over again.

To keep your workflow clean and prevent these headaches in the future, I always recommend using a specific naming convention or a dedicated tag for local testing. If I’m working on a feature, I’ll tag it my-app:dev-local and keep that tag strictly for my Minikube environment. It saves me from accidentally deploying a local-only image to a production cluster later on.

Hope this saves you a few hours of debugging and gets your pods running on the first try. Happy coding, and may your deployments always be successful!

為什麼 Minikube 總是抓不到我的 Local Docker Image？別再傻傻推送到 Docker Hub 了！

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了測試一個小小的改動，硬是把 Docker Image 推到 Docker Hub 再從 Minikube 拉下來，那時候網路慢得像龜速，我坐在螢幕前看著 ImagePullBackOff 的錯誤訊息，心態真的差點崩潰，感覺自己像個傻瓜一樣在浪費生命。

其實這個問題的核心很單純，因為 Minikube 本質上是一個跑在虛擬機（或是 Container）裡的獨立環境，它有自己的 Docker Daemon。簡單來說，你的電腦上有一個 Docker，Minikube 裡面也有一個，當你執行 kubectl apply 時，Minikube 是去它自己的「小世界」裡找 Image，當然看不見你本機 Docker 裡剛 build 好的那個檔案。

要解決這個問題，最直覺的方式就是讓 Minikube 直接用你的 Docker 環境。只要在執行 kubectl 之前，先下一行指令把環境變數指過去，讓你的終端機暫時變成 Minikube 的形狀，這樣你在本機 docker build 的東西，就會直接進到 Minikube 的快取裡了。在 Mac 或 Linux 上，你只需要這樣做：


eval $(minikube docker-env)

執行完這行之後，你再跑一次 docker build -t my-app:v1 .，接著直接在你的 YAML 檔裡設定 imagePullPolicy: IfNotPresent，這樣 Kubernetes 就會乖乖抓你剛剛 build 好的那個 Local Image，而不會去遠端伺服器瞎忙了。

為了避免以後又遇到這種「明明 build 好了卻找不到」的痛苦時刻，我強烈建議大家養成一個習慣，那就是在 deployment.yaml 的容器設定中，永遠把 imagePullPolicy 設為 IfNotPresent。這樣就算你哪天忘記切換環境，或者真的有推送到遠端，它也會優先檢查本地有沒有現成的，真的省下不少無謂的等待時間。

以後別再為了測試一行程式碼就去跑漫長的 push/pull 流程了，把這招學起來，開發效率直接起飛！
