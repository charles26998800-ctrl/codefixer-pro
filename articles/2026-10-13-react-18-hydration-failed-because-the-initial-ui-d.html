Fixing React 18 Hydration Mismatch Errors in Next.js

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in React 18. I was pushing a critical update on a Friday afternoon, convinced my code was perfect, only to see my entire dashboard flicker and throw an ugly console error the second the page finished loading. I spent three hours staring at my screen, questioning my life choices and blaming the framework, only to realize I had been doing something incredibly simple that broke the entire SSR contract.

Basically, this error happens because React is a perfectionist. When you use Next.js, the server pre-renders your HTML and sends it down to the browser. Then, React "hydrates" that static HTML by attaching event listeners and turning it into a dynamic app. If the HTML the browser receives doesn't match the HTML React generates on the client during that first render, React just throws its hands up and gives up. This usually happens when you rely on browser-specific APIs like window or localStorage, or when you use random values like Math.random() or new Date() that differ between the server and the client.

The fix is actually quite straightforward once you stop fighting the framework. You need to ensure the component only renders the "dynamic" part once it's officially mounted on the client. I’ve found that using a useEffect hook to toggle a state variable is the cleanest way to handle this. By initializing a state to false and flipping it to true inside useEffect, you tell React to wait until the client-side environment is ready before rendering the content that might cause a mismatch.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Your dynamic content that uses window or dates goes here */}
      <p>Current time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

To prevent this from ever ruining your day again, my golden rule is to treat the server-side render as a "pure" environment. Never assume the browser APIs exist until the component has mounted. If you catch yourself reaching for window or document inside the main body of your component function, stop immediately and move that logic into a useEffect or a specialized client-side hook.

Hope this saves you from the same Friday night headache I had. Happy coding, and may your console stay clean!

救命，React 18 的 Hydration 錯誤快把我搞瘋了！

來源：Stack Overflow ↗ · 341 票

記得剛升級到 Next.js 搭配 React 18 那陣子，我真的是邊寫邊罵。那天熬夜趕一個電商專案的結帳頁面，明明在本地開發跑得好好的，一部署到測試環境，瀏覽器 Console 就瘋狂噴出「Hydration failed」的紅字警告，導致整個頁面閃爍、功能失效。當時我心想：「這不是應該自動處理好的嗎？為什麼伺服器給我的跟瀏覽器長得不一樣？」那種眼看著 Deadline 逼近，卻對著螢幕乾瞪眼的無力感，真的是工程師生涯最想刪除的記憶之一。

其實這問題的根源說穿了就是「溝通不良」。當你使用 SSR（伺服器端渲染）時，Next.js 會先在後端產生一段 HTML 給瀏覽器，但 React 載入後，會試圖把這些靜態 HTML 變成動態的互動介面。如果後端算出來的結果跟瀏覽器第一次執行 React 時算出來的結果對不上——哪怕只是多了一個空格、一個時間戳記，或者是像 typeof window !== 'undefined' 這種判斷導致的差異——React 就會因為「這根本不是我預期的那個畫面」而直接放棄，選擇重繪整個頁面，這就是那個惱人的錯誤。

我當時為了抓這個 Bug，真的是一行一行把程式碼註解掉。後來發現最常見的兇手就是我們喜歡用的 Date() 物件或是隨機數。因為伺服器產生的時間跟瀏覽器執行當下的時間永遠有毫秒級的落差，這在 React 眼裡就是天大的錯誤。我最後的解決方案是把這些「不確定性」高的內容，通通移到 useEffect 裡面執行。因為 useEffect 只會在瀏覽器端跑，這樣伺服器就不會因為算出的結果跟瀏覽器不一致而崩潰。

具體來說，我會寫一個簡單的 Hook 來確保元件只在客戶端掛載後才渲染：


import { useState, useEffect } from 'react';

export function useMounted() {
  const [mounted, setMounted] = useState(false);
  useEffect(() => {
    setMounted(true);
  }, []);
  return mounted;
}

// 在你的元件裡這樣用：
const MyComponent = () => {
  const isMounted = useMounted();

  if (!isMounted) return null; // 或者放個 Loading 轉圈圈

  return <div>現在時間是: {new Date().toLocaleString()}</div>;
};

要預防這種鳥事再發生，最好的習慣就是把「會變動的內容」與「靜態架構」徹底分開。養成在開發時隨時打開 Console 檢查的習慣，不要忽視那些小小的警告，因為 Hydration 錯誤通常不會讓程式直接掛掉，但它會讓你的網頁體驗變得超級差。

希望這篇心得能幫你少掉幾根頭髮，下次遇到這種鬼打牆的問題時，記得先檢查是不是哪裡偷偷用了不該在後端執行的邏輯喔！
