How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster. I had this perfect container image built locally, and I spent a good three hours watching ImagePullBackOff errors blink at me in the terminal, completely baffled because I could literally see the image when I typed docker images. I felt like an absolute amateur, convinced I’d broken my entire environment, only to realize that Minikube and my host machine were essentially living in two different dimensions.

The reason this happens is pretty straightforward once you look under the hood: Minikube runs inside its own isolated virtual machine or container. When you build an image on your laptop, it lives in your host’s Docker daemon. Minikube, however, has its own internal Docker daemon that doesn't have a clue what’s happening outside of its own little sandbox. It tries to pull the image from a registry, fails because your image isn't public, and throws a tantrum.

The most reliable way I’ve found to fix this is to point your local terminal directly at the Minikube Docker daemon. Instead of building your image and trying to "push" it into the cluster, you tell your shell to perform the build command inside the Minikube environment. First, run the following command in your terminal:


eval $(minikube docker-env)

Once you’ve run that, any docker commands you execute will be directed at the Docker daemon running inside your Minikube cluster. Now, you can build your image as you normally would:


docker build -t my-local-image:latest .

After the build finishes, verify it exists inside the cluster by running docker images. The final step is crucial: make sure your Kubernetes deployment manifest has imagePullPolicy: IfNotPresent set. If you leave it at the default Always, Kubernetes will still try to reach out to a registry to check for a newer version of the image, which will fail since your image doesn't exist anywhere but inside that VM.

To prevent this headache in the future, I always set my image pull policy to IfNotPresent by default during development. It’s a small detail, but it saves me from the frustration of local images being ignored by the cluster. Once you get the hang of minikube docker-env, it becomes muscle memory, and you’ll stop fighting your local environment entirely.

Hope this saves you a few hours of debugging! Happy coding, and may your deployments always be smooth.

別再把 Docker Image 推到 Docker Hub 了！Minikube 本地開發的正確姿勢

來源：Stack Overflow ↗ · 690 票

記得剛開始碰 Kubernetes 的時候，為了測試一個小小的 API 修改，我每次都要跑 docker build，然後 docker push 到 Docker Hub，再從 Minikube 裡面 kubectl delete pod 等它重新拉取。最慘的一次是網路剛好慢到懷疑人生，我光是為了看一行 log 的修改，就在電腦前發呆了快二十分鐘，那種「明明程式碼就在我硬碟裡，為什麼還要繞地球一圈才能跑起來」的無力感，真的是會讓人想直接把筆電闔上。

其實會遇到這個坑，是因為我們忽略了 Minikube 的運作本質。Minikube 其實是一個跑在虛擬機（或容器）裡的獨立環境，它有自己的一套 Docker Daemon。當你在你的 Mac 或 Windows 的終端機打 docker build 時，你是在「主機」的 Docker 環境建立鏡像，但 Minikube 這個小世界根本看不見你主機裡的東西，它只會從網路上（Docker Hub）去抓。所以除非你給它一個 registry 路徑，不然它永遠找不到你剛蓋好的那個 image，這就是為什麼大家都會卡在 ImagePullBackOff 的無限迴圈裡。

要解決這個問題，其實根本不需要搞什麼私有倉庫，最快的方法就是讓 Minikube 直接去讀你當前終端機的環境變數。只要在執行 docker build 之前，先執行下面這行指令，把 Docker 的連線指向 Minikube 內部的 Daemon，一切就解決了：


eval $(minikube docker-env)

執行這行之後，你再跑 docker build -t my-app:v1 .，這個 image 就會直接被建立在 Minikube 的環境裡。這時候你的 Kubernetes Deployment 只要把 imagePullPolicy 設定成 IfNotPresent，它就不會再去網路上找，而是直接使用你剛蓋好的那個本地版，速度快到讓你懷疑剛才那二十分鐘的等待到底是在幹嘛。

為了避免以後又被這種「明明有 image 卻抓不到」的狀況搞瘋，我現在養成一個習慣，就是把這個環境變數的設定直接寫在我的 shell 設定檔（像 .zshrc 或 .bashrc）裡，或者乾脆寫一個簡單的 Makefile 把流程自動化。只要養成「建置前先確定環境指向」的習慣，開發體驗真的會提升好幾個檔次。

希望這些經驗能幫你省下不少崩潰的時間，別再讓網路延遲成為你開發路上的絆腳石了！
