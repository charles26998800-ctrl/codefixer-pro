RuntimeError: How to Fix Mismatched Device Types in PyTorch

Source: Stack Overflow ↗ · 202 votes

I remember the first time I ran into this error back when I was training my first ResNet model. I had spent nearly three hours debugging my data pipeline, convinced that my preprocessing logic was broken, only to realize I’d sent my model to the GPU but left my input data sitting lonely on the CPU. It’s one of those classic "aha!" moments that makes you want to facepalm, but it’s a rite of passage for every PyTorch developer.

The reason this happens is actually quite logical once you peek under the hood. PyTorch is extremely strict about where your tensors live. When you call model.to(device), you’re moving the model's weights and biases to your GPU memory. However, PyTorch doesn’t automatically move your incoming data batches to the same device. When the forward pass starts, the model expects the input tensors to be on the same hardware as its parameters. If your model is on cuda and your input is on cpu, the engine throws an error because it can’t perform matrix multiplication across different memory spaces.

To fix this, you need to manually push your inputs (and labels, if you’re calculating loss on the GPU) to the same device you assigned to your model. It’s a simple two-line change inside your training loop that saves you a massive headache. Here is how I handle it:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move the data to the device before passing it to the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... calculate loss and backprop

If you’re doing this frequently, you’ll want to prevent this from ever biting you again by keeping your device logic consistent. My best tip is to define your device at the very top of your script and create a small utility function or a wrapper to move data. If you’re working with more complex structures, like lists or dictionaries of tensors, consider writing a recursive function that traverses your data structure and calls .to(device) on every tensor it finds. It keeps your training loop clean and ensures you don't accidentally leave a stray tensor on the CPU.

Hope this clears up the confusion and gets your training runs back on track. Happy coding, and may your GPU utilization stay high!

PyTorch 報錯 `RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same`，這坑我幫你踩過了！

來源：Stack Overflow ↗ · 202 票

記得剛開始接觸 PyTorch 的時候，那天晚上為了趕一個模型訓練的 Demo，我看著螢幕上的 Loss 曲線一直遲遲跑不出來，結果終端機突然噴出一大串紅字，說什麼 Input 是 CPU 的 FloatTensor，而權重是 CUDA 的 FloatTensor。當下我真的差點崩潰，心想：「大哥，我明明都已經寫了 .to(device) 了啊，到底還想要我怎樣？」那種好不容易把環境架好、資料前處理都弄完了，卻卡在這種「硬體溝通不良」的小問題上，真的是會讓人瞬間懷疑人生，感覺就像準備好要大顯身手，卻被一條電線絆倒一樣無奈。

其實問題的核心非常直白：PyTorch 對於資料的「居住地」要求非常嚴格。當我們把模型丟到 GPU 上（model.to(device)）之後，模型裡面的參數就已經住進顯存裡了，但我們從 Dataloader 抓出來的那些訓練資料，預設還是乖乖待在電腦的記憶體（CPU）裡。這就像是你把廚師送進了廚房，但食材卻還留在客廳的冰箱裡，廚師沒辦法隔空處理食材，所以 PyTorch 就會跳出來報錯，告訴你：「喂，這兩邊根本不在同一個空間，要我怎麼算？」

解決這個問題的方法其實很單純，就是要記得在餵資料給模型之前，把每一筆進來的資料也「強制搬家」。我後來養成了一個習慣，會在迴圈裡多加一行 .to(device)，確保資料跟模型是在同一個頻率上。程式碼大概會長這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就是這行，把 inputs 和 labels 一起搬到 GPU 上
    inputs, labels = data[0].to(device), data[1].to(device)
    
    outputs = model(inputs)
    # 後續的 loss 計算也要確保 labels 在同個裝置上
    loss = criterion(outputs, labels)

為了避免以後再被這種低級錯誤搞到心態爆炸，我現在寫程式時會習慣把 device 宣告成一個全域變數，或是直接寫成一個小工具函式。每當我在寫訓練迴圈時，只要看到 model(inputs)，我就會強迫自己檢查 inputs 是不是已經 to(device) 了。其實只要養成這種「物件與資料同步搬遷」的肌肉記憶，這種錯誤很快就會從你的除錯清單中消失了。

說真的，這種錯誤雖然讓人火大，但解決之後看著 GPU 使用率飆升的那一刻，還是挺有成就感的，大家加油啦！
