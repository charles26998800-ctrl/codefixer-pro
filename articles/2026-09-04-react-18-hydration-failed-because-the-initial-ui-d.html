Troubleshooting React 18 Hydration Errors in Next.js

Source: Stack Overflow ↗ · 341 votes

I remember the first time I saw the "Hydration failed" error in React 18; it felt like I was being gaslit by my own code. I spent four hours digging through my components, convinced I’d messed up my server-side logic, only to realize I had a simple new Date() call generating different timestamps on the server and the client. It’s one of those bugs that makes you want to throw your monitor out the window, but once you understand the mechanism, it becomes much easier to squash.

The root of this frustration is actually quite logical: React expects the HTML sent from the server to be an identical match to the initial HTML rendered by the client. When you use Next.js, the server renders your component into static HTML, and then the browser "hydrates" it by attaching event listeners and turning it into a living, breathing React app. If the server says "Hello" and the client says "Hi" because of some dynamic data, a local storage check, or a random number, React panics. It sees the mismatch, assumes the server is wrong, and throws the hydration error to prevent a messy UI state.

To fix this, I always ensure that any code relying on browser-only APIs or dynamic values is deferred until after the component mounts. If I’m working with something like localStorage or a client-side library that doesn't exist on the server, I use a useEffect hook to set the state. By initializing the state as null and only updating it once the component has successfully mounted, I ensure that the server-rendered HTML is consistent.


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This only renders after hydration: {window.localStorage.getItem('theme')}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

If you’re dealing with third-party libraries that mess with the DOM, you might also need to use suppressHydrationWarning on specific elements if you’re absolutely certain the mismatch is harmless, like a date stamp that changes every millisecond. However, I’ve found that using the useEffect pattern is almost always the cleaner, more robust way to go.

The best way to prevent this in the future is to keep your server-side rendering as "pure" as possible. I try to avoid accessing window or document inside my component bodies at all costs. If you treat your components as if they could be rendered in a vacuum without a browser, you’ll rarely run into these hydration headaches.

Hope this saves you a few hours of debugging time today. Happy coding!

React 18 Hydration 錯誤：那個讓你懷疑人生的「UI 不匹配」惡夢

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我正興高采烈地要把 SSR 給搞定，結果打開瀏覽器控制台一看，整排紅字寫著 Hydration failed because the initial UI does not match what was rendered on the server。當下我真的差點把鍵盤給砸了，明明程式碼看著都沒問題，為什麼伺服器給的 HTML 跟瀏覽器第一次渲染的結果就是對不起來？我整整花了一個下午，對著那幾行錯誤訊息發呆，心裡只想著：「我明明什麼都沒做錯，為什麼 React 要這樣刁難我？」

其實這個問題的核心很單純，就是「時差」。在 SSR 的過程中，伺服器會先幫你產生一份 HTML，當這份 HTML 傳到瀏覽器時，React 會進行「Hydration（水合）」動作，簡單說就是把這份靜態 HTML 變成活的互動元件。但如果你的程式碼裡包含了一些隨機數、當前的時間，或者會根據瀏覽器環境（例如 window 物件）調整的邏輯，伺服器跑出來的結果就會跟瀏覽器第一次執行時不一樣。React 很死腦筋，它發現兩邊長得不一樣，就會直接報錯並放棄水合，導致頁面看起來雖然有東西，但完全失去互動性。

我當時踩坑最慘的一次，是因為我在頁面顯示了當前的系統時間，伺服器產生的時間戳記永遠跟瀏覽器渲染出的那一秒有誤差。後來我學乖了，如果要處理這種「只有瀏覽器才知道」的資料，最穩妥的方法就是強制讓它在掛載後才渲染。我會用一個 useEffect 來處理這種不一致，確保元件在伺服器端渲染時是一致的，直到瀏覽器環境準備好才更新：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者給一個簡單的 Loading 佔位符
  }

  return <div>現在時間是：{new Date().toLocaleString()}</div>;
}

這樣寫之後，伺服器就會先拿到一個空的或預設的狀態，而不會因為時間差跟瀏覽器吵架。

至於要怎麼預防下次再被搞瘋，我的建議是開發時養成習慣，只要是用到 window、localStorage 或者像 Math.random() 這種會隨機生成的東西，一律把它們丟進 useEffect 裡處理。不要在元件的頂層直接呼叫這些會導致環境差異的函式，只要讓元件在「初始渲染」時保持絕對的純粹與可預測性，你就能省下大把除錯的時間。

希望這篇筆記能救你一命，下次遇到這種紅字別急著崩潰，先深呼吸檢查一下是不是哪裡「時差」跑掉了。
