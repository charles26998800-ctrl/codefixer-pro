How to Undo Your Most Recent Local Git Commits Without Losing Your Work

Source: Stack Overflow ↗ · 27251 votes

I remember the first time I accidentally committed a massive set of debug logs and half-finished experimental code to my main branch. I was so confident in my terminal speed that I didn't bother checking the staged files, and it wasn't until I saw the commit hash pop up that I realized I’d just permanently baked a mess into my local history. I spent a good hour sweating, convinced I’d have to manually revert every single file line-by-line, feeling like a total junior developer all over again.

This usually happens because we get into a "flow state" where our fingers move faster than our brains. You’ve probably been there—you git add . everything in sight, hit git commit -m "update", and immediately realize that you didn't mean to include that config.local.json file or those messy print statements. Since you haven't pushed to the remote server yet, the commit only exists in your local repository. The good news is that Git is actually designed to be flexible here; it's keeping track of your history, and you can easily rewrite it as long as you haven't shared those mistakes with your team.

When I need to fix this, I reach for git reset. The command you want depends on whether you want to keep your file changes or completely wipe them out. If I just want to undo the commit but keep all my work sitting in the staging area so I can fix the files and commit again, I use a soft reset.


# Undo the commit, but keep the changes staged
git reset --soft HEAD~1

If I realized the entire commit was a disaster and I just want to get back to the state I was in before I typed that command, I perform a mixed reset. This keeps your files in your working directory, but it unstages them.


# Undo the commit and unstage the changes
git reset HEAD~1

If you’re feeling particularly aggressive and just want to delete the commit and every change associated with it because the code was totally broken, you can use a hard reset. Be careful with this one, because you’ll lose any unsaved work in those files permanently.


# WARNING: This deletes all changes in that commit
git reset --hard HEAD~1

To stop this from becoming a regular headache, I’ve made it a habit to use the --patch flag whenever I'm staging my code. Instead of doing a lazy git add ., I run git add -p. This forces Git to walk me through every single "hunk" of code I’ve changed, asking me if I actually want to stage it. It’s saved me from committing accidental debug code more times than I can count, and it makes my commit history look much cleaner for my teammates to review.

Hope this helps you clean up your history without the stress. Happy coding, and try not to commit those secret keys!

手滑 commit 錯檔案？別慌，這招幫你把 Git 時光倒流

來源：Stack Overflow ↗ · 27251 票

記得有一次凌晨兩點，我趕著要修完最後一個 Production 的 Bug，腦袋已經呈現半當機狀態。我以為我只改了 auth.js，結果一個 git commit -am "fix bug" 下去，才發現我把一堆還在測試、甚至包含測試資料庫連線字串的垃圾檔案也一起塞進去了。當時我盯著螢幕，看著那個剛跑完的 commit 訊息，心跳直接漏了半拍，整個人冷汗直流，那種「我該不會把機密資訊推上遠端吧」的恐懼感，真的是工程師最不想體驗的惡夢。

其實 Git 會發生這種事，通常就是我們對 git commit 太有自信，以為自己已經 git add 得乾乾淨淨。但 Git 的機制其實很單純，它就是一個嚴格的時光紀錄器，一旦你執行了 commit，它就幫你把當下的狀態封裝成一個節點。如果你還沒 push 到遠端，代表這些紀錄都還只存在你的電腦裡，這時候只要把那個節點「拆掉」就好了，完全不需要擔心遠端會出現災難。

如果你的目標只是想撤銷最後一次 commit，但想保留檔案的修改內容（畢竟辛苦改的程式碼不能丟），我最常用的指令就是這個：


git reset --soft HEAD~1

這行指令的威力在於，它會把那個 commit 拆掉，但你的檔案會全部退回到「已暫存（Staged）」的狀態，你只要重新 git reset 把不要的檔案移除，或是直接改一下再 commit 就行。如果你連剛剛改的內容都覺得寫爛了，想徹底毀屍滅跡，那就直接用 --hard：


git reset --hard HEAD~1

這招下去，剛剛那個 commit 裡的檔案改動會直接消失，連暫存區都不留，用起來雖然爽快但真的要小心，因為那可是真的會讓你的程式碼憑空蒸發的。

為了不要再經歷這種心臟病發作的時刻，我後來養成了一個習慣，就是在 commit 之前，一定會先打 git status 看一眼。如果怕手殘打錯，甚至可以考慮用圖形化工具（像 SourceTree 或 GitKraken）先預覽一下這次要打包的檔案清單。多花那三秒鐘檢查，真的能幫你省下後面半小時的除錯時間。

好啦，下次如果不小心又手滑，記得冷靜下來用 reset 把時間撥回去就好，別像當年的我一樣差點把整台電腦關機逃避現實。
