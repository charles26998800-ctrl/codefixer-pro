Troubleshooting RuntimeError: Input type and weight type should be the same in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a distributed training job on a multi-GPU cluster. I had spent hours obsessively tuning my hyperparameters and double-checking my data augmentation pipeline, only to have the whole thing crash exactly ten seconds after the training loop started. I stared at that RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same message for an embarrassingly long time, convinced I had somehow corrupted my CUDA installation before realizing I’d simply forgotten to move my tensors to the GPU.

The root cause here is actually quite simple, even if the error message sounds cryptic. PyTorch is incredibly strict about device affinity. When you call model.to(device), you’re successfully moving the model’s weights and parameters over to your GPU’s memory. However, your data is still sitting comfortably in your system’s RAM (as a CPU tensor). When your model tries to perform the very first matrix multiplication, it essentially hits a wall because it can't perform math between a tensor on the GPU and a tensor on the CPU. They have to "speak the same language" by residing on the same hardware.

To fix this, you just need to ensure that every batch of data coming out of your DataLoader is moved to the exact same device as your model. I usually handle this right inside the training loop before passing the data to the model. Here is exactly how I patch it up:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # Move the inputs and labels to the same device as the model
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you’re working with complex objects or custom datasets, it’s easy to miss one of these tensors, and the error will pop up again. My best tip for preventing this in the future is to stop hardcoding device names everywhere. Instead, I always grab the device from the model itself by using next(model.parameters()).device. This ensures that if you ever decide to switch from a single GPU to a specific multi-GPU setup, your data will follow the model wherever it goes without you needing to hunt down every instance of .to('cuda') in your codebase.

Hopefully, this saves you the headache it caused me back in the day. Happy coding, and may your gradients always converge!

救命！PyTorch 的 GPU 裝置不匹配錯誤，搞到我懷疑人生

來源：Stack Overflow ↗ · 202 票

還記得剛開始玩 PyTorch 的時候，為了加速訓練，我興奮地把模型丟到 GPU 上，結果程式一跑，螢幕直接跳出那行紅通通的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。當下我真的傻眼，明明我已經寫了 model.to(device) 啊，怎麼還是報錯？盯著那個螢幕看了半小時，心裡想著「這程式是不是在耍我」，甚至懷疑是不是顯卡驅動壞了，那種明明程式碼看起來沒問題，卻死活跑不動的挫折感，真的是每個工程師的惡夢。

後來我才搞懂，這其實是 PyTorch 最經典的「裝置不對盤」問題。簡單來說，PyTorch 是一個非常龜毛的框架，它要求參與計算的所有張量（Tensors）必須待在同一個地方。我的模型已經乖乖搬到 GPU（cuda）上了，但我的資料（inputs）卻還留在 CPU（FloatTensor）裡。想像一下，你在台北車站準備搭車去高雄，結果車子開了，你的行李箱還留在月台上，這不吵架才怪！PyTorch 就是因為找不到資料對應的裝置，才直接罷工給你看。

解決方法其實很簡單，就是要在迴圈裡把資料也「搬」進去。我後來學乖了，在處理 DataLoader 的時候，一定要記得對資料做 .to(device) 的動作。修改後的程式碼長這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！把輸入和標籤都移到跟模型同一個 device 上
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就可以安心計算 loss 了

為了預防下次又踩到同一個坑，我現在養成了一個習慣，就是寫一個小工具函數，或者直接在訓練迴圈開頭統一處理裝置轉換。如果你跟我一樣健忘，甚至可以寫個簡單的 data = [d.to(device) for d in data]，這樣不管資料結構多複雜，通通都會被強制搬運，省得之後又為了這點小事在那邊除錯半天。

搞定這些之後，看著顯卡風扇終於開始轉起來，那種成就感真的無價。希望這個小技巧能幫你省下不少崩潰的時間，大家寫程式順利啦！
