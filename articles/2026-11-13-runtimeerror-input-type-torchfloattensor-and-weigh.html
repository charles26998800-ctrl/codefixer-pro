How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I still remember the first time I set up a training loop on a multi-GPU server, feeling like a genius for finally getting my model moved to the device. I hit run, watched the progress bar for three seconds, and then watched it crash immediately with a wall of red text screaming about mismatching tensor types. I spent three hours refactoring my entire custom dataset class, convinced my data loaders were corrupted, only to realize I’d completely forgotten to move the actual data tensors to the GPU. It’s one of those classic PyTorch rites of passage that makes you want to throw your monitor out the window, but once you understand the "why," you’ll never make the mistake again.

At its core, this error is PyTorch’s way of saying that your model is living in the fast lane on your GPU, but your data is still stuck back on your CPU. PyTorch is extremely strict about memory location; it doesn't automatically move your input data to the GPU just because your model is already there. If your model weights are defined as torch.cuda.FloatTensor (meaning they’re sitting in VRAM) and your input data is just a standard torch.FloatTensor (meaning it’s sitting in your system RAM), the mathematical operations will fail. They have to share the same physical memory space to interact, and PyTorch won't perform that migration for you implicitly.

Fixing this is fortunately straightforward, though it’s easy to overlook. You need to explicitly move your input tensors to the same device as your model during every iteration of your training loop. I usually define my device variable once at the top of my script and then reuse it inside the loop. Here is how I handle it in my own projects:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data, labels in dataloader:
    # Move the inputs and labels to the same device as the model
    inputs = data.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

Once you add those .to(device) calls, the error disappears instantly. If you’re working with a complex model that has multiple inputs, just make sure you’re passing every single tensor through that same device object before they touch the model layers.

If you want to avoid this headache in the future, my best tip is to write a small helper function or use a wrapper that handles device assignment for you. I often create a to_device() utility function that can handle nested structures like lists or dictionaries of tensors. By centralizing the movement logic, you stop relying on manual calls inside your training loop and reduce the chance of missing a tensor somewhere deep in your pipeline.

Happy coding, and may your training runs stay green!

當 PyTorch 跟我鬧脾氣：RuntimeError: Input type and weight type should be the same

來源：Stack Overflow ↗ · 202 票

還記得剛開始學 PyTorch 那陣子，為了趕一個重要的 Demo，我凌晨三點還在電腦前死磕。好不容易把模型架構弄好，信心滿滿地按下執行，結果螢幕直接噴出一行紅色的 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same。那一刻我真的差點崩潰，心想：「我不是明明就寫了 .to(device) 了嗎？到底是在演哪齣？」

其實這問題說穿了就是一種「雞同鴨講」。PyTorch 很講究門戶之見，你的模型權重（weight）被我丟到了 GPU 上（也就是 cuda.FloatTensor），但從 Dataloader 吐出來的資料（inputs）卻還留在 CPU 的記憶體裡（FloatTensor）。這就像是你要叫一個講英文的工程師去操作一個只會講日文的機器，兩邊根本對不上頻率，PyTorch 當然會直接罷工，告訴你這兩者的「類型」不匹配。

當時我盯著螢幕發呆了快半小時，看著那行錯誤訊息，心裡滿是無力感。後來才發現，問題就出在我們往往只記得把模型送去 GPU，卻忘了把每一批進來的資料也同步送過去。修正的方法其實超簡單，只要在訓練迴圈裡，把從 Dataloader 拿到的資料手動搬運一下就好。我通常會這樣寫：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # 這行是關鍵，把資料搬到跟模型同一個地方
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來的 loss 計算也要記得把 labels 也搬過去哦！

為了避免以後再被這種低級錯誤搞到崩潰，我後來養成了一個習慣，就是在寫訓練迴圈時，直接把資料搬運寫成一個通用的函式，或是乾脆在定義變數時就養成「先 .to(device) 再說」的肌肉記憶。如果你是用 PyTorch Lightning 之類的框架，這部分通常會自動幫你處理好，但如果是從頭手寫訓練迴圈，這一步絕對不能省。

下次再看到這個錯誤，別急著懷疑人生，記得檢查一下你的資料是不是還懶洋洋地躺在 CPU 裡沒跟上腳步。希望這篇小撇步能幫大家省下寶貴的除錯時間，祝各位的 Loss 都能順利下降！
