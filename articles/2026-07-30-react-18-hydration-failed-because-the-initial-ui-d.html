Debugging the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I encountered the dreaded "Hydration failed" error in a Next.js project. I was three hours into a late-night coding session, convinced I had built a perfect component, only to see my browser console scream at me in red text. I spent way too much time staring at my code, questioning my sanity, and wondering why on earth my perfectly fine UI was suddenly "mismatched" the second it hit the browser.

This error pops up because React 18 is incredibly strict about the consistency between what the server sends and what the client renders. Essentially, the server generates a static HTML snapshot of your app, and when that HTML reaches your browser, React tries to "hydrate" it by attaching event listeners and turning it into a dynamic app. If the server says "I have a timestamp here," but the client-side code renders something different—like a time based on the user's local timezone or a random number—React freaks out. It expects the initial render to be an identical match to the server's output, and if even a single attribute or text node differs, it throws the towel in.

The most common way I’ve fixed this is by delaying the rendering of the problematic component until the client has officially mounted. If you have a component that relies on browser-only data like window, localStorage, or dynamic dates, you shouldn't try to render that on the server at all. I usually reach for a simple useEffect hook to toggle a state once the component is mounted. Here’s how I typically structure that fix:


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // Or a loading skeleton
  }

  return (
    <div>
      {/* Your dynamic content that used to cause the mismatch */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
}

By returning null during the initial server-side render, I tell React to skip the logic that causes the mismatch. Once the browser takes over, isMounted flips to true, and the component renders the dynamic content perfectly without confusing the hydration process.

To prevent this in the future, I’ve made it a rule of thumb to keep my server-side components as pure as possible. Whenever I feel the urge to use a browser-specific API, I ask myself if that data truly needs to be visible the millisecond the page loads. If it doesn't, I always defer it to the client side using the pattern above. It’s saved me countless hours of debugging, and honestly, it makes my code a lot cleaner.

Hope this helps you clear those console errors and get back to building cool stuff. Good luck with the debugging!

Next.js 報 Hydration Error？別慌，這其實是 React 在跟你玩「找不同」

來源：Stack Overflow ↗ · 341 票

記得剛升級到 React 18 那陣子，我滿心期待地把專案搬上去，結果打開瀏覽器控制台一看，整排紅字寫著「Hydration failed」，當下真的差點當場崩潰。明明程式碼看著都沒問題，伺服器渲染（SSR）出來的 HTML 跟瀏覽器第一次跑出來的結果，就像是玩「大家來找碴」一樣，只要有一點點細微的差異，React 就會直接翻臉，把整個 DOM 砍掉重練。

最讓我痛苦的時刻，莫過於那次在處理一個根據使用者瀏覽器時區顯示時間的功能。因為伺服器跑的是 UTC 時間，瀏覽器跑的是使用者本地時間，兩邊渲染出來的字串根本對不起來。每次重新整理頁面，畫面就閃爍一下，然後報錯，那種「明明功能可以用，但就是卡一個錯誤在那邊礙眼」的挫折感，真的會讓人想把鍵盤砸了。

其實會發生這件事，是因為 React 18 對 Hydration 的檢查變嚴格了。當你用 Next.js 做 SSR 時，伺服器會先吐出一份靜態 HTML 給瀏覽器，然後瀏覽器再接手讓頁面「活起來」。如果伺服器渲染的結構跟瀏覽器第一次執行 React 的結果有一丁點不同——哪怕只是一個空格、一個隨機產生的 ID，甚至是根據 localStorage 判斷的邏輯——React 就會認為這是不安全的，乾脆報錯並強制重繪。

解決這個問題，最直覺的方法就是「讓 React 晚點再渲染那部分」。如果你有某些內容是「只存在於瀏覽器端」的（例如根據 window 物件決定要顯示什麼），我通常會用一個簡單的 useEffect 來控制渲染時機。當組件掛載（mount）後，狀態變更了，React 才會去渲染那些會造成差異的內容，這樣就能避開伺服器那一關的檢查。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者你可以放一個簡單的 Loading skeleton
  }

  return (
    <div>
      {/* 這裡放那些會導致 Hydration error 的邏輯 */}
      {window.innerWidth > 768 ? '桌面版內容' : '手機版內容'}
    </div>
  );
}

想要預防這種地獄，最好的習慣就是盡量讓你的組件保持「純粹」。在設計 UI 時，盡量不要在渲染階段直接讀取 window、localStorage 或 new Date()。如果真的非用不可，請務必把它們包進 useEffect 裡，或者乾脆等到組件掛載完成後再觸發渲染。只要伺服器跟瀏覽器第一次「握手」時看到的內容是一樣的，這些惱人的錯誤基本上就會離你遠去了。

希望這些經驗能幫你省下幾小時的除錯時間，祝大家開發順利，少點紅字多點咖啡！
