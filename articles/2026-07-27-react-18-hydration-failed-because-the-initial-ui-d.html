Debugging the "Hydration Failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in a React 18 project. I was three hours into a late-night coding session, convinced my logic was flawless, only to be greeted by a console full of angry red text that basically told me my server and client were living in two different realities. It’s one of those bugs that makes you want to throw your laptop out the window because the code looks perfectly fine, yet the browser refuses to acknowledge that the server even sent it the same markup.

The reason this happens is actually quite logical once you stop staring at the error message in despair. When you’re using Server-Side Rendering (SSR) or Static Site Generation (SSG), Next.js renders your component to HTML on the server and sends it to the browser. Once the browser loads the JavaScript bundle, React "hydrates" that HTML, attaching event listeners and making it interactive. If the HTML the server generated doesn’t match exactly what the client-side React code generates on the first render—perhaps due to a random number generator, a date that changed, or browser-specific storage access—React panics. It sees a mismatch in the DOM tree, throws its hands up, and tells you the hydration failed.

I finally fixed this by ensuring that my component doesn't attempt to render dynamic data until it's safely on the client side. The trick is to use a standard useEffect hook to toggle a "mounted" state. By default, I set the state to false, and once the component mounts in the browser, I flip it to true. This way, the server renders a neutral fallback (or nothing at all), and the client renders the dynamic content only after the hydration process is already complete.


import { useState, useEffect } from 'react';

const MyComponent = () => {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  if (!hasMounted) {
    return null; // Or a simple skeleton/loading state
  }

  return (
    <div>
      {/* Your dynamic content that usually causes the mismatch */}
      <p>Current Time: {new Date().toLocaleTimeString()}</p>
    </div>
  );
};

To prevent this from becoming a recurring nightmare in your codebase, get into the habit of isolating your browser-only logic. If you're using localStorage, window.innerWidth, or any library that relies on global browser objects, always wrap that logic in a useEffect or check for the existence of the window object before rendering. If you treat your server-side render as a "static snapshot" and your client-side render as the "interactive layer," you'll avoid these mismatches entirely.

Hope this saves you from the same headache I had! Happy coding, and may your builds stay green.

React 18 Hydration Error：那個讓我熬夜到凌晨兩點的「伺服器不乖」惡夢

來源：Stack Overflow ↗ · 341 票

還記得那天晚上，我正信心滿滿地想把專案升級到 React 18，想說趁著夜深人靜把 SSR 搞定，結果瀏覽器控制台突然噴出一整排紅字：「Hydration failed because the initial UI does not match」。當時看著螢幕上那個不斷閃爍的錯誤訊息，我真的差點崩潰，心想明明程式碼看起來都沒問題，為什麼伺服器給的內容跟瀏覽器跑出來的長相會不一樣？

最讓我痛苦的時刻，莫過於我發現明明在開發環境下一切正常，一上線部署或是執行 build 之後，畫面就開始詭異地跳動，甚至直接噴出錯誤導致頁面沒辦法正常互動。那種「我明明寫對了，但電腦卻說我錯」的無力感，真的是每個前端工程師的惡夢。

其實這個問題的核心很簡單，就是「伺服器產出的 HTML」跟「瀏覽器初始渲染的 HTML」對不上。想像一下，伺服器先跑了一次程式，產生了一份結構，然後把這份結構丟給瀏覽器。結果瀏覽器載入 JavaScript 後，React 開始執行自己的那套邏輯，卻發現：「欸？怎麼跟我剛才收到的結構不一樣？」比如你用了 new Date().toLocaleDateString() 或者隨機數產生器，伺服器跑的時間跟瀏覽器跑的時間當然有差，這一丁點微小的差異，就會觸發 React 的嚴格檢查機制，直接宣告 Hydration 失敗。

要解決這個問題，我發現最有效的做法就是「讓瀏覽器先閉嘴，等它長大一點再顯示」。如果是因為時間戳記或是 localStorage 這類只有瀏覽器才知道的資料導致的差異，我通常會用一個簡單的 useEffect 來處理。我會先設定一個 isMounted 的狀態，等到組件掛載完畢後，才把那些會導致差異的內容渲染出來。


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isMounted, setIsMounted] = useState(false);

  useEffect(() => {
    setIsMounted(true);
  }, []);

  if (!isMounted) {
    return null; // 或者放一個骨架屏 (Skeleton)
  }

  return (
    <div>
      現在時間是：{new Date().toLocaleString()}
    </div>
  );
}

透過這種方式，我確保了伺服器傳出的 HTML 不會包含那些會變動的內容，等瀏覽器執行完 JS，確認環境一致後才進行渲染，這樣就不會再發生不匹配的狀況了。

至於怎麼預防這種問題再次發生？我現在養成了一個習慣，只要是會用到「瀏覽器特有 API」（像是 window、localStorage 或隨機數）的邏輯，我絕對不會直接放在組件的最外層渲染。我會盡量把它們包在 useEffect 裡面，或者確保這些資料是透過 props 從伺服器端傳遞下來的，而不是讓客戶端自己在那邊「猜」。只要記住「伺服器渲染的是靜態骨架，動態邏輯留給客戶端」，基本就能避開九成這類的問題。

希望這些經驗能幫你省下幾個小時的除錯時間，別再為了這些紅字熬夜啦！
