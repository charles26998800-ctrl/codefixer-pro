How to Use Local Docker Images with Minikube Without Pushing to a Registry

Source: Stack Overflow ↗ · 689 votes

I remember the first time I set up a local Kubernetes cluster, I spent a solid three hours banging my head against the wall because my pods were stuck in ImagePullBackOff. I was convinced my YAML was broken, but it turned out I was just trying to pull an image that existed only on my laptop, not in the cloud. It’s an incredibly common rite of passage for every developer starting out with Minikube, and honestly, waiting for a Docker push to a private registry just to test a one-line code change is a massive productivity killer.

The reason this happens is actually quite logical once you peek under the hood: Minikube runs inside a virtual machine or a separate containerized environment. When you build an image using the Docker daemon on your host machine, that image is stored in your local Docker engine. Minikube, however, has its own isolated Docker daemon running inside its node. Even though you’re on the same physical laptop, the two environments are totally invisible to each other. Kubernetes thinks it needs to reach out to a registry to fetch your image, but since it can’t find it there, it throws up its hands and fails.

The cleanest way I’ve found to bridge this gap is to point your local terminal directly to the Minikube Docker daemon. By doing this, any docker build command you run will build the image directly inside the Minikube environment, making it immediately available to your pods. Before you run your build, simply execute this command in your terminal:


eval $(minikube docker-env)

Once you’ve run that, your current shell session is essentially "hooked" into Minikube. Now, just build your image as you normally would:


docker build -t my-app:v1 .

After the build finishes, you can update your Kubernetes deployment YAML to use imagePullPolicy: IfNotPresent. This is the secret sauce—it tells Kubernetes to check for the image locally first, and only try to pull from a remote registry if it can't find it. This setup feels like magic because you get near-instant feedback loops without ever needing to touch a container registry.

To save yourself the headache in the future, always make sure your deployment manifests explicitly set the pull policy to IfNotPresent rather than Always. If you leave it at Always, Kubernetes will try to reach out to the registry every single time a pod restarts, which will cause your local images to fail even if you’ve built them correctly. Keep that policy set, and you'll stop fighting your own cluster.

Happy coding, and may your pods always hit Running on the first try!

為什麼 Minikube 總是找不到我的 Image？教你如何優雅地使用本地映像檔

來源：Stack Overflow ↗ · 689 票

還記得幾年前剛開始玩 Kubernetes 的時候，我為了測試一個微服務，為了改一行程式碼，硬是把 Docker image 推送到 Docker Hub，然後再讓 Minikube 去抓。來回折騰了快一小時，看著那個 ImagePullBackOff 的錯誤訊息，我真的差點要把鍵盤砸了。當時心想：「明明程式就在我電腦裡，為什麼一定要繞地球一圈才肯跑？」那種網路慢到懷疑人生，還要在那邊等 Registry 上傳的痛苦，相信不少工程師都經歷過。

其實這背後的原因很單純，因為 Minikube 是一個運行在虛擬機或容器裡的獨立環境，它的 Docker daemon 跟我們本機電腦的 Docker daemon 是完全隔離的。當你執行 kubectl apply 時，Kubernetes 會去問 Minikube 裡面的 Docker：「欸，你有這個 image 嗎？」Minikube 一看，發現自己倉庫空空如也，當然就只能乖乖去網路上的 Registry 抓，抓不到就直接報錯給你看。

解決這個坑最快的方法，就是直接把你的環境變數切換到 Minikube 內部的 Docker 環境。只要在終端機輸入這一行指令，就能讓你的本地 Docker 指令直接對準 Minikube：


eval $(minikube docker-env)

執行完這行之後，再重新 docker build -t 我的專案名稱:tag . 一次。這時候你的 image 就會直接被建置在 Minikube 的肚子裡，下次你部署的時候，Kubernetes 就能在本地秒讀到這個 image，不用再花時間去網路上下載了。

另外，如果你不想每次都要手動切環境，或者覺得 eval 很麻煩，我建議養成一個好習慣：在你的 deployment.yaml 檔案裡，把 imagePullPolicy 設成 IfNotPresent。這樣就算你偶爾忘了切環境，系統也不會強迫一定要去遠端 Registry 抓取，只要本機有快取就會優先使用。

以後再也不用為了測個小改動在那邊跑 CI/CD 流程了，把這些時間省下來去喝杯咖啡還比較實際。
