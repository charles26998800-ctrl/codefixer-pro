How to Undo Your Last Local Git Commit Without Losing Your Mind

Source: Stack Overflow ↗ · 27227 votes

I still remember the first time I accidentally committed my .env file containing actual production credentials to a local repo. My heart dropped into my stomach, and I spent a solid two hours frantically searching for a way to "delete" the commit without nuking my entire project directory. It’s a rite of passage for every developer, but that sinking feeling never really gets any easier.

The reason we get into this mess is that Git is designed to be a permanent record of your progress, which is great for history but terrible for mistakes. When you run git commit, you’re essentially snapping a photo of your project state and locking it into the local database. If you haven't pushed that code to a shared server yet, you’re in luck because you haven't broken anyone else's workflow, but Git still treats that commit as a firm milestone that needs to be explicitly undone.

To fix this, I always reach for git reset. The command you need depends on whether you want to keep your changes or throw them away entirely. If you want to undo the commit but keep the files in your working directory so you can fix the mess, run this:


git reset --soft HEAD~1

This command effectively "un-commits" your last action, moving those changes back into your staging area. If you realize you completely botched the code and want to wipe those changes off the face of the earth, just use the hard reset:


git reset --hard HEAD~1

Just be careful with that one, because it’ll permanently delete any work you haven't saved elsewhere. If you're just looking to tweak your commit message or add one last file you forgot, git commit --amend is your best friend. It lets you take that last commit and essentially "re-do" it on the fly, which keeps your history clean without having to reset anything at all.

To keep this from happening again, I’ve started using a pre-commit hook that runs a script to check for sensitive patterns or large files before the commit is even allowed to finish. It’s a bit of extra setup, but it saves me from that panic-induced adrenaline spike when I realize I’ve committed something I shouldn't have.

Hopefully, this saves you from a few stressful hours of Googling. Catch you in the next one, and happy coding!

Git 手滑救星：還沒推上遠端前，如何優雅地「吃後悔藥」？

來源：Stack Overflow ↗ · 27227 票

說實話，剛入行時我真的有過那種心臟漏跳一拍的時刻。記得有次我為了趕專案進度，一股腦把還在測試階段、甚至包含一堆亂七八糟 console.log 的代碼給 commit 下去，按完 Enter 才發現我竟然把這些垃圾一起丟進了主分支。當時看著螢幕上顯示的「commit success」，我腦中閃過的畫面只有「完了，這下要被同事笑死了」，那種想找地洞鑽進去卻又不敢推上伺服器的焦慮感，真的會讓人想把鍵盤給砸了。

其實這問題的根本原因很簡單，就是我們對 Git 的「暫存區」和「歷史紀錄」還不夠熟。Git 的 commit 就像是在時光機上打了一個節點，當你發現 commit 內容不對勁時，我們其實是在對那個節點進行「反悔」。只要你還沒執行 git push，這些錯誤都還只是停留在你自己的電腦裡，所以別擔心，這完全是可以被「抹除」或「修正」的。

如果你只是想撤銷最後一次 commit，同時又想保留那些改好的代碼（方便你修正後再 commit 一次），我最常用的指令就是 git reset --soft HEAD~1。這個指令會把你的 commit 拆掉，但原本寫好的檔案變更會全部留在暫存區（Staging Area），你可以直接修改錯誤的檔案，然後重新 commit，簡直是救命神器。

不過，如果你的情況更慘，比如那些改動根本就是廢物，想直接把檔案回到 commit 前的狀態，那就改用 git reset --hard HEAD~1。這招比較狠，執行下去後，你最後一次 commit 的所有變更會直接消失，連檔案內容都會變回原本的樣子，所以使用前一定要確認你真的不想要那些代碼了，不然刪掉可是找不回來的。

要預防這種手滑悲劇，我現在養成了一個習慣，就是每次 commit 前一定會先打 git status 看一下清單，或者乾脆用 git commit -p 這種互動模式來選取要加入的檔案。這樣就算我不小心改了十個檔案，我也能確保只有我檢查過的那幾個檔案會被打包進去，省得之後還要在那邊手忙腳亂地補救。

Git 雖然有時候很折磨人，但習慣這些指令後，真的會發現它其實挺好用的。反正還沒推上去之前，一切都好商量，別讓這種小失誤壞了你一整天的好心情！
