How to Use Local Docker Images with Minikube Without Pulling Your Hair Out

Source: Stack Overflow ↗ · 688 votes

I still remember the first time I set up a local Kubernetes cluster. I had this perfect little microservice container built on my machine, and I spent three hours banging my head against the wall because my Pods kept stuck in ImagePullBackOff. I was convinced I’d mistyped the tag, but the truth was much more annoying: my Minikube cluster was looking at a remote registry instead of my local machine, and I was treating it like it could magically see my hard drive.

The reason you’re running into this is that Minikube runs inside its own virtual machine or container environment. When you run docker build on your laptop, that image exists in your host's Docker daemon. Minikube, however, has its own isolated Docker daemon inside the VM. When Kubernetes tries to pull your image, it checks the local Minikube environment, fails to find it, and then tries to reach out to Docker Hub or another registry. Since your image isn't pushed anywhere, the cluster just gives up.

The fastest way I found to solve this is to point your terminal's Docker environment directly to the one inside Minikube. By running the eval command, you tell your shell to send all your Docker commands—including build—straight into the Minikube environment. Just run this in your terminal:


eval $(minikube docker-env)

Once you’ve run that, any image you build with docker build -t my-app:latest . will be immediately available to your Minikube cluster. Now, when you deploy your YAML file, just make sure your imagePullPolicy is set to IfNotPresent so Kubernetes doesn't try to go searching the internet for an image that’s already sitting right there in the cluster's memory. If you aren't a fan of switching your environment variables, you can also use minikube image load my-app:latest, which copies the image from your host daemon into the Minikube cluster, though it’s a bit slower for large images.

To keep your sanity, the best tip I can give you is to always be explicit with your image tags. Don't rely on latest because Kubernetes can get confused about whether it needs to pull a fresh version. If you tag your builds with the current timestamp or a git commit hash, you’ll never have to wonder if you’re running the code you actually just compiled.

Hope this saves you those three hours I lost! Happy coding and keep your clusters healthy.

為什麼 Minikube 總是讀不到我剛打包好的 Docker Image？

來源：Stack Overflow ↗ · 688 票

還記得第一次學用 Minikube 開發時，我為了測試一個小小的 API 改動，反覆執行 docker build 之後就急著跑 kubectl apply。結果 Pod 一直報 ImagePullBackOff，我盯著螢幕看了半小時，心想：「明明 docker images 列表裡就有這張圖啊，你是瞎了嗎？」那種明明程式碼寫好了，卻被環境卡死、只能坐在電腦前乾瞪眼的崩潰感，真的會讓人想把鍵盤砸了。

會發生這種事，其實是因為 Minikube 的架構設計。簡單說，Minikube 是一個跑在虛擬機（或容器）裡的獨立環境，它有自己的 Docker Daemon。當你在電腦終端機輸入 docker build 時，你是把映像檔丟進你主機的 Docker，但 Minikube 的那台虛擬機根本連線不到你的主機環境。這就像是你把便當放在自己家冰箱，卻叫 Minikube 去它的冰箱拿午餐，當然會餓死啊！

我後來發現，最快且最不廢話的解法，就是讓 Minikube 直接共用當前的 Docker 環境。如果你是用 Mac 或 Linux，只要在執行 build 指令前先跑這行：


eval $(minikube docker-env)

這行指令會把你的終端機環境變數指向 Minikube 內部的 Docker Daemon。在那之後，你再執行 docker build -t my-app:v1 .，這個映像檔就會直接被打包進 Minikube 的環境裡。這時候你再去部署 YAML，Kubernetes 就會發現它在「家裡」就能找到映像檔，再也不用經過 Registry 上傳下載，速度快到讓你感動流淚。

不過，這招有個隱憂，就是如果你切換了終端機視窗，或者重啟 Minikube，這些設定就會失效。為了預防下次又卡在 ImagePullBackOff，我現在養成習慣，只要開始開發專案，第一件事就是確認環境。如果你不想每次都打這串指令，建議直接把 eval $(minikube docker-env) 加到你的 .zshrc 或 .bashrc 的 alias 裡，或者乾脆在 YAML 的 imagePullPolicy 設定為 IfNotPresent，這樣就算你不小心漏了步驟，K8s 也不會瘋狂去遠端 Registry 找不存在的圖片。

搞定這個之後，開發效率真的差很多，祝大家部署順利，少踩點坑！
