How to Undo Your Last Local Git Commit Without Losing Your Mind

Source: Stack Overflow ↗ · 27251 votes

I still vividly remember my third week as a junior dev when I accidentally committed a massive, half-baked config file containing actual production credentials to a local feature branch. I spent nearly two hours sweating in my chair, convinced that I had permanently tainted my repo history and was about to get fired for a security breach. I eventually learned that git reset is essentially the "undo" button for the terminal, and it’s saved my bacon more times than I care to admit.

The reason you’re in this spot usually boils down to how Git treats your local history as a linear timeline that you can manipulate before it’s shared with the rest of the team. When you run git commit, you’re essentially snapping a photo of your staged changes and locking them into the project history. If you haven’t pushed that commit to a remote server like GitHub or GitLab yet, that history exists only on your machine. Because it hasn't been shared, Git allows you to reach back into the past and rewrite it as if that mistake never happened.

When I need to walk back a commit, I reach for git reset. The specific command depends on what you want to do with the files that were in that commit. If you want to keep the changes in your working directory—maybe you just want to unstage them and keep working—use a soft reset. This is my go-to move because it keeps your code safe while letting you fix the commit message or add the correct files.


git reset --soft HEAD~1

If you realized the entire commit was a disaster and you want to wipe those changes entirely, you'll want to use the hard reset. Be careful here, because this command effectively deletes your work from that commit. It resets your index and working directory to match the commit before the one you’re currently on.


git reset --hard HEAD~1

If you’re ever unsure about what you’re doing, run git status before and after these commands. It helps me stay sane to see exactly where my files are sitting—whether they’re staged, unstaged, or gone.

The best way to prevent this heart-stopping moment is to embrace the habit of checking your staging area before you hit enter on that commit. I started using git status -s religiously before every single commit. It’s a short, clean summary that forces me to look at exactly what I’m about to package up, which usually catches those rogue config files before they ever become a "problem" in the first place.

Hopefully, this helps you clean up your git log without any more stress. Happy coding, and may your merges always be conflict-free!

手殘黨救星：還沒 Push 的 Git Commit 怎麼優雅地「反悔」？

來源：Stack Overflow ↗ · 27251 票

還記得那是個週五下午，我正準備趕在下班前把功能收尾，結果腦袋一打結，竟然把一堆測試用的垃圾 log 跟沒寫完的半成品全給 commit 進去了。看著螢幕上那個刺眼的 [master 8a2b3c4]，我心跳瞬間漏了一拍，當下真的差點崩潰，滿腦子想著要是這些廢物代碼被推上去，週一絕對會被同事釘在牆上，那種「完了，我要變成部門罪人」的絕望感，真的不是開玩笑的。

其實這問題說穿了，就是 Git 把你的 commit 當成一個個的時間點紀錄下來，而你只是想回到「還沒 commit 之前」的狀態。當我們執行 git commit 時，Git 其實是在本地資料庫幫你存了一份快照，只要你還沒執行 git push 把這些紀錄發送到遠端伺服器，這些錯誤就還只存在你的電腦裡，這時候要處理簡直易如反掌，完全不用擔心會影響到其他隊友。

如果你只是想撤銷 commit，但想保留剛剛辛苦寫的程式碼，那我最常用的就是 git reset --soft HEAD~1。這一招超好用，它會把那個錯誤的 commit 拆掉，但你的檔案還是會留在暫存區（Staged），你可以直接調整要 commit 的內容再重新提交。但如果你是像我那次一樣，整包東西都寫爛了，想徹底毀屍滅跡，那就直接用 git reset --hard HEAD~1，這指令會把 commit 砍掉，連檔案變更也會直接抹除，乾淨俐落。不過要提醒一下，用 --hard 前一定要確認你真的不想要那些檔案了，不然真的會欲哭無淚。

為了不要讓這種心臟病發作的時刻再次上演，我現在養成了一個習慣：每次 commit 前一定會先打 git status 看一下清單。如果覺得這習慣太麻煩，我後來乾脆設定了 git add -p（patch mode），它會一個區塊一個區塊問你「這段要不要加進去？」，這過程雖然有點囉唆，但真的能幫我過濾掉那些不小心加進去的 debug log，或是沒寫完的測試程式碼。

只要學會這幾招，Git 基本上就再也沒辦法拿你怎麼樣了，大家下次手滑時記得先深呼吸，別急著亂打指令喔！
