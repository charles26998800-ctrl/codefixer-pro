Stop Pushing to Registry: How to Use Local Docker Images with Minikube

Source: Stack Overflow ↗ · 690 votes

I still remember the first time I set up a local Kubernetes cluster, feeling like a total genius until I tried to deploy my first custom image. I spent three hours banging my head against the wall because my pod kept stuck in ImagePullBackOff, even though I could clearly see the image sitting right there in my terminal when I ran docker images. It’s one of those "aha!" moments that every developer hits early on, and it’s honestly a rite of passage for anyone getting into local K8s development.

The reason you’re running into this is that Minikube runs inside its own isolated virtual machine or container. When you build an image on your host machine, it lives in your host’s Docker daemon. Minikube, however, has its own internal Docker daemon that doesn't know anything about your local environment. It’s like trying to access a file on your laptop while sitting inside a locked server room halfway across the world—your cluster just can’t see what you’ve built unless you explicitly point it to your local environment.

The cleanest way I’ve found to fix this is by pointing your local shell directly at the Docker daemon running inside your Minikube instance. Instead of pushing to a registry like Docker Hub or ECR, you run a simple command that redirects your docker commands to the Minikube environment. Just run this in the terminal where you plan to build your image:


eval $(minikube docker-env)

Once you run that, any docker build command you execute will build the image directly inside the Minikube node. You can verify it worked by running docker images, and you'll see the Minikube-specific images alongside yours. Now, when you update your Kubernetes YAML to set imagePullPolicy: IfNotPresent, your pod will find the image locally and start up instantly without reaching out to the internet. If you ever need to switch back to your host's Docker daemon, just open a new terminal tab or run eval $(minikube docker-env -u).

To prevent this headache in the future, I highly recommend adding a small check in your deployment manifest. Always set your imagePullPolicy to IfNotPresent for your local development tags. If you leave it as the default Always, Kubernetes will keep trying to pull from a registry even if the image is already sitting there, which is a classic way to lose your mind during a debugging session.

Hope this saves you from the same three-hour rabbit hole I fell down! Happy coding and enjoy your local cluster.

為什麼 Minikube 總是抓不到我的 Local Docker Image？別再傻傻推送到 Docker Hub 了！

來源：Stack Overflow ↗ · 690 票

還記得剛開始玩 Kubernetes 的時候，我為了測試一個微服務，硬是把 Docker Image 推到 Docker Hub 再讓 Minikube 拉下來，結果網路慢到我想哭，改一行程式碼就要等十分鐘的 build 和 push，那種看著進度條慢慢跑的無力感，真的會讓人懷疑人生，差點就在辦公室崩潰摔鍵盤。

其實這背後的原因很單純：Minikube 是一個運行在虛擬機（或是 Docker 環境）裡的輕量級 K8s 叢集，它有自己獨立的 Docker Daemon。簡單來說，你電腦本機的 Docker 和 Minikube 裡面的 Docker 根本是兩個不同世界，你辛辛苦苦在終端機輸入 docker build 產出的映像檔，其實是存在你電腦的 Docker 裡，Minikube 當然像個局外人一樣，完全看不到這些檔案。

後來我發現，最快的方法其實是直接讓你的終端機暫時「借用」Minikube 內部的 Docker 環境。只要執行這行指令：


eval $(minikube docker-env)

執行完這行之後，你現在的終端機視窗就會直接連上 Minikube 內部的 Docker。這時候你再跑一次 docker build -t my-app:v1 .，這個映像檔就會直接被塞進 Minikube 的肚子裡了。這時候只要把你的 Deployment YAML 裡的 imagePullPolicy 改成 IfNotPresent，Minikube 就會乖乖用你剛才 build 好的版本，再也不用經過 Docker Hub 那種慢到讓人厭世的流程。

不過要提醒大家，這個設定只對「當前這一個」終端機視窗有效，如果你關掉視窗或是換個分頁，記得要重新執行一次。為了預防下次又忘記搞錯環境，我後來養成了一個習慣，就是把這個指令寫進一個簡單的 build.sh 腳本裡，或者乾脆在開工前先檢查一下 docker images，確認裡面真的有我要的 Image，才不會又在那邊因為 ImagePullBackOff 的錯誤訊息卡半天。

學會這招真的省下我不少開發時間，希望這也能幫你脫離等待 Docker Hub 上傳的苦海！
