How to Undo Your Most Recent Local Git Commits Without Panicking

Source: Stack Overflow ↗ · 27237 votes

I still vividly remember the time I accidentally committed a .env file containing my local database credentials to a repo at 2:00 AM. I stared at my screen for ten minutes, sweating bullets, convinced I’d just compromised my entire dev environment and would have to deal with the fallout the next morning. It’s that sinking "oh no" feeling we’ve all had, but thankfully, Git is designed to be forgiving if you know which command to reach for.

The reason this happens is usually just a simple lapse in focus; we get into a "commit flow" where we’re stage-all-ing and committing without double-checking the git status. Since Git treats your commit history as a series of snapshots, when you commit, you’re essentially sealing that snapshot into your local branch. If you haven't pushed that snapshot to the remote server yet, you’re in a great position because the "mistake" only exists on your machine. You aren't breaking anyone else's build, you're just tidying up your own local history.

When I need to fix this, my go-to tool is git reset. If I just want to undo the commit but keep my work in the staging area so I can fix the files, I use a soft reset. This is the safest way to handle it because you don't lose any of your hard-earned code. I run this in my terminal:


git reset --soft HEAD~1

After running that, the commit is gone, but the changes are still there, sitting in my index waiting for me to adjust them. If I messed up so badly that I want to completely trash the changes I just committed, I use the hard reset instead. Just be careful with this one, because it’s destructive:


git reset --hard HEAD~1

That command effectively nukes the last commit and wipes the changes from your working directory. I’ve definitely used that one when I realized I was working on the wrong branch entirely.

To stop this from becoming a recurring nightmare, I started using git status as a religious ritual before every single commit. I also highly recommend using a GUI tool like GitKraken or the built-in view in VS Code to inspect the "Staged Changes" list. Seeing exactly which files are about to be wrapped up in that commit block has saved me from accidentally including debug logs or local config files more times than I can count.

Hopefully, this gets you out of your current jam without too much stress. We’ve all been there, so don't sweat it—happy coding!

救命，我不小心把還沒寫好的爛代碼 Commit 了！Git 撤銷大法公開

來源：Stack Overflow ↗ · 27237 票

記得剛入行那年，有次趕著下班去約會，心想最後改個小 Bug 就收工，結果腦袋一抽，直接把整個測試用的 Debug Log 和還沒串接好的 API 亂碼一起 git commit 了下去。按下 Enter 的那一刻，看著終端機顯示「One commit ahead」，我整個人差點原地崩潰，心想這下慘了，要是推上遠端被同事看到這堆垃圾代碼，我工程師的尊嚴還要不要啊？

其實這問題發生得非常頻繁，原因很簡單：Git 把我們的每一次 commit 都當成一個「歷史紀錄點」。當你執行了 commit 指令，Git 就會把這些檔案打包並鎖定在你的本地分支上。如果你還沒 push 到遠端，這些紀錄其實還只是待在你的電腦裡，所以我們完全有機會把這段黑歷史從時光軸裡抹掉。

我當時冷靜下來後，用的就是 git reset 這個強大的武器。如果你只是想撤銷 commit，但想保留修改過的檔案內容，可以輸入：


git reset --soft HEAD~1

這行指令的意思是「把指標往回移一個位置」，原本提交的那些檔案會乖乖地回到「暫存區（Staging Area）」，這時候你就可以繼續修改、把不要的檔案移出暫存區，然後再重新 Commit，完全神不知鬼不覺。但如果你是改到懷疑人生，想把那次 commit 的所有改動直接清掉、還原到什麼都沒發生過的狀態，那就用這個狠一點的：


git reset --hard HEAD~1

這招真的要小心，它會直接把你最後一次提交的改動全部銷毀，檔案會直接變回 commit 前的模樣，真的會有一種「剛才是在寫心酸的嗎」的痛苦感。我以前就因為手滑用了 --hard，結果搞丟了一段辛苦寫的邏輯，坐在椅子上發呆了五分鐘。

為了不再重蹈覆轍，我後來養成了一個習慣：在 git commit 之前，一定會先敲一遍 git status 看一下到底有哪些檔案被改動了。如果真的不放心，也可以考慮把 git add 的範圍縮小，不要每次都無腦 git add .，明確指定你要提交的檔案，這樣能幫你擋掉很多不小心把機密資訊或 Debug 雜訊送進歷史紀錄的慘劇。

Git 就是這樣，熟了它是神，不熟的時候就是你的惡夢。希望這些指令能幫你從崩潰邊緣救回來，趕快去改代碼吧，別再手滑啦！
