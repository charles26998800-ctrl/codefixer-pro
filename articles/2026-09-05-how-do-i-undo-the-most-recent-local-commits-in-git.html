How to Safely Undo Your Last Local Git Commit

Source: Stack Overflow ↗ · 27237 votes

I still remember the first time I accidentally committed a massive folder of local build artifacts and sensitive environment variables to a production-ready repo. I spent a good three hours sweating bullets, convinced I’d just nuked my entire project history or, worse, exposed my API keys to the world. It’s one of those classic "oh no" moments that every developer goes through, but the good news is that Git is actually designed to be forgiving if you know which lever to pull.

The reason you’re in this spot is that Git is a distributed version control system that separates your staging area, your local commit history, and the remote server. When you run git commit, you’re simply taking a snapshot of your staged files and locking them into your local history. Because you haven't pushed yet, that "mistake" only exists on your machine, which means you have total control to rewrite history without affecting your teammates' workflows.

If you just want to undo the last commit but keep your changes in the staging area so you can fix them, I always use the soft reset command. This is my go-to when I realized I forgot to include one tiny file or if I just want to tweak the commit message.


git reset --soft HEAD~1

Now, if you want to completely wipe the commit and discard all the changes you made in that commit, you need to use the hard reset. Be careful here—this is the nuclear option. Any code you wrote in that commit will be gone forever, so only use this if you’re absolutely sure you don't want those changes anymore.


git reset --hard HEAD~1

If you’re somewhere in the middle—where you want to undo the commit but keep the files in your working directory as "unstaged" changes—simply drop the flag entirely. I find this the most useful when I've bundled too many unrelated changes into one commit and want to break them apart into cleaner, smaller commits.


git reset HEAD~1

To keep yourself from living through this panic again, I’ve started using git status like a nervous tick before every single commit. I also make a habit of using git add -p to stage my changes hunk-by-hunk, which forces me to review exactly what I’m about to commit before I hit enter.

Hope this saves you from the same heart attack I had back in the day. Happy coding!

Git 誤操作救援：還沒 push 到遠端前，如何優雅地撤銷 commit？

來源：Stack Overflow ↗ · 27237 票

記得那是剛進公司沒多久的時候，我心想「搞定這版功能了」，手速飛快地執行 git commit -m "Update everything"。結果按下 Enter 的那一瞬間，我才發現自己把剛才測試用的除錯 Log 檔、還有不小心刪掉的一堆設定檔全給包進去了。那種心跳漏一拍、冷汗直接冒出來的感覺，真的會讓人想當場把螢幕關掉裝死。

其實這背後的道理很簡單，Git 的架構就像是在你的電腦裡存了一連串的「歷史紀錄」，當你執行 commit 時，就像是把當下的狀態拍了一張照存進去。如果還沒 push 到遠端，這些照片其實都還留在你的本機倉庫裡，所以我們隨時都可以把這些紀錄「撕掉」。但最痛苦的時刻莫過於，你以為撤銷 commit 會連同檔案一起消失，結果手殘用了錯誤的指令，導致辛辛苦苦寫的程式碼瞬間「原地蒸發」，那時候真的會想對著電腦大吼。

針對這種還沒推送到遠端的 commit，我最常用的救命指令就是 git reset。如果你只是想撤銷 commit，但想保留剛才改動過的檔案內容，好讓你重新整理一下再 commit，那就用這個指令：


git reset --soft HEAD~1

這行指令的意思是把 HEAD 指標往回移一個位置，但檔案內容會完好無損地留在你的 Staging Area（暫存區）。如果你發現連檔案內容都寫錯了，想徹底回到 commit 之前的原始狀態，那就加上 --hard 參數：


git reset --hard HEAD~1

請務必小心使用 --hard，因為它會毫不留情地把所有改動都清空，這可是我以前繳過不少學費才記住的慘痛教訓。

為了避免以後再發生這種慘劇，我現在養成了一個習慣：在 commit 之前，一定會先執行一次 git status 看一下到底有哪些檔案被標記了。如果還是怕手殘，可以考慮把 git add -p 變成日常，它會逐行詢問你是否要加入這些改動，這樣就能在 commit 前精準過濾掉那些不該出現的垃圾檔案。

搞定這些之後，心跳總算恢復正常了，以後手別太快，commit 前多看一眼真的能救你一命。
