Fixing the RuntimeError: Input type and weight type mismatch in PyTorch

Source: Stack Overflow ↗ · 201 votes

I still remember the first time I ran into this error back when I was training my first ResNet model. I had spent nearly three hours debugging my custom dataset loader, convinced that my labels were corrupted, only to realize I’d completely forgotten to move the incoming data tensors to the GPU. It’s one of those classic PyTorch "gotchas" that makes you want to throw your keyboard out the window, especially when you’re staring at a perfectly configured model that just refuses to talk to your inputs.

The reason you’re seeing this RuntimeError is actually pretty straightforward: PyTorch is very strict about device consistency. When you call model.to(device), you’re successfully shipping your neural network’s parameters over to the GPU, but that doesn’t automatically move the incoming data from your DataLoader. The model is sitting there on the GPU waiting for data, but your inputs are still chilling on your CPU’s RAM. Because PyTorch requires the model weights and the input tensors to live on the exact same device to perform the matrix multiplication, it throws this mismatch error the second it tries to process the first batch.

To fix this, you need to manually move your input tensors to the same device your model is using during your training loop. I usually keep a reference to my device object and simply call .to(device) on my data before passing it into the model. Here is how I usually structure that part of my loop:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for inputs, labels in dataloader:
    # Move the data to the same device as the model
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    # Now the forward pass works perfectly
    outputs = model(inputs)
    # ... rest of your training logic

If you’re working with multiple inputs or complex data structures, just make sure every single tensor that touches the model parameters is sent to that device.

To prevent this from happening again, I started a habit of defining a small helper function or a simple wrapper that handles the device transfer for my batches. If you get into the practice of moving your data to the device the very second you pull it out of the iterator, you’ll stop seeing this error entirely.

Hope this helps you get your model training without any more headaches. Good luck with the rest of your project!

PyTorch 報錯解密：為什麼我的 Tensor 和 Model 總是不在同一個頻道？

來源：Stack Overflow ↗ · 201 票

記得剛開始碰 PyTorch 的時候，為了趕一個重要的 Demo，我在深夜三點對著電腦螢幕抓狂。當時我好不容易寫完訓練迴圈，按下執行鍵後滿懷期待地想看 GPU 跑起來，結果終端機直接吐出一長串紅色錯誤：「RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same」。那一刻我真的差點把鍵盤砸了，心想：「大哥，我明明已經寫了 .to(device) 啊，為什麼還是不理我？」

其實這個問題的核心非常單純，就是 PyTorch 雖然很強大，但它非常「死腦筋」。當我們定義 model.to(device) 時，我們確實把模型的權重（weights）搬到了 GPU 上，但這並不代表你從 DataLoader 撈出來的數據（inputs）會自動跟著一起過去。PyTorch 要求運算的雙方必須身處同一個「世界」——要嘛都在 CPU，要嘛都在 GPU。當你的模型在 GPU 喝咖啡，你的數據還在 CPU 那邊排隊，兩邊語言不通，程式當然只能停下來跟你抗議。

我當初就是太天真，以為把模型丟給 GPU 就萬事大吉，完全忘了數據也要「手動」搬家。解決的方法其實很直覺，就是在訓練迴圈裡，把從 DataLoader 撈出來的資料也強制指定到你定義好的那個 device 上面。你可以直接用 .to(device) 把資料送過去，像這樣：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 這裡就是關鍵！記得把 inputs 和 labels 都搬過去
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # ... 後續的 loss 計算等 ...

為了避免以後再被這個低級錯誤絆倒，我後來養成了一個習慣：在寫 DataLoader 的處理邏輯時，直接寫一個小小的 Helper Function 或者在迴圈開頭就統一處理搬移動作。只要養成「只要拿到數據，第一件事就是確認它在哪個 device」的肌肉記憶，這種錯誤基本上就絕跡了。

現在看到這個錯誤訊息，我反而會有一種「老朋友又來打招呼」的親切感，畢竟這可是新手村必經之路啊。希望這篇筆記能幫你省下那寶貴的除錯時間，趕快把模型訓練起來吧！
