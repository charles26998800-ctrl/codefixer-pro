React 18 Hydration Mismatch: Why Your SSR Is Breaking and How to Fix It

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" error in React 18. I had spent three hours fine-tuning my server-side rendering setup, feeling pretty proud of myself, only to refresh the page and see my console turn into a giant, angry wall of red text. I stared at my code for an hour, convinced React was hallucinating, before realizing my browser extensions and server-generated content were in a full-blown war with each other.

The root of this headache is actually pretty simple once you pull back the curtain. When you use Next.js or any SSR framework, the server generates the initial HTML based on your components and sends that to the browser. Once the JavaScript loads, React takes over and attempts to "hydrate" that static HTML by attaching event listeners and turning it into a dynamic app. The problem kicks in when the HTML the server sent doesn't match exactly what React expects to render on the client. Even something as tiny as a random number generator, a timestamp, or a browser-specific check in your useEffect will cause React to panic because the DOM tree it sees on the client doesn't match the snapshot it received from the server.

To fix this, I stopped trying to force the server to render volatile data that only the client knows about. The most common culprit is rendering something based on window or localStorage directly in your component body. Instead, I move that logic inside a useEffect hook, which only runs after the component has mounted on the client. Here is how I handle it:


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <p>This only renders after hydration: {window.location.href}</p>
      ) : (
        <p>Loading...</p>
      )}
    </div>
  );
}

By using that isClient flag, I ensure that the server renders a predictable "Loading" state, and the client only renders the browser-specific logic once it's safe to do so. If you’re using a library that forces you into these mismatches, you can also use suppressHydrationWarning on the specific HTML element, but only use that as a last resort because it’s basically just putting a piece of tape over a check engine light.

The best way to prevent this in the future is to keep your render functions pure. If you find yourself reaching for window or document inside your component logic, take a step back and ask if that value is absolutely required for the initial paint. If it isn't, keep it locked behind a useEffect or a lifecycle check, and your hydration errors will disappear for good.

Hope this saves you from the same headache I had. Happy coding!

React 18 Hydration 錯誤搞得我頭好痛？別怕，這其實是「時空錯亂」造成的

來源：Stack Overflow ↗ · 341 票

記得那是個趕上線的週五傍晚，我正信心滿滿地想把專案切換到 Next.js 的 SSR 模式，結果瀏覽器控制台一打開，整頁紅通通的錯誤訊息直接把我原地送走。看著那行「Hydration failed because the initial UI does not match what was rendered on the server」，我當下真的差點把鍵盤砸了，心想：「我程式碼明明寫得好好的，伺服器跟瀏覽器是在吵架嗎？」最痛苦的是，這不是什麼邏輯錯誤，而是畫面渲染完後，伺服器產出的 HTML 跟瀏覽器第一次跑 React 時長得不一樣，這種「明明看起來一樣，電腦卻說不對」的感覺，真的是開發者最大的精神折磨。

其實這背後的原理說穿了就是「時空錯亂」。SSR 的運作方式是先在伺服器把 HTML 算好傳給瀏覽器，瀏覽器拿到後再「接手」（Hydrate）變成互動式的 React 應用。問題在於，如果你的程式碼依賴了像 Math.random()、Date 這種會隨著時間或環境變動的數值，或者你把一些「只有瀏覽器才有的東西」（例如 window 或 localStorage）放在了初始化階段，伺服器算出來的畫面就會跟瀏覽器自己跑出來的畫面產生落差。React 發現兩邊不對盤，為了保險起見，它就會直接報錯報給你看，這就是為什麼你明明覺得沒錯，但它就是不爽的原因。

要解決這個問題，最核心的策略就是「讓 React 知道這個元件先別急著渲染」。我後來發現，只要強制讓元件等到瀏覽器載入完成後再掛載，問題就迎刃而解了。最簡單的做法就是利用 useEffect，因為它只會在客戶端執行，我可以寫一個簡單的 hook 來判斷現在是不是已經進入客戶端環境：


import { useState, useEffect } from 'react';

function useHasMounted() {
  const [hasMounted, setHasMounted] = useState(false);

  useEffect(() => {
    setHasMounted(true);
  }, []);

  return hasMounted;
}

// 在你的元件裡這樣用：
function MyComponent() {
  const hasMounted = useHasMounted();

  if (!hasMounted) {
    return null; // 或者給一個簡單的 loading 骨架圖
  }

  return <div>這裡放那些會導致錯誤的互動內容</div>;
}

透過這個方式，伺服器端只會渲染出一個空的容器，等到瀏覽器真的準備好接手了，React 才會把真正的內容補上去，這時候兩邊的數值就會完全一致，錯誤自然就消失了。

至於怎麼預防這種鬼打牆的情況再次發生？我強烈建議大家在寫元件時，一定要養成「嚴格區分伺服器與客戶端邏輯」的習慣。如果發現元件必須用到 window 物件，或者內容會隨時間改變，乾脆一開始就把它封裝在 useEffect 或是 Next.js 的 dynamic import 裡面並設定 { ssr: false }。不要心存僥倖想說「應該沒事吧」，只要是會變動的 UI，預設把它當成「客戶端限定」來處理，絕對能幫你省下大把除錯的時間。

希望這篇心得能幫你少走點冤枉路，下次遇到這種紅色錯誤訊息時，記得先深呼吸，它們只是在抗議兩邊溝通不良而已啦！
