How to Undo Your Most Recent Local Git Commits (Without Losing Your Work)

Source: Stack Overflow ↗ · 27249 votes

I still remember the first time I accidentally committed my local .env file—filled with actual production API keys—to a repository I was about to push. I felt that sudden, cold pit in my stomach as I stared at the screen, panic-scrolling through my terminal history while praying I hadn't hit git push yet. I spent a good twenty minutes hyperventilating and googling commands until I realized that Git is actually a safety net, provided you know which lever to pull.

It happens to everyone because Git is designed to be a continuous stream of snapshots, and sometimes we’re moving faster than our brain can process. The root cause here is usually a simple case of "commit-itis," where you’re in a flow state, running git add . and git commit -m "update" repeatedly without checking the git status output. Since Git tracks your history locally before it ever touches a remote server like GitHub or GitLab, your local repository is essentially a sandbox. You haven't made a mistake in the eyes of your teammates yet; you've just made a mistake in your own local timeline.

When I need to walk back a commit, I reach for git reset. It’s the Swiss Army knife of Git history manipulation. If I just want to undo the commit but keep the changes in my staging area so I can fix a typo or add a missed file, I use a soft reset.


git reset --soft HEAD~1

This command moves your branch pointer back by one commit while keeping all your files exactly as they were, sitting comfortably in your staging area ready to be committed again. If, however, I want to completely wipe the slate clean and throw away the changes I just committed, I go for the hard reset. Just be careful with this one, because it will permanently delete those changes.


git reset --hard HEAD~1

That command effectively deletes the last commit and reverts your working directory to the state of the previous commit. It’s the equivalent of hitting the "undo" button on a time machine.

To avoid this headache in the future, I’ve made it a habit to use git status and git diff --cached before every single commit. It takes an extra five seconds, but it forces me to look at exactly what I’m about to bake into my history. If you get into the rhythm of reviewing your staged changes, you’ll catch those stray .env files or debug console.log statements long before they ever become a commit.

Hope this saves you from a few grey hairs today. Happy coding, and try to keep your history clean!

Git 後悔藥：不小心 commit 了錯誤檔案該怎麼辦？

來源：Stack Overflow ↗ · 27249 票

我永遠記得那天下午，為了趕一個客戶的緊急需求，我在終端機裡瘋狂地 git add . 然後 git commit -m "fix something"，結果按下 Enter 的瞬間，我才發現我把幾十個測試用的 Debug Log 還有一個根本不該上傳的環境設定檔全給包進去了。最慘的是，我當時手抖了一下，commit 的描述還打成「asdf」，那一刻我真的是心跳漏掉半拍，看著螢幕上的 [master (root-commit) 4a2b3c] asdf，真的差點崩潰，想說這下完蛋了，是不是要整份專案砍掉重練。

其實這問題之所以讓人心慌，是因為我們對 Git 的運作機制還不夠熟。Git 的 commit 其實就像是幫你的檔案狀態拍了一張快照，而「還原」的本質，其實就是把「指針（Pointer）」移回到上一個正確的快照位置而已。只要你還沒把這些 commit 推送到遠端的 Server，這一切都還在你的本地端掌控之中，完全有救，不需要在那邊懷疑人生。

如果要救回這種狀況，我最常用的就是 git reset。如果你只是想撤銷 commit，但想保留剛剛辛苦寫好的程式碼內容，可以直接用 git reset --soft HEAD~1。這一招最溫柔，它會把你的 commit 拆掉，但你剛剛修改的檔案通通會留在暫存區（Staging Area），讓你重新 add 正確的檔案再 commit。如果連檔案內容都不想要了，徹底想回到 commit 之前的樣子，那就用 git reset --hard HEAD~1，這指令下去就像從來沒寫過那段程式碼一樣乾淨，但也請記得，這會直接刪掉你當下所有未保存的修改，按 Enter 前真的要再三確認啊！

我有一次就是因為太順手，直接 hard 了下去，結果把下午兩小時寫的邏輯直接原地蒸發，那種看著螢幕發呆、心裡大喊「我剛剛到底寫了什麼」的痛苦，真的是工程師生涯最不想回憶的時刻之一。

為了不要再經歷這種心臟病發作的瞬間，我後來養成了「先檢查再 commit」的壞習慣，喔不，是好習慣。現在我每次 commit 前，一定會習慣性地打 git status 看一眼，甚至會養成用 git diff --cached 去檢查到底有哪些檔案被放進這次的 commit 裡。如果你的專案比較複雜，建議直接安裝一些 GUI 工具，像是 SourceTree 或 GitKraken，它們能讓你用滑鼠視覺化地確認變更，把不該進去的檔案勾選掉，真的能幫你省下不少心力。

搞懂這些 Git 指令後，你會發現寫程式其實沒那麼可怕，至少犯錯了還有後悔藥可以吃。下次不小心 commit 錯東西時，深呼吸，冷靜把指針移回去就好，千萬別像我當年一樣急著想重灌電腦啊！
