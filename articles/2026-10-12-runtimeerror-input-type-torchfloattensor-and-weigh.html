How to Fix "RuntimeError: Input type and weight type should be the same" in PyTorch

Source: Stack Overflow ↗ · 202 votes

I remember the first time I ran into this error back when I was training my first ResNet model on a local GPU. I’d spent nearly four hours curating my dataset and meticulously setting up my training loop, only to hit this "RuntimeError" the second the first batch hit the model. I honestly stared at my monitor for a solid ten minutes wondering why PyTorch was yelling at me about types when I had clearly sent my model to the GPU, feeling like a complete novice all over again.

The root cause here is actually pretty straightforward, even if it feels like the framework is being unnecessarily pedantic. PyTorch is extremely strict about data locality; your model parameters and your input tensors must live in the exact same memory space. When you call model.to(device), you’re successfully moving the model's weights to the GPU (the cuda device). However, when your DataLoader yields a batch of data, that data is still residing in your system's RAM (the cpu). When you try to pass those CPU-bound tensors into your GPU-bound model, PyTorch throws an error because it doesn't know how to perform calculations between different memory locations.

To fix this, you have to manually move your input tensors to the same device as your model during the training loop. You don't need to overcomplicate it—just grab your inputs and labels and push them to the device right before you pass them into the model. Here is the snippet that finally got my training loop running smoothly:


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # This is the line that saves your sanity
    inputs, labels = data[0].to(device), data[1].to(device)
    
    outputs = model(inputs)
    # ... rest of your training logic

If you’re using a more complex setup, you can also write a small utility function to handle this recursively if your data is packed into lists or dictionaries, but for most standard use cases, calling .to(device) on your tensors is the gold standard.

To prevent this from ever happening again, I started a habit of always defining my device variable at the very top of my training script and using it consistently throughout my code. Whenever I write a new project, I make sure that any tensor I touch is explicitly moved to that device immediately after creation or retrieval. It’s a small bit of boilerplate, but it saves me from those late-night debugging sessions where I’m chasing down type mismatches.

Happy coding, and may your GPU memory always be sufficient. Hopefully, this gets your training back on track today!

PyTorch 常見惡夢：RuntimeError: Input type and weight type should be the same

來源：Stack Overflow ↗ · 202 票

這真的是每個剛開始摸 PyTorch 的人必經的「成年禮」。記得剛開始寫訓練迴圈的時候，模型架構好不容易跑通了，我滿懷期待地按下執行鍵，結果電腦跑不到兩秒就噴出這行紅字錯誤，看著那一長串 RuntimeError: Input type (torch.FloatTensor) and weight type (torch.cuda.FloatTensor) should be the same，我當時真的差點把鍵盤砸了。明明都已經用了 .to(device) 把模型丟到 GPU 上了，為什麼它還是這麼固執地跟我說輸入跟權重型別不合？

其實這背後的邏輯說穿了很單純，就是 PyTorch 非常嚴格，它要求模型參與運算的每一個「組件」都必須待在同一個物理空間。當你把模型透過 model.to(device) 移到 GPU（cuda）時，模型裡面的權重參數就變成 cuda.FloatTensor 了。但問題出在你的資料：當你從 dataloader 取出 inputs 和 labels 時，它們預設還是躺在 CPU 的記憶體（也就是 FloatTensor）裡。這就像是你把模型搬到台北的辦公室，卻要求還留在高雄的資料去跟它進行運算，GPU 當然會因為找不到資料來源而直接罷工。

解決方法其實超簡單，只要在你把資料餵給模型之前，順手把它們也踢進 GPU 就行了。我當時為了修正這個問題，直接在迴圈裡面加了一行程式碼，讓 inputs 和 labels 同步搬家。你可以這樣修改你的訓練迴圈：


device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)

for data in dataloader:
    # 關鍵就在這裡，要把讀取出來的資料同步移到 GPU
    inputs, labels = data
    inputs = inputs.to(device)
    labels = labels.to(device)
    
    outputs = model(inputs)
    # 接下來就是正常的 loss 計算與反向傳播...

說真的，這種錯誤發生過一次就會記住一輩子。為了以後不要再為了這種「搬運」問題浪費除錯時間，我後來養成了一個習慣：直接寫一個小的輔助函數，或者在 Dataset 類別裡多加留意。最推薦的做法其實是寫一個統一的 device 管理，確保在整個流程中，只要是進入 model 的張量，都強制經過 .to(device)。如果你懶得每次都寫兩行，甚至可以寫成 inputs, labels = inputs.to(device), labels.to(device) 這種寫法。

只要記得讓資料跟模型站在同一個陣線，這個討厭的錯誤就不會再來煩你了，趕快回去試試看吧！
