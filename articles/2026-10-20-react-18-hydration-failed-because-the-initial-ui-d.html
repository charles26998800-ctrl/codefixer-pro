Solving the "Hydration failed" Error in Next.js and React 18

Source: Stack Overflow ↗ · 341 votes

I still remember the first time I saw the "Hydration failed" warning flashing in my console after upgrading a project to React 18. I had spent nearly four hours convinced my API was returning bad data, only to realize I was just being "clever" with some browser-specific logic that the server had no clue how to handle. It’s one of those bugs that makes you want to throw your keyboard out the window because the code looks perfectly fine in your editor, yet the browser just refuses to cooperate.

The root cause of this headache is actually quite logical once you peel back the layers. When you're using Next.js, the server renders your component into a static HTML string and sends it to the browser. Once the JavaScript loads, React tries to "hydrate" that static HTML by attaching event listeners and turning it into a dynamic app. If the HTML the server sent doesn't perfectly match what the client-side code renders on that very first pass—even by a single attribute or a slight difference in timestamp—React throws its hands up and warns you that the UI is mismatched. This is almost always triggered by using browser-only APIs like window, localStorage, or dynamic values like Date.now() during the initial render phase.

I eventually fixed this by ensuring that my client-side code didn't touch those browser-specific APIs until after the component had successfully mounted. The cleanest way to handle this is to use a useEffect hook to trigger the dynamic content, which effectively tells React, "Hey, don't worry about this part until the browser is fully ready." Here’s how I usually structure it to avoid that nasty mismatch:


import { useState, useEffect } from 'react';

export default function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <span>{new Date().toLocaleTimeString()}</span>
      ) : (
        <span>Loading...</span>
      )}
    </div>
  );
}

By adding that simple isClient check, I ensure the server renders the "Loading..." state, which is identical on both ends, and the browser only swaps it out for the dynamic timestamp once it's actually in the user's viewport.

To prevent this from haunting you in the future, my best advice is to always look for code that relies on the environment. If you're accessing window or document directly inside your component body, you're just asking for trouble. Get into the habit of wrapping any browser-only logic in a useEffect or a custom hook that checks for the window object, and you'll save yourself a world of pain.

Good luck with your debugging, and I hope this helps you get back to building features instead of fighting with the console!

React 18 惡夢：Hydration Failed 的除錯心路歷程

來源：Stack Overflow ↗ · 341 票

還記得剛升級到 React 18 那陣子，我滿心期待地想體驗 SSR 的效能提升，結果專案一跑起來，瀏覽器控制台直接噴出一堆紅字：「Hydration failed because the initial UI does not match」。當時我盯著螢幕看了半小時，心想：「我程式碼明明寫得好好的，伺服器算出來的跟瀏覽器跑出來的怎麼會不一樣？」那種感覺真的很無力，就像是你精心準備了一場完美的直播，結果觀眾一進來卻發現畫面跟預告完全不對，那種抓狂感真的會讓人懷疑人生。

其實說穿了，這個錯誤的本質就是「時空錯亂」。React 在伺服器端（SSR）預先渲染出了一份 HTML，當這份 HTML 傳到瀏覽器時，React 會進行「水合（Hydration）」動作，試圖把事件綁定上去。但如果瀏覽器第一次渲染出來的 DOM 跟伺服器給的不一樣，React 就會崩潰，直接放棄治療。最常見的兇手就是那些依賴瀏覽器環境的變數，比如 Date.now()、Math.random()，或是你用 localStorage 來判斷當前是否處於登入狀態，這些東西在 Server 端跟 Client 端執行時結果根本對不上，React 一看到對不起來，就會直接跳出這個討厭的錯誤。

我當時是怎麼處理的呢？其實最簡單粗暴但有效的方法，就是「先讓它靜止」。我後來發現，只要讓元件在第一次渲染時保持一致，等到瀏覽器確定掛載完畢後再執行那些「動態」邏輯，問題就迎刃而解了。我寫了一個小小的 useEffect 來處理這種情況，確保元件在伺服器渲染時只跑基礎結構，剩下的邏輯都留給瀏覽器：


import { useState, useEffect } from 'react';

function MyComponent() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient ? (
        <span>現在時間是：{new Date().toLocaleTimeString()}</span>
      ) : (
        <span>載入中...</span>
      )}
    </div>
  );
}

透過這樣的小技巧，伺服器端永遠只會看到那個「載入中」的靜態內容，而瀏覽器在執行完 useEffect 後才會顯示時間，這樣兩邊就不會打架了。

要預防這種鳥事再次發生，我建議大家養成一個好習慣，就是儘量把「瀏覽器專屬」的邏輯全部隔離在 useEffect 或者是 dynamic import 裡面，不要讓它們直接出現在渲染路徑的最上層。如果你發現某個元件會噴這個錯，第一時間先檢查裡面有沒有用到 window、document 或者任何依賴當下時間的變數，把它們藏進去，你的除錯人生會順遂很多。
